<findings_that_change_the_brief>
**FINDING A — there is a fourth reader the contract did not name.**
`app/api/webhooks/docuseal/route.ts:314-320` builds the Certificate of Signature
(`renderCompletionCertificate`, the `funuunObserved` block) directly from
`split_sheet_parties.legal_name / pro / publishing_designee / administrator`. That
certificate IS the audit evidence deliverable 3 requires to come from the mint snapshot.
It is therefore **in scope for deliverable 3** and is converted in Task 2. Leaving it out
would ship a fix whose own audit artifact contradicts the document it certifies.

**FINDING B — migration 115 makes a bare `ADD COLUMN` silently unreadable.**
`115:35-60` REVOKEs the table-wide SELECT on `split_sheet_parties` and re-GRANTs an
explicit column list, and says so at `:39-42`: *"A new column added later must be added
here too, or it becomes silently unreadable through the authenticated client."*
Migration 228 MUST carry its own `GRANT SELECT (...) TO authenticated` for the three new
columns. Without it the new columns 42501 through the authenticated client and the gate
degrades to always-passing. This is the single most likely way this fix ships broken.

**FINDING C (label integrity) — two proposed names assert more than the data carries.**
Applying `Skill(label-integrity-funun)` to the new schema before it exists:

- `identity_source = 'party_asserted'` would claim *the described person asserted this*.
  The write site guarantees only that **the holder of the 256-bit approval token POSTed
  it** — email control is unproven and its verification flow is explicitly out of scope.
  Renamed to `'token_holder_submitted'`. The default for writes by the initiator's own
  routes is `'inviter_supplied'`.
- `identity_approved_digest` would claim *the approver approved this identity*. Claim 7
  shows approval is NOT identity confirmation — the correction UI is optional and
  collapsed, and a party approves a **split**. What the write site actually guarantees is
  *the resolved identity at the instant this party's approve/counter was recorded*.
  Renamed to `identity_digest_at_approval`, and the gate's user-facing copy must say
  "changed since they last responded", never "they approved a different identity".
- **Backfill honesty:** existing rows cannot be classified. Some already carry a
  historical `update_identity` write (the party-row half of that write succeeded even
  though the collaborators half 42703'd). Defaulting them to `'inviter_supplied'` would
  be a populated, plausible, wrong label — instance 1 of the skill, exactly. Existing
  rows backfill to `'unknown'`, and the gate grants `'unknown'` no special power.

**FINDING D — `collaborators.publisher` exists (claim 10), and mapping to it is the wrong
fix.** The tempting repair for the write-back is `publishing_designee → publisher`. Do
not. Ruling 2 says a publisher for one song is not a fact about a person; writing a
work-specific choice into a person-scoped roster row is the same error in the opposite
direction. The write-back carries the person-scoped fields only.

**HAZARD, recorded and NOT fixed (per `out_of_scope`):** the track/composer sync matches
parties by `normalizeName()` (claim 12). Two collaborators sharing a normalized name
cross-write each other's `pro`/`ipi`. Out of scope; recorded in the module header.

<design>
## The policy (Ruling 2, made explicit)

Two field classes, not one:

| Class | Fields | Rule |
|---|---|---|
| Person-scoped | `legal_name`, `pro`, `ipi` | A claimed party's CURRENT `user_profiles` value wins pre-mint. Blank live value falls back to the party row (never blank a real value). |
| Work-specific | `publishing_designee`, `administrator` | The party row wins, always. A profile default NEVER overwrites it. A profile value fills it ONLY when the party row is blank. |

Post-mint (`esign_pending` / `executed`) nothing is live-linked: the persisted mint
snapshot is truth for that document.

## Resolution order, one function, every caller

`resolvePartyIdentitiesForSheet(sheetId)`:

1. Read sheet status + all party rows (service client).
2. If the sheet is post-mint AND the current envelope (latest row for the sheet with
   `status <> 'voided'`, `created_at desc`) has a `party_identity_snapshot` → return the
   snapshot. One truth for the minted document, for every surface.
3. Otherwise resolve live: `collaborators.claimed_by` for linked parties → one
   `user_profiles` read → apply the policy table above per party.
4. Return `ResolvedPartyIdentity[]` keyed by party id.

The initiator's own row resolves by the same rule. The builder's self-row prefill from
`user_profiles` (claim 23) is a FORM PREFILL, not a party identity read, and stays.

## The gate (Ruling 1)

One exported predicate, so a future ruling changes the policy without touching the gate:

```
identityDriftSinceLastAction(party, resolved) -> IdentityDrift[] | []
```

Conflict when ALL hold: the party has a non-null `identity_digest_at_approval`, AND the
digest of the freshly-resolved identity differs, AND the difference is in the five
identity fields. No baseline (fast-lane mint from `draft`, nobody has responded) → no
conflict → mint proceeds, unchanged from today.

On conflict the mint returns **409 with a structured body** before the counsel gate, the
cap check, the PDF render and the DocuSeal call — i.e. before anything that spends:
`{ error, conflicts: [{ partyId, partyName, field, valueWhenTheyResponded, valueNow }] }`.
Copy says *"changed since they last responded"* (Finding C). It is a gate, not a wall:
the response carries what the initiator needs to resolve it on the same screen.

## Persistence

`esign_envelopes.party_identity_snapshot JSONB` — written in the SAME insert that records
the envelope (step 6 of the mint route), holding the exact array the PDF was rendered
from. The PDF is rendered from that in-memory object and the object is what is stored, so
"render from what was persisted" holds by construction without a pre-render write that
could orphan on a failed mint.

## Schema — migration 228 (additive, transactional, reviewable)

`split_sheet_parties`:
- `identity_source TEXT NOT NULL DEFAULT 'inviter_supplied'`, CHECK in
  (`'inviter_supplied'`, `'token_holder_submitted'`, `'unknown'`); pre-existing rows
  backfilled to `'unknown'` (Finding C).
- `identity_submitted_at TIMESTAMPTZ`
- `identity_digest_at_approval TEXT`
- `GRANT SELECT (identity_source, identity_submitted_at, identity_digest_at_approval) ON split_sheet_parties TO authenticated;` **(Finding B — not optional)**

`esign_envelopes`:
- `party_identity_snapshot JSONB` (no GRANT needed — claim 19)

## Why two modules and not one

`identity-policy.ts` is pure (no Supabase, no I/O) so the policy, the digest and the gate
predicate are unit-testable without mocks — the same discipline
`lib/split-sheets/project-sync.ts:1-12` states for itself.
`resolve-party-identities.server.ts` owns all I/O. The boundary test asserts the pure
module is never imported by a `'use client'` component, reusing the
`placements-client-server-boundary` precedent.
</design>
