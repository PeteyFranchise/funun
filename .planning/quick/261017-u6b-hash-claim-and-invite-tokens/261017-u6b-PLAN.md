## Path chosen: throttle + design note (NOT hashing at rest)

The investigation found both token columns are re-read in raw form after creation, so hashing at rest changes product behavior and cannot be done safely inside a quick task:

**curators.claim_token**
- Writer: `app/api/admin/curators/[id]/route.ts` `issue_claim` action (~line 61-72). Stores raw token + 72h expiry, returns `claimUrl` (and the full row, including `claim_token`, via `.select()`) to the admin.
- Readers by token: `app/api/curators/claim/[token]/route.ts` (lookup line 29-33, three conditional claim UPDATEs keyed on `.eq('claim_token', token)` at lines 79-86, 98-105, 122-129) and `app/curators/claim/[token]/page.tsx` (validity lookup line 24-28).
- **Raw re-read:** `app/api/pitches/route.ts` lines ~104-107 select `claim_token` and line ~198 builds `${appUrl}/curators/claim/${curator.claim_token}` into EVERY pitch email sent to an unclaimed curator. A hash-only column makes this impossible without either rotating the token on each pitch send (earlier links die, 72h expiry restarts, pitches start minting claim tokens admins never issued) or storing the token encrypted.
- Schema: migration 030 column, migration 032 partial UNIQUE index `idx_curators_claim_token`, migration 031 column privileges exclude it from client SELECT.

**artist_invites.invite_token**
- Writer: `mint_or_rotate_artist_invite` RPC (migration 101), called only via `lib/invites/mintInvite.ts` from `app/api/admin/artist-invites/route.ts`, `app/api/admin/artist-invites/[id]/convert/route.ts`, and `app/api/admin/artist-invites/broadcast/route.ts`.
- **Raw re-read:** the RPC's `'reused'` outcome returns the EXISTING raw `invite_token` (migration 101 lines ~97-122). The broadcast route emails `mint.token` on reuse (~line 177); the convert route re-sends `mint.token` when it differs from `artist_waitlist.invite_email_sent_token` (~lines 205, 236, 265) and uses it in the Resend idempotency key `artist-convert-${id}-${mint.token}`.
- **Second raw copy:** `artist_waitlist.invite_email_sent_token` (migration 103) stores the exact raw token that was emailed.
- Readers by token: `lib/invites/allowlist.ts` `isSignupInviteValid` (line 99), `app/api/signup/invite/[token]/route.ts` (line 83), migration 214 `handle_new_user` gate (lines ~120, ~130) and `complete_verified_signup_claim` (lines ~211, ~233; already writes `verified_signup_invite_claims.token_hash` via `extensions.digest(v_token, 'sha256')`).
- `collaborator_invites.invite_token` shares the same lookup paths (`allowlist.ts` line 109, signup invite route line 104, `app/join/[inviteToken]/page.tsx`, `lib/collaborators/invite.ts` ~191-218, which also re-reads a recent raw token) and would need the same treatment for consistency.

Hashing is therefore a product decision (rotate-on-send vs. encrypt-at-rest vs. drop the link from pitch emails), not a mechanical migration. This task ships the throttle now and writes that decision up.

<interfaces>
From lib/security/rate-limit.ts (do not modify):
- `checkRateLimit(key: string, options?: { windowMs?: number; maxAttempts?: number; failClosed?: boolean }): Promise<boolean>` returns TRUE when the caller IS limited. On RPC error or throw it returns `options.failClosed === true`. Throws RangeError if the key is empty or longer than 256 chars. Defaults: 15 min window, 5 attempts. It creates its own service client internally, so in tests it must be mocked (the existing mock service objects have no `rpc`, which would make a fail-closed call return true and break every test).
- `getClientIp(request: Request): string` prefers `x-real-ip`, then the last `x-forwarded-for` entry, else `'unknown'`.

Existing token shape: `lib/curators/tokens.ts` `generateClaimToken()` = `randomBytes(32).toString('hex')` (64 lowercase hex). It is the only writer of `curators.claim_token`, so a `/^[a-f0-9]{64}$/i` gate rejects nothing legitimate.

Existing precedent for a token-format gate + IP limit on a public token route: `app/api/signup/invite/[token]/route.ts` lines ~70-76.

ClaimButton (`components/curators/ClaimButton.tsx`) already renders `json.error` for any non-OK status, so a 429 with an `error` string needs no UI change.
</interfaces>
