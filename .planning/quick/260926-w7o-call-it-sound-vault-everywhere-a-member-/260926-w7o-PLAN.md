## Task 1 — Write the guard and prove it is red

**Create** `__tests__/sound-vault-naming.test.ts`, following the `readFileSync`-and-assert shape of `__tests__/member-api-boundary.test.ts`.

### Matcher

```
const BARE_VAULT = /\b(?:your|the|a)\s+vault\b/i
```

This was dry-run against the current tree: **14 hits, 0 false positives, 0 exclusions needed.** It needs no allowlist, because it is precise rather than subtractive:

- **Qualified usage passes for free.** The determiner must sit immediately before `vault`. `"your Sound Vault"` has `Sound` in between, so it never matches. No "already says Sound Vault" exception is required — the shape of the regex *is* the exception.
- **Identifiers and paths are excluded by `\b` alone.** `vault_projects` (`_` is a word char), `vaultProject`, `VaultIcon`, `/vault`, `@/components/vault/...` — none match, and none needed listing.

### Scope of the scan

Recursive walk of `app/` and `components/` for `.tsx`, skipping `*.test.tsx` / `*.spec.tsx`.

- Walk the filesystem directly; do **not** shell out to `git ls-files`. Verified: `git ls-files 'app/**/*.tsx' 'components/**/*.tsx'` returns 485 while the walk returns 489, because git's `**` does not match zero directories and silently drops top-level files like `app/page.tsx`. The walk is the correct set.
- Neither `node_modules` nor `.claude/worktrees/` lives under `app/` or `components/` (verified — no nested `node_modules`), so the walk needs no prune list.
- The guard file itself lives in `__tests__/`, outside the scanned roots, so it cannot match itself.
- **Skipping test files is the single scope rule, and it is deliberate:** the guard governs product surfaces, not fixtures. Without it, a future regression test that legitimately quotes the old literal would be blocked with no escape hatch — which is the "allowlist grows" failure mode arriving from the other direction. One principled rule is not an allowlist.

### Comment handling, and which way it fails

Line-anchored. Skip a line whose trimmed form starts with `//`, `*`, `/*`, or `{/*`. Do **not** regex-strip comments out of the source body.

**Failure direction — and it is the safe one.** This can produce a **false FAIL**, never a meaningful false pass:

- False fail: a trailing comment on a code line (`const x = 1 // the vault ...`), or a `/* */` continuation line not starting with `*`. Loud, surfaces at authoring time, fixed by moving the comment.
- False pass would require a member-facing line that *begins with* `//`, `*`, `/*`, or `{/*`. No JSX text node or quoted display string takes that shape. The only contrived counter-example is a template literal whose continuation line starts with `*`; none exists in this tree.

For a drift guard, over-reporting is correct — a false fail costs a minute, a false pass ships the drift.

### Assertions

1. Collect hits as `` `${file}:${line}: ${text}` `` and assert `expect(hits).toEqual([])`, so a failure **names every offending location** rather than printing a count.
2. Second `it()`: assert `components/nav/ArtistNav.tsx` still contains `label: 'Sound Vault'`. The guard's whole premise is that this is the canonical name; pin that claim to its source so a future product rename re-opens the guard instead of leaving it enforcing a dead name.
