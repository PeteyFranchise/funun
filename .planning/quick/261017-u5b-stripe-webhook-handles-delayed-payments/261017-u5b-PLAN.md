<objective>
Close the delayed-payment hole from GitHub issue #189 in the Stripe webhook, and make refunds and disputes visible without inventing schema.

Today `checkout.session.completed` with `payment_status !== 'paid'` returns 400, so a delayed-method checkout (ACH and similar, possible because `lib/stripe/connect.ts` creates the session without `payment_method_types`, which lets Stripe's dynamic payment methods offer them) is retried by Stripe for days and the later `checkout.session.async_payment_succeeded` is ignored, so the deal never reaches `paid`. Refund and dispute events fall through to the generic 200 with no trace.

Purpose: a buyer who pays by a delayed method gets their deal marked paid when the money actually clears; Stripe stops retrying events the app correctly ignores; money moving backwards (refund, dispute, failed async payment) is reported to the owner instead of silently swallowed.

Output: updated webhook route + extended webhook tests. No migration, no change to `lib/stripe/connect.ts`, no change to the RPCs.
</objective>

<schema_facts>
Established by the planner from the code; executor does not need to re-derive:

- Deals live in `public.license_requests`. `payment_status` CHECK (migration 215) allows only `'unpaid' | 'creating_payment' | 'awaiting_payment' | 'paid'`. Columns: `stripe_checkout_session_id`, `stripe_payment_intent_id`, `paid_at`, `stripe_checkout_url`, `stripe_checkout_economics_fingerprint`, claim columns. There is NO refunded/disputed/failed status and NO column for refund or dispute state. All writes to `license_requests` are revoked from authenticated/anon; service-role only.
- `complete_license_checkout(p_deal_id, p_checkout_session_id, p_economics_fingerprint, p_payment_intent_id, p_amount_cents, p_currency, p_application_fee_cents, p_transfer_destination)` returns BOOLEAN. It locks the row, returns `stripe_checkout_session_id = p_checkout_session_id` if already paid (idempotent replay), otherwise re-verifies amount/currency/fee/destination/fingerprint/session id against stored economics and sets `paid`. It does not read `payment_status` of the Stripe session, so the route MUST gate on `session.payment_status === 'paid'` before calling it.
- After a delayed-method `checkout.session.completed`, the deal correctly stays `awaiting_payment` (set by `finalize_license_checkout`). Nothing needs to be written at that point.
- Stripe sends `checkout.session.async_payment_succeeded` / `checkout.session.async_payment_failed` with a `Checkout.Session` object (same shape as `checkout.session.completed`); on success `payment_status` is `'paid'`.
- Consequence the executor must record in SUMMARY (not fix): after `async_payment_failed`, the deal stays `awaiting_payment` pointing at a consumed session, and `claim_license_checkout` returns `'existing'` with the dead checkout URL for the same fingerprint, so the admin pay route cannot issue a fresh session. Resetting that needs a new service-role RPC (migration), which is out of scope here.
</schema_facts>
