<objective>
Close Pass 6's C-1 finding (`.planning/deliberations/2026-10-05-pass-6-identity-access-review.md`): `collaborators.claimed_by` -- documented as the only verified-identity signal in this codebase, and consumed by three separate `SECURITY DEFINER` trigger chains to grant real project visibility, work membership, and invite-acceptance state -- is directly writable today by the roster owner through ordinary table-level `INSERT`/`UPDATE` privilege plus an RLS policy (`018:30-31`) that checks only `auth.uid() = user_id`, with nothing below the row level restricting which column that access covers. A roster owner who knows another Funūn member's UUID can set `claimed_by` to that UUID directly via PostgREST and make the system behave as if that member claimed the roster row themselves.

Make `claimed_by` client-immutable via a `BEFORE INSERT OR UPDATE` trigger (not a column `REVOKE` -- `collaborators` has never had a table-level `REVOKE` issued against it, which is the exact precondition that made migration 230's column `REVOKE` on `tracks.work_id` a proven silent no-op, corrected by migration 231). The trigger admits exactly the writers this investigation verified by file:line: a direct database session or `service_role` (migration 231's `auth.role()` idiom), OR a transaction-local GUC set by the two functions that legitimately write this column today -- `claim_collaborators()` (076, live) and `link_existing_member_collaborator()` (179) -- extending migration 145's GUC mechanism, because one of those two writers runs under an ordinary authenticated roster-owner session and `auth.role()` alone cannot distinguish it from the forgery this fix exists to stop.

Purpose: in a rights product, an identity link that can be forged by the person it is supposed to verify is not a documentation gap -- it is unauthorized access dressed as a signup. `claimed_by` is the ONLY signal three different `SECURITY DEFINER` chains trust to grant project visibility, work membership, and invite acceptance; a forged value grants all three to an account that never claimed anything.

Output: `supabase/migrations/233_claimed_by_write_lockdown.sql` (human-gated, never pushed by the executor), its paired `__tests__/migration-233-claimed-by-write-lockdown.test.ts`, and an owner todo carrying the push, the owner-run behavioral probes, and a read-only production audit query this session cannot run itself.
</objective>
