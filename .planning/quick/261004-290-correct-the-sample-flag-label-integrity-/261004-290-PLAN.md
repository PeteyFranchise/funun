# Quick Task 261004-290 — Correct the sample-flag readiness-cap claim

A label-integrity defect of exactly the kind `label-integrity-funun` targets: a
comment and a user-facing banner assert a consequence nothing enforces.

## The false claim

`components/vault/SampleFlagToggle.tsx:9-10` — flagging a sample *"creates a
required Sample Clearance requirement and **caps the readiness score** until
that clearance is signed."*

First clause true. Second clause false.

## Verified ground truth (2026-10-04)

| Claim | Verdict | Evidence |
|---|---|---|
| Flagging adds a `sampleclear` requirement, severity `required` | **TRUE** | `lib/vault/stage3.ts:277-299` — iterates tracks, `if (!t.has_sample) continue`, pushes `severity: 'required'` |
| An uncleared sample blocks Stage 3 progression | **TRUE** | `lib/vault/stage3.ts:330` `sampleBlock = reqs.some(r => r.tool === 'sampleclear' && r.status !== 'signed')`; `:338` `canContinue: readinessScore >= CONTINUE_THRESHOLD && !sampleBlock` |
| The readiness score is capped | **FALSE** | `lib/vault/readiness.ts` has zero `has_sample` hits (grepped); its `ReadinessInput.tracks[]` type (`:26-39`) declares no such field. `readinessScore` is an *input* to `computeStage3` (`:176-181`), sourced from `project.vault_readiness_score` (`app/(artist)/vault/[projectId]/documents/page.tsx:174`) |

### Root cause — why the comment was once true

- `supabase/migrations/005_stage3_additions.sql:88-101` **did** cap: `IF EXISTS (… has_sample = true AND NOT EXISTS (… sample_clearance … signed/verified)) THEN score := LEAST(score, 70)`.
- `calculate_vault_readiness()` was later rewritten for split-sheet coverage. The **final** definition is `supabase/migrations/070_readiness_definer_privilege_sweep.sql:59-197` ("byte-identical to migration 068's body"), which ends `RETURN LEAST(score, 100)` and contains **no** `has_sample` reference and no 70-cap.
- No migration after 070 redefines the function (`grep "CREATE OR REPLACE FUNCTION.*calculate_vault_readiness"` → 001, 005, 008, 070 only; highest migration is 228).

So migration 068's rewrite silently dropped the cap and the comment was never
updated. `supabase/migrations/109_reconcile_tracks_sample_columns.sql:22-29`
flagged this as a "SEPARATE investigation … confirm separately if needed" — this
task is that confirmation.

## Scope boundary — behaviour does NOT change

The owner's instruction is explicit: the current behaviour is correct, only the
description is wrong. Restoring the migration-005 cap would be a product change,
not a fix. Whether the cap's disappearance in 068 was intended is a separate
owner decision, to be surfaced, not decided here.

**files:** `lib/vault/stage3.test.ts`

**done:** A regression in either direction — score reading `has_sample`, or the
