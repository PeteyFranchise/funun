# Quick Task 261004-290 — Summary

Corrected a label-integrity defect: `SampleFlagToggle`'s header comment and
`DocumentStage`'s warning banner both told the reader that flagging a sample
caps the project's readiness score. It does not. **No behaviour changed.**

## What was true, and what was not

| Claim | Verdict | Evidence |
|---|---|---|
| Flagging adds a REQUIRED Sample Clearance requirement | TRUE | `lib/vault/stage3.ts:277-299` |
| An uncleared sample blocks Stage 3 progression | TRUE | `lib/vault/stage3.ts:330,338` — `sampleBlock` is a separate conjunct of `canContinue` |
| It caps the readiness score | **FALSE** | `lib/vault/readiness.ts` — zero `has_sample` hits; its per-track input type declares no such field. `readinessScore` is an *input* to `computeStage3`, sourced from `project.vault_readiness_score` |

## Root cause — the comment was true once

This is the useful finding, and it was not in the task brief.

- `supabase/migrations/005_stage3_additions.sql:88-101` **did** cap: an uncleared
  flagged sample forced `score := LEAST(score, 70)`.
- `calculate_vault_readiness()` was later rewritten for split-sheet coverage. The
  **final** definition is `supabase/migrations/070_readiness_definer_privilege_sweep.sql:59-197`
  — described in its own header as "byte-identical to migration 068's body" — and
  it ends `RETURN LEAST(score, 100)` with **no** `has_sample` reference and no cap.
- Nothing after 070 redefines the function (`CREATE OR REPLACE … calculate_vault_readiness`
  appears only in 001, 005, 008, 070; the tree is at migration 228).

So migration 068's rewrite silently dropped the cap and the comment outlived its
mechanism by ~160 migrations.

`supabase/migrations/109_reconcile_tracks_sample_columns.sql:22-29` had already
flagged this as *"a SEPARATE investigation … confirm separately if needed."*
**This task is that confirmation: the function on the remote has no sample
branch.** That open question can be closed.

## The test, and proof it bites

The pre-existing test asserted only `canContinue: false` at score 100 — it would
have passed unchanged if someone *added* a score cap, which is why it never
caught this. The new block asserts both halves:

1. `readinessItemsForProject` returns a deep-equal checklist (statuses **and**
   points) for a sampled vs. an otherwise identical clean track.
2. `computeStage3` on that same track still returns `sampleBlock: true` /
   `canContinue: false`, with the requirement's `severity` pinned to `required`.

Verified by mutation rather than assumed — per the repo's "running it proves the
mechanism, not the meaning" rule:

| Mutation | Result |
|---|---|
| `readinessItemsForProject` downgrades an item when `has_sample` is set | assertion 1 **FAILS** ✓ |
| `!sampleBlock` removed from `canContinue` | assertion 2 **FAILS** ✓ (and the pre-existing test too) |

Both probes were reverted; `grep -rn "_mutSampled\|MUTATION PROBE"` is clean and
the behaviour files show no diff.

## Open question for the owner — NOT decided here

**Was dropping the migration-005 score cap intended?** Migration 068 was about
split-sheet coverage, not samples, so the cap's disappearance looks incidental
rather than decided. Two defensible positions:

- **Leave it.** The progression block already prevents distribution, which is
  the outcome that matters; the score then honestly reports asset/metadata
  readiness without conflating it with rights state. This is also consistent
  with `lib/sync-library/readiness.ts:312`, where sample clearance is
  *"deliberately ABSENT"* by owner decision.
- **Restore it.** If the score is shown anywhere as a release-readiness summary,
  a 100 on a project that cannot be released is misleading in the other
  direction.

Either way the fix above stands, because the description now matches the code.
Per the repo's "gates are provisional" note this is a product call, not a
cleanup. Filed as a follow-up.
