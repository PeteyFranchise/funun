<objective>
Close a live production defect across three rights-bearing tables that migration 136 granted `FOR ALL` (INSERT, UPDATE, DELETE) to a work's owner or any work member, with no mechanism below the row-level RLS check restricting which columns or which operations that access actually needs: `ai_entries` (AI-disclosure ledger, currently rewritable/deletable with no trace), `lyric_blocks` (whose `author_user_id` column migration 135 documents as "the fact that MOVES SPLITS" and which is currently reassignable by any work member), and `work_versions` (recording provenance, currently mutable and deletable outside the archive workflow). Apply the posture this schema already uses correctly elsewhere (`work_diary_events`'s REVOKE, migration 145's transaction-local-GUC trigger, migration 231's `auth.role()` trigger) to these three tables specifically — three different mechanisms, chosen per table to match how that table's verified, enumerated legitimate writers already work, with zero behavior change to any of them.

Purpose: in a rights product, a column that can be silently rewritten by the person it describes is not a documentation gap, it is a money bug. `lyric_blocks.author_user_id` decides who a split sheet pays. `ai_entries` is the evidentiary record a future AI-provenance gate (Phase 50, explicitly paused pending this exact finding per the Pass 7/Pass 5 deliberations) will have to trust. `work_versions` is the human-take registry the AI-disclosure "when-in-doubt" rule depends on being able to prove a take predates a tool. All three are exploitable today by any authenticated work member via a direct PostgREST call, independent of what the Next.js app's own routes choose to send.

Output: `supabase/migrations/232_rights_ledger_write_lockdown.sql` (human-gated, never pushed by the executor), its paired `__tests__/migration-232-rights-ledger-write-lockdown.test.ts`, and an owner todo carrying the production verification steps this session cannot run itself.
</objective>

## Separate findings surfaced during investigation — explicitly NOT fixed by this plan

1. **INSERT-time identity spoofing via direct PostgREST, bypassing the Next.js app entirely.** Every legitimate INSERT path for `lyric_blocks.author_user_id` and `work_versions.user_id` sets the value from the authenticated session server-side (never from client input) — but nothing in the database stops a direct REST call, under a real work member's own JWT, from INSERTing a brand-new row naming a *different* user's id in either column, fabricating authorship or provenance from the first row rather than rewriting an existing one. This is a real, same-class gap, but it is not what either Pass 5 or Pass 7 reported (both describe rewriting an *existing* fact, i.e. UPDATE), and guarding it would mean either forcing the column to `auth.uid()` on every INSERT (a value-correctness rule, which the brief's constraints say this fix must not add — "do not alter... what a valid row looks like") or accepting a larger, differently-shaped change. Left as a follow-up recommendation in the owner todo, not built here.
2. **`lyric_blocks.repeat_of_block_id`** can be directly UPDATEd (outside `detach_lyric_block_with_text()`) to point an existing block at a *different* source block, which — per the REPEAT RULE (135:190-198) — would change whose authorship that block displays without touching `author_user_id` itself. No application route exposes this today (`PatchFieldsSchema` at `blocks/[blockId]/route.ts:49-58` has no such field), so there is no live client path, but a direct-REST actor could still do it. Noted for the owner; not in scope for this fix, which is scoped to the two columns both deliberations named explicitly.
3. **`resolveTrackAiProvenance()` returning `'clear'` on an empty `ai_entries` list** (`lib/catalogue/track-work-link.ts:62-64`) is a real epistemic gap Pass 5/7 both flagged, but it is application logic, not a write-lockdown question, and — per the module's own header (`track-work-link.ts:5-6`) — it has no live caller yet; nothing in production reads `tracks.work_id` or invokes this function today. Out of scope for this plan by the brief's own constraint ("do not alter the API routes' validation logic"); this fix makes the ledger beneath that resolver trustworthy, which is the precondition for fixing the resolver itself later, not a substitute for it.
4. **Whether AI disclosures should be permanently append-only or may be superseded with history preserved** is the owner decision the brief names explicitly. This plan does not choose: it makes `ai_entries` append-only *today* (closing the live rewrite/delete hole), and a future correction mechanism — if the owner wants one — must be built as a new INSERT-based supersede pattern (e.g., a `supersedes_entry_id` self-reference on a fresh row) rather than an UPDATE or DELETE of the original, which this migration does not foreclose.
