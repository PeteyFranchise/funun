# BOTTOM LINE

I would not run the remaining fourteen-step storage program now: at 0.047 GB, with a handful of known users and no observed abuse, its opportunity cost is larger than the expected storage loss it prevents.  
I would spend roughly two to four hours changing the existing daily job to report one summary-only global byte total and growth delta, because that preserves the useful warning signal without pretending migration 227 can attribute shared-work paths to accounts (`supabase/migrations/227_storage_usage_by_owner.sql:47-60`; `app/api/cron/storage-usage-check/route.ts:40-45,59-86`).  
I would then stop, document the triggers below, and accept that an authenticated beta user can temporarily store an oversized or unattached object.  
None of the four candidates earns immediate implementation; if a trigger fires, I would take migration 228 first for a cheap attribution repair, the narrow size-gap remedy second, policy revocation third, and the full ledger last.  
Before open or materially untrusted signup, I would reassess that ordering and make policy revocation a launch gate, because the adversary and blast radius would then be different.

# SIZE GAP

**Verified platform capability.** The repository pins `@supabase/supabase-js` and `@supabase/storage-js` 2.109.0 (`package-lock.json:19-20,5087-5110`). In that client, `createSignedUploadUrl` accepts a path plus only `{ upsert }`, posts an empty body to the sign endpoint, and returns the token (`node_modules/@supabase/storage-js/src/packages/StorageFileApi.ts:381-418`). `uploadToSignedUrl` accepts the token, body, and ordinary file options; it does not supply a server-signed expected length (`node_modules/@supabase/storage-js/src/packages/StorageFileApi.ts:275-338`). Supabase's current official reference likewise documents only path/options for signed URL creation and says the token lasts two hours: [createSignedUploadUrl reference](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl). The current official resumable-upload guide shows the same token with `x-signature` and only the `upsert` signing option; TUS knows the client's chosen upload length, but the signed token is not documented as committing to the application's declared length: [resumable uploads](https://supabase.com/docs/guides/storage/uploads/resumable-uploads).

**Conclusion:** on the supported API used by this application, a signed upload URL cannot be bound to an application-specified content length. This is verified against the pinned client implementation and current official API documentation. I did not send a destructive or billable probe to production, and the repository does not reveal the hosted Storage server build; therefore I am not claiming that no private/undocumented server feature could exist. An undocumented parameter would not be an acceptable production control in any event.

**What Supabase does support as a hard control.** Supabase documents global and per-bucket maximum file sizes, with the bucket maximum constrained by the global maximum: [Storage file limits](https://supabase.com/docs/guides/storage/uploads/file-limits). Its bucket guide states that uploads which do not meet a bucket's `fileSizeLimit` are rejected: [creating buckets](https://supabase.com/docs/guides/storage/buckets/creating-buckets). That is authoritative pre-upload enforcement, but it is bucket-wide—not per URL, path family, or intent.

That makes the present bucket layout the constraint. `track-audio` is set to 262,144,000 bytes so stems ZIPs can approach 250 MB (`supabase/migrations/041_track_audio_stems_config.sql:6-25`), while ordinary catalogue audio constants are 50 MB (`lib/catalogue/audio-mime.ts:13`; `lib/vault/track-audio.ts:2`). Lowering this bucket to 50 MB today would enforce the desired ceiling but break a supported stems flow. The cheapest **strict pre-upload** solution is therefore: create a dedicated stems bucket capped at 250 MB, migrate the stems writer/reader/reference assumptions, verify it, and only then lower `track-audio` to 50 MB in a new human-gated migration. That is smaller than a ledger but is not a one-line bucket edit.

The cheapest **eventual enforcement** solution is a completion-required sweep: after a grace period, remove an object that is over the path family's limit or has no owning-table reference. This makes “50 MB retained” enforceable, but not “more than 50 MB can never be transmitted or temporarily stored.” Existing completion routes already demonstrate the core check-and-remove behavior (`app/api/ideas/[ideaId]/recordings/complete/route.ts:32-55`; `app/api/vault/[projectId]/tracks/[trackId]/audio/complete/route.ts:48-63`). For this beta, eventual enforcement is the proportionate option if evidence first shows a problem.

I would not proxy large bodies through a Next.js route merely to inspect `Content-Length`: it adds bandwidth, runtime, timeout, and partial-stream failure modes and undermines the purpose of direct-to-Storage uploads. I would also not treat a client `Content-Length` or TUS `Upload-Length` as the missing guarantee; without a server-issued commitment to the admitted size, the uploader chooses that value.

# SWEEPER VS LEDGER

A sweeper substitutes for **most of the ledger's present operational value**, because the current business problem is “do abandoned bytes accumulate?” rather than “can Funūn produce exact, billable storage accounting?” It does not substitute for most of the ledger's future accounting value.

A minimal sweeper can remain much smaller than the proposed ledger:

1. A service-only `SECURITY DEFINER` reporting function reads `storage.objects`; this access shape is already established because authenticated/PostgREST clients must not read every object's metadata (`supabase/migrations/227_storage_usage_by_owner.sql:20-33,63-68`). Any new SQL remains proposed and human-gated until a human applies it.
2. The function classifies known path families and left-joins object names to their owning tables. It returns only aggregate counts/bytes to the cron response and alert, never paths or raw user rows, preserving T-32-06 (`app/api/cron/storage-usage-check/route.ts:70-86`).
3. Start report-only. Treat an object as stale only after a conservative grace period. **Operational inference:** use at least 48 hours because ordinary signed upload tokens are documented as lasting two hours, while resumable upload URLs can last up to 24 hours; 48 hours also tolerates delayed callbacks and transient outages.
4. If evidence warrants enforcement, delete only objects that are still unreferenced or oversized on a later run. Log aggregate results and require a privileged manual investigation for surprises. Quarantine is not worth building unless deletion recovery becomes a product promise.

What it catches:

- Bytes that landed but never acquired an owning application row.
- Objects whose actual stored size exceeds the path family's allowed size, including users who lied at intent creation and skipped `/complete`.
- Callback/database failures that leave bytes after upload.
- Direct-policy writes that use a known path family but never attach.

What it misses or handles less safely than a ledger:

- It cannot record an intent that was issued but never uploaded; there is no Storage object to see.
- It cannot reliably recover `uploader_user_id` for work-scoped and idea-scoped paths, because those deliberate paths do not encode the uploader (`lib/catalogue/audio-mime.ts:125-137`).
- It cannot distinguish a genuine orphan from an unusually delayed legitimate completion except by age and repeated observation. A ledger has `pending`, expiry, and completion state.
- It cannot reserve quota before upload, make admission atomic, compare declared versus actual bytes per intent, or stop temporary storage consumption.
- It cannot provide exact customer-visible owner/uploader accounting, transfer semantics, or billing evidence.
- A path parser plus joins must be updated whenever a new storage family is introduced; a ledger-backed common intent API centralizes that obligation.
- If a legitimate owning-table write stores an unexpected path shape, a destructive sweep could false-positive. That is why report-only, a long grace period, repeat observation, and tests against every path family are mandatory before deletion.

At current scale, those missing capabilities are not worth an estimated additional week or two. The sweeper is the right intermediate control **only after** stale/oversized bytes are observed or the growth trigger fires. Until then, even the sweeper is premature; one global total/growth signal plus manual cleanup is enough.
