<objective>
Make the Antenna opportunity-posting gate actually admit a legitimately-created Industry account, and stop
the `member_type` ↔ `capability_grants` drift at its source (the admin-approve path).

Today `POST /api/antenna/opportunities` requires BOTH `hasCapability(user,'industry')` AND a row in the dead
`industry_profiles` table (migration 001) — nothing writes `industry_profiles`, so every account 403s
(RESEARCH Pitfall 1). This plan removes the dead second gate (INDUSTRY-01) and keeps `hasCapability` as the
one authoritative boundary. Separately, `grantCapability()` currently writes `capability_grants` + role badges
but never touches `member_type`, so an admin-approved self-serve industry request leaves `member_type='artist'`
(RESEARCH Pitfall 2). This plan makes the industry grant also sync `member_type='industry'` (INDUSTRY-06).

Reconciliation decision (planner call, documented): `capability_grants` stays authoritative for capability
*checks*; `member_type` stays the account-lane discriminant kept in LOCKSTEP with it. The full cutover of the
6+ existing `member_type` read sites is DEFERRED (Phase 19/20-style blast-radius split) — this plan only stops
the drift going forward. The capability_grants WRITE at account creation + the backfill of existing accounts
live in the human-gated migration (Plan 28-05); this plan is pure app code.

Purpose: an invited Industry member can post an opportunity; the four capability surfaces stop disagreeing.
Output: a satisfiable Antenna gate + a lockstep grant path.
</objective>
