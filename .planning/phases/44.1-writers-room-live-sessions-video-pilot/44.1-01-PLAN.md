# Plan 44.1-01: Managed-provider spike and architecture gate

## Objective

Validate the beta design against managed-provider options before introducing a provider SDK into
production code. This plan gathers evidence and presents tradeoffs; it is forbidden from selecting a
winner on the owner's behalf.

## Work

1. Re-check Daily, LiveKit, Twilio, Zoom Video SDK, and any then-credible alternative for official
   pricing/limits, data processing/regions, retention/logs, incident history,
   browser/mobile support, screen-share/system-audio behavior, webhooks, token revocation, accessibility,
   observability, CSP/COOP/COEP requirements, bundle/runtime cost, and spend controls. Compare Zoom Video
   SDK rather than Meeting SDK, and verify its current Build Platform credit conversion instead of using
   legacy pricing.
2. Build comparable disposable spikes outside production surfaces for the shortlisted options, covering
   two-to-six participants, camera/mic switching,
   application/window screen share, reconnect, bandwidth adaptation, Safari/Chrome/Edge, and mobile view.
3. Test DAW-window legibility and confirm call audio is not reliable/master quality. Record actual bitrate,
   CPU, participant minutes, downstream transfer, and failure behavior.
4. Threat-model token theft, unauthorized joins, room-ID guessing, stale membership, blocked/removed users,
   malicious names, provider webhooks, screen-share privacy, denial of service, and abandoned calls.
5. Produce a neutral decision brief—not a completed ADR—with the same test evidence, forecast for
   100/1,000 four-person 90-minute sessions, abstraction implications, rollout/kill-switch design, and
   owner demo for each viable option.

## Human gate

Owner selects the provider and approves budget/alerts, DPA/privacy posture, max duration, idle timeout,
and exact v1 device/screen-share scope. No production SDK/package/schema work begins before this gate.
