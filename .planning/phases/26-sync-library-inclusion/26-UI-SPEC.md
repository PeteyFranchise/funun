# Phase 26 — UI Design Contract: Sync-Library Inclusion & Artist Submission

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder (from 26-CONTEXT.md):** this phase populates the sync library — invite, submit, blanket-agreement sign, admit — and stops there. No buyer-side transaction UI, no pricing UI, no deal-terms UI ships in this phase.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — this is a mature, 25+-phase brownfield hand-rolled Tailwind design system, not a fresh project. Introducing shadcn now would contradict the phase's own mandate to "match the existing dark UI, do not invent a new visual language." All net-new components must be composed from the existing token/pattern vocabulary below, not a component-library import. |
| Preset | not applicable |
| Component library | none (hand-rolled Tailwind + inline SVG) |
| Icon library | hand-rolled inline SVG components, `components/nav/icons.tsx` convention: 24×24 viewBox (nav) or smaller inline (row-level), `stroke="currentColor"`, `strokeWidth` 1.7–2.2, `strokeLinecap="round"`, accepts an optional `gradient?: boolean` prop for the active-state gradient stroke (`#ng` linearGradient defined once in `ArtistNav.tsx`). No external icon package (no lucide/heroicons import) — new icons for this phase (Sync Library nav item, "+Sync Library" row affordance) are drawn in this same idiom. |
| Font | `var(--font-sans)` → system-ui stack (`tailwind.config.ts`) — unchanged, no new font. |

**Two token systems in play — do not cross them:**

1. **Artist-app surfaces** (dashboard, Vault, the new Sync Library hub, the signing page) render in the always-dark artist shell (`app/(artist)/layout.tsx`, no theme toggle). Use the raw Tailwind design tokens directly: `bg-ink`, `bg-card`, `bg-card2`, `text-lav`, `text-lavdim`, `border-hair`, `border-hairstrong`, `bg-grad`, `.gtext`, `shadow-cta`, `rounded-card`. This is what `ArtistNav.tsx`, `VaultProjectCard.tsx`, `DocumentCard.tsx`, and the dashboard already use.
2. **Admin-console surfaces** (the new `/admin/sync-library` invite + curation queue) render inside the `.fncon` scope (`app/(admin)/layout.tsx` injects `ADMIN_CONSOLE_CSS`) which supports a light/dark toggle (`AdminThemeToggle`). Use the CSS-variable-backed classes — `text-[color:var(--ink)]`, `text-[color:var(--ink-2)]`, `bg-[color:var(--panel)]`, `bg-[color:var(--panel-2)]`, `border-[color:var(--border)]`, `.fncon-cta` / `.gtext` — exactly as `BuyerOrgsAdmin.tsx`, `CapabilityRequestsAdmin.tsx`, and `DealsQueue.tsx` do. **Never hardcode `bg-ink`/`text-lav` inside an admin component** — that bypasses the light-theme override and will look broken when an admin switches themes. The two systems share the same hex values in dark mode by design (`--ground:#0a0a0f` etc. mirror `ink`/`card`/`card2`), so visually they match; only the class mechanism differs.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, chip internal padding |
| sm | 8px | Compact row internal gaps, badge padding |
| md | 16px | Default card padding, section-internal spacing |
| lg | 24px | Section-to-section spacing within a page |
| xl | 32px | Major layout gaps (e.g. hub page section breaks) |
| 2xl | 48px | Page-header-to-content breaks |
| 3xl | 64px | not used by this phase's surfaces |

**Exceptions (existing codebase convention, keep for consistency — do not "fix"):** `ArtistNav.tsx` and several card components use fine-grained arbitrary values (`px-[14px]`, `py-[13px]`, `gap-[9px]`, `text-[13px]`) for information-dense chrome (nav rows, chips, stat labels). This phase's new components should default to the clean 4px-multiple scale above for layout/section spacing, but may match an *existing sibling component's* arbitrary value when directly extending it (e.g. a new chip added to `TrackList.tsx`'s row should match that row's existing `gap-2`/`px-2 py-1` micro-spacing, not introduce a different scale mid-row).

## Typography

Declared for Phase 26's net-new surfaces (matches the codebase's dominant real-world usage, not every ad hoc size in the repo):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 11px | Semibold (600) | 1.2, uppercase, `tracking-[.14em]` |
| Body | 14px | Regular (400) | 1.5 |
| Heading | 18px | Semibold (600) | 1.2 |
| Display | 24px | Semibold (600) | 1.2 |

Only two weights used: **Regular (400)** for body copy/descriptions, **Semibold (600)** for everything else (labels, headings, button text, chip text). This matches `dashboard/page.tsx`'s `text-2xl font-semibold` (h1), `StatCard`'s `font-semibold`, and the button convention across `BuyerOrgsAdmin`/`CapabilityRequestsAdmin` (`font-bold` in those files renders as 700 via Tailwind's `font-bold` utility — for *new* Phase 26 components, standardize on `font-semibold` (600) to avoid a third weight creeping in; do not reach for `font-bold`/`font-extrabold`/`font-black` except where directly extending an existing component that already uses them, e.g. `TrackList.tsx` row titles use `font-medium` — match the sibling, don't introduce drift mid-component).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0a0a0f` (`ink` / `--ground`) | Page background |
| Secondary (30%) | `#0E0D1E` (`card` / `--panel`) and `#1A1838` (`card2` / `--panel-2`) | Cards, rows, panels, raised surfaces |
| Accent (10%) | `linear-gradient(105deg,#818CF8 0%,#D946EF 100%)` (`bg-grad` / `.gtext` / `.fncon-cta`) | See "Accent reserved for" below — one flagship action per screen only |
| Destructive | `#F43F5E` (rose-500/rose-400 family) | Destructive actions + terminal-negative status text only |

**Accent reserved for (explicit list — the two-CTA-idiom rule this codebase already follows):**

- **Gradient (`bg-grad`, high-emphasis, one per screen):** "Review invitation" (dashboard spotlight card), "Submit for review" (Vault self-apply confirm panel), "Sign agreement" inline chip-action on a track row (deliberate exception — mirrors Phase 17's e-sign CTA treatment for the same class of action: signing a legal document), "Send invite" (admin invite form submit), the active-state Sync Library nav-item rail indicator + icon stroke (matches every other `ArtistNav` item), the coach-mark's single "Got it" button.
- **White-on-black (`bg-white text-black`, admin/utility primary, row-level or repeatable actions):** "Admit" button in the admin curation queue (mirrors `CapabilityRequestsAdmin`'s "Approve"), "Submit another song" on the hub page.
- **Outline/neutral (`border-white/10 text-white/60`, secondary/dismiss):** "Reject" in the admin curation queue (mirrors `CapabilityRequestsAdmin`'s "Deny" — reject is a real state transition but not visually alarmed), "Cancel" everywhere.
- **Never** apply the gradient to more than one control per screen, to list-row bulk actions, or to plain navigational links.

**Destructive reserved for:** the artist's "Withdraw" action on an admitted song (removes it from the catalogue — see Copywriting Contract for the required confirmation copy) and the `rejected`/`withdrawn` status-chip text/border only. Do not use rose for the admin "Reject" button itself (see Accent note above — that stays neutral/outline, matching `CapabilityRequestsAdmin`'s existing Deny treatment).

### Status Chip Semantics (new — this phase introduces two status-chip families)

Both families reuse the exact chip idiom already established by `DocumentCard.tsx`'s `STATUS_META` and `VaultProjectCard.tsx`'s `CHIP` — a small colored dot + pill border + label, never a solid-fill badge:

| Song sync-library status | Chip label | Color | Notes |
|---|---|---|---|
| `applied` | "Submitted" | amber (`border-amber-400/30 bg-amber-400/10 text-amber-300`) | Static, non-interactive |
| `under_review` | "In review" | amber (same as above) | Static |
| `agreement_pending` | "Sign agreement" | **gradient** (documented exception above) | **Interactive** — clicking opens the signing surface |
| `admitted` | "Live in Sync Library" | emerald (`border-emerald-400/30 bg-emerald-400/10 text-emerald-300`) | Static; links to the Sync Library hub |
| `rejected` | "Not accepted" | rose, muted (`border-rose-400/20 bg-rose-400/5 text-rose-300/80`) — deliberately softer than a hard-error rose to keep the phase's supportive tone (see Copywriting Contract) | Static |
| `withdrawn` | "Withdrawn" | muted (`border-white/10 bg-white/5 text-lavdim`) | Static |

| Admin admission-queue stage | Chip label | Color |
|---|---|---|
| awaiting admin review | "Needs review" | amber |
| agreement signed, awaiting admission | "Ready to admit" | indigo (`border-brandindigo/30 bg-brandindigo/10 text-brandindigo`) |
| admitted | "Admitted" | emerald |
| rejected | "Rejected" | rose |

**4. Sync Library hub (post-admission, appears only once ≥1 song is admitted):**

- Section "In progress" (any other songs not yet admitted — applied/under review/agreement_pending/rejected/withdrawn): reuses the same chip set as the Vault row (Status Chip Semantics table above), so status language is identical wherever a song's sync-library state appears

**5. New-feature highlight (fires once, on first admission):**

## State & Badge Model (informs the Status Chip tables above — visual contract only, not a schema)

Two independent gates, both required before a song is "Live in Sync Library":

1. **Artist trust gate** — is this artist allowed to submit at all? Invited artists pass this instantly (pre-approved via the spotlight-card invite). Self-applying artists pass it only when staff moves their submission out of `under_review`.
2. **Song admission gate** — is *this specific song* turned on in the catalogue? Always staff-controlled, always per-song, for both entry paths.

Visual state progression per song:

`applied` → `under_review` → (staff accepts) → `agreement_pending` *(only shown if the artist has never signed the one-time blanket agreement before — see below)* → `admitted` (or `rejected` / `withdrawn` at any point before `admitted`)

**Flagged assumption (invited-path skip):** for an artist entering via an accepted invite, `under_review` is assumed to be skipped or shown only momentarily, since staff already vetted the *artist* at invite time — the song still needs its own `applied` → `agreement_pending`/`admitted` progression, just without a visible staff-review wait state. **This is a UI-visible interpretation of the locked product decision, not independently confirmed — flag for planner/owner sign-off before building the state machine.**

**Flagged assumption (sign-once skip):** because the blanket agreement is signed once per artist (owner-confirmed 2026-08-07), a second and later submission's badge should skip `agreement_pending` entirely once the artist has a signed agreement on file, going straight from `applied`/`under_review` to `admitted`-pending (staff review only, no further signature step). **The exact badge label for "already signed, just waiting on staff to flip the switch" is not specified in locked context — recommend reusing `under_review`'s "In review" label for this case rather than inventing a 6th chip state, since visually the artist is in the same "waiting on Funūn" posture. Flag for planner confirmation.**
