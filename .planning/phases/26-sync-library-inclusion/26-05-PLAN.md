<objective>
Ship the staff/admin side of the pipeline: the invite mint, the single admit/reject curation gate, and the leadership-only takedown — each staff-gate-first, DB-loaded-target, transition-guarded, and unconditionally audited.

Purpose: This is the curation authority for the whole catalogue. Getting the staff gates right (right role set, target from DB not body, one consistent admit/reject gate per decision #2, leadership-only removal per the takedown decision) is the security core of the phase. It also fires the admission notification that triggers the artist's new-feature highlight.

Output: `POST /api/sync-library/invite`, `POST /api/sync-library/admin/[listingId]` (admit/reject), `POST /api/sync-library/admin/[listingId]/remove` (leadership), and three notification builders.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff session → invite/admit/reject | A non-staff or wrong-role session could try to curate the catalogue |
| AE/BD session → remove | An AE/BD (permissioned but not leadership) could try to take down an admitted song |
| request body → listing target | The target listing/grant could be spoofed via the body |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-17 | Elevation of Privilege | non-staff reaching a curation route | high | mitigate | `requireStaff([...])` is the FIRST statement of every route, before any DB read (T-05-02 doctrine) |
| T-26-18 | Elevation of Privilege | AE/BD performing a leadership-only takedown | high | mitigate | remove route uses `requireStaff(['leadership'])`; admit/reject use `['leadership','ae']` — role sets enforced server-side per CONTEXT |
| T-26-19 | Tampering | target listing/grant taken from request body | high | mitigate | Target loaded from the DB by the path param; body carries only decision + reason (allowlisted); never trusted for identity |
| T-26-20 | Tampering / Mass assignment | reason/decision injecting arbitrary columns | high | mitigate | Fixed allowlisted update column set per branch; body never spread into the write |
| T-26-21 | Repudiation | staff action without audit | high | mitigate | `logStaffAction` called UNCONDITIONALLY after every admit/reject/remove/invite (non-throwing) |
| T-26-22 | Tampering | double-decide advancing an already-terminal listing | medium | mitigate | `isValidTransition` guard returns 409 on any non-actionable status |
</threat_model>
