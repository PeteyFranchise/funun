<objective>
Ship the two artist-owned write routes that open and close a song's sync-library journey: the ungated self-apply submit (per-song, batched) and the artist's own withdrawal.

Purpose: Self-apply is the ONLY pre-admission door for an uninvited artist (locked CONTEXT), and it must be open to every artist for their own songs — while being airtight against submitting or withdrawing someone else's song. This is the security-critical entry point of the whole pipeline.

Output: `POST /api/sync-library/submit` and `POST /api/sync-library/[listingId]/withdraw`, both server-owned-write, ownership-gated, mass-assignment-safe, with route tests.
</objective>

    Create app/api/sync-library/submit (POST). Body: `{ projectId: string, trackIds: string[] }` (batched — locked "submit 1, several, or a whole release"). Steps, in order:
    1. `createApiClient()` + `auth.getUser()`; 401 if no user. This route is UNGATED by capability (locked: self-apply is open to ALL artists) — do NOT require a sync_library grant here.
    2. Validate body: projectId is a non-empty string; trackIds is a non-empty array of strings (cap the array length, e.g. <= 50, reject otherwise with 400). Never trust the raw shape — reject early.
    3. Ownership: on the SESSION client, load the vault_project by `.eq('id', projectId).eq('user_id', user.id).maybeSingle()`; 404 "Not found or not authorized" if absent. Then load the project's tracks and confirm EVERY submitted trackId belongs to that project (reject with 400 if any trackId is not a track of this owned project — this prevents attaching a listing to someone else's track id).
    4. Switch to `createServiceClient()`. Determine `entry_source`: if this artist has an approved `capability_grants` row `capability='sync_library'`, `source='admin_invited'`, use entry_source='admin_invited' (invited path); otherwise entry_source='self_applied'. This is the ONLY place the two paths diverge — there is no separate invited-add route. Determine `alreadySigned` by looking up an existing vault_documents row `type='blanket_agreement'`, `user_id=user.id`, status='signed' (or readEsignState→allSigned). For each valid trackId with no existing ACTIVE listing (respect the partial-unique-index states), insert a sync_listings row with an explicit allowlisted column set ONLY: vault_project_id, track_id, artist_user_id=user.id, entry_source (as resolved above), status=`initialStatusForEntry(entry_source, alreadySigned)`. Never spread the request body into the insert (mass-assignment guard — profile-route EDITABLE_FIELDS precedent).
    5. Idempotent-friendly: a track that already has an active listing is skipped (not an error) and reported back. Return `{ data: { created: [...listingIds], skipped: [...trackIds] } }`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| artist session → submit route | Untrusted projectId/trackIds cross here; an artist could try to submit another artist's song |
| artist session → withdraw route | An artist could try to withdraw another artist's listing by guessing a listingId |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-07 | Elevation of Privilege | submit route submitting a non-owned song | high | mitigate | Session-client `.eq('user_id', user.id)` project ownership check + per-trackId membership check before any insert; artist_user_id is set from `user.id`, never the body |
| T-26-08 | Tampering / Mass assignment | submit/withdraw insert-update column injection | high | mitigate | Fixed allowlisted column set on both insert and update; request body is never spread into the write (EDITABLE_FIELDS precedent) |
| T-26-09 | Information Disclosure | withdraw route revealing another artist's listing | medium | mitigate | 404 (not 403) on a non-owned/absent listing — no existence leak (connections PATCH precedent) |
| T-26-10 | Elevation of Privilege | self-apply used to fabricate an admitted listing | high | mitigate | submit only ever writes status ∈ {applied, agreement_pending, pending_admit} via `initialStatusForEntry`; `admitted` is unreachable from this route (only the staff admit route in 26-05 can set it) |
</threat_model>
