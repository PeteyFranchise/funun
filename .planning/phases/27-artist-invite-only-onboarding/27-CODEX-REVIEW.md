## Follow-up review (2026-08-09) — concurrency/atomicity of the B3/H1/M5 fix commits

**Scope:** an independent re-audit of the B3/H1/M5 fix itself (`fd526b8`, `def0c0f`), not the original 097-100 findings. Found the shared `mintOrRotateInvite()` claim helper those commits introduced was not actually atomic, plus two related write-result-ignored/non-atomic issues in the routes that call it.

- **HIGH — mintInvite rotation race (read-then-unconditional-update).** `rotateRow()` (`lib/invites/mintInvite.ts`, pre-fix ~:46) issued a plain `SELECT` to find the pending row, then an unconditional `UPDATE ... SET invite_token = <new>` keyed only on `id`+`status` — no compare-and-set against the row's prior token/expiry. Two concurrent callers reading the SAME expired row (broadcast fan-out, or a convert racing an issue) could each mint their own token and each `UPDATE` would succeed — a torn read/write: whichever email went out first silently stopped working the instant the other caller's `UPDATE` landed. **FIXED** (commit `e3d2d54`): migration 101's `mint_or_rotate_artist_invite()` — a SECURITY DEFINER, `search_path=''`, service-role-only RPC — collapses the entire mint/rotate/reuse decision into ONE row-locked `INSERT ... ON CONFLICT (LOWER(email)) WHERE status='pending' DO UPDATE` statement against migration 099's partial unique index. Two concurrent callers now serialize on Postgres's own row lock instead of racing in application code; the second caller re-evaluates its `CASE` against the just-rotated (no-longer-expired) row and correctly resolves to `'reused'`. `lib/invites/mintInvite.ts` now only generates a candidate token/expiry and calls the RPC — no JS-side select-then-branch, no 23505 fallback handling (the DB collapses that into the same statement).
- **HIGH — reintroduced ILIKE wildcard.** `mintInvite.ts` used `.ilike('email', email)` (pre-fix ~:68/:105) with no escaping — reintroducing M1's original bug (an email containing `%` or `_` would match multiple/other rows) despite `lib/invites/allowlist.ts` already establishing the correct escaping pattern (`exactCaseInsensitiveEmailPattern()`) elsewhere in this same phase. **FIXED** (commit `e3d2d54`), as a direct consequence of the atomicity fix above: the RPC matches via the same exact `LOWER(email)` equality the partial unique index and `handle_new_user()`'s gate already use — there is no client-side `SELECT` left to express with `.ilike()` at all. Covered by `lib/invites/mintInvite.test.ts`'s new test asserting a `%`/`_`-containing email reaches the RPC as an untouched parameterized string.
- **HIGH — broadcast recipient claim was select-then-stamp, not atomic.** `broadcast/route.ts` (pre-fix ~:35) selected eligible rows, then stamped `notified_reopen_at` only AFTER a successful send — not a claim. Two overlapping broadcast runs (a retry racing a still-in-flight leadership click, or two leadership members triggering it near-simultaneously) could both select the SAME unnotified row and both mint+email it before either stamp landed. **FIXED** (commit `b963ca2`): each row is now atomically claimed via a single conditional `UPDATE ... WHERE notified_reopen_at IS NULL`, checked via `.select('id').maybeSingle()` BEFORE any mint/send work — a lost claim race (another concurrent run already owns the row) is distinguished from a genuine DB error and is not double-counted. A mint or send failure resets the claim (`notified_reopen_at = null`) so the row stays retryable instead of silently marked delivered or stuck.
- **MEDIUM — broadcast `notified_reopen_at` update result ignored; `delivered` incremented unconditionally.** Superseded by the HIGH fix directly above — the same atomic-claim rewrite checks every update's result and only increments `delivered` after a confirmed send.
- **MEDIUM — convert `converted_to_invite_at` update ignored before send.** `convert/route.ts` (pre-fix ~:71) stamped `converted_to_invite_at` with a fire-and-forget `UPDATE` (result never checked) AFTER deciding, from a stale read taken at the top of the handler, whether to send. Two concurrent first-time convert calls for the SAME row could both read `converted_to_invite_at` as `null`, both pass `mintOrRotateInvite` (one `'created'`, one `'reused'` once atomic), and the `'reused'` caller's duplicate check (`row.converted_to_invite_at && state === 'reused'`) was still false against its OWN stale read — double email. **FIXED** (commit `16cb802`): a first-time conversion now requires winning an atomic `UPDATE ... WHERE converted_to_invite_at IS NULL` claim BEFORE any mint/send work; losing that race returns `duplicate: true` with no email sent. An already-converted row skips the claim entirely and keeps H1's re-issue-on-expiry path (decided by `mintOrRotateInvite`'s own atomic state), but its restamp write is now checked via `.select('id').maybeSingle()` instead of ignored.

**Disposition of the original B3/H1/M5 entries above:** B3, H1, M5 were **PARTIAL** at the code-review level (the right shape, the right idea) but not atomic under concurrency — now **RESOLVED** by the three fixes in this section. M1 (mintInvite ILIKE reintroduction, not the original `allowlist.ts` M1) is also **RESOLVED**.

**Status:** `npm test` (166 suites / 1951 tests), `tsc --noEmit`, `next lint`, and `next build` all clean after this section's fixes. Migration 101 is drafted TEXT/test-only — **NOT pushed** — applies after 100, reviewed and pushed by the owner alongside 097-100 at the phase's blocking cutover checkpoint.

## Follow-up review #2 (2026-08-09) — broadcast/convert durability under PARTIAL failure

**Scope:** a second independent re-audit, this time of failure modes distinct from concurrency — a process dying mid-send, an ambiguous provider timeout, or a caller never seeing an RPC's response even though it committed. Both remaining findings were classified MEDIUM.

- **MEDIUM — broadcast's claim doubled as the final delivered marker, not durable against a dead process.** `broadcast/route.ts`'s follow-up-#1 fix (`b963ca2`) atomically claimed each recipient by stamping `notified_reopen_at` itself, then resetting it to `NULL` on a mint/send failure. This closes concurrent-run races, but not a process that dies BETWEEN claiming and resetting: the claim lands, the reset code is never reached, and the row is stuck permanently "notified" with nothing ever delivered — no lease, no way for a later run to distinguish "abandoned claim" from "genuinely in flight" and reclaim it. **FIXED 2026-08-09** (commits `0923f4a`/`45470b9`): migration 102 adds `artist_waitlist.claim_token`/`claimed_at` as a PER-ATTEMPT lease, separate from `notified_reopen_at` (now strictly the FINAL confirmed-delivered marker). `broadcast/route.ts` claims each row with a fresh `claim_token` via `UPDATE ... WHERE notified_reopen_at IS NULL AND (claimed_at IS NULL OR claimed_at < now() - lease)` — a claim orphaned by a dead process is reclaimable by a later run once `CLAIM_LEASE_MS` (10 min) elapses. Mint/send failure releases the lease via a `claim_token` compare-and-set (checked, not fired-and-forgotten); `notified_reopen_at` is stamped only via that same CAS on confirmed send success — a row is counted `delivered` only when the CAS actually lands. Every send also carries a stable, day-scoped Resend `Idempotency-Key` (`artist-reopen-{waitlist_id}-{day}`) — the provider-level backstop for an ambiguous timeout where the request may have already been accepted even though this process never saw (or died before seeing) the response. Covered by new tests in `broadcast/route.test.ts`: mint-failure lease release, send-failure lease release, a post-send CAS-loss non-finalize case, and an idempotency-key-format assertion.
- **MEDIUM — convert's duplicate-suppression was keyed on claim state, not a confirmed send, silently swallowing a lost-response retry.** `convert/route.ts`'s follow-up-#1 fix (`16cb802`) suppressed a resend whenever `!ownsFirstConversion && mint.state === 'reused'` — i.e. whenever the row had been claimed before AND its invite was still active, regardless of whether an email had ever actually, confirmedly gone out. If the WINNING caller's process died (or its `mintOrRotateInvite()` response was lost) after the RPC committed but before `sendEmail()` ran, a later retry read `converted_to_invite_at` as already set, `mintOrRotateInvite()` correctly returned the SAME still-active invite (`state: 'reused'`), and the old check fired on that combination alone — reporting `duplicate: true` and silently never sending, with no email ever delivered. **FIXED 2026-08-09** (commit `b0d0161`): migration 102 adds `artist_waitlist.invite_email_sent_at`, a marker DISTINCT from `converted_to_invite_at`, stamped only after a CONFIRMED `sendEmail()` success (best-effort write, does not gate the response — a failed write here only risks a safe future resend, never a silent skip, since the idempotency key below covers that case too). `convert/route.ts`'s duplicate check is now `!ownsFirstConversion && mint.state === 'reused' && row.invite_email_sent_at` — a lost-response retry (invite reused, but `invite_email_sent_at` still null) correctly falls through and (re)sends using the reused invite. A mint failure on a first-time claim now also releases it via a `converted_to_invite_at` compare-and-set (CAS'd on the exact timestamp just written) instead of leaving the row permanently "claimed" with nothing minted or sent; a mint failure on an already-converted row touches nothing (there was no claim to release). Every send carries a stable idempotency key (`artist-convert-{waitlist_id}-{invite_token}`) — keyed on the EXACT token being sent, so a genuinely rotated/re-minted invite (different content) still gets a fresh key. Covered by new tests in `convert/route.test.ts`: the lost-mint-response retry scenario explicitly, plus mint-failure-releases-first-time-claim and mint-failure-on-already-converted-touches-nothing.

**Disposition of the original M5/H1 durability gap:** both were **RESOLVED** at the concurrency level by follow-up review #1, but left a residual durability gap under partial/sequential failure — now **RESOLVED** by the two fixes in this section.

**Status:** `npm test` (167 suites / 1959 tests), `tsc --noEmit`, `next lint`, and `next build` all clean after this section's fixes. ## Follow-up review #3 (2026-08-09) — remaining delivery-durability edges in the migration-102 fix commits

**Scope:** a third independent re-audit of the follow-up review #2 fix (`0923f4a`/`45470b9`/`b0d0161`, migration 102), focused on two remaining MEDIUM correlation/stability gaps plus one LOW observability gap. No HIGH/BLOCKER findings.

- **MEDIUM — convert's invite_email_sent_at is a boolean presence check, not correlated to WHICH token was sent (NEW ISSUE 1).** `convert/route.ts`'s follow-up #2 fix suppressed a resend whenever `!ownsFirstConversion && mint.state === 'reused' && Boolean(row.invite_email_sent_at)` — i.e. whenever ANY send had ever been confirmed for the row, regardless of which invite token that confirmed send actually carried. The admin issue-invite route, this route, and the reopen broadcast all share `mintOrRotateInvite()` for the same email, so the row's active `artist_invites` token can rotate out from under a convert call between attempts (e.g. token A confirmed sent, A later expires, a DIFFERENT call rotates to token B, and B's own send fails or its process dies before confirming). A retry then sees `mintOrRotateInvite()` return the SAME still-active token B (state `'reused'`), and the boolean-only check would read "yes, something was confirmed sent before" and silently suppress a resend of token B — which was never actually delivered to anyone. **FIXED 2026-08-09** (commit `bff852f`): migration 103 adds `artist_waitlist.invite_email_sent_token`, stamped alongside `invite_email_sent_at` with the EXACT token that was just confirmed sent. The duplicate check is now a direct token comparison (`row.invite_email_sent_token === mint.token`) instead of a presence/state check — a match is a true duplicate (the currently-active token was already delivered); any mismatch (rotated, still-active-but-different, or null/never-confirmed) always falls through to (re)send, independent of `mint.state`. Covered by new tests in `convert/route.test.ts`: exact-token-match suppresses, and a still-active-but-different token (`state: 'reused'`, mismatched `invite_email_sent_token`) resends instead of reporting a false duplicate.
- **MEDIUM — broadcast's idempotency key was day-scoped, not row-scoped (NEW ISSUE 2).** `broadcast/route.ts`'s follow-up #2 fix computed a single `reopenEpoch` (`new Date().toISOString().slice(0, 10)`) once per broadcast RUN and built each recipient's key as `artist-reopen-{waitlist_id}-{reopenEpoch}`. A retry that is merely delayed, or that straddles a UTC-midnight rollover between the original attempt and the retry, computes a DIFFERENT epoch and therefore a different key — defeating the key's entire purpose for exactly the ambiguous-provider-timeout scenario it exists to cover (a lost response whose underlying send may have already been accepted by Resend). **FIXED 2026-08-09** (commit `feb63ec`): the key is now scoped to the recipient row alone (`artist-reopen-{waitlist_id}`), with no time component. Safe because each `artist_waitlist` row can only ever be broadcast to once in its lifetime — the eligibility query (`notified_reopen_at IS NULL`) excludes any row that has ever been confirmed-delivered, so a stable per-row key can never collide with a genuinely later, distinct reopen campaign for that same row. Covered by new tests in `broadcast/route.test.ts`: the key format has no date component, and a simulated UTC-midnight rollover between two calls reuses the identical key.
- **LOW — claim-release UPDATE results ignored in both routes, despite comments claiming otherwise.** Both `convert/route.ts` (the mint-failure release of the first-time claim) and `broadcast/route.ts` (the mint-failure and send-failure releases of the claim lease) fired their release UPDATE and discarded the `{data, error}` result entirely, even though the surrounding comments described release semantics as if the result mattered. **FIXED 2026-08-09** (commits `bff852f`, `feb63ec`): all three release sites now capture and branch on the result — a genuine DB error is distinguished from a benign CAS-miss (the lease/claim was already reclaimed or released by another attempt, which the existing comments already documented as expected). Both are surfaced rather than silently dropped: `convert/route.ts` calls `logStaffAction` with a dedicated `artist_invite.convert_release_failed` audit entry; `broadcast/route.ts` collects a `releaseIssues` array across the run's loop and attaches it to the run's existing `artist_invite.broadcast` audit entry when non-empty. No `console.log`/`console.error` used, matching this codebase's logging convention (staff-write side effects are surfaced exclusively via `lib/staff/audit.ts`). Covered by new tests in both route test files: a DB-error release and a CAS-miss release each produce a distinct, asserted audit-log entry.

**Disposition of the original NEW ISSUE 1/NEW ISSUE 2/LOW findings above:** all three **RESOLVED** by the fixes in this section.
