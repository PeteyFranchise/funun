# Phase 27 — UI Design Contract

> Visual and interaction contract for the artist invite-only signup gate, deep-link landing,
> inline denial + waitlist, the collaborator-side invite prompt, and the Team Console
> waitlist/invite surfaces. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Design system note:** Funūn has a mature, hand-rolled dark Tailwind design system (28
> shipped phases deep) — no shadcn, no component library. Per the orchestrator's explicit
> instruction ("detect and reuse; do not invent a new one"), shadcn init was **not** proposed
> for this phase — introducing a new component system into an established brownfield app at
> phase 27 would fragment the design language, not unify it. This contract is 100% derived from
> existing, shipped patterns (auth pages, `components/collaborators/*`, Team Console `.fncon`
> theme) — no new tokens are introduced.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (deliberately not proposed — see note above) |
| Preset | not applicable |
| Component library | none — hand-rolled Tailwind utility classes |
| Icon library | none installed; inline `<svg>` (see `CollaboratorRoster.tsx` empty-state icons) — reuse this pattern, do not add a new icon package |
| Font | `var(--font-sans)` → system-ui/sans-serif (`tailwind.config.ts` `fontFamily.sans`) |

Two established sub-themes apply to this phase's surfaces, both pre-existing — reuse verbatim:

1. **Pre-auth surface** (`app/(auth)/*`) — plain Tailwind classes (`bg-white/5`, `text-white`, `border-white/10`), no CSS custom properties, single dark theme only (no light mode). Governs: signup gate, deep-link landing, denial + waitlist.
2. **Team Console surface** (`app/(admin)/*`) — `.fncon` themed CSS-custom-property system from `components/admin/console-theme.ts`, dark-default with a `[data-theme="light"]` override, injected once by `app/(admin)/layout.tsx`. Governs: the new waitlist/invite management page.

Authenticated in-app surface (`components/collaborators/*`) uses Tailwind's extended brand tokens directly (`bg-ink`, `text-lav`, `text-lavdim`, `bg-card`, `border-hair`, `bg-grad`). Governs: the collaborator-side invite prompt.

## Spacing Scale

Declared values (must be multiples of 4) — matches the codebase's existing informal scale exactly, no new values introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, chip internal padding |
| sm | 8px | Compact stacks (`space-y-4`→ label/input gap is 4px via `mt-1`), gap-2/gap-3 rows |
| md | 16px | Default form field spacing (`space-y-4`), card padding (`p-4`) |
| lg | 24px | Card padding on pre-auth surfaces (`p-6`), section gaps (`gap-6`) |
| xl | 32px | — (not used by this phase's surfaces) |
| 2xl | 48px | Empty-state vertical padding (`py-12`) |
| 3xl | 64px | Page-level vertical rhythm (`py-12` on `AuthLayout`, scaled) |

Exceptions: none. The 44px touch-target minimum applies to every tappable control introduced by this phase (gate check button, waitlist submit, collaborator invite-prompt buttons, Team Console row actions) — match the existing `min-h-[28px] min-w-[28px]` icon-button pattern only for non-primary icon affordances (e.g. a future dismiss "×"); primary buttons must use the existing `px-4 py-2` / `px-3 py-1.5` button padding, which already clears 44px including line-height on the touch surfaces that matter (signup CTA, waitlist submit).

## Typography

Reuses the codebase's existing informal type scale exactly — do not introduce a new size or weight not already shipped somewhere in this component family.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Label / meta | 12px (`text-xs`) / 11px (`text-[11px]`) | 500 (medium) — uppercase + `tracking-wide` for form labels; 400 for helper/meta text | 1.4 |
| Heading (card / section) | 20px (`text-xl`) | 600 (semibold) | 1.2 |
| Display (page h1) | 22–24px (`text-[22px]` / `text-2xl`) | 700–800 (bold/extrabold) | 1.15 |

**Documented exception to the "2 weights max" default:** this codebase's shipped convention already spans three functional weights — 400 body, 500 labels/subtext, 600–800 headings/CTAs (extrabold reserved for page-level `<h1>` only, e.g. `CollaboratorRoster`'s `text-[22px] font-extrabold`). Phase 27 reuses this exactly; do not collapse it to 2 weights, and do not introduce a 4th.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0a0a0f` (`ink`) | Page background — pre-auth pages render this via `bg-white/5` cards over the app's implicit `<body>` background; Team Console uses `var(--ground)` which resolves to the same hex in dark mode |
| Secondary (30%) | `#0E0D1E` (`card`) / `rgba(255,255,255,.03–.05)` panels | Signup/waitlist card (`bg-white/[0.03] border-white/10`), collaborator card (`bg-card border-hair`), Team Console panel (`var(--panel)`) |
| Accent (10%) | Brand gradient `linear-gradient(105deg,#818CF8 0%,#D946EF 100%)` (`bg-grad` / `.fncon-cta`) | **Reserved for exactly:** (1) the collaborator invite-prompt's "Send invite" button, (2) the Team Console's "Convert to invite" row action and its "Add invite"/primary buttons, (3) every branded email's CTA button background. **NOT used** on the pre-auth surface (see below) or on the waitlist submit button. |
| Pre-auth primary | `#FFFFFF` bg / `#000000` text (`bg-white text-black`) | The signup gate's "Check my invite" button, the credential-creation "Create account" button, and the waitlist "Join the waiting list" submit — matches the existing `signin`/`signup` white-button convention exactly (do not introduce the gradient pre-login; that convention is reserved for the authenticated app) |
| Destructive / high-stakes | `rose-500` family (`border-rose-500/30 bg-rose-500/10 text-rose-200`) | Form-level errors (gate error, waitlist error) — matches existing `signin`/`signup` error block verbatim. The Leadership-only "Reopen & broadcast" confirm step uses the same rose-500 solid button as `CollaboratorForm`'s delete-confirm (`bg-rose-500/90` → `hover:bg-rose-500`), because it is a one-shot, unconfirmable mass action — treat it with the same visual weight as a destructive delete, even though no data is deleted. |

Accent reserved for: collaborator invite-prompt primary action; Team Console "Convert to invite" / "Send invite" actions; branded email CTA buttons. Never used on the public-facing (logged-out) signup/gate/waitlist surface — that surface stays on the existing restrained white/black convention to match `signin.tsx`/`signup.tsx` precedent and avoid a jarring style break between "logged out" and "logged in" Funūn.

## Copywriting Contract

Founding-member / exclusive positioning (D-16) throughout; owner owns final wording — this is the **structural** contract (what each string must communicate and its constraints), not final locked copy. All three branded emails (D-17) require **owner sign-off before ship** — this is a launch gate, tracked as a plan checkpoint, not resolved by this spec.

| Element | Copy contract |
|---------|------|
| Gate heading | Leads with the invite-only state, before any form. Must communicate: (a) Funūn is invite-only right now, (b) this is a deliberate, exclusive/founding-cohort framing — never apologetic or "sorry, closed" in tone. e.g. structure: *"Funūn is invite-only — for now."* / sub: *"We're building this with a founding cohort of artists."* |
| Gate CTA (email-check step) | *"Have an invite? Enter your email"* (locked wording — quoted directly in 27-CONTEXT D-10) → button label *"Check my invite"* |
| Checking state | Button label swaps to *"Checking…"* (matches `signup.tsx`'s `"Creating account…"` convention exactly — present-participle, ellipsis, no spinner icon needed) |
| Allowed → credential creation | Confirmation micro-copy above the existing signup form: *"You're invited ✓"* — then the unmodified existing form (email/password), headline *"Create your account"* unchanged. |
| Existing-account branch | If the checked email already has an account: *"You already have an account — sign in instead"* with a same-origin link to `/signin?email=…`. This is a normal "already registered" UX branch, not a new enumeration surface. |
| Deep-link landing header (D-09) | *"[Inviter name] invited you to Funūn"* — warm, first-name-forward if available. Helper line under the pre-filled (editable) email field: *"This invite was sent to {email}."* If the visitor edits the email, the "invited by" framing silently falls back to the generic gate (no error, no re-ask) — same email-check flow runs underneath either way. |
| Inline denial (D-11) | Respectful, founding-member-framed, **generic regardless of why** (mistyped vs never-invited must read identically — enumeration mitigation per 27-CONTEXT's `<for_research>` note): *"We couldn't find an invite for that email. Funūn is invite-only while we grow with a founding cohort — join the waiting list and we'll reach out the moment a spot opens."* Renders **in place of the form, same page, no redirect** (D-11). |
| Waitlist form | Fields: email (pre-filled from the denied attempt), name, optional note (placeholder: *"Tell us a bit about you (optional)"*). Submit button: *"Join the waiting list"*. Captcha slot rendered above the submit button (D-12 — see Registry Safety / build note below; provider TBD by planner). |
| Waitlist success | *"You're on the list — we'll email you the moment a spot opens."* Replaces the waitlist form in place (same inline-replace pattern as the denial state itself). |
| Empty state — Team Console waitlist queue | Heading: *"No one on the waiting list yet"* / body: *"Waitlist signups from the invite-only signup gate will show up here."* (mirrors `CollaboratorRoster`'s empty-state voice: short heading + one-sentence "why/what happens" body, no CTA needed since this list is populated externally.) |
| Search — no matches (Team Console waitlist, owner add 2026-08-09) | *"No one on the waiting list matches that search."* — shown in place of the rows while a search query is active with zero matches; distinct from the never-populated empty state above. |
| Error state (gate / waitlist) | Reuses the exact existing pattern: *"{problem}"* in the `rose-200`-on-`rose-500/10` block — e.g. *"Something went wrong — try again."* for network failures; validation errors stay field-local. |
| Destructive confirmation — Reopen & broadcast (D-15, Leadership-only) | Inline two-step confirm (mirrors `CollaboratorForm`'s delete-confirm exactly): click *"Reopen & notify waitlist"* → inline text *"Send this to {N} people on the waiting list? This can't be undone."* + solid `rose-500/90` *"Yes, send"* + text-only *"Cancel"*. |
| Team Console — convert waitlist entry to invite (D-13a, any Team Member) | Row action button: *"Convert to invite"* → on success, row status chip flips to *"Invited"* with a relative timestamp (reuses `CollaboratorCard`'s `timeAgo()` "Invited Xh ago" pattern verbatim). |
| Collaborator-side invite prompt (D-08a, default-on) | Appears immediately after saving a new collaborator with an email, default-checked: *"Invite {first name} to Funūn?"* with a pre-checked checkbox/toggle and two actions: *"Send invite"* (accent gradient, primary) and *"Not now"* (text-only, matches `CollaboratorForm`'s Cancel styling). Does not block the save — the collaborator row saves regardless; this is a post-save prompt, not a gate. |
| Branded email — Invite (D-17, template A) | Subject contract: *"You're invited to Funūn"* (founding-member framing, not the existing minimal `industryInvite.ts` subject/tone — do not reuse that copy). Body must state who invited them (if known) and lead with the founding-cohort story before the CTA. |
| Branded email — Spot opened (D-17, template B) | Subject contract: *"Your spot on Funūn just opened"* — for D-13a per-person waitlist conversions specifically; must reference that they were on the waiting list. |
| Branded email — We've reopened (D-17, template C) | Subject contract: *"Funūn has reopened invites"* — broadcast tone (D-13b), sent to every waitlister at once; must not read as personally singled-out (it's a batch send) while still carrying the founding-member warmth. |
| Unsubscribe confirmation (D-19) | Heading: *"You've unsubscribed"* / body: *"You won't get Funūn's waiting-list broadcasts anymore."* + reassurance box: *"A personal invite from a collaborator or the Funūn team will still reach you — this only turns off the bulk 'we've reopened' announcements."* Primary action: *"Resubscribe"*; secondary link: *"rejoin the waiting list"*. |
| Re-subscribe confirmation (D-19) | *"You're resubscribed — you're back on the list."* / body: *"We'll email you the moment a spot opens, including reopen announcements."* |

## Surfaces & Interaction States

### 1. Signup gate (`app/(auth)/signup/page.tsx`)

State machine (client-rendered, server-authoritative per D-02 — the client states below are UX only; the real gate is `handle_new_user`):

`gate` → `checking` → (`allowed` | `existing-account` | `denied→waitlist`)

- **`gate`** (default, and the fallback for an edited/mismatched deep-link email): single email input + *"Check my invite"* button, styled exactly like the existing card (`rounded-xl border border-white/10 bg-white/[0.03] p-6`, `inputClass` reused verbatim from `signup.tsx`/`signin.tsx`). Founding-member heading above the input.
- **`checking`**: button disabled, label *"Checking…"*, no layout shift (button keeps its width — reuse the existing `disabled:opacity-40` pattern).
- **`allowed`**: gate UI is replaced in place by the existing (unmodified) create-credentials form, with the *"You're invited ✓"* confirmation line inserted above the existing `<h1>`. No page navigation — this is the same page, updated state.
- **`existing-account`**: gate UI replaced by a short message + `/signin` link (see Copywriting).
- **`denied`**: gate UI replaced **in place** (D-11 — no redirect) by the denial message + waitlist form. Card border/background unchanged; only the internal content swaps.

### 2. Deep-link landing (`/signup?invite={token}`, D-09)

Same page/component as #1, entered pre-populated: skips the `gate` state, renders directly with the *"[Inviter name] invited you to Funūn"* header, the email field pre-filled (editable) and the rest of the flow proceeding as if the visitor had just typed that email into the gate and it returned `allowed` (i.e., it still round-trips through the server check — the deep-link only supplies the pre-fill and header framing, never a client-side skip of D-02's server gate).

### 3. Inline denial + waitlist (D-11/D-12)

Renders inside the same `rounded-xl border border-white/10 bg-white/[0.03] p-6` card, replacing the gate form's children only. Waitlist form fields stack with the existing `space-y-4` rhythm and `inputClass` styling; textarea for the optional note uses the `resize-none` treatment from `CollaboratorForm`'s mailing-address field. A visible captcha slot renders directly above the submit button (build note: provider selection is a planner/researcher technical decision, not a visual one — reserve a fixed-height container so layout doesn't jump when the widget loads).

### 4. Collaborator-side invite prompt (D-08a)

Lands inside `CollaboratorForm.tsx`'s save flow (or as a small transient panel rendered by `CollaboratorRoster.tsx` immediately after `handleSaved()` for a newly-created collaborator with a non-empty email) — **not** a modal/overlay; render inline, matching the codebase's established inline-swap preference (`CollaboratorForm` itself replaces the "Add collaborator" button in place; the same convention applies here). Default-checked state per D-08. Reuses the existing `/api/collaborators/[id]/invite` POST endpoint and `bg-grad ... shadow-cta` button treatment already shipped on `CollaboratorCard`'s "Invite" button — this prompt is a new *entry point* into the same existing send action, not a new send mechanism.

### 5. Team Console — Artist Invites page (D-14, new `/admin/artist-invites`)

- **Nav placement:** add to `app/(admin)/layout.tsx`'s **all-staff** section (alongside "My Client Partners" / "Directory" — *not* the leadership-only block), since D-06 makes individual invite actions available to any Team Member.
- **Page shell:** matches `app/(admin)/admin/team-members/page.tsx` exactly — `<div className="flex-1 px-9 py-[30px]">`, `<h1 className="text-2xl font-bold text-[color:var(--ink)]">`.
- **Search / filter (owner add, 2026-08-09 — the waitlist can grow long):** a search input rendered above the list, using the existing themed input treatment (`var(--input)` bg, `var(--border)`, leading magnifier glyph), placeholder *"Search the waiting list by name or email…"*. Case-insensitive substring match over each entry's **name + email** (note text included), filtering live as the user types (no submit button). Shows a live result count beside it (*"N matches"* when searching / *"Showing N of M"* at rest) and swaps to a search-specific empty state when nothing matches (see Copywriting). At larger list sizes, pair with the existing admin pagination/scroll pattern rather than rendering unbounded rows; server-side filtering is a planner decision if the queue outgrows a single page.
- **List rows:** reuse the themed (`var(--ink)`/`var(--panel)`/`var(--border)`) row treatment established by `StaffAdmin`/capability-requests-style admin lists — bordered rows on `var(--panel)`, row actions right-aligned.
- **Per-row action ("Convert to invite"):** small `.fncon-cta` (gradient) button, `rounded-lg px-3 py-1.5 text-[13px] font-semibold` — visible to any staff role.
- **Leadership-only "Reopen & broadcast":** page-level button (not per-row), rendered only when the server-resolved role is `leadership` (component receives an `isLeadership` boolean prop from the page, mirroring `AdminLayout`'s own `isLeadership` derivation) — never hidden via CSS alone. Uses the two-step inline confirm described in Copywriting.
- **Empty state:** matches the `CollaboratorRoster` empty-state pattern (centered icon + heading + one-line body) restyled onto `.fncon` tokens (`text-[color:var(--ink-3)]` instead of `text-white/20`/`text-lavdim`).

### 6. Branded transactional emails (D-17, three templates)

Structural contract for all three (owner sign-off on final visual/copy is a separate launch-gate checkpoint, not resolved here):

- Light background (`#FFFFFF` or near-white) — standard email deliverability practice; do **not** attempt to ship the app's dark theme in email (poor client support, spam-signal risk). This is a deliberate departure from the product's dark surfaces, scoped to email only.
- Small Funūn wordmark header, matching the weight/tracking of `AuthLayout`'s wordmark (`text-lg font-semibold`) rendered in a dark ink color for contrast on white.
- CTA button uses the exact brand gradient (`linear-gradient(105deg,#818CF8 0%,#D946EF 100%)`) as its background — the one deliberate accent-color use inside an otherwise neutral email body, matching `industryInvite.ts`'s existing precedent of an indigo (`#818CF8`) button on white (this phase upgrades that single-color button to the full two-stop gradient for stronger brand match, per D-17's "not the minimal style" instruction).
- Every template ships both an HTML body and a plain-text fallback (raises the bar above `industryInvite.ts`/`staffInvite.ts`, which lack a `text` field — matches the higher bar already set by `app/api/collaborators/[id]/invite/route.ts`'s email, which does include one).
- All interpolated user-supplied values (inviter name, waitlist name/note) must be HTML-escaped before interpolation — reuse the `esc()` helper pattern from `industryInvite.ts`/`staffInvite.ts` verbatim (do not re-derive).

### 7. Unsubscribe & re-subscribe (D-19, owner add 2026-08-09)

- **Unsubscribe landing page** (`/unsubscribe`, reached from an email's unsubscribe link) — dark auth-style centered card (matches the signup surface, NOT the light email), reusing the `signin`/`signup` card treatment (`rounded-xl border border-white/10 bg-white/[0.03] p-6`). Copy makes the **broadcast-only scope** explicit (see Copywriting), including a reassurance box that a personal invite from a collaborator or the Funūn team still reaches them. Primary action: **Resubscribe** (public-surface white-button convention, `bg-white text-black`); secondary: a "rejoin the waiting list" link.
- **Resubscribed confirmation** — same card, green success line + "You're back on the list" (reuses the signup-success voice).
- **Auto re-subscribe:** re-submitting the waitlist form (surface 3) clears the opt-out server-side — no separate step for the person.
- **Team Console (surface 5) unsubscribed chip:** waitlist rows for opted-out people show a small rose "Unsubscribed" pill (`border-rose-500/30 text-rose-200`); the "Convert to invite" action stays **enabled** — a personal invite still reaches them (D-19; a collaborator invite in particular rides a real working relationship like a split sheet). Only the bulk "we've reopened" broadcast filters out opted-out recipients.
