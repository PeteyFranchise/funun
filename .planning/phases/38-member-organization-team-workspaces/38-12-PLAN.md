<objective>
Implement project attachment and detachment, the workspace catalogue read, and workspace-created
projects that are born held by the subject Member.

Purpose: this is where D-26's "one canonical project, many views" becomes real code. The failure
mode to avoid is a catalogue that copies, denormalizes or caches project data into a
workspace-shaped table — which would fork the record, break D-25's never-move guarantee, and make
detachment a deletion problem.

Output: `lib/workspaces/catalogue.ts` with its paired test, plus the attachments and projects API
routes.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| attachment request → a Member's project | The moment a workspace gains reach over a specific record |
| catalogue query → field exposure | Where a permission set becomes visible data |
| service-client insert → project custody | The one audited write that sets `user_id` to someone other than the caller |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-38-12-01 | Elevation of Privilege | Attaching a project the roster relationship does not cover | critical | mitigate | Three preconditions before insert: relationship belongs to the workspace, relationship is accepted and live, project custodian equals the relationship's Member — each with its own refusal reason |
| T-38-12-02 | Elevation of Privilege | Attaching against an inert proposal (D-05) | critical | mitigate | The accepted-and-live check uses the same liveness rule as the RLS helper; an attachment created against a proposal would still resolve to no access, but the route refuses it outright so the state never exists |
| T-38-12-03 | Information Disclosure | The catalogue returning fields the grant does not expose | high | mitigate | `fields` keys are populated only from `resolveEffectivePermissions`; the reader uses the RLS-scoped client so the policy is the row filter and the permission set is the field filter |
| T-38-12-04 | Information Disclosure | The catalogue becoming a path to clean masters (custody D-01, D-09) | critical | mitigate | The reader returns no URL, path or signable identifier at all; acceptance greps assert no storage or signed-URL import and a test asserts no URL-shaped value in any entry at any permission level |
| T-38-12-05 | Tampering | Detachment deleting or moving project data (D-25) | critical | mitigate | Detach sets a timestamp on the attachment row only; acceptance greps assert no delete call and no write to any of the five project-side tables |
| T-38-12-06 | Elevation of Privilege | A workspace-created project born held by the workspace or the caller rather than the Member (D-24, D-28) | high | mitigate | The insert sets `user_id` from the relationship's `member_user_id`; no code path assigns the caller; the project carries no workspace identifier |
| T-38-12-07 | Spoofing | A workspace-created project implying authorship, credit or a split-sheet interest (D-43) | high | mitigate | The route creates no split-sheet party, credit or rights record; an acceptance grep asserts no query against those tables; the diary records who created it, which is attribution, not authorship |
| T-38-12-08 | Elevation of Privilege | The service-client insert becoming a general write-as-anyone primitive | high | mitigate | The route accepts no arbitrary `user_id` — it derives one from a verified relationship — and it is the single audited exception, documented as such in a header comment |
| T-38-12-09 | Tampering | npm/pip/cargo installs | high | accept | No new package; 38-RESEARCH.md Package Legitimacy Audit records none proposed |
</threat_model>
