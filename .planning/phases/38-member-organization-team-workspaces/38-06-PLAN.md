<objective>
Implement the workspace seat invitation lifecycle: issue a pending seat by email, reconcile an
existing Member service-side, notify by email, expire what is not accepted, rate-limit issuance per
workspace, and bind a seat to the accepting person's own authenticated identity.

Purpose: D-12 is the acceptance criterion the whole phase is judged on first — "a Member creates a
Management workspace, invites a colleague by email, and that colleague accepts and works in it —
under one login, with no duplicate account." The correctness risk is the reconciliation step: it
must be service-only, and it must never create an account.

Output: `lib/workspaces/invitations.ts` (pure token and expiry logic, unit-tested) plus the two API
routes.
</objective>

  <behavior>
    - `hashInvitationToken` produces a stable hex digest for a given token and a different digest for a different token; it never returns the input.
    - `createInvitationToken` returns a token of at least 32 characters drawn from a cryptographically secure source and its paired hash.
    - `isInvitationRedeemable({ status, expiresAt, now })` is true only for status `pending` with `expiresAt` strictly after `now`; it is false for `accepted`, `refused`, `revoked`, `expired`, and false for a `pending` invitation whose `expiresAt` has passed.
    - `resolveInvitationExpiry({ role, now })` returns a shorter window for a time-boxed role than for a standing role, and both windows are finite — nothing is issued without an expiry.
    - `normalizeInvitedEmail` trims and lowercases, and returns null for an empty or malformed address, so a null result is an explicit refusal rather than an empty-string insert.
    - `INVITATION_RATE_LIMIT` exports the per-workspace window and maximum used by the route, so the route does not inline magic numbers.
  </behavior>
  <action>
Create `lib/workspaces/invitations.ts`. This module is pure except for Node's `crypto` — no
Supabase import, no network call.

Export `createInvitationToken(): { token: string; tokenHash: string }` using
`crypto.randomBytes(32).toString('base64url')` for the token and
`crypto.createHash('sha256').update(token).digest('hex')` for the hash. Export
`hashInvitationToken(token: string): string` using the same digest so the route can look up by hash
without ever storing the raw token.

Export `isInvitationRedeemable`, `resolveInvitationExpiry`, `normalizeInvitedEmail` and the
`INVITATION_RATE_LIMIT` constant per the behavior block. For `resolveInvitationExpiry`, use 7 days

and binds only on acceptance by the recipient's own authenticated session (D-12); and Funūn never
auto-provisions an account from an invitation, because that collides with the Phase 27 invite-only
gate and the signup trigger, which this phase does not touch.

Create `lib/workspaces/invitations.test.ts` covering every behavior bullet, using an injected `now`

  <action>
Create `app/api/workspaces/[workspaceId]/invitations/route.ts`. Read `workspaceId` from the route
params only.

`POST` — issue an invitation.
1. `requireWorkspaceAccess` on the path `workspaceId`, then compose with
   `canManageWorkspaceMembers`; return the gate's status and error verbatim on failure.
2. `checkRateLimit` with key prefix `workspace-invite:` plus the workspace id, using
   `INVITATION_RATE_LIMIT`'s window and maximum. On refusal return 429 with a plain message.
3. Zod-validate the body: `email` (string) and `role` (one of `WORKSPACE_ROLE_VALUES`). Reject a
   role of `owner` — ownership transfer is promote-then-step-down, not an invitation (D-13).
   Normalize the address with `normalizeInvitedEmail`; a null result is a 400.
4. Using the **service client**, call the `find_auth_user_id_by_email` RPC to resolve an existing
   identity. Never accept a user id from the request body, and never expose the RPC's result to the
   client beyond a boolean "this address already has a Funūn account".
5. Insert the `workspace_invitations` row with `token_hash` from `createInvitationToken`,
   `expires_at` from `resolveInvitationExpiry`, `status` left at its `pending` default, and
   `invited_by` set to the caller. Insert the paired **pending seat** in `workspace_members` with
   the requested role, `status` `pending`, `invited_email` set, and `user_id` set to the resolved
   identity when one exists or left null when it does not. Set `expires_at` on the seat when
   `isTimeBoxedRole` is true for the requested role.
6. Send the invitation email through a new `lib/email/workspaceSeatInvite.ts` written in the style
   of `lib/email/staffInvite.ts` — same shared send helper, same `esc()` escaping of every
   interpolated value. The accept link carries the raw token. The raw token exists only in memory
   and in that email.
7. `logWorkspaceAction` with action `workspace.invitation.issued`, `subjectMemberId` set to the
   resolved identity or null, `targetType` `workspace_invitation`, and `changes` carrying the role
   and the normalized address.

Never create an `auth.users` row, never call any admin user-creation API, and never modify the
signup trigger. If the address has no Funūn account, the invitation simply waits — state this in a
comment citing the Phase 27 invite-only gate.

`GET` — list the workspace's invitations for owners and admins. Return `id`, `email`, `role`,
`status`, `expires_at`, `created_at`. Never return `token_hash`.

`DELETE` — revoke a pending invitation by id: set its status to `revoked` and set the paired
pending seat's status to `removed`. Log with action `workspace.invitation.revoked`.

Every handler returns `NextResponse.json` and passes the service client to `logWorkspaceAction`.

   `accepted_at` and `accepted_by`; then update the paired pending `workspace_members` row, setting

   accepting user, `targetType` `workspace_member`.
7. Return the workspace id and the granted role so the client can navigate.

server state — acceptance is an ordinary authenticated request under one identity (D-33).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| invitation email → accepting session | The token travels out of band; the binding must still be to the session's own verified identity |
| request body email/user id → seat assignment | The classic invitation-hijack surface |
| workspace admin → invitation volume | Unbounded invitation issuance is both a spam vector and an enumeration oracle |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-38-06-01 | Spoofing | A stolen or forwarded token accepted by the wrong person | high | mitigate | Acceptance requires an authenticated session whose verified email matches the invitation address after normalization; the seat binds to `auth.getUser()`'s id, never a body value |
| T-38-06-02 | Elevation of Privilege | A client-supplied user id or email steering the seat to another account | critical | mitigate | An acceptance grep proves no identity field is read from the body; reconciliation uses the service-role-only `find_auth_user_id_by_email` RPC |
| T-38-06-03 | Elevation of Privilege | An invitation auto-provisioning an account and bypassing the Phase 27 invite gate | critical | mitigate | No user-creation API is called anywhere in this plan; an unregistered address leaves the invitation pending; acceptance greps assert the absence of `auth.admin.createUser` and `signUp(` |
| T-38-06-04 | Information Disclosure | Token material at rest, or a `token_hash` leaking through the list endpoint | high | mitigate | Only the sha256 digest is persisted; the GET select list omits `token_hash`; a 404 on lookup miss is generic and does not confirm existence |
| T-38-06-05 | Denial of Service | Unbounded invitation issuance used for spam or address enumeration (D-51) | medium | mitigate | `checkRateLimit` keyed per workspace with `INVITATION_RATE_LIMIT`; note the limiter's documented fail-open posture is acceptable here because the surface is abuse-annoyance, not access |
| T-38-06-06 | Elevation of Privilege | An `owner` seat issued by invitation, side-stepping promote-then-step-down (D-13) | medium | mitigate | The issuance schema refuses role `owner` explicitly |
| T-38-06-07 | Elevation of Privilege | An expired invitation still redeemable because nothing sweeps the table | medium | mitigate | Redemption is evaluated on read via `isInvitationRedeemable`, and the row self-heals to `expired` on first touch — no scheduled job is required |
| T-38-06-08 | Tampering | npm/pip/cargo installs | high | accept | No new package; Resend and the rate limiter are already in `package.json` per 38-RESEARCH.md's Package Legitimacy Audit |
</threat_model>
