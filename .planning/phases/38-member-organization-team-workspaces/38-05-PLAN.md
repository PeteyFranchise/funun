Create `app/api/workspaces/route.ts`.

`POST` — create a workspace. Gate with `requireMemberApiAccount` (only Member accounts create
workspaces; staff and Client-Partner-only identities are refused). Validate the body with a Zod
schema accepting `name` (trimmed, 1-120 chars), `workspaceType` (one of `WORKSPACE_TYPE_VALUES`),
optional `rosterEnabled` and `catalogueEnabled` booleans, and an optional `subjectMemberId` UUID
used only when the type is `artist_team`. Reject anything else in the body by relying on Zod's
default strip plus an explicit allowlist constant named `WORKSPACE_CREATE_FIELDS`, commented to
record that `verification_state`, `verified_at` and `verified_by` are deliberately excluded because
verification is a separate auditable act, never a creation input (D-04).

Using the service client, insert the `workspaces` row with `verification_state` left at its
database default, `created_by` set to the caller, and a slug derived from the name plus a short
random suffix to satisfy the unique constraint. In the same request, insert the creator's
`workspace_members` row with role `owner` and status `active` — the workspace is born with exactly
one owner so the D-13 floor holds from the first row. If the membership insert fails, delete the
just-created workspace row before returning the error, so no ownerless workspace is left behind.
Call `logWorkspaceAction` with action `workspace.created`, `subjectMemberId` null, `targetType`
`workspace`.

Do not auto-create a workspace anywhere, for anyone, under any condition. Do not read, write or
reference `member_type`, `industry_roles` or `capability_grants` (D-54).

`GET` — list the workspaces the caller holds an `active` membership in, selecting through the
RLS-scoped `createApiClient` so the database is the filter rather than an application `WHERE` on a
service client.

Create `app/api/workspaces/[workspaceId]/members/route.ts`.

Take `workspaceId` from the route params only. Every handler begins with `requireWorkspaceAccess`
against that path segment, and returns the gate's status and error verbatim on failure.

`GET` — list members of the workspace for any active member; return `id`, `user_id`, `role`,
`status`, `expires_at`, `created_at` only.

`PATCH` — change a member's role or status. Compose the gate with `canManageWorkspaceMembers`. Zod
schema accepts `memberId` plus optionally `role` (one of `WORKSPACE_ROLE_VALUES`) and `status` (one
of `WORKSPACE_MEMBERSHIP_STATE_VALUES`). Before writing, load the target row, and: refuse an
illegal status move using `isLegalMembershipTransition`; when the change would demote or deactivate
an owner, count the workspace's remaining `owner` + `active` rows and refuse via `canRemoveMember`
with the shared floor message. Write through the service client. Call `logWorkspaceAction` with
action `workspace.member.role_changed` or `workspace.member.status_changed`, `subjectMemberId` set
to the target member's `user_id`, and `changes` carrying the before/after values.

`DELETE` — set the target member's status to `removed`; never delete the row, because removal ends
future access while contributions, approvals, signatures and audit entries persist attributed
(D-14). Apply the same owner-floor refusal. Log with action `workspace.member.removed`.

Every handler must return `NextResponse.json`, throw no bare errors to the client, and pass the
service client — never the caller's client — to `logWorkspaceAction`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP request body → workspace mutation | Untrusted mass-assignment surface; the allowlist and Zod schema are the control |
| route path segment → acting workspace | The only trusted source of the acting workspace id (D-31) |
| caller's client → service client | Privilege elevation point; the gate must have already passed before the service client is used |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-38-05-01 | Elevation of Privilege | A client-supplied workspace id in a request body treated as the acting context (D-31) | critical | mitigate | `requireWorkspaceAccess` takes the id as an explicit argument, routes pass the path param only, and an acceptance grep proves no handler reads a workspace id from the body |
| T-38-05-02 | Elevation of Privilege | Mass assignment setting `verification_state` to verified at creation (D-04) | high | mitigate | `WORKSPACE_CREATE_FIELDS` allowlist plus Zod strip; the insert omits the column entirely so the database default applies; acceptance criterion greps for its absence |
| T-38-05-03 | Elevation of Privilege | A Funūn Team Member identity acquiring a workspace seat (D-33, ACCOUNT-TYPES staff separation) | high | mitigate | The staff branch fails closed before any database lookup, mirroring `requireMemberApiAccount`; test asserts the client was never queried |
| T-38-05-04 | Repudiation | A delegated mutation landing with no audit row, or with one collapsed identity (D-22, D-50) | high | mitigate | `logWorkspaceAction` is called on every mutating handler with both ids; acceptance criteria count the call sites |
