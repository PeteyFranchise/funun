<objective>
Implement the roster relationship lifecycle: a workspace proposes, the named Member accepts,
refuses, or refuses-and-blocks, either side records agreement evidence with a declared scope, and
the Member may end an accepted relationship unilaterally at any moment.

Purpose: this is the consent layer the entire access model rests on. Acceptance criterion 2 of the
phase — "a workspace names a Member on its roster; that Member sees the claim and the workspace can
see nothing until acceptance" — and criterion 7 — "the Member revokes the relationship
unilaterally; workspace access stops immediately" — are both proven here.

Output: `lib/workspaces/roster-service.ts` (I/O-bearing service with a paired test), the two
workspace-side routes, and the Member-side route.
</objective>

Rate-limit with key prefix `workspace-roster-propose:` plus the workspace id, using
`ROSTER_PROPOSAL_RATE_LIMIT`; 429 on refusal. Zod-validate `memberUserId` (UUID),
`professionalRole` (optional string), `effectiveFrom` and `terminatesOn` (optional dates). Call
`assertCanPropose`; on refusal return its status and error. Insert the relationship row with
`state` left at its `proposed` default and `proposed_by` set to the caller. Notify the named Member
through the project's notification helper. Log `workspace.roster.proposed` with `subjectMemberId`
set to the named Member.

The response must not include any field about the named Member beyond what the proposing workspace
already supplied plus a public display name — a proposal grants no read (D-05). Add a comment
stating this explicitly.

`GET` — list the workspace's roster relationships for any active member, selecting through the
RLS-scoped `createApiClient` so migration 183's policy is the filter. For each row include the
resolved authority tier from `loadRelationshipTier` so the roster card can show what the
relationship currently supports without the client deriving it.

`PATCH` — update only the fields in `ROSTER_EDITABLE_FIELDS`, or end the relationship. When the
body carries `action: 'end'`, call `assertWorkspaceMayEnd`, then set `state` to `ended`, `ended_at`
to now and `ended_by` to the caller, guarded by `assertCanTransition`. Never delete a row. Log
`workspace.roster.updated` or `workspace.roster.ended`.

Create `app/api/workspaces/[workspaceId]/roster/evidence/route.ts`.

`POST` — record agreement evidence. Gate with `requireWorkspaceAccess` composed with
`canManageRoster`. Zod-validate `relationshipId` (UUID), `declaredScope` (non-empty trimmed
string), optional `documentId` (UUID), optional `effectiveFrom` and `expiresAt`. Confirm the
relationship belongs to this workspace and is in state `accepted`; refuse otherwise. Insert the
`workspace_agreement_evidence` row with `declared_by` set to the caller and
`witnessed_by_signature` set to true only when the referenced `vault_documents` row records a
Funūn-executed signature — read that from the document row; default false. Log
`workspace.roster.evidence_recorded` with the declared scope in `changes`.

Funūn must not open, parse, extract from, or validate the referenced file anywhere in this route.
State that in a comment citing D-36 and D-37: the rights holder declares the scope, and the
document is supporting evidence for that declaration.

`GET` — list evidence for a relationship through the RLS-scoped client, returning the provenance
shape from `describeProvenance` rather than raw columns, so the surface speaks in observations.

`DELETE` — supersede rather than remove: set `superseded_at` and, when a replacement id is
supplied, `superseded_by`. Never delete an evidence row, because a billing or relationship event
must never destroy rights evidence (D-46).

Gate every handler with `requireMemberApiAccount` only. There is no `requireWorkspaceAccess` here;
authorization is "this row names me", enforced by matching `member_user_id` to the authenticated
user before any write, and by migration 183's SELECT policy for reads.

`GET` — list relationships where `member_user_id` is the caller, through the RLS-scoped client.
Include the workspace's name, type and `verification_state` so the Member can judge the claim, and
the resolved authority tier.

`PATCH` — body carries `relationshipId` and one of `action: 'accept' | 'refuse' | 'block' | 'end'`.
For every action: load the row with the service client, refuse with 403 unless `member_user_id`
equals the authenticated user, then gate the move with `assertCanTransition`.
- `accept` → `state` `accepted`, `accepted_at` now; set `effective_from` to today when it is null.
- `refuse` → `state` `refused`, `refused_at` now.
- `block` → `state` `refused` plus an upsert into `workspace_roster_blocks` for the pair, so the
  same workspace cannot propose again (D-51). Use `ON CONFLICT DO NOTHING` semantics so a repeat
  block is a no-op.
- `end` → `assertMemberMayEnd`, then `state` `ended`, `ended_at` now, `ended_by` the caller. This
  path takes no approval, no notice period and no counterparty acknowledgement — add a comment
  stating that D-18 makes this unconditional and that Funūn must never trap someone in a disputed
  relationship.

Log every action through `logWorkspaceAction` with the relationship's `workspace_id`, `actorId` and
`subjectMemberId` both set to the acting Member, and an action name of
`roster.accepted` / `roster.refused` / `roster.blocked` / `roster.ended`. The log is visible to both
sides (D-50), which is what makes an ending non-deniable in either direction.

Never delete a relationship row. Never write to any project, track, asset or document table from
this route.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workspace proposal → the named Member's data | The whole point of D-05: this boundary must be impassable until acceptance |
| Member-side route → a relationship row | Authorization here is row ownership, not workspace membership |
| uploaded agreement file → Funūn's claims about it | Parsing the file would convert storage into a representation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-38-07-01 | Information Disclosure | The proposal response leaking the named Member's data before acceptance (D-05) | critical | mitigate | The POST response is restricted to what the proposer supplied plus a public display name; all reads go through the RLS-scoped client so migration 183's policy, not application code, is the filter |
| T-38-07-02 | Elevation of Privilege | A Member patching a relationship that names someone else | critical | mitigate | Every write path loads the row and compares `member_user_id` to `auth.getUser()`'s id before mutating; the acceptance criterion names this check |
| T-38-07-03 | Elevation of Privilege | Authority tier granted from evidence attached to a non-accepted relationship (D-16) | high | mitigate | The evidence route refuses unless the relationship state is `accepted`; `resolveAuthorityTier` independently returns `none` for any other state |
| T-38-07-04 | Repudiation | Funūn implying it validated an agreement by parsing it (D-36, D-37) | high | mitigate | No parsing, extraction or validation code path exists in the evidence route; `describeProvenance` is the only vocabulary the GET returns; final labels remain counsel-gated |
| T-38-07-05 | Denial of Service | A workspace re-proposing repeatedly after a refusal, harassing a Member (D-51) | medium | mitigate | `workspace_roster_blocks` upsert on the `block` action plus `assertCanPropose`'s block check, backed by per-workspace `checkRateLimit` on the propose route |
| T-38-07-06 | Tampering | Rights evidence destroyed by an ending or an administrative delete (D-46) | high | mitigate | Evidence is superseded, never deleted; relationships are ended, never deleted; acceptance criteria grep for the absence of `.delete()` in all three route files |
| T-38-07-07 | Elevation of Privilege | A workspace blocking the Member's own exit by contesting the end | high | mitigate | The Member's `end` branch has exactly two preconditions, both about legality and identity; no approval or acknowledgement path exists to contest it (D-18) |
| T-38-07-08 | Tampering | npm/pip/cargo installs | high | accept | No new package; 38-RESEARCH.md Package Legitimacy Audit records none proposed |
