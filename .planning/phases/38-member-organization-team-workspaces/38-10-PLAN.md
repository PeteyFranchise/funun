Section (a) `public.workspace_attachments`: `id` UUID PK default `gen_random_uuid()`;
`workspace_id` NOT NULL REFERENCES `public.workspaces` ON DELETE CASCADE; `project_id` NOT NULL
REFERENCES `public.vault_projects` ON DELETE CASCADE; `relationship_id` UUID REFERENCES

`auth.users`; `attached_at` TIMESTAMPTZ NOT NULL DEFAULT NOW(); `detached_at` TIMESTAMPTZ;
`detached_by` UUID REFERENCES `auth.users`; `created_at`.

A partial unique index on `(workspace_id, project_id) WHERE detached_at IS NULL` so one live
attachment exists per pair while detached rows persist as history. A covering index on
`(project_id, workspace_id) WHERE detached_at IS NULL` — this is the index migration 186's helper
enters the chain through, so comment it as load-bearing. An index on
`(workspace_id) WHERE detached_at IS NULL` for the catalogue query.

Enable row level security. Add a table comment stating D-25 and D-26 in plain words: detachment
severs the link only; nothing moves, copies or is deleted; a workspace catalogue is a query over
these rows and never a copy of the project.

Section (b) `public.workspace_custody_transfers`: `id`; `project_id` NOT NULL REFERENCES
`public.vault_projects` ON DELETE CASCADE; `from_user_id` UUID NOT NULL REFERENCES `auth.users`;
`to_user_id` UUID NOT NULL REFERENCES `auth.users`; `offered_by` UUID NOT NULL REFERENCES
`auth.users`; `workspace_id` UUID REFERENCES `public.workspaces` ON DELETE SET NULL (nullable — a
transfer may be offered outside any workspace context); `state` TEXT NOT NULL DEFAULT `'offered'`
CHECK IN (`'offered'`, `'accepted'`, `'declined'`, `'withdrawn'`); `offered_at` TIMESTAMPTZ NOT NULL
DEFAULT NOW(); `responded_at` TIMESTAMPTZ; `note` TEXT; `created_at`.

Add `CHECK (from_user_id <> to_user_id)`. Add a partial unique index on
`(project_id) WHERE state = 'offered'` so at most one live offer exists per project. Enable row
level security.

Add a table comment stating D-29: custody may transfer, but only as a two-sided act — the current
holder offers, the recipient accepts, and the diary records it permanently. Never unilateral. Note
that the actual `vault_projects.user_id` write is performed by the service route on acceptance, not
by a trigger here, so the diary entry and the custody change are one reviewable code path.

Section (c) Write lockdown: `REVOKE INSERT, UPDATE, DELETE ... FROM authenticated, anon;` on both
tables.

Section (d) SECURITY DEFINER helpers, declared with 182's conventions (`LANGUAGE sql STABLE
SECURITY DEFINER SET search_path = ''`, `REVOKE EXECUTE` then `GRANT EXECUTE TO authenticated`,
plus a `COMMENT ON FUNCTION` naming each as an RLS-policy helper intended to be wrapped as
`(SELECT ...)`):
- `public.workspace_attachment_visible(p_attachment_id UUID, p_uid UUID) RETURNS BOOLEAN` — true for
  an active member of the attachment's workspace, or for the project's current custodian.
- `public.custody_transfer_visible(p_transfer_id UUID, p_uid UUID) RETURNS BOOLEAN` — true only for
  the offer's `from_user_id`, `to_user_id`, or `offered_by`. A workspace membership alone must not
  reveal a custody negotiation.

Section (e) Own SELECT policies, both routed through the helpers above and scalar-subselect wrapped:
`workspace_attachments_select` and `workspace_custody_transfers_select`.

Section (f) A BEFORE INSERT trigger `guard_custody_transfer_offered_by_holder()` on
`workspace_custody_transfers`, in 172's shape: raise an exception when `offered_by` is not equal to
`from_user_id` and is not an active `owner` or `admin` of the row's `workspace_id`. Use `ERRCODE =
'insufficient_privilege'` and a message naming the two-sided rule. This is what makes a unilateral
grab structurally impossible even if a future route forgets to check.

Section (g) `NOTIFY pgrst, 'reload schema';`

Do not add any column to `vault_projects`. Do not alter any existing policy on `vault_projects`,
`tracks`, `vault_assets`, `vault_documents`, `tool_outputs`, `project_members` or `work_members`.
Do not define the three-hop project-permission helper — that is migration 186.
