<planner_decisions>
Decisions taken here so no executor has to re-derive them:

1. **`manage_payouts` / `view_tax_information` are NOT members of `WorkspacePermission`.**
   D-42 requires a structural exclusion, not "a permission defaulting to false." They live in a
   separate `STRUCTURALLY_EXCLUDED_CAPABILITY_VALUES` union that is deliberately *not* part of the
   grantable union, so `isSubsetGrant()` cannot be called with one under `strict` TypeScript and
   migration 184's CHECK constraint cannot store one. 38-RESEARCH.md Pattern 3 sketched a single
   union with a `STRUCTURALLY_EXCLUDED` set; that sketch is superseded here because a value inside
   the grantable union IS "a permission defaulting to false" — exactly what D-42 forbids.

2. **`document-supported` is a derived authority tier, not a stored roster state.**
   Per 38-RESEARCH.md Open Question 2's compute-on-read recommendation (D-39 lapse with no cron
   job). `types.ts` therefore declares five stored roster states and a separate three-value
   authority-tier union. Plan 38-02 implements the resolver.

3. **Bundles are data, not code branches.** Preset bundles are exported as a readonly record of
   permission arrays. Nothing anywhere keys behavior off a bundle name or a workspace role name
   (D-19: "Nothing is hardcoded to a role name").
</planner_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| request body → grant issuance | An untrusted permission-name string reaches `isSubsetGrant` from an API payload; this module is the point at which it is validated against the catalogue |
| granter's own held set → issued grant | The privilege ceiling; a defect here silently widens every downstream grant |
