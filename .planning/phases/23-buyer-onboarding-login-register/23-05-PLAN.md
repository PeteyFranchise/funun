<objective>
Add the **buyer password auth mechanism** (locked directive 3): make the shared password-recovery/set flow role-aware so buyers land on `/sync/catalog` instead of the artist `/vault`, and switch the buyer invite to a recovery-style link that lands on a "set your password" step. Isolate the mechanism so it can be swapped to magic-link-only later.

Purpose: RESEARCH Pitfall 1 — the CONTEXT-locked Marmoset modal wants email/password + forgot-password, but buyers today log in via magic-link only and never set a password; Pitfall 2 — `/auth/callback` and `/update-password` hardcode `/vault`, which strands a buyer on the artist app. This plan resolves both at the backend so the modal (23-07) can use `signInWithPassword`.
Output: A role-aware post-auth destination resolver, the recovery-link buyer invite, and the fixed `/vault`-hardcode redirects.

**AUTH DECISION — LOCKED (owner confirmed 2026-08-07): password path.** Buyers authenticate with email/password (matching the Marmoset modal design), set via the recovery-style invite + the existing `/forgot-password` / `/update-password` flow. Execute Tasks 1–3 as written. The mechanism stays isolated (a one-line `generateLink` `type` swap would revert to magic-link-only) but that path is NOT taken. DEPENDENCY RISK — **Resend is NOT configured in prod**, so invite/reset emails no-op silently until the owner sets `RESEND_API_KEY`/`RESEND_FROM_EMAIL`; the in-app notification + admin queue are the reliable channels until then, and a buyer's first-time set-password link may need out-of-band delivery (owner/AE hands it over, as done for the `pete@funun.studio` bootstrap) until email is live.
</objective>
