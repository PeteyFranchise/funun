# Phase 31.1: Code Review Report

**Reviewed:** 2026-08-24T00:00:00Z
**Depth:** standard
**Files Reviewed:** 50
**Status:** issues_found

## Summary

Access control is solid throughout this phase: every new table (`pipeline_stages`, `health_rules_config`, `game_plans`, `onboarding_tasks`) is RLS-enabled with zero policies plus an explicit `REVOKE` from `authenticated`/`anon` (migration 128), so all four are reachable only through service-role staff routes. `requireStaff`/`requireStaffPage`/`verifyAdmin` gate every route and page correctly, leadership-only surfaces (`health-rules`, `pipeline-stages`, AE assignment) are consistently `['leadership']`-gated, and the "hide, not filter" contract for the Client Partners room's All tab is real — `loadWholeBookWithCoverage` is only ever invoked inside the `isLeadership` branch and is proven server-side by `lib/admin/gate.test.ts`. Own-book scoping (`canAccessOrgContacts`/`isAssignedToOrg`) resolves to 404, never 403, consistently. Mass-assignment protection (allowlist-then-zod, `.strict()` schemas) is applied correctly on `health-rules`, `pipeline-stages`, and `game-plan` writes. The executed/signed-license stamping in `lib/deals/executed.ts` is genuinely idempotent under a race (pre-read + a conditional `WHERE executed_at IS NULL` write, with a re-read fallback for the losing concurrent caller), and correctly never touches deal `stage`. The AE-assign route's best-effort side effects (relationship log, onboarding task, notification/intro email) are each independently wrapped in `.catch(() => {})` after the authority write commits, matching the D-07 contract, and this is proven by dedicated tests for each failure mode.

The one correctness defect serious enough to block is that the `at_risk_after_days` threshold — the third of four "sets the color" inputs on the leadership-only Health Rules screen — is stored, validated, and exposed as a live control, but is never actually read by `computeHealth()`'s band logic. Changing it has zero effect on any client's computed health. See CR-01 below. The remaining findings are quality/robustness gaps: unchecked Supabase read errors across the new signals data-source layer, no idempotency guard on repeat onboarding-task creation, and a content-sniffing gap on the prospect-image upload.

## Critical Issues

### CR-01: `at_risk_after_days` is dead configuration — the Health Rules "At risk" threshold has no effect on computed health

**File:** `lib/client-partners/health.ts:80-105`
**Issue:** `computeHealth()`'s band ladder only branches on `good_within_days`, `warning_after_days`, and `cold_after_days`:

```ts
if (days <= rules.good_within_days) {
  base = 'good'
} else if (days <= rules.warning_after_days) {
  base = 'warning'
} else if (days <= rules.cold_after_days) {
  base = 'at_risk'
} else {
  base = 'cold'
}
```

`rules.at_risk_after_days` is never referenced anywhere in this function (or anywhere else in the health-compute path — confirmed via `grep -rn at_risk_after_days`, which only turns up storage/validation/UI usages, never a read inside `computeHealth`). The function's own docstring even documents this inconsistency without resolving it: `days <= cold_after_days -> at_risk (covers at_risk_after_days..cold_after_days)` — i.e. the comment claims `at_risk_after_days` is a sub-boundary, but the code never checks it; the entire `(warning_after_days, cold_after_days]` range is one undifferentiated "at_risk" band regardless of what `at_risk_after_days` is set to. `health.test.ts` even encodes this as expected behavior (`'executed at_risk_after_days+1 ago → still at_risk (until cold_after_days)'`), which proves the tests were written to match the buggy implementation rather than catch it.

The bug surfaces directly to leadership: `components/admin/HealthRulesForm.tsx` renders "At risk" as one of four `NumberField`s under a badge that literally says **"sets the color"** (`HealthRulesForm.tsx:237-246`), and `app/api/admin/health-rules/route.ts` validates `at_risk_after_days` ordering (`good < warning < at_risk < cold`) as if it were load-bearing. A leader who narrows or widens the "At risk" window — reasonably believing it changes when clients flip to the at-risk color, per the UI copy and the D-31.1-03 goal of "tunable Good/Warning/At-risk/Cold thresholds" — will see no change in any client's health state. This directly undermines a core deliverable of this phase (the leadership-configurable health engine) and will produce silently incorrect expectations about which clients are at risk.

**Fix:** Either wire the threshold in, or stop presenting it as live. The minimal fix that matches the documented ladder intent is to split the `at_risk` band using the fourth threshold:

```ts
} else if (days <= rules.at_risk_after_days) {
  base = 'warning'
} else if (days <= rules.cold_after_days) {
  base = 'at_risk'
} else {
  base = 'cold'
}
```
(Then remove `warning_after_days` from the ladder, or repurpose it — whichever the D-31.1-02 design actually intends; the key point is that every stored/validated/user-facing threshold must correspond to an actual branch in `computeHealth`.) Update `health.test.ts`'s boundary tests to assert the corrected behavior, and re-verify the `HealthRulesForm` preview reflects the change live.

## Warnings

### WR-01: New signals data-source layer never checks Supabase read errors — a DB failure silently renders as "no data" instead of surfacing

**File:** `lib/client-partners/signals.ts:45-341` (all of `fetchHealthRulesConfig`, `fetchPipelineStages`, `fetchDealsForOrgs`, `fetchCountByOrg`, `fetchOpenBriefsByOrg`, `fetchLastSelectsSentByOrg`, `fetchLastContactByOrg`, `fetchStaffNames`, `loadBook`, `loadWholeBookWithCoverage`)
**Issue:** None of these functions destructure or check `error` from their Supabase calls — every one does `const { data } = await service.from(...)...` and falls back to `[]`/`null` on any failure (permissions error, timeout, RLS misconfiguration, etc.). Concretely: if `fetchDealsForOrgs` fails (e.g. a transient RLS/service-role hiccup on `license_requests`), `lastExecutedLicenseAt` resolves to `null` for every org in the batch, and `computeHealth` renders every client as `'prospect'` — indistinguishable from "this client has genuinely never licensed." This masks the exact class of failure the health engine exists to surface (churn risk), and violates the project's own documented convention ("No silent failures — functions either complete successfully or throw", CLAUDE.md § Error Handling). Contrast with `lib/client-partners/contacts.ts` and `lib/client-partners/game-plan.ts` in the same phase, which do check `error` and throw with descriptive messages.
**Fix:** Check `error` in each fetch helper and throw (mirroring `contacts.ts`'s `if (error) throw new Error(...)` pattern), or at minimum log/report the failure so a broken query doesn't get silently interpreted as "no clients have ever licensed."

### WR-02: No idempotency guard on `onboarding_tasks` creation — repeat/duplicate assignment piles up identical handoff tasks

**File:** `lib/client-partners/onboarding.ts:55-80`, `app/api/admin/buyer-orgs/[id]/ae/route.ts:117-136`
**Issue:** `insertOnboardingTask` unconditionally inserts a new row every time the AE-assign route runs with a non-null `ae_user_id` — including a reassignment to the *same* AE (explicitly covered as valid behavior by `staff-buyer-orgs-api.test.ts`'s "reassigning an org to the SAME AE" test) and including a client-side double-submit (network retry, double-click before `AssignAePanel`'s `submitting` guard engages). There is no unique constraint on `(buyer_org_id, assignee_id, status)` in migration 128, and no existing-open-task check before insert. The result: an AE's "Your handoff tasks" panel (`OnboardingTasksPanel`) can accumulate multiple identical "Welcome X to your book" cards with the same seeded checklist for one org.
**Fix:** Before inserting, check for an existing `open` onboarding task for `(buyer_org_id, assignee_id)` and skip/update instead of duplicating — or add a partial unique index (`onboarding_tasks (buyer_org_id, assignee_id) WHERE status = 'open'`) as a DB-level backstop, matching the `buyer_org_contacts_one_primary_per_org` pattern already used elsewhere in this codebase.

### WR-03: Prospect-image upload trusts the client-supplied MIME type with no content verification

**File:** `app/api/admin/health-rules/prospect-image/route.ts:24-68`
**Issue:** The route gates on `file.type` (browser-supplied `Content-Type`) against `EXT_BY_MIME` and stores the file under an extension derived purely from that header — it never inspects the actual file bytes (magic-number sniffing). A malicious or malformed upload with a spoofed `Content-Type: image/png` header (e.g. containing SVG/HTML/script content) would pass validation and be stored in the public `vault-assets` bucket, then served back via `getPublicUrl` and rendered in an `<img>` tag by `HealthRulesForm`. The blast radius here is narrow (leadership-only route, and `<img src>` doesn't execute embedded scripts the way navigating to the URL directly would for an HTML/SVG payload with a spoofed extension), but it's the same file-upload-validation gap the project's own `README`/`CLAUDE.md` review checklist calls out ("Unvalidated File Uploads to Storage" anti-pattern) and is worth closing given the bucket is public.
**Fix:** Validate actual file content (e.g. check the PNG/JPEG/WebP magic bytes) before upload, not just the `Content-Type` header, mirroring how a defense-in-depth upload handler should behave.

### WR-04: Deleting a pipeline stage leaves referencing orgs with a stale `stage_entered_at` and no visible stage

**File:** `app/api/admin/pipeline-stages/route.ts:145-167` (`DELETE`), `supabase/migrations/128_ae_console_health.sql:106-108` (`ON DELETE SET NULL`)
**Issue:** `buyer_orgs.pipeline_stage_id` is `ON DELETE SET NULL`, so deleting a stage that orgs currently reference nulls out `pipeline_stage_id` but leaves `stage_entered_at` untouched. In `lib/client-partners/signals.ts`'s `assembleRows`, `resolveStage(org.pipeline_stage_id, stages)` then returns `null` (rendering `status: null`, i.e. a dash in the UI), while `daysInStage(org.stage_entered_at, now)` still computes and renders a stale, now-meaningless day count next to that dash — e.g. a row showing "—" for status but "214d" for days-in-stage. The DELETE route (`app/api/admin/pipeline-stages/route.ts`) has no guard warning leadership that in-use stages are about to be orphaned this way, nor does it clear `stage_entered_at` alongside the FK null-out.
**Fix:** Either block deletion of a stage that's currently referenced by any `buyer_orgs` row (surface the count in the 400), or have the DELETE route also null `stage_entered_at` for affected orgs in the same request so the two columns stay consistent.

### WR-05: AE-assign route hand-rolls body validation instead of the project's zod `.strict()` convention

**File:** `app/api/admin/buyer-orgs/[id]/ae/route.ts:41-62`
**Issue:** Every other write route touched by this phase (`health-rules`, `pipeline-stages`, `game-plan`) validates its body with a zod `.strict()` schema. The AE-assign route instead manually type-checks `body.ae_user_id`/`body.note` with ad-hoc conditionals. There's no mass-assignment risk in practice (the eventual `update()` call only ever writes a hand-built `{ ae_user_id: aeUserId }` object, never a spread of `body`), so this is a consistency/maintainability gap rather than an exploitable defect — but it also means `note` has no length cap (an arbitrarily large string is accepted and written to `client_relationship_log.body` and `onboarding_tasks.handoff_note` with no bound), unlike every other free-text field in this phase (e.g. `GamePlanTopicSchema`'s `note: z.string().max(2000)`).
**Fix:** Introduce a small zod schema (`z.object({ ae_user_id: z.string().uuid().nullable(), note: z.string().trim().max(2000).optional() }).strict()`) for consistency and to bound `note`'s length.

## Info

### IN-01: `pipeline-stages` POST leaves `sort_order` defaulting to `0` for every new stage with no collision handling

**File:** `app/api/admin/pipeline-stages/route.ts:21-28`
**Issue:** `sort_order` is optional on create; the DB column defaults to `0`. Creating multiple stages without specifying `sort_order` gives them all `sort_order = 0`, and `GET`'s `ORDER BY sort_order ASC` then falls back to unspecified/insertion-order tie-breaking. Cosmetic today (stage counts are small and leadership-curated) but worth a `COALESCE(MAX(sort_order)+1, 0)` default if this ever gets heavier use.

### IN-02: `admin/clients/[personId]/page.tsx` duplicates the staff-gate logic `requireStaffPage()` already centralizes

**File:** `app/(admin)/admin/clients/[personId]/page.tsx:45-53`, `app/(admin)/admin/client-partners/[orgId]/page.tsx:44-54`
**Issue:** Both pages manually reimplement `requireStaffPage`'s session-fetch + `getStaffRole` + `'it'`-exclusion + redirect sequence inline (with a comment explaining why: "layout redirect alone is not relied upon"), rather than calling `requireStaffPage(['leadership','ae','bd',...])` from `lib/admin/gate.ts`, which exists precisely for this. Functionally equivalent today, but the duplication means a future change to the staff-role exclusion list (e.g. adding a new restricted role) has to be applied in multiple places instead of one.

### IN-03: `HealthRulesForm` number inputs silently accept non-integer input the server will reject

**File:** `components/admin/HealthRulesForm.tsx:99-107`
**Issue:** The threshold `<input type="number">` has no `step="1"` and `onChange` does `Math.max(1, Number(e.target.value) || 1)`, which happily accepts `90.5`. `handleSave` PATCHes the raw draft value; the server's `z.number().int().positive()` then rejects it with a generic 400 ("Invalid health rules payload") that doesn't explain *why* — the leader has to guess it was the decimal. Coercing with `Math.round`/`Math.trunc` client-side (or adding `step="1"`) would avoid the round-trip failure.
