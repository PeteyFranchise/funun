## Decisions Made
- Threshold-ordering check on PATCH reads the current row and merges it with the incoming partial patch before validating `good_within_days < warning_after_days < at_risk_after_days < cold_after_days` — a single-field PATCH (e.g. only `warning_after_days`) is still validated against the real current neighbors, not just the fields present in the request body.
- Pipeline-stages PATCH validates `id` via a separate minimal schema, then runs the pick-allowlist-first/validate-second pattern on the remaining fields — an unlisted key (e.g. `buyer_org_id`) is silently dropped rather than causing the whole PATCH to 400, matching the health-rules config route's established behavior (and my own test suite, adjusted mid-implementation to match this intended semantics rather than a hard `.strict()` 400 on the raw body).
- The Health Rules screen's live-preview sample is built by a page-local `loadSampleSignals()` rather than reusing `lib/client-partners/signals.ts`'s `loadWholeBookWithCoverage` — that exported loader bakes `health` against the CURRENTLY SAVED config, but the preview needs the raw, unbaked `HealthSignals` per org so it can be recomputed against the leader's in-progress draft thresholds before Save. No changes were made to `signals.ts` (plan's `files_modified` scope is respected — 31.1-04's signals module is untouched).
- Prospect-marker placeholder renders the neutral 🦁 emoji (same neutral placeholder the approved `phase-31.1-health-rules-mockup.html` ships) rather than any team-logo image asset, per D-31.1-08's explicit prohibition on embedding a trademarked logo.

## Deviations from Plan

None — plan executed exactly as written. Restructured PATCH to pick-then-validate (same pattern as `route.ts` for health-rules) before the implementation commit — this was resolved entirely within Task 1's TDD RED/GREEN cycle, not a deviation from the shipped plan.
