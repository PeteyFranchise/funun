**Researched:** 2026-08-23

## Summary

Phase 31.1 is almost entirely an **assembly-of-existing-parts** phase, not a greenfield build. The shared list surface (`ClientPartnersList` + `lib/client-partners/columns.ts`), the own-book scoping (`getStaffRole`/`requireStaff`/`requireStaffPage`), the AE-assign write path (`PATCH /api/admin/buyer-orgs/[id]/ae`), the relationship log (`client_relationship_log`), the in-app notification (`createNotification`), and the image→storage→config-value avatar pattern (`/api/admin/staff/[id]/avatar`) all already ship and are directly reusable. The work is: (1) consolidate the two existing pages into one tabbed room with server-side leadership gating on the All tab; (2) add the missing **data model** for health/stages/game-plan/onboarding-tasks (migrations 128+); (3) build the **compute-on-read health engine** and the leadership **Health Rules** config surface; and (4) extend the existing assign route into the full **D-07 structural handoff**.

The single largest risk-bearing finding is the **health-color data source**. The color is driven by "last actual license recency" (D-31.1-02). The deal substrate exists — `license_requests` (migration 081) with a `stage` pipeline including `closed_won` and `gross_fee_cents`/`budget_cents` — but there is **no dedicated `closed_won_at` timestamp**. Today's deals metrics route approximates the close date with `updated_at`, which is unreliable for recency (any later row edit moves it). The minimal, correct addition is a `license_requests.closed_won_at TIMESTAMPTZ` column set on transition to `closed_won`. This gates the entire health feature and must be a first-wave dependency.

Second: there is **no D-10 pipeline-stage model yet**. `buyer_orgs.status` (migration 095) is a lead/onboarding status (`pending_onboarding`), NOT the New lead → Contacted → Active → Negotiating → Closed/Dormant pipeline the tower renders. The `daysInStage`/`status` columns in `columns.ts` currently have **no live source**. 31.1 must add a leadership-configurable `pipeline_stages` table + a stage pointer + `stage_entered_at` on `buyer_orgs`.

**Primary recommendation:** Do the data-model migration (128) first as a blocking Wave 0/1 dependency (adds `closed_won_at`, `pipeline_stages`, `buyer_orgs.pipeline_stage_id`/`stage_entered_at`, `health_rules_config`, `game_plans`, `onboarding_tasks`), then build the pure `lib/client-partners/health.ts` compute-on-read module (unit-tested in isolation like `columns.ts`), then wire the tabbed room + Health Rules + the D-07 handoff extension on top. Reuse `ClientPartnersList` unfiltered; never rebuild it.

## The Last-License / Paid-Placement Date Source (KEY DEPENDENCY — D-31.1-02)

**Verdict: the deal substrate EXISTS, but the recency-safe date does NOT — a minimal column addition is required and gates the whole health color.**

- **What exists** [VERIFIED: migration 081 `license_requests`]: per-client deal rows keyed by `buyer_org_id`, a `stage` pipeline (`submitted → in_negotiation → terms_agreed → contract → closed_won → closed_lost`), `gross_fee_cents`, `budget_cents`, `created_at`, `updated_at`, and `contract_document_id`→`vault_documents` (type `sync_license`, added by 081).
- **What's missing:** no `closed_won_at`. The existing deals-metrics route (`app/api/admin/deals/metrics/route.ts`) approximates close time with `updated_at` [VERIFIED], which is unreliable — any later edit to a closed row moves the "recency" and would silently re-color a client. `updated_at` is fine for lifetime aggregation, wrong for the health clock.
- **Minimal addition (recommended):** `license_requests.closed_won_at TIMESTAMPTZ`, set atomically when the stage-transition route moves a deal to `closed_won`. Backfill from `updated_at` for existing closed rows (prod is empty → no-op today). Then:
  - **Health color clock** = `now() − MAX(closed_won_at)` over that org's `closed_won` deals. No `closed_won` row → **Prospect (🦁)**, off the color axis (D-31.1-02).
  - **Lifetime value** column = `SUM(gross_fee_cents)` over `closed_won` for the org.
  - **Open deal** column = `gross_fee_cents` (or `budget_cents` fallback) over non-terminal stages.
- **Alternatives** if the owner prefers "executed" over "won": COALESCE `closed_won_at` with `esign_envelopes.completed_at` (migration 124) via `contract_document_id`, or the `sync_library` executed date. Flag for the owner; default to `closed_won_at` for simplicity. `[ASSUMED]` that "closed_won === a paid/executed license" for health purposes — confirm with owner (some deals may close won before payment/signature).
- **Also gated by this:** the coverage strip's "Open pipeline $" and "Lifetime" and the By-AE "$X lifetime" all read the same `license_requests` aggregation.

## Health Compute-on-Read Approach (D-06)

Build `lib/client-partners/health.ts` as a **pure function**, mirroring `columns.ts`/`lib/crate-requests/ranking.ts` (pure, no I/O, unit-tested via `health.test.ts`). The RSC page loads the raw signals in `Promise.all` (as `my-client-partners/page.tsx` already does for briefs/selects/contacts) and passes them to the pure resolver:

```ts
// Source: pattern mirrors lib/client-partners/columns.ts (pure, testable)
export type HealthState = 'good' | 'warning' | 'at_risk' | 'cold' | 'prospect'

export function computeHealth(input: {
  lastClosedWonAt: string | null       // MAX(closed_won_at) for the org
  hasOpenBrief: boolean                 // open buyer_briefs (non-terminal)
  hasOpenDeal: boolean                  // non-terminal license_requests
  lastSelectsSentAt: string | null
  lastContactAt: string | null          // MAX(client_relationship_log.created_at)
  rules: HealthRulesConfig
  now?: number
}): HealthState {
  if (!input.lastClosedWonAt) return 'prospect'          // never licensed → 🦁
  const days = daysBetween(input.lastClosedWonAt, input.now ?? Date.now())
  let base: HealthState =
    days <= rules.good_within_days   ? 'good'    :
    days <= rules.warning_after_days ? 'warning' :
    days <= rules.at_risk_after_days ? 'at_risk' :
    days <= rules.cold_after_days    ? 'at_risk' : 'cold'
  // keeps-warm holds: never drop BELOW warning while actively worked
  const warm =
    (rules.keep_warm_open_brief && input.hasOpenBrief) ||
    (rules.keep_warm_open_deal && input.hasOpenDeal) ||
    (rules.keep_warm_recent_selects && within(input.lastSelectsSentAt, rules.recent_selects_days)) ||
    (rules.keep_warm_recent_contact && within(input.lastContactAt, rules.recent_contact_days))
  if (warm && (base === 'at_risk' || base === 'cold')) base = 'warning'
  return base
}
```

- **No storage, no scheduling.** Config save changes nothing to recompute — the next render reads the new `health_rules_config` row and recomputes. This is exactly the D-06 mockup promise ("health recomputes on next view").
- **Extend `columns.ts` `HealthValue`** from `'good'|'warning'|'at_risk'|'unknown'` to add `'cold'` and `'prospect'`, and add `HEALTH_TONE`/`HEALTH_RANK` entries (`prospect` renders the configurable image, not a color; `unknown` stays the dashed no-data slot). [VERIFIED: current `HealthValue` in columns.ts]
- **Sort:** extend `HEALTH_RANK` so `at_risk < cold < warning < prospect < unknown < good` (or per owner preference) — keep deterministic tiebreak already in `sortRows`.

## Common Pitfalls

### Pitfall 1: Passing functions across the RSC → Client boundary (ALREADY BIT THIS REPO TWICE)
**What goes wrong:** A Server Component passes a function prop (e.g. an href-builder, an `onX` callback, a formatter) to a Client Component. Production throws `Functions cannot be passed directly to Client Components because they're not serializable` — a hard 500 on a `force-dynamic` page. **Dev tolerates it; `next build` does not catch it** because the page only renders on request.
**Why it happens:** RSC serializes props; functions aren't serializable.
**Evidence:** commit `80443bb` fixed exactly this on `ClientPartnersList` (href builders → string bases; row href built client-side as `${base}/${id}`). The component's own JSDoc now documents the rule [VERIFIED].
**How to avoid:** Client Components take **data + string paths**, never functions. Build hrefs/handlers inside the client component. The assign panel, Health Rules form, and Game Plan editor must all be `'use client'` and receive plain serializable props (rows, config object, string action endpoints) — the RSC page fetches, the client component POSTs to string routes.
**Warning signs:** any arrow function in JSX props handed to a `'use client'` child from a server page.

### Pitfall 2: `buyer_orgs` is empty in prod right now
**What goes wrong:** The tower, coverage strip, By-AE grouping, and health engine all render against zero rows in production today.
**How to avoid:** Every surface needs a real empty state (the `ClientPartnersList` `EmptyState` already exists; add tower/coverage/By-AE empty states). The `closed_won_at` backfill and any seed are no-ops. Do NOT gate acceptance on "see colored rows in prod" — verify with seeded/test data and unit tests on `health.ts`. Flag to the owner that visible data depends on creating client orgs first.

### Pitfall 3: Migration numbering collision
**What goes wrong:** 113/114 already used; picking a taken number or racing another concurrent phase corrupts ordering.
**How to avoid:** Start at **128** (repo tip is 127). Confirm `ls supabase/migrations/ | tail -1` at plan time. Human-gated push only — never `supabase db push` from an agent; the owner reviews at a checkpoint. Draft + jest text-test the SQL only.

### Pitfall 4: Column privilege / RLS on new columns and tables
**What goes wrong:** Adding a column to `buyer_orgs`/`license_requests` and it silently becomes buyer-readable, or a new staff table is reachable by `authenticated`.
**How to avoid:** New columns are private by default (do NOT add to migration-080's authenticated GRANT allowlist). New tables: `ENABLE RLS` + **zero policies** + full `REVOKE` from `authenticated, anon` (migration 112 §e pattern). Reads/writes only via service-role staff routes. [VERIFIED: 112, 081]

### Pitfall 5: Health color driven by the wrong clock
**What goes wrong:** Using `updated_at` (moves on any edit) or `last_contact` (D-31.1-02 says contact does NOT set the color) to drive health, or letting a client with no `closed_won` render green.
**How to avoid:** Color = `closed_won_at` recency ONLY. No closed_won → prospect (🦁), never green/unknown-as-good. `resolveHealth` already defaults absent data to a non-green state — preserve that invariant when adding `cold`/`prospect`.

### Pitfall 6: Email must never block assignment
**What goes wrong:** Awaiting the intro email inline; a Resend failure (the known prod `RESEND_FROM_EMAIL` deliverability issue in project memory) 500s the whole handoff.
**How to avoid:** Wrap `createNotification`/email in `.catch(() => {})` after the `ae_user_id` write commits (existing route already does this for notifs — extend to the email). The assignment is the authority action; the email is best-effort.
