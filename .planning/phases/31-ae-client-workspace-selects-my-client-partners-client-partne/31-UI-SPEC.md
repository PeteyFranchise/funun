# Phase 31 — UI Design Contract: AE Client Workspace + Selects

> Visual and interaction contract for **My Client Partners**, **Client Partners** (leadership tower),
> **Crate Requests**, **The Playbook**, health/rules config, the **Selects builder**, and the
> **shareable `/selects/{token}` player**. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Non-interactive run — every field below is pre-populated from
> `31-SPEC.md` (locked requirements), `31-CONTEXT.md` (D-01…D-13 decisions), the existing
> token system, and shipped code precedent. Fields with no explicit upstream answer are marked
> **Source: default — Claude's discretion** so the owner can review before build.

**Design system is established — not proposed here.** Funūn has a mature, single-sourced
Tailwind + CSS-variable token system, 30 phases deep, zero shadcn anywhere in the codebase
(confirmed: no `components.json`, `lucide-react` not installed, every icon is hand-authored
inline SVG). This phase extends the existing `.fncon` Team Console theme and reuses the buyer
player base (`CatalogBrowserLight.tsx`) — it does not invent new tokens.

**Two surface families, one contract:**
- **A — Internal (Team Console):** My Client Partners, Client Partners tower, Crate Requests,
  health + rules config, The Playbook, Game Plan. Inherits `.fncon` dark/light + role×room
  gating (`components/admin/console-theme.ts`).
- **B — Client-facing (`/selects/[token]`):** the shareable player. This is the **one
  brand-critical, client-facing surface** in the phase and the reason `31-CONTEXT.md` D-13
  routed it through `/gsd-ui-phase` before build — it gets the most detail below.

**Visual source of truth:** the interactive mockup produced 2026-08-13
(`claude.ai/code/artifact/0ac07e60-412d-4f4c-98bc-9074c3982314`) — My Client Partners list +
workspace, Crate Requests, Selects builder, assign-to-AE, The Playbook, health-rules settings,
role toggle, light/dark, collapsible rail. **Build to match this look.** This document
translates that mockup into the project's existing token vocabulary; where the mockup and this
contract conflict on a token value, this contract (grounded in shipped code) wins — file the
discrepancy rather than inventing a third value.

## Typography

Base scale for Family A (Team Console rooms). Matches the codebase's shipped informal scale —
no new sizes introduced beyond what the client player needs (declared separately below since
it is a visually distinct, brand-critical hero surface, same pattern Phase 9 used for its
public player).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-[14px]`) | 400 (regular) | 1.5 |
| Label | 12px (`text-[12px]`) uppercase, `tracking-[.14em]` for section eyebrows / column headers; no tracking for inline labels | 600 (semibold) | 1.4 |
| Heading | 20px (`text-[20px]`) | 700 (bold) | 1.25 |
| Display (page h1) | 24px (`text-2xl`) | 700 (bold) | 1.2 |

Permitted weights across Family A: **400 (regular)** and **700 (bold)** only, matching the
existing `MyCompanies.tsx` / admin-page convention (`text-2xl font-bold` page titles,
regular-weight body). Do not introduce a 500/600 weight into Family A components other than the
12px label row noted above, which already exists in the mockup as a semibold eyebrow — treat it
as the one sanctioned exception, not a precedent to add more weights.

Numeric values (health thresholds, days-in-stage, lifetime value, listen counts, durations) use
`font-variant-numeric: tabular-nums` — existing codebase convention (Phase 9 precedent).

## Surface Spec — Family A: Internal Team Console Rooms

All Family A surfaces inherit `.fncon` (dark base, `[data-theme="light"]` override) and the
role×room gating already established for `/admin/*`. What follows specifies only the
**phase-new** interaction patterns not already covered by the base console contract.

### My Client Partners / Client Partners — list + tabs (R1, R5, R6)

- Room lands on a **pill tab switcher** (Clients / Companies) — reuse the `.tabs`/`.tab`
  rounded-pill idiom already shipped in `FNBL_CSS` (`background: var(--wash); border-radius:
  999px; padding: 5px`), re-themed onto `.fncon` tokens (`--panel-2` background, `--grad` active
  pill).
- Default sort: **Next action, overdue-first** (deterministic, per SPEC edge coverage).
- A row click drills into the person/company workspace — a full-panel navigation (not a modal),
  consistent with every other Team Console detail route.
- **Leadership's own My Client Partners** = a personal hold-queue variant of the same list
  component (unassigned + coverage), not a separate component — same table, filtered.

### Company / person workspace — the four jobs (R1)

Four-job layout: **Contacts · Activity · Curation (Selects) · Notes+status**, plus company
website for the company workspace. Render as a **secondary tab row inside the workspace header**
(not the primary Clients/Companies pill — a second-level tab, visually lighter: text tabs with
an underline indicator in `--indigo`, not a full pill). Person workspace mirrors the same four
tabs, person-scoped, plus the **Game Plan** panel (R14, person view only).

### Insight columns — show/hide, reorder, sort (R2)

- A **"Columns" control** (gear/sliders icon button, top-right of the table) opens a popover
  listing every available column with a checkbox (show/hide) and a drag handle (reorder). Use
  the same drag-handle glyph pattern as `ChecklistAdmin.tsx`'s existing grip icon — do not invent
  a new drag affordance.
- **Identity column is pinned**: no checkbox, no drag handle, always first, rendered visually
  distinct (slightly heavier weight, `--panel-2` background strip) so it reads as structurally
  different from the reorderable set.
- Column headers are click-to-sort: a subtle chevron (`▲`/`▼`, using `.icn`) appears on hover,
  solid once that column is the active sort key. Multi-column sort is out of scope — one active
  sort key at a time, per SPEC.
- Persistence: same **per-member cookie mechanism** the console theme already uses (constraint
  from `31-CONTEXT.md`) — column order/visibility/sort key stored per-AE, restores on reload.
- Companies columns (12): Company · Next action · Status · Health · Days in stage · Open briefs ·
  Active Selects · Open deal · Lifetime value · Last brief · Last touch · Contacts.
- Clients columns (10): Client · Next action · Company · Role · Status · Last touch · Last brief ·
  Briefs · Selects seen · Deals.

### Relationship health — chips + rules config (R3, R4)

- Health renders as a **small pill chip** with a leading dot (filled circle in the semantic
  color) + label text ("Good" / "Warning" / "At risk"), or the **dashed unknown chip** (see Color
  section) with a dash glyph instead of a dot.
- Clicking a health chip opens a lightweight popover: the computed "why" explanation (which
  signal(s) drove it), plus **Override** and **Snooze** actions with a visible expiry date once
  set (never a silent, undated override).
- **Health-rules config** (leadership-only surface): a form of per-signal threshold pairs
  (warning / at-risk, numeric inputs) + a combine-rule toggle ("worst signal wins" vs. "two
  warnings = at-risk," a segmented two-option control) + override-policy fields. A **live
  distribution-preview bar** — one horizontal stacked bar, 4 segments (green/amber/rose/unknown,
  in the semantic colors above), recomputes on every input change (health is computed live per
  D-06, so this preview is cheap — no debounce-and-spinner needed, update on blur/change).
- Non-overlapping band validation renders inline under the offending input pair in the
  destructive rose, not a blocking modal.

### Client Partners leadership tower — assign/route (R6, R7, R8)

- Same list/column/sort component as My Client Partners, unfiltered (leadership sees all).
- **Assign** action: from the company header (a labeled button, "Assign to AE") and from the
  list row (an inline AE-avatar picker, click to open a dropdown of AE avatars + "Move to
  unassigned"). Reassigning to the current AE is a visual no-op — the dropdown closes with no
  toast, no log-write animation, confirming SPEC's no-duplicate-email rule silently.
- Assignment triggers three things visibly: an in-app notification badge on the target AE's nav
  (existing `lib/notifications` bell pattern), a relationship-log entry (rendered inline in the
  Notes+status tab, "Assigned to {AE} by {Leader} · {timestamp}"), and (non-blocking, per SPEC)
  an email — the UI itself does not wait on email send/fail before confirming the assignment.

### Crate Requests — demand inbox (R10)

- Feed of rows, each: client name/avatar, activity type icon, intent badge, one-click action
  button. Intent badges use the health-adjacent-but-distinct visual language: **Hot** = filled
  rose-adjacent warm chip (use `--fuchsia`-tinted, NOT the health-rose, to avoid implying "at
  risk" — Source: default, Claude's discretion), **Warm** = amber chip, **New lead** = outlined
  neutral chip with a "guest" glyph (no account attached).
- One-click actions per row: **Build Selects**, **Reply**, **Follow up**, **See lead** — render
  as a single compact button matching the row's dominant action (not four buttons per row).
- Anonymous/guest signals render identically to a client row but with a muted avatar placeholder
  and the "New lead" badge — visually present, not hidden or de-emphasized.

### The Playbook — SOP editor (R9)

- Accordion list of named SOPs (Intro call, Onboarding call, Re-engage at-risk, + addable). Each
  expands to an ordered checklist of steps (drag-reorder, add/remove step, each step a plain-text
  line). A trigger selector (dropdown: which event fires this SOP — e.g. "new/unassigned
  assignment," "existing-account assignment"). Leadership/ops-only edit affordance; AE view is
  read-only (steps visible, no edit controls rendered at all — not just disabled).

### Game Plan — pre-call topic planning (R14)

- Person workspace panel: a list of 3–5 topic chips (add via a text input + "suggested topics"
  quick-add row below it — suggested chips are outlined/ghost until clicked, then become filled
  panel-2 chips in the plan). A soft cap indicator ("4 of 5") — never blocks adding a 6th, per
  SPEC's boundary edge, but visually nudges toward 5.
- On/after the call: each topic gets a checkbox (covered/not covered) + optional inline note.
  **Log conversation** is the primary CTA that closes the loop, writing "{N} of {M} covered" +
  notes to the relationship log — 0-of-N is a valid, clearly-labeled log entry, never a blank.

## Surface Spec — Family B: Client-Facing Selects Player (`/selects/[token]`)

**The one brand-critical surface in this phase.** SSR, service-role read, no login required for
a valid token. Base layout: the full-bleed immersive hero player already proven in
`~/Desktop/design_handoff_funun_app/music-player-playlists.html` (art/gradient hero → scrub →
transport → tracklist), re-skinned for a curated multi-track Selects instead of a single artist
profile, using `CatalogBrowserLight.tsx`'s existing player mechanics as the functional base
(per `crate-lead-engine-BUILD-SPEC.md` §6 reuse note).

### Layout

1. **App bar** (translucent, blurred pill buttons, `rgba(10,9,16,.5)` + `backdrop-filter:
   blur(8px)`) — back/close on the left, a "Now playing" or Selects-name label center, a
   share/overflow icon on the right.
2. **Hero** — cover art/collage (Selects tracks' artwork composited, or a branded gradient card
   if no artwork), scrim gradient to the page background at the bottom for text legibility.
3. **Meta block** (over the hero scrim, bottom-anchored): the `chip-funun`-style pill ("FUNŪN ·
   A Selects") + eyebrow ("SELECTS") + Selects title (display type) + AE byline ("Curated by
   {AE name}") + a small **Preview** badge (see below).
4. **AE cover note** — a short paragraph, `--ink-2` colored, directly under the meta block.
5. **Player** — scrub bar + transport controls, exact visual spec from the design ref (6px bar,
   15px knob, `--grad` fill, 78px circular play button with `box-shadow: 0 18px 44px -12px
   rgba(217,70,239,.65)`).
6. **Track list** — each row: artwork thumb, title, "why this fits" note (muted caption), per-
   track reaction icons (love/pass/more-like-this, icon-only, 44px touch targets), duration.
7. **Response bar** — sticky bottom action row (mirrors `.fnbl .mini` bottom-sheet pattern):
   Request changes (ghost) · Approve (solid indigo) · License (primary gradient) · Download to
   test-sync (secondary, icon+label).

### "Preview" affordance (D-01)

A small, unobtrusive but legible pill badge near the meta block (not overlaid on the play
button, not alarming) — matches the existing `chip-funun` pill treatment: `rgba(10,9,16,.55)`
translucent background, blurred, `1px solid rgba(199,203,247,.22)` border, 12–14px bold text,
reading **"Preview"** with a small waveform/headphone glyph. It signals "this is a tagged
preview stream" without reading as a warning label — the whole point (per D-01) is that a 30s+
evaluative listen still feels natural.

### Watermark character (Claude's discretion, per CONTEXT)

`31-CONTEXT.md` leaves the audible tag's exact character to "sensible planner choices," leaning
"tonal/soft over spoken to preserve evaluability." **Default: a brief, soft sub-audible tonal
pulse at fixed intervals (not a spoken voice tag), mixed low enough that a genuine 30s+
evaluative listen (R13's qualified-listen bar) remains meaningful.** This is a content-pipeline
decision, not a pixel one — flagged here only so the UI contract (the "Preview" badge above) and
the actual audio treatment stay conceptually aligned. **Source: default — Claude's discretion,
confirm with Pete before the watermarking research task locks it in.**

### Reactions

Three icon-only buttons per track row: love / pass / more-like-this. No text labels (matches the
mockup). Selected state: filled icon in `--indigo`; unselected: outlined `--ink-3`. 44×44px
touch target each, tight visual footprint (icons themselves ~20px).

### Download (R12, D-01/D-02/D-03)

- Button: **"Download to test-sync"**, secondary weight (not the primary gradient — License
  keeps that slot).
- Helper microcopy directly below: "Forensically watermarked — good for cutting into your edit,
  not for release."
- **Disabled state** (AE turned it off at send time, or length-capped): button renders greyed
  (`opacity-40`, disabled cursor) with microcopy swapped to: "Download's off for this Selects —
  stream only." Never hide the button entirely — a visibly-disabled affordance communicates the
  boundary better than an absent one.
- The file served is **never** a clean master, by design (prohibition table, R12) — this is a
  data-flow guarantee, not a UI toggle; the UI only reflects whatever the AE configured at send.

### Invalid / expired token state (R12, safe failure)

Full-bleed dark page (`--ground` #0a0a0f, no light-mode variant needed — a dead link has no
theme preference to honor), centered:
- A single muted icon (broken-link / disconnected-plug glyph, `--ink-3`, ~48px)
- Heading: **"This link isn't live."**
- Body: **"Links expire or get swapped out — ping whoever sent it and they can send you a fresh one."**
- **No** org name, client name, AE name, track titles, artwork, or any hint of what the Selects
  contained. No "back to Funūn" navigation link that could imply the visitor has app access they
  don't. This is the R12 "leaks nothing" guarantee rendered as UI — treat any data-bearing element
  on this state as a bug, not a design choice.

### OpenGraph / rich unfurl (R12)

- `og:title`: **"{Selects name} · A Selects from Funūn"**
- `og:description`: the AE cover note, truncated to ~160 chars, falling back to **"{N} tracks
  curated for {client name}."** if no cover note is set
- `og:image`: a branded card — cover-art collage over the `--grad` gradient, or the gradient
  alone with the Selects title overlaid if no artwork exists yet
- Rendered server-side (SSR page, per the BUILD-SPEC §4 route contract) so forwarding into
  Slack/iMessage/email produces a legible, on-brand unfurl — not a bare link.

### Engagement telemetry (R13) — not a visible client-side element

Per-track qualified-listen tracking (≥30s audible time, default, owner-editable) is **silent
telemetry on the client player** — no progress ring, no "you've listened X seconds" indicator
visible to the client. The only place this surfaces visually is **back in the AE's Selects
workspace view** (Family A): a small per-track readout (plays / qualified-listens / replays) as
a compact stat row under each track in the builder/detail view, plus a Selects-level summary
line at the top ("{N} of {M} tracks qualified-listened"). Use tabular-nums, `--ink-3` label +
`--ink` value, consistent with the console's numeric-stat convention.
