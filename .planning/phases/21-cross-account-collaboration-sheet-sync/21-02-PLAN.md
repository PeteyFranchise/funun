<objective>
Auto-grant a `viewer` project membership to a split-sheet writer the moment they are (a) a claimed
Funūn account holder and (b) named on a project-linked sheet that has been shared (left draft). This
is the "no re-entry" payoff of ②: being a writer on a linked sheet puts the shared project in your
own account automatically.

Purpose: Wire auto-membership to the ONLY live verified-identity signal in this codebase —
`collaborators.claimed_by` — not the dead `split_sheet_parties.user_id` column (RESEARCH Pitfall 2),
satisfying the CONTEXT identity rule "cross-account membership grant keys off VERIFIED identity only,
never a typed email." Implements ② auto-membership and the `identity-dedupe-claim` decision (claim =
verified/cross-owner, kept distinct from roster dedupe = typed/per-owner).

Output: migration 079 (authored, string-assertion-tested, human-gated push) — a SECURITY DEFINER
trigger mirroring migration 066/072's plpgsql precedent, plus its smoke test.
</objective>

| trigger (SECURITY DEFINER) → project_members / collaborators | Runs with RLS bypassed; search_path and the identity signal it trusts are the attack surface |

| T-21-09 | Information Disclosure | draft sheet visibility leak | high | mitigate | Grant gated on sheet.status != 'draft' AND vault_project_id IS NOT NULL (RESEARCH A1 / P18-11) — a private unsent draft grants nothing |

<planner_decisions>
## Planner decisions

- **Trigger, not app-layer (RESEARCH primary recommendation):** a single SECURITY DEFINER trigger
  handles all three event orderings in one place (mirrors migration 066), avoiding fragile app-layer
  coordination across claim_collaborators(), the PATCH route, and the send-for-approval route.
- **Grant boundary = "sheet has left draft" (RESEARCH Assumption A1, adopted explicitly):** a writer
  gains project visibility only once the initiator has actually shared the sheet (status != 'draft'),
  never while it is a private draft — matching the existing P18-11 drafts-invisible-to-non-initiators
  rule.
- **`identity-dedupe-claim` coverage:** this plan is where the distinction is enforced concretely —
  membership (cross-account access) keys off the CLAIM signal (verified claimed_by), while roster
  dedupe (per-owner, typed email; already shipped Phase 18/19) is untouched and never a membership
  input.
</planner_decisions>
