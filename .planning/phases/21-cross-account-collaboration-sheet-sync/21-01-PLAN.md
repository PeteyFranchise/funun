<objective>
Ship the load-bearing foundation of the post-beta access model: a `project_members` guest-list
table and an RLS rewrite that changes vault access from "you own it" to "you own it OR you're on
its guest list" — for `vault_projects` AND its four child tables (`tracks`, `vault_assets`,
`vault_documents`, `tool_outputs`). This wave SOAKS FIRST, alone; nothing else in Phase 21 is safe
until it is proven live.

Purpose: Correctly widen an already-recursion-scarred RLS surface without reintroducing the exact
`42P17` bug migration 064 already paid for, and without leaving the child-table sharing hole that
keys access on the row's own `user_id` instead of the project's owner (RESEARCH Pitfall 1 — the
single most important correction). Implements ① (shared visibility, owner-controlled editing) and
② (membership foundation, four roles day one).

Output: migration 078 (authored, string-assertion-tested, NOT pushed by an executor), the pure
role-helper module `lib/vault/membership.ts`, and a documented manual RLS access-matrix smoke
checklist for the human-gated push.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → PostgREST → Postgres RLS | Every read/write of a project or its child rows crosses here; RLS is the sole multi-tenancy enforcement layer |
| RLS policy body → SECURITY DEFINER helper | Helpers read the "other" table with RLS bypassed — a privileged surface that must not become an oracle or a recursion trap |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-01 | Information Disclosure | vault_projects + 4 child tables SELECT | critical | mitigate | SELECT policies scoped to owner OR project_member_role IS NOT NULL, resolved via DEFINER helpers; non-member matches no permissive policy → [] |
| T-21-02 | Elevation of Privilege / Tampering | vault_projects + child UPDATE/DELETE | critical | mitigate | UPDATE policy = owner OR role IN (co-owner, editor); DELETE = owner only; viewer is SELECT-only by construction |
| T-21-03 | Denial of Service | project_members ↔ vault_projects RLS cycle | high | mitigate | SECURITY DEFINER helper pair (mirror migration 064) so the rewriter never re-enters a relation on its expansion stack — no 42P17 |
| T-21-04 | Elevation of Privilege | is_project_owner / project_member_role helpers | high | mitigate | SET search_path = '' + fully-qualified public. refs (search-path hijack, T-08-04); REVOKE EXECUTE FROM PUBLIC, anon, authenticated then GRANT TO authenticated only |

<planner_decisions>
## Planner decisions (explicit — not silent gaps)

1. **Editor/co-owner write scope (RESEARCH Pitfall 4 / Open Q1, Assumption A2 adopted):** migration
   078 RLS *permits* co-owner/editor row-level writes on all five tables (data model correct and
   forward-compatible). The API-route audit — rewriting every `app/api/vault/**` `.eq('user_id',
   user.id)` ownership check to project-membership — is DEFERRED, NOT in this phase. In v1, functional
   project-edit affordances ship only for the owner path (① 's "owner or co-owner mutates" is the safe
   functional default); editor write stays RLS-permitted-but-route-unexercised until a later phase
   builds the editor edit surface. This keeps Wave 1/2 from roughly doubling.

2. **Guest-list management API DEFERRED (consistent with CONTEXT "rich co-owner/editor promotion UX
   deferred"):** no `app/api/vault/[projectId]/members/route.ts` in this phase. The only membership
   write path in v1 is the SECURITY DEFINER auto-membership trigger (Plan 21-02) plus this migration's
   owner backfill; all authenticated/anon writes on project_members are REVOKEd. This mitigates the
   guest-list EoP threat (T-21-06) by absence of a client write path.
</planner_decisions>
