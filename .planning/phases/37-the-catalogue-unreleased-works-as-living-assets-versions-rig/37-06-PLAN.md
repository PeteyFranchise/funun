<objective>
Build the capture API: audio in, AI entries filed, notes annotated.

POST versions takes a multipart body from either capture path — a MediaRecorder blob or a picked
file — validates it, writes it to the existing `track-audio` bucket under a work-scoped path, and
inserts the row whose trigger writes the diary entry. POST ai-entries files a structured,
zero-split DDEX-component entry whose citation is composed server-side. POST notes writes the one
diary kind that has no trigger behind it. `lib/catalogue/audio.ts` holds the MIME allow-list, the
size ceiling, the path builder and the batch signed-URL reader.

Purpose: S-01 is the whole reason this phase ships first. A hum captured in the app is
platform-timestamped at the moment of creation — the strongest form the authorship trail takes,
and the thing an uploaded file can only claim. That value is entirely destroyed by a route that
accepts anything, stores it under a path a collaborator cannot use, or lets an artist type their
own citation.

Output: three route files plus one audio helper module with a suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser multipart body → Supabase Storage | Arbitrary bytes with an attacker-controllable MIME and filename |
| artist's flow answers → a durable citation | What is asserted becomes a record a buyer or registrar may rely on |
| collaborator session → another artist's work | A contribute-tier member writing audio and entries into someone else's song |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-34 | Elevation of Privilege | Uploading into a work by guessing its id | high | mitigate | `resolveWorkAccess()` runs before any storage write or insert. UUIDs are not guessable, but the check defends against a leaked or logged id rather than brute force, so it exists regardless. |
| T-37-35 | Tampering | A mislabelled or executable file uploaded with an audio MIME | medium | accept | The `EXT_BY_MIME` allow-list trusts the browser-reported type only for extension mapping, never for content validation — the same residual risk the existing track-audio route already accepts, since no server-side audio sniffing exists anywhere in this codebase. Inherited, not introduced; flagged for a future content-check pass. |
| T-37-36 | Denial of Service | Oversized uploads exhausting storage | medium | mitigate | `MAX_BYTES` is checked before any byte is written and matches the bucket's own 50MB limit, so the ceiling is enforced twice and the rejection is cheap. |
| T-37-37 | Tampering | Path traversal or overwrite via a crafted filename | high | mitigate | The path is built entirely server-side from the work id, a server-generated version id and a mapped extension. The uploaded filename is never used for anything. |
| T-37-38 | Repudiation | A false AI citation typed by the artist | high | mitigate | The route rejects any citation string in the body and composes it from the verified answers. The maximal-ownership citation additionally requires a human-source version that provably belongs to this work. |
| T-37-39 | Information Disclosure | Cross-work reference in an AI entry (pointing at another song's take) | medium | mitigate | Every supplied version id and block id is verified to belong to THIS work before use, so an entry cannot borrow another song's evidence. |
| T-37-40 | Repudiation | Storage orphans obscuring what was actually captured | low | mitigate | A failed insert removes the uploaded object, matching the existing track-audio route's rollback, so storage contents and diary contents stay consistent. |
| T-37-41 | Information Disclosure | Diary content leaking into the public wall feed | high | mitigate | No route in this plan imports the activity emitter or references the public feed table, and the notes route's header records why. |
| T-37-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task exists in this plan — zero new packages in Phase 37.1. |
</threat_model>
