<objective>
Build the lyrics pad's API: create sections anywhere, edit them, tag who sings them, repeat and
detach them, and reorder them atomically.

POST blocks handles three creation shapes — one empty section, a repeat linked to an existing
section, and a bulk create from a pasted lyric. PATCH and DELETE on a single block serve the pad's
debounced autosave, its type changes, its performer tags and its detach action. POST reorder hands
the whole new order to migration 138's RPC in one transaction.

Purpose: the lyrics pad is half of what an artist actually owns — the hum evidences the melody, the
pad evidences the words, and together they cover the whole copyrightable song. Every rule in this
route file exists so that evidence survives editing: the writer badge comes from the session
because it moves splits, repeats stay links because a duplicate would split one writer's claim in
two, and reorders go through the RPC because a partial reshuffle would leave the song in an order
nobody chose.

Output: three route files.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → block writes | A collaborator edits the words in someone else's song |
| request body → authorship attribution | The one field on this table with money attached |
| client-supplied order → bulk position update | A multi-row write driven entirely by client input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-42 | Spoofing | Attributing a block to someone else | high | mitigate | `author_user_id` is set from the authenticated session and the schemas carry no author field. The writer badge moves splits, so accepting it from a body would be a direct path to a fabricated publishing claim. |
| T-37-43 | Elevation of Privilege | Editing blocks in a work the caller is not on | high | mitigate | `resolveWorkAccess()` runs first on all three routes, and every block id is additionally verified to belong to the work in the path. |
| T-37-44 | Information Disclosure | Block-id enumeration across works | medium | mitigate | A block belonging to another work returns the same 404 as a nonexistent one, so the response is not an existence oracle. |
| T-37-45 | Tampering | A partial reorder leaving the song in an unchosen order | high | mitigate | The atomic RPC with its table lock, contiguity validation and row-count check is the only bulk position writer; the route maps its serialization failure to a 409 rather than retrying blindly. |
| T-37-46 | Tampering | Displayed lyrics disagreeing with stored lyrics on a repeat | medium | mitigate | A text edit on a linked repeat is refused with guidance to detach first, and a repeat is never created by copying text. |
| T-37-47 | Denial of Service | An unbounded paste or reorder payload | medium | mitigate | The paste and the reorder schemas are both bounded, and the RPC independently caps the order length — the limit is enforced on both sides. |
| T-37-48 | Repudiation | A block edit that never reaches the diary | medium | mitigate | Capture is a database trigger on `lyric_blocks`, so a route that forgets — including a route written later — still produces the entry. No route in this plan writes a diary row. |
| T-37-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task exists in this plan — zero new packages in Phase 37.1. |
</threat_model>
