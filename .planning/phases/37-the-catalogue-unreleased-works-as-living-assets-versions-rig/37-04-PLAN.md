<objective>
Build the phase's shared vocabulary and its authorization primitive.

`types/catalogue.ts` declares the row types for the six tables migration 135–138 creates, so
every route and component in waves 2 through 5 speaks one language. `lib/catalogue/membership.ts`
declares the two-tier capability matrix, mirroring `lib/vault/membership.ts`'s established shape.
`lib/catalogue/access.ts` is the single decision function every work API route calls first, plus
the thin wrapper that fetches the two facts it needs. `lib/catalogue/diary.ts` types each diary
kind's payload and turns a row into the three-part entry sketch 001 specifies.

Purpose: this plan exists so that the answer to "may this person write into this song?" is
computed in exactly one place. S-02 puts other people's hands inside an artist's work for the
first time in this codebase, and the failure mode is not a dramatic one — it is a route that
checks ownership instead of membership, or membership instead of tier, and nobody notices until
a contributor cannot upload or an outsider can. Making the rule a single tested function is what
prevents that.

Output: one types module and three pure-logic modules with their suites, green with no DB.
</objective>

  <name>Task 2: lib/catalogue/access.ts — one decision function for every work route</name>
  <files>lib/catalogue/access.ts, lib/catalogue/access.test.ts</files>
  <behavior>
    - With no signed-in user, the decision is a refusal carrying 401.
    - With a signed-in user who owns the work, the decision is a grant with the administer tier and the owner flag set — an owner never needs a membership row to act on their own song.
    - With a signed-in user holding the contribute tier, the decision is a grant with that tier and the owner flag clear.
    - With a signed-in user holding no tier and no ownership, the decision is a refusal carrying 404 — not 403 — so a probe cannot distinguish "exists but not yours" from "does not exist".
    - Requiring the administer tier refuses a contribute-tier member with 403, because at that point the caller has already proved they may see the work.
    - Requiring the administer tier grants the owner.
    - The wrapper calls both database facts and passes them to the pure decision, and performs no authorization reasoning of its own.
    - Injecting fake fact-getters exercises every branch with no Supabase client present.
  </behavior>
  <action>
    Create `lib/catalogue/access.ts` with two exports and a hard line between them.

    `decideWorkAccess(input)` is PURE. It takes the caller's user id (or null), whether they own
    the work, the tier the database returned (or null), and the tier the route requires. It returns
    a discriminated result: either a grant carrying the effective tier and an owner flag, or a
    refusal carrying an HTTP status. Implement the four statuses exactly as the behaviour list
    specifies, and comment the 404-not-403 choice: a work id is a UUID and is not guessable, but a
    leaked or logged id must not become an existence oracle. Note that the same reasoning does NOT
    apply once membership is proven — a contribute-tier member asking for an administer action gets
    403, because hiding the work from them at that point would be confusing rather than protective.

    Comment why an owner is granted the administer tier without a membership row: plan 05 creates
    the owner's row at work creation, but the ownership column on `works` is the authority, and a
    route must keep working if a membership row is ever missing.

    `resolveWorkAccess(deps, workId, userId, requiredTier)` is the thin I/O wrapper. Its `deps`
    argument carries two async fact-getters — one answering ownership, one answering tier. It calls
    both, hands the results to `decideWorkAccess`, and returns its result unchanged. It contains no
    branching beyond awaiting. Export a small factory that builds the real `deps` from a Supabase
    client by calling migration 136's `is_work_owner` and `work_member_tier` RPCs.

    Comment the split's purpose: the decision is the thing worth testing and it is testable without
    a database; the wrapper is the thing that cannot be tested without one and therefore contains
    nothing worth testing. Note that the RPCs are granted to `authenticated` (migration 136), so the
    caller's own session client is sufficient — the wrapper does not need and must not use the
    service role.

    Comment the standing rule for every consumer: no route may read a tier from a request body, a
    query parameter or a header. The tier is a database fact, fetched here, every time.

    Write the suite covering every behaviour above using injected fake fact-getters. No Supabase
    import appears in the test file.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| request → work API route | Every write into someone else's song passes through one decision function |
| database tier fact → route behaviour | The tier must come from the database, never from the request |
| stored diary payload → rendered text | What the feed says is what the record holds |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-20 | Elevation of Privilege | A route inventing its own access check | high | mitigate | `decideWorkAccess` is the only implementation of the rule and every wave-2 route calls `resolveWorkAccess` as its first statement. The plan-level prohibition plus the wave-2 plans' own verify gates make a hand-rolled check visible in review. |
| T-37-21 | Spoofing | A client-supplied tier value | high | mitigate | The tier is fetched via migration 136's `work_member_tier` RPC inside the wrapper. The module documents that no route may read a tier from a body, query or header, and `decideWorkAccess`'s signature has no slot for a client-asserted tier. |
| T-37-22 | Information Disclosure | Work-id enumeration through status codes | medium | mitigate | A non-member gets 404 rather than 403, so the response cannot distinguish an existing work from a missing one. 403 is used only after membership is already proven. |
| T-37-23 | Elevation of Privilege | Contribute tier reaching a money or release door | high | mitigate | `canOpenMoneyOrReleaseDoors` is typed and tested now, before the 37.2 doors exist, so the door plans inherit a correct predicate instead of writing one under deadline. |
| T-37-24 | Repudiation | Diary text drifting away from the stored record | medium | mitigate | `describeDiaryEvent` renders the stored citation verbatim for AI entries and derives everything else from the row's own payload; it fetches nothing and recomposes nothing. |
| T-37-25 | Information Disclosure | Diary events leaking into the public wall feed | high | mitigate | The module never imports the activity emitter and never references the public feed table, and the header records why. `work_diary_events` has its own member-scoped SELECT policy (37-01). |
| T-37-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task exists in this plan — zero new packages in Phase 37.1. |
