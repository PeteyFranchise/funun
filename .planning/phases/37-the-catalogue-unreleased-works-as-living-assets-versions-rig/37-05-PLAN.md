<objective>
Build the work's own API: create, read, rename, set the vocal state, and manage who is on the
song.

POST /api/works is the 🎵 door — it creates the composition, the owner's membership row and the
living-draft split sheet in one call. GET and PATCH on a single work serve the header's live
title input and its three-state vocal control. POST members adds a collaborator through the
invite machinery that already exists, and — separately and only on request — promotes someone to
writer, which redrafts the living sheet to equal shares.

Purpose: this is where S-02 becomes real, and it is the first time in this codebase that one
artist's session writes into another artist's song. Two things have to hold. Access is decided in
exactly one place (plan 04's `resolveWorkAccess`), and membership is kept strictly separate from
ownership — the doctrine's own line is that being on the work and being on the splits are
different facts, and the simplest possible implementation is the one that breaks it.

Output: three route files plus one service-role split-sheet reader with a suite.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → POST /api/works/[workId]/members | The request that decides who may write into someone else's song |
| request body → collaborator row and invite email | User-entered names and addresses reach a roster row and an outbound email |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
