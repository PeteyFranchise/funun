BEFORE the AI sings, not after.

    - `pickSupportedMimeType()` returns the FIRST candidate the injected support predicate accepts.
    - With a predicate that accepts only the MP4 family, it returns an MP4-family type rather than the WebM one.
    - With a predicate that accepts nothing, it returns null.
    - Every candidate it can return maps to a known extension in plan 06's upload allow-list — asserted by importing that map rather than by restating it.
    - The support predicate is injectable, so the suite runs with no browser API present.
  </behavior>
  <action>
    Create `lib/catalogue/hum-capture.ts` as a pure module. Export an ordered candidate list and
    `pickSupportedMimeType(isTypeSupported)` taking the support predicate as an injectable parameter
    that defaults to the browser's own, returning the first accepted candidate or null.

    Order the candidates per the RESEARCH's findings: the Opus-in-WebM type first (the default on
    Chrome, Edge and Firefox, and recordable on recent Safari when explicitly requested), then the
    MP4/AAC family (Safari's own default across all versions), then bare AAC. Comment the reasoning
    and its uncertainty honestly, because the RESEARCH flagged it: the browser-support claims here
    are from secondary sources and were not verified against a live device in that session. That is
    exactly why the choice is made by ASKING the browser at runtime instead of by branching on a user
    agent — the worst case of a wrong assumption becomes a suboptimal codec rather than a broken
    recorder. Record that the owner device test (plan 13) is the verification step for playback
    across Chrome desktop and iPhone Safari, and that it is a UAT gate rather than a blocker on this
    module.

    Export the extension helper that maps a recorder's actual `mimeType` (which may carry codec
    parameters) to a bare type plan 06's allow-list accepts.

    Write the suite covering every behaviour above with injected predicates. Import plan 06's
    `EXT_BY_MIME` in the test to assert the candidate list and the upload allow-list agree — a drift
    between them would produce a recording the server rejects, and the test is what stops that
    silently.

    Then build `HumCaptureButton.tsx` as a client component. Request the microphone through
    `getUserMedia`, construct a `MediaRecorder` with the picked type (or let the browser choose when
    the pick is null), collect chunks, and on stop assemble a blob, post it as multipart to plan 06's
    versions route with source hum and the measured duration, then hand the created version back
    through a callback.

    Three behaviours are not optional and each needs a comment. First, the microphone track is
    stopped in every exit path — success, cancel, error and unmount — because a live mic indicator
    left on after a take is both a privacy failure and the kind of thing that ends trust in a
    recording feature. Second, when no candidate is supported at all, render nothing and tell the
    parent so the upload path is offered instead: capture degrades to the plain file input, which has
    no browser-API dependency. Third, a denied microphone permission renders an inline error with a
    way forward rather than a dead end, matching the honest-skip posture of sketch 003.

    Show elapsed time while recording, as the sketch does. Keep the component presentational beyond
    the recorder itself — the parent decides what happens with the created version.

    Write a `renderToStaticMarkup` smoke suite: the idle state renders the record affordance; the
    unsupported state renders nothing; the denied state renders the inline error. Structural
    assertions only — there is no jsdom to drive a real recording.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser microphone → a stored, timestamped take | The strongest authorship evidence this product produces |
| artist's flow answers → a stored citation | An assertion that becomes a durable record |
| server-composed receipt → what the artist reads | The text they are attesting to |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-54 | Information Disclosure | Microphone left open after a take | high | mitigate | Every media track is stopped on success, cancel, error and unmount, and the plan states it as a prohibition so a later refactor cannot quietly drop the cleanup. |
| T-37-55 | Denial of Service | An unsupported codec silently producing an unplayable or rejected take | medium | mitigate | The type is chosen by asking the browser at runtime, the candidate list is asserted against the server's upload allow-list in a test, and the no-candidate case hides the button in favour of upload. The residual playback question is the owner device test in plan 13. |
| T-37-56 | Repudiation | A citation the artist did not actually attest to | high | mitigate | The receipt rendered is the one the server returned and stored; the component composes no citation and posts only answers. |
| T-37-57 | Repudiation | Uncertainty resolved by choosing a softer label | high | mitigate | "Not sure" routes to the hum-evidence check rather than to a default citation, and a server refusal renders the re-author guidance instead of a substitute label. |
| T-37-58 | Tampering | A hygiene wall pushing artists to lie to get past it | medium | mitigate | Every moment has an honest exit — the skip names its cost, keep-as-is is a legitimate choice, and nothing blocks the artist. Guidance that cannot be escaped gets escaped dishonestly. |
| T-37-59 | Information Disclosure | Vendor names leaking into artist-facing copy | low | mitigate | Prohibited at plan level and asserted in both component suites; DDEX vocabulary is confined to the receipt. |
| T-37-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task exists in this plan — MediaRecorder is a native browser API and needs no package. |
</threat_model>
