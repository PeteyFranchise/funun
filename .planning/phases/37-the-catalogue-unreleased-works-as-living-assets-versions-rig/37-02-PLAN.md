<objective>
Build the pad's pure logic: the two modules that turn stored rows into what an artist sees,
without touching a database.

`lib/catalogue/blocks.ts` owns section-numeral derivation, linked-repeat resolution,
copy-on-write detach, paste auto-splitting, and the two "Copy full lyric" serializers.
`lib/catalogue/versions.ts` owns vN derivation and version presentation.

Purpose: these are the rules that make evidence hold. The RENUMBERING RULE exists because
authorship binds to a block's identity and never to its numeral — a stored numeral would
create a renumbering write cascade on every drag AND would let a reshuffle smudge who wrote
what. The REPEAT RULE exists because a duplicated chorus splits its own authorship in two.
Both are testable without a browser or a database, so they get dedicated suites here in wave
1 rather than being discovered inside a React component in wave 3.

Output: two pure modules and two Jest suites, green with no DB connection.
</objective>

  <name>Task 1: lib/catalogue/blocks.ts — numeral derivation and the repeat/detach semantics</name>
  <files>lib/catalogue/blocks.ts, lib/catalogue/blocks.test.ts</files>
  <behavior>
    - Three verses at positions 0, 2, 5 derive labels Verse 1, Verse 2, Verse 3 regardless of what sits between them.
    - Swapping the positions of the first and second verse swaps their labels and changes nothing else about either row.
    - A single chorus derives the label Chorus with no numeral; a second chorus turns both into Chorus 1 and Chorus 2.
    - Two custom blocks both labelled "Drop" both render as Drop — custom sections never take a numeral.
    - Deleting the middle verse renumbers the last one from Verse 3 to Verse 2, and the surviving rows keep their ids.
    - A block linked to a chorus resolves to the chorus's text and the chorus's author, and reports itself as a repeat.
    - Editing the source chorus's text changes what every linked repeat resolves to, with no write to the repeat rows.
    - `planDetach()` on a linked repeat returns the source's current text as the new row's own text, clears the link, and assigns the detaching user as the author; the source row is returned unchanged.
    - A link that points at a missing or deleted source resolves to empty text rather than throwing.
    - A chain (a repeat pointing at a repeat) resolves through to the original source and cannot loop forever.
  </behavior>
  <action>
    Create the module in the pure style of `lib/split-sheets/approval.ts`: named exports, types
    first, no I/O, no framework imports, section-header comments in this repo's dashed style.

    Declare and export the structural input type the module works over — a block-shaped record
    carrying id, block_type, custom_label, position, text, author_kind, author_user_id and
    repeat_of_block_id. Declare it locally rather than importing a shared types module, so this
    plan has no wave-1 sibling dependency; plan 04's `types/catalogue.ts` will be the row type
    for database reads and will be structurally compatible with this one.

    Export a `BLOCK_TYPE_LABELS` record and a `BLOCK_TYPE_VALUES` array following this repo's
    `_LABELS` / `_VALUES` naming convention (see `lib/metadata/schema.ts`). The seven fixed
    types plus custom, with the display labels sketch 006-A uses: Verse, Pre-Chorus, Chorus,
    Bridge, Intro, Outro, Hook.

    Export `deriveBlockNumerals(blocks)` returning, for each block in position order, the block
    plus a resolved display label. The numeral is the block's ordinal among same-type siblings
    ordered by position. Two rules make it correct: a type with exactly one instance gets no
    numeral at all (a lone chorus is "Chorus", not "Chorus 1"), and custom blocks are excluded
    from numbering entirely and display their `custom_label` (falling back to a neutral label
    when it is blank). Comment the invariant loudly: nothing in this function reads a stored
    ordinal, because authorship binds to block identity and a stored numeral would let a
    reshuffle rewrite history.

    Export `resolveRepeat(block, byId)` returning the effective text, the effective author and
    a flag for whether this block is a linked repeat. Follow the link, guarding against a
    missing target (return empty text, not a throw) and against a cycle (walk with a visited
    set and a hard depth cap, returning the last resolvable node). Comment why attribution
    follows the link: a repeat is the same words by the same writer, so it must never create a
    second authorship claim.

    Export `planDetach(block, byId, detachingUserId)` returning the field patch the detach
    should write — the resolved source text as this row's own text, a cleared link, and the
    detaching user as author with author kind human — plus the source block untouched. Comment
    that this is copy-on-write for the final-chorus lift, that the detach is itself a diary
    event (plan 01's trigger fires on the link being cleared), and that the new block takes its
    own authorship from that moment.

    Write the test file alongside, as a dedicated suite per rule: one describe block for
    numeral derivation (the RENUMBERING RULE), one for linked repeats and detach (the REPEAT
    RULE). Cover every behaviour listed above by constructing plain object fixtures — no
    database, no mocks beyond plain data.
  </action>
