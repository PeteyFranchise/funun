# Plan 43.1-01: Disclosure request lifecycle

## Objective

Create a payer-to-contributor request with exact purpose/scope and route the contributor's decision into
Phase 42 Requests without exposing financial data.

## Work

1. Preflight migration numbering exactly as 43-02 requires; do not use 228 and do not apply SQL.
2. Model request, requested categories, payer legal entity, named recipient, contributor, workspace/work/
   deal/invoice context, rail/currency, purpose, deadline, expiry, status, and metadata audit. Store no
   bank/tax value on the request.
3. Define who may request on behalf of a workspace; authorization to request never implies authority to
   view or approve. The target Member alone decides.
4. Add create/cancel/list/detail routes with explicit projections and rate limits. Bind target identity
   server-side; do not accept arbitrary ownership claims from the client.
5. Add the request kind to `/requests`, Dashboard, and summary notification flows. Approval UI enumerates
   the exact categories/recipient/purpose/expiry and warns about irreversible downloads.
6. Test duplicate/concurrent/stale/cancelled/expired requests and cross-account access.

## Human gate

Owner applies the reviewed migration under the production checklist. Runtime remains feature-disabled
until actual remote grants/RLS and two-account behavior are verified.

## Acceptance

- Workspace owners cannot approve for contributors.
- Tax documents require an explicit requested category and separate choice.
- Notifications and request summaries contain no raw values or storage paths.
- Decline/cancel/expiry are first-class states and cannot be bypassed by a stale approve call.
