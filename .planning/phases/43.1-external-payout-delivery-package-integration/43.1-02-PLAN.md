# Plan 43.1-02: Immutable consent snapshot and access grant

## Objective

Turn an approved request into a cryptographically bound, versioned snapshot and a recipient-specific
access grant whose scope cannot drift.

## Work

1. On approve, inside one transaction, lock/revalidate the request, contributor, profile version,
   recipient, categories, expiry, block/relationship rules, and recently-changed risk state.
2. Create an immutable encrypted disclosure snapshot containing only approved categories. Bind payer,
   recipient, request, contributor, purpose, expiry, and schema/key versions as authenticated context.
3. Create a grant with random high-entropy token material stored only as a hash, bounded attempts,
   expiry, consumption state, and revocation state. Never place a token in audit or notification data.
4. Require recent auth for contributor approval; require explicit acknowledgement for tax documents and
   for any downloadable format.
5. Define replacement/change behavior: pending request shows a changed warning; approved snapshot never
   silently updates; finance must request a fresh disclosure when policy requires.
6. Test transaction races, token hashing, replay, wrong recipient/context, expiry, revocation, and bank
   change between render and approval.

## Acceptance

- No generic workspace permission can mint or consume a grant.
- Snapshot content is minimal and immutable.
- Revocation prevents future access, while history accurately records prior consumption.
- Every failure is fail-closed and emits only summary-safe operational data.
