# Plan 43-02: Human-gated schema and encryption boundary

## Objective

Author—not apply—the minimum schema/RLS and server-only crypto boundary approved in 43-01.

## Before authoring SQL

Inspect `supabase/migrations/`, untracked files, `.planning/quick/**`, and the authoritative roadmap
ledger. Confirm migration 228 remains reserved and select the next actually available number. Record the
preflight. Never run `supabase db push` in this plan.

## Work

1. Model Member-owned profile metadata, versioned encrypted payloads, separate tax-document metadata,
   verification/change state, retention state, and metadata-only audit events. Keep ciphertext/key refs
   inaccessible to browser roles.
2. Enforce ownership, immutable versions, allowed state transitions, deletion semantics, and direct
   privilege revokes in SQL. Use service-only functions only where the approved design requires them.
3. Build a narrow server crypto module: encrypt on write, authenticated decrypt only for future approved
   disclosure, key/version binding through associated data, safe failures, and zero secret logging.
4. Add migration text-lock/structure tests, RLS two-account tests, crypto round-trip/tamper/wrong-context
   tests, and serialization tests proving APIs cannot return secret fields.

## Human gates

- Security reviews SQL, grants, RLS, crypto boundary, and key IAM before merge.
- Owner alone applies the migration later under the normal production checklist. Until then all artifacts
  say **NOT APPLIED** and dependent runtime remains disabled.

## Acceptance

- `anon` and `authenticated` cannot directly select ciphertext, key references, or tax objects.
- No generic workspace permission participates in authorization.
- Raw values do not appear in audits, fixtures committed to the public repo, snapshots, logs, or errors.
- Rollback/recovery and key-rotation procedures are documented and tested without production secrets.
