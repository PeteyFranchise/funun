# Plan 43-01: Threat model and architecture gate

## Objective

Resolve the decisions that cannot safely be invented during implementation. No real bank or tax value
may be persisted in this plan.

## Work

1. Inventory current Stripe payout routes/UI, authentication and reauthentication primitives, audit
   service, storage/document controls, notification/logging/telemetry, backup, and deletion behavior.
2. Write a data-flow/threat model covering browser, Next.js route, database, object storage, key service,
   backups, support access, logs, exports, recipient delivery, and deletion. Include insider, compromised
   workspace, link theft/replay, BEC/payment-change fraud, and cross-tenant threats.
3. Compare viable managed KMS/envelope-encryption and tax-document storage designs. Specify key hierarchy,
   associated data, rotation, versioning, recovery, regional availability, and failure behavior.
4. Define MVP countries, payment rails, currencies, exact fields, validation versus ownership claims,
   retention/deletion, support access, step-up auth, change holds, and legal/privacy notices.
5. Produce an architecture decision record and abuse-case test matrix.

## Human gate

Owner/security/legal must approve the processor/KMS, data scope, retention, recipient model, step-up
mechanism, and tax-document inclusion. If any is unresolved, mark the phase blocked; do not begin schema.

## Acceptance

- Every raw-value transit/store is named and protected or removed.
- The design does not rely on Stripe Connect tokens as exportable bank instructions.
- The design preserves `lib/workspaces/permissions.ts:159-181` unchanged.
- Incident response, key loss/rotation, backup deletion, and support access are addressed.
