# Phase 38.1-02 Summary — Roster and Activity Workspace Views

## Delivered

- Added one server-side workspace room read model over the authenticated
  `workspace_roster_page` and `workspace_audit_page` RPCs.
- Preserved the database's blocked-to-refused privacy collapse and repeated that collapse in the
  TypeScript normalization boundary as defense in depth.
- Replaced the roster API's per-row authority-evidence lookup with one bounded bulk query.
- Enriched only already-authorized user identifiers with display-safe names and handles.
- Added read-only Roster and Activity workspace pages, empty/error states, responsive cards and a
  redaction-aware activity timeline that never renders the audit `changes` object.
- Added persistent Roster/Activity workspace navigation and capability-aware workspace-root landing:
  roster-enabled workspaces land on Roster; all others land on Activity.
- Kept personal catalogues and every existing workspace mutation path unchanged.

## Security and performance controls

- Both pages re-resolve the URL-carried workspace context and live membership server-side.
- Both RPCs receive the authenticated user ID on the session client and retain their PostgreSQL
  `auth.uid()` binding, cohort gate, kill switch and 200-row ceiling.
- Service-role enrichment occurs only after an authorized RPC has returned the relevant IDs.
- Profile reads are one bounded bulk query; agreement evidence is one bounded bulk query for all
  accepted relationships on the page.
- Unknown states, malformed identifiers, mismatched workspace rows and malformed activity records
  fail closed.
- Raw audit `changes`, emails, and provider data are not part of the UI read model.
