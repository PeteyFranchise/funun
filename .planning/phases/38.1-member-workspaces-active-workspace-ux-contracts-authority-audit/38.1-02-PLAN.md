# Plan 38.1-02 — Roster and Activity Workspace Views

## Objective

Turn the protected workspace shell into a useful operating room. Management, Label, and roster-enabled
Artist Team workspaces land on a roster view, with Activity as a sibling view backed by the same
server-side, workspace-scoped read model.

## Scope

1. Add a shared server read model for the existing `workspace_roster_page` and
   `workspace_audit_page` RPCs.
2. Enrich visible user IDs with display-safe profile labels only after workspace access succeeds.
3. Compute authority tiers from current evidence in one bounded query rather than one query per row.
4. Add read-only Roster and Activity pages with clear empty, redacted, and error states.
5. Add persistent Roster/Activity links to workspace navigation; the workspace root redirects to
   its capability-appropriate landing view.
6. Make roster-enabled workspaces land on Roster and non-roster workspaces land on Activity.
7. Keep existing mutation APIs and personal catalogue routes unchanged.

## Validation

- Focused tests for bounded pagination, display fallbacks, block-state collapse, authority-tier mapping,
  audit labels, redaction, and malformed rows.
- Existing workspace roster route, access, cohort, audit, and structural-exclusion tests.
- TypeScript typecheck and focused lint.
- Static checks proving both read RPCs use the session client with the authenticated user ID and that
  no raw `workspace_audit_log` read or raw workspace roster read is introduced.
- Human visual and live-data testing remains a recorded later TODO.

## Risks and controls

- **Blocked-state disclosure:** roster normalization collapses `blocked` to `refused` even though the
  database reader already does so.
- **Audit data leakage:** the UI never renders the raw `changes` object; it honors `changes_redacted`
  and shows only approved activity vocabulary and actor/subject display labels.
- **BOLA/IDOR:** each page re-runs `requireWorkspaceAccess`; the RPCs additionally bind `p_uid` to
  `auth.uid()` and workspace membership in PostgreSQL.
- **N+1 performance:** roster evidence and visible display profiles are loaded in bounded bulk queries.
- **Wrong-context mutations:** this slice is read-only and introduces no workspace write action.
