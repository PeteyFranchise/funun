# Plan 38.1-03 — Member-Visible Workspace Audit Surface

## Objective

Turn the Activity room from a safe chronological summary into a discoverable operational audit
surface. Members can find relevant events and understand who acted, what category changed, when it
happened, and whether detail was withheld, without receiving raw audit payloads or bypassing target
resource authorization.

## Scope

1. Add a pure audit presentation model for category, action label, searchable text, and safe
   workspace-local target links.
2. Add client-side search and filters for category, person, date window, and protected-detail state
   across one bounded server-loaded audit page.
3. Add an accessible activity detail panel containing only allowlisted presentation fields already
   returned by the hardened audit reader.
4. Add pagination controls that preserve workspace URL context and never request more than the
   existing 200-row database ceiling.
5. Preserve the existing session-client `workspace_audit_page` call, `p_uid = auth.uid()` binding,
   membership/cohort/kill-switch gates, and service-role enrichment-after-access rule.
6. Do not send the raw `changes` object to a Client Component, even for privileged viewers; richer
   change-detail allowlists remain a future, action-specific security review.

## Risks and controls

- **PII leakage:** filters operate on the normalized record only; raw `changes` never crosses the
  server read-model boundary.
- **IDOR through links:** only workspace-local routes are generated, and every destination retains
  its own server authorization. Unsupported targets are descriptive text, not links.
- **False completeness:** the UI says it is showing a bounded activity page and offers pagination;
  filters do not claim to search un-loaded history.
- **Browser load:** the default remains 50 and selectable page sizes remain within the database's
  hard 200-row maximum.
- **Context drift:** every URL includes the current `/w/[workspaceId]` prefix.
