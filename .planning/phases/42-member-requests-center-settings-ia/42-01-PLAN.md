# Plan 42-01: Unified requests read model

## Objective

Create a server-only, typed aggregate read model for pending decisions, active access, history, and counts
without moving mutations or weakening any domain's authorization.

## Read first

- `42-CONTEXT.md` and the owner-facing Phase 42 plan.
- `components/settings/PermissionsTab.tsx` and its backing API routes.
- `components/settings/RightsProposalsPanel.tsx` and rights-proposal routes.
- `components/settings/MasterClaimsPanel.tsx` and master-claim routes.
- `lib/notifications/index.ts`; existing dashboard next-moves loader/types.

## Tasks

1. Add `lib/requests/types.ts` with a discriminated union for the three request kinds and explicit
   summary/detail projections. Include stable ID, kind, state, created/decided time, source link,
   requester/workspace display, optional work display, urgency/deadline, and allowed action names.
2. Add `lib/requests/load.ts` as a server-only fan-in. Reuse existing authorized queries/presenters;
   never use a service client merely to simplify aggregation. A source error must be represented and
   visible, not converted to an empty list.
3. Implement deterministic ordering: consequential/deadlined decisions first, then oldest pending;
   active/history ordered by effective/decided time. Document ties.
4. Add a single count function derived from the same result/filter rules as the page.
5. Unit-test normalization, ordering, sensitive-field omission, source failure, unknown rows, and counts.

## Acceptance

- Aggregate types cannot represent a raw IPI/proposed value, email, bank/tax value, evidence path, or
  storage path in a summary item.
- Cross-account fixtures return no rows.
- One failing source cannot silently display “all caught up.”
- No new mutation route or database object is created.
- Focused tests plus `npm run typecheck:strict` pass.
