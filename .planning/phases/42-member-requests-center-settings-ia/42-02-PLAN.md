# Plan 42-02: Requests center UI and domain decisions

## Objective

Ship `/requests` with Needs your decision, Active access, and History while preserving each domain's
existing mutation authority and stale-write behavior.

## Tasks

1. Add a server page at `app/(artist)/requests/page.tsx`; parse an allowlisted `view`, `kind`, and record
   query for deep links. Invalid filters fall back safely.
2. Add focused Requests components rather than embedding the three large Settings panels unchanged.
   Reuse domain decision controls/helpers where safe; keep permission approve/decline/revoke, rights
   confirm/decline, and master confirm/dispute/support as distinct mutations.
3. Label rights proposals **Rights information updates** and explain that confirmation updates the
   Member's own canonical rights profile.
4. Show optimistic busy state but reload authoritative data after each decision. A stale/decided record
   reports its current state; it never appears successfully decided twice.
5. Implement keyboard focus, screen-reader labels/live results, responsive cards, empty states, partial
   failure states, and error recovery.

## Acceptance

- Direct links open the intended authorized request without leaking its existence to another account.
- A detail view shows only the information necessary for that decision.
- Active access can be revoked through the existing authorized path.
- Back/forward navigation and filters are stable.
- Component/route tests use explicit test paths and fail if zero tests run; strict typecheck passes.
