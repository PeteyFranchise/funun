## Accomplishments
- `POST /api/selects/[token]/engagement` — the exact structural analog of `app/api/selects/[token]/react/route.ts` (resolve → rate-limit → scope → persist), handling both per-track audible-time delta events and open/view events over one endpoint

## Decisions Made
- **Clamp, don't reject, over-ceiling deltas server-side.** The plan's must_haves truth says the route "clamps the delta to ≤15s" — implemented via `clampDelta` after zod parsing (schema itself only requires `z.number().finite()`), rather than PATTERNS.md's illustrative `zod.max(15)` shape which would reject instead of clamp. A delta that clamps to 0 (non-finite/negative/zero) is rejected with 400 since inserting a 0-second row would violate the DB CHECK anyway.
- **Attribution is viewer_key only.** Migration 132's `selects_track_engagement`/`selects_opens` tables carry no `reacted_by`-equivalent authenticated-user column (unlike `selects_reactions`), so the route does not replicate the react route's `buyer_members` org-membership lookup — it simply persists whatever `viewerKey` the client sends (or `null`).
- **Task 3 folded into Task 1's commit.** Both tasks modify the exact same file (`route.test.ts`); the D-31.2-14 contract assertion was written as part of Task 1's initial file authoring and re-verified green after Task 2's SelectsPlayer changes landed. There was no incremental diff left for a separate Task 3 commit.
