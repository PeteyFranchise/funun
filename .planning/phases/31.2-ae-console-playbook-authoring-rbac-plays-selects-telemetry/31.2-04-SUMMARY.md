# Phase 31.2 Plan 04: Playbook Authoring API (SOP + Topic draft->publish) Summary

**Room-scoped SOP/Topic authoring API generalizing the Tips tip_draft/tip_approved flow into playbook_entries' JSONB content/draft_content/status columns, with a server-derived (never client-supplied) role-tiered publish gate.**

## Performance

- **Duration:** ~16 min
- **Started:** 2026-08-24T22:08:17-04:00 (base commit)
- **Completed:** 2026-08-24T22:22:06-04:00
- **Tasks:** 3
- **Files modified:** 5 created

## Accomplishments
- Pure draft->publish transition logic (`resolveWrite`/`applyApproval`/`applyReject`) generalized from the live Tips `tip_draft`->`tip_approved` precedent into `playbook_entries`' JSONB `content`/`draft_content`/`status` shape, fully unit-tested
- `isRoomLead(service, roomId, userId)` reads `playbook_room_leads` for server-derived approval authority (leadership OR room-lead)
- `POST`/`GET /api/admin/playbook/entries`: room-scoped create + list. A regular member's create always lands `draft_pending` (content untouched); leadership/room-lead lands `published` directly. `zod .strict()` rejects any client-supplied `status`/`approver` field outright — the isApprover decision is 100% server-derived, matching T-31.2-10's threat mitigation
- `PATCH /api/admin/playbook/entries/[id]`: approve/reject require server-derived approval authority (403 otherwise); edit is forward-only — an approver's edit updates `content` in place (status stays `published`), a non-approver's edit becomes a new `draft_content` (never a direct publish), satisfying R9's forward-only acceptance
- Every create/approve/reject/edit branch calls `logStaffAction` (T-31.2-12)

## Decisions Made
- `requireRoomAccess(roomKey)` is defined locally in `lib/playbook/entries.ts` rather than imported from `lib/playbook/rooms.ts` (see Deviations) — a spec-faithful implementation that composes `requireStaff`, short-circuits true for leadership with no extra DB read (Pitfall 5), and otherwise checks `playbook_room_role_grants` for any of the caller's held roles (multi-role aware, matching 31.2-03's documented `canAccessRoom` semantics)
- `content`/`draft_content` are typed as `Record<string, unknown>` (JSONB per migration 130), not `string` — the SOP checklist and Topic coaching-bundle shapes differ and are opaque to this layer
- `listEntries` runs two independent queries (published rows + the caller's own drafts) rather than building a single `.or()` filter string with interpolated UUIDs, avoiding any raw string-building into a PostgREST filter even though the UUID source (`auth.uid()`) is trusted
