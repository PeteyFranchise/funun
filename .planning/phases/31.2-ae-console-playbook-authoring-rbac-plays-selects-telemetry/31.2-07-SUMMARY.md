# Phase 31.2 Plan 07: Access-Editor Matrix + Data-Driven Playbook RBAC Summary

**Leadership room x role access-editor matrix wired live to a DB-driven Rail2/layout, and all 5 IT-room pages re-pointed from the Phase 33 hardcoded `requireStaffPage(['leadership','it'])` literal to `requireRoomAccessPage('it-team')` — closing Pitfall 6 so the matrix is a real gate, not cosmetic.**

## Performance

- **Duration:** ~12 min
- **Tasks:** 3/3 completed
- **Files modified:** 9 (2 created, 7 modified)

## Accomplishments
- Built `AccessEditorMatrix.tsx` — a client-side room x non-leadership-role grid; each toggle PATCHes `/api/admin/playbook/rooms` with `{ roomId, role, granted }`, applies the route's returned matrix, and `router.refresh()`es. The leadership column is structurally absent (GRANTABLE_ROLES already excludes it) — never rendered or toggleable.
- Built the leadership-gated `/admin/playbook/access` page (`requireStaffPage(['leadership'])` self-guard, runs before any data read) that loads the matrix via the same `loadRooms`/`readRoomGrants`/`buildGrantMatrix` functions the GET route uses and mounts the matrix.
- Converted `PlaybookLayout` to call `loadRooms(service)` + `readRoomGrants(service)` and filter rooms per D-31.2-03's mixed-reading rule (leadership sees all; non-sensitive rooms are visible to everyone; sensitive rooms need `canAccessRoom`), replacing the hardcoded `canSeeItRoom` boolean. Passes the visible rooms list + `isLeadership` down to `Rail2`.
- Converted `Rail2` to accept `rooms: PlaybookRoom[]` (the DB shape) + `isLeadership: boolean` as data props instead of importing `PLAYBOOK_ROOMS` from `nav.ts`. Visual treatment (ghost rooms, IT sub-nav with `IT_SUBPAGES`, collapse behavior) is unchanged. Added a leadership-only "Access" nav link to the new editor.
- Re-pointed all 5 IT-room pages (dashboard, vendor-directory, runbook, operating-rhythm, thresholds) from the hardcoded `requireStaffPage(['leadership', 'it'])` literal to `requireRoomAccessPage('it-team')`, imported from `lib/playbook/rooms.ts`. The guard still runs before any content/health read on every page (D-02 discipline preserved).

## Decisions Made
- The access page reads matrix data via direct lib calls (`loadRooms`/`readRoomGrants`/`buildGrantMatrix`) instead of an RSC-to-own-route HTTP fetch — mirrors the Monitoring Dashboard's existing "never a self-HTTP call" precedent (T-33-07) and the Tips admin page's own direct-service-client-read pattern.
- Rail2's room-visibility filter (in `layout.tsx`) implements D-31.2-03's "mixed reading" rule exactly: `!room.sensitive || canAccessRoom(roles, grantedRolesForRoom)` — reusing `canAccessRoom` from `lib/playbook/rooms.ts` rather than re-deriving the predicate.
- The leadership-only "Access" nav link was added as part of Task 2 (inside the Rail2 rework) rather than Task 1, since `Rail2.tsx` is Task 2's file in the plan's per-task `<files>` scoping and the DB-driven room list + the Access link naturally belong together.
- `nav.ts`'s `PLAYBOOK_ROOMS`/`PlaybookRoom` type were left untouched (not in this plan's file set) — Rail2 no longer imports them, but `IT_SUBPAGES` from the same module stays in use for the IT room's fixed sub-page list (which hasn't moved to the DB in this phase).
