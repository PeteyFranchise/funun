### Locked Decisions

**RBAC & Access Model**
- **D-31.2-01 — Full data-driven access editor.** Build DB-stored rooms + per-room role grants + a leadership-editable **clickable room×role matrix** ("access editor"). Guardrails: **last-admin protection** + an **audit log** on every grant change. Generalizes Phase 33's hardcoded `requireStaff([...])` room gates; builds on the shipped roles-as-a-set model (migration 119). This is the intended larger RBAC build, chosen deliberately.
- **D-31.2-02 — Room-lead = both.** A distinct **per-room room-lead role** (approves that room's entries, manages sub-groups) **AND** leadership holds room-lead abilities everywhere (leadership is a strict superset). Room-leads assigned via the Team admin surface (roles-as-data).
- **D-31.2-03 — Mixed reading.** Most Playbook rooms readable by **all Team Members**; **sensitive rooms (IT, Leadership) are view-gated** per role. Create/edit/publish always follows the authority gradient regardless of read access.
- **D-31.2-04 — Authority gradient.** Rooms → **admins only**; sub-groups → **room-leads + admins**; entries/articles → **any member of that room drafts** → **room-lead OR leadership approves** → published.

**Playbook Authoring + Topic Sourcing**
- **D-31.2-05 — Author all three asset types now.** SOPs (checklists), Topics (coaching bundles: heading + open-ended questions), Plays (leadership actions).
- **D-31.2-06 — Role-tiered publish gate.** Leadership + room-leads publish on-save (no self-approval). Regular Team Members submit draft → room-lead/leadership approves → publishes. Mirrors the Tips precedent (`tip_draft` → `tip_approved`).
- **D-31.2-07 — Game-Plan topic picker keeps BOTH.** Authored Playbook Topics **augment** the 31.1 seeded starter topics — do NOT replace them. AI-generated topics stay deferred.

**Plays & "Today's Play"**
- **D-31.2-08 — One active play, many assignments.** One active team-wide "today's play" at a time (publishing a new one replaces it). A Play is a container of several assignments — structurally analogous to a Game Plan holding several topics.
- **D-31.2-09 — Two assignment kinds.** (a) Client-targeted — health band OR pipeline stage, evaluated per-AE against their OWN book, deep-links into My Client Partners filtered to those clients (reuses 31.1 filters + revised health bands 🟢≤30/🟡31–60/🔴61–180/🔵>180). (b) General team task — checkable directive (title + note + optional link/attachment), not client-filtered.
- **D-31.2-10 — Social/general task: directive now, posting-hook fast-follow.** The general/social assignment carries its content (copy + asset + link), posting-ready + forward-compatible; actual in-app posting via Buffer/campaign tooling is a DEFERRED fast-follow.
- **D-31.2-11 — Follow-through closes the loop.** AE marks assignments done (both kinds); leadership sees a "who's acted" completion rollup. Banner placement: **top of My Client Partners**.

**Selects Telemetry (R13)**
- **D-31.2-12 — Full engagement signal.** Genuine audible listen-time accumulator (play/pause/seek-aware, NOT wall-clock), per-track replay detail, open/view events, alongside existing 31.1 reactions + approve/request-changes.
- **D-31.2-13 — Surfaces in two places.** AE per-Selects view + leadership aggregate rollup across the team's book.
- **D-31.2-14 — Per-recipient attribution, staff-only.** Recorded against the recipient the Selects was sent to. Standard B2B sales-tool posture. Internal/staff-only — NEVER shown to the client.

## Summary

31.2 is a **generalization phase**, not a greenfield one: every one of its four capabilities has a live, working precedent already shipped in this codebase that the plan should extend rather than reinvent. The Playbook shell (Phase 33) already renders a hardcoded `PLAYBOOK_ROOMS` array and a role-conditional IT room; the Tips system already runs the exact draft→approve publish gate D-31.2-06 asks for; the Game Plan (31.1) already stores per-account topics as JSONB and has an explicit code comment marking where 31.2's dynamic sourcing plugs in; `funun_staff.staff_roles` (migration 119) is already a multi-role, roles-as-data model; and the Selects player + reactions system already has a per-recipient attribution scheme (`SELECTS_VIEWER_COOKIE` + `resolveSelectsByToken`) plus a proven flood-defense doctrine (rate limit + DB cap trigger) that the new telemetry writes must copy.

The single highest-leverage design decision is: **make `leadership` a hardcoded, non-revocable admin over every room** (never itself entered into the room×role grant matrix). This turns "last-admin protection" (D-31.2-01's guardrail) from a runtime invariant that must be checked-and-enforced into a structural impossibility — leadership can never lock itself out because leadership's access is never data-driven. Every other role's room access lives in a new `playbook_room_role_grants` table the access editor writes to.

For R13, the phase-31 original SPEC already specified the exact acceptance bar for a "qualified listen" (≥30s audible, scrub-excluded, replay distinct) — 31.2 is simply the first phase to build it. The accumulator should live client-side against the `<audio>` element's native `timeupdate`/`seeking`/`pause`/`ended` events (no library needed — `next/font`, `@dnd-kit`, and everything else already in `package.json` covers UI needs; no audio-timing library exists or is needed), batching deltas to the server via periodic heartbeat + `sendBeacon` on unload, with a server-side per-request delta cap and the same rate-limit doctrine the reaction route already uses.

**Primary recommendation:** Build the access editor as an ADDITIVE authorization layer (new `requireRoomAccess(roomKey)` helper backed by DB grants) that composes with — never replaces — the existing `requireStaff`/`requireStaffPage` primitives; keep Playbook Topics and Game-Plan seeded topics as two arrays merged at render time (never a DB migration of the seeded list); and build the telemetry accumulator as a pure client-side hook (`useAudibleTimeAccumulator`) whose output is periodically flushed as small deltas to a new staff-only, RLS-zero-policy table, mirroring the `selects_reactions` cap-trigger pattern exactly.

### Pattern 1: Additive room-access gate composed with the existing staff gate

**What:** A new `requireRoomAccess(roomKey, allowed?)` helper that (a) first calls the existing `requireStaff`/`requireStaffPage` to establish the caller IS staff, then (b) checks whether ANY of the caller's roles has view access to `roomKey` — reading `playbook_room_role_grants` — UNLESS the caller's primary role is `leadership`, which always passes without a DB read.
**When to use:** Every Playbook room/sub-group/entry route and page, replacing the Phase-33 hardcoded `requireStaffPage(['leadership','it'])` call sites.
**Example:**
```typescript
// lib/playbook/rooms.ts — NEW, composes rather than replaces lib/admin/gate.ts
import { requireStaffPage, type RequireStaffPageResult } from '@/lib/admin/gate'
import { createServiceClient } from '@/lib/supabase/server'

export async function requireRoomAccessPage(roomKey: string): Promise<RequireStaffPageResult> {
  const auth = await requireStaffPage() // base staff check, unchanged (OPERATIONAL_STAFF_ROLES default)
  if (auth.staffRole === 'leadership') return auth // leadership: never gated, never in the grants table

  const service = createServiceClient()
  const { data: room } = await service
    .from('playbook_rooms')
    .select('id')
    .eq('key', roomKey)
    .maybeSingle()
  if (!room) redirect('/admin/playbook')

  const { data: grant } = await service
    .from('playbook_room_role_grants')
    .select('role')
    .eq('room_id', room.id)
    .eq('role', auth.staffRole)
    .maybeSingle()
  if (!grant) redirect('/admin/playbook')

  return auth
}
```
This preserves Phase 33's "layout hide is not the authority — every page self-guards" discipline (D-02) while making the ALLOWED-ROLE LIST data-driven instead of a hardcoded array literal.

### Pattern 2: Draft→approve generalized from the Tips precedent

**What:** `playbook_entries` carries `content` (live/published) + `draft_content` (pending, nullable) + `status`. A room-lead/leadership author writes directly to `content` with `status='published'`. A regular member writes to `draft_content` with `status='draft_pending'`; a subsequent approve action by a room-lead/leadership moves `draft_content → content`, clears `draft_content`, sets `status='published'`.
**When to use:** SOP and Topic entries (D-31.2-05/06).
**Example:**
```typescript
// Mirrors app/api/admin/tips/[itemKey]/route.ts's approve/reject shape exactly,
// generalized from a single global launchpad_checklist_items row to a
// per-room-scoped playbook_entries table with an explicit role check.
export async function PATCH(request: Request, { params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const auth = await requireStaff() // OPERATIONAL_STAFF_ROLES
  if ('error' in auth) return NextResponse.json({ error: auth.error }, { status: auth.status })

  const service = createServiceClient()
  const { data: entry } = await service.from('playbook_entries').select('room_id, status').eq('id', id).maybeSingle()
  if (!entry) return NextResponse.json({ error: 'Not found' }, { status: 404 })

  const isApprover = auth.staffRole === 'leadership' || await isRoomLead(service, entry.room_id, auth.user.id)
  const body = (await request.json()) as { action: 'approve' | 'reject' }
  if (body.action === 'approve') {
    if (!isApprover) return NextResponse.json({ error: 'Forbidden' }, { status: 403 })
    // draft_content -> content, status='published' ...
  }
  // ... logStaffAction(service, { actorId: auth.user.id, action: 'approve_playbook_entry', targetType: 'playbook_entries', targetId: id })
}
```

### Pattern 3: Client-targeted Play-assignment eligibility (own-book scoping)

**What:** A client-targeted assignment (health band OR pipeline stage) is evaluated per-AE against ONLY that AE's own assigned book — never a global list — mirroring `loadBook`/`canAccessOrgContacts` from `lib/client-partners/signals.ts` and `lib/client-partners/contacts.ts`.
**When to use:** Computing whether "Call all your yellow contacts today" is actionable for a given AE, and building the deep-link filter into My Client Partners.
**Example:**
```typescript
// lib/client-partners/plays-eligibility.ts (NEW)
// Reuses computeHealth() (lib/client-partners/health.ts) — never a second
// health implementation. The deep-link target is the SAME filtered list
// the 31.1 room filters already expose — e.g. ?health=warning — not a new UI.
export function matchingClientCount(
  book: ClientPartnerRow[],
  assignment: { healthBand?: HealthState; pipelineStageKey?: string }
): number {
  return book.filter(row =>
    (!assignment.healthBand || row.health === assignment.healthBand) &&
    (!assignment.pipelineStageKey || row.pipelineStageKey === assignment.pipelineStageKey)
  ).length
}
```

### Pattern 4: Audible-time accumulator against the existing `<audio>` element

**What:** A client hook that owns exactly the bookkeeping needed to distinguish "audible playback seconds" from "elapsed wall-clock seconds" and from "seek jumps," attached to `SelectsPlayer.tsx`'s existing single `<audio ref={audioRef}>` element.
**When to use:** R13's accumulator — the phase's watch-out capability.
**Example:**
```typescript
// components/selects-player/useAudibleTimeAccumulator.ts (NEW)
// Genuine accumulator, not a naive setInterval timer — see Common Pitfalls.
export function useAudibleTimeAccumulator(
  audioRef: React.RefObject<HTMLAudioElement>,
  onFlush: (deltaSeconds: number, event: 'heartbeat' | 'pause' | 'ended' | 'unload') => void
) {
  const lastTimeRef = useRef<number | null>(null)
  const pendingRef = useRef(0)

  useEffect(() => {
    const el = audioRef.current
    if (!el) return

    function onTimeUpdate() {
      const t = el.currentTime
      if (lastTimeRef.current != null && !el.seeking) {
        const delta = t - lastTimeRef.current
        // Genuine-accumulator guard: only count small, forward, contiguous
        // deltas as audible playback. A negative delta or a jump > 2s
        // (browsers fire timeupdate roughly every 250ms during normal
        // playback) is a seek/scrub — reset the anchor WITHOUT accumulating.
        if (delta > 0 && delta <= 2) pendingRef.current += delta
      }
      lastTimeRef.current = t
    }
    function onSeeking() {
      lastTimeRef.current = null // break the contiguity chain — the next
                                  // timeupdate after a seek starts fresh
    }
    function flush(event: 'heartbeat' | 'pause' | 'ended' | 'unload') {
      if (pendingRef.current > 0) {
        onFlush(pendingRef.current, event)
        pendingRef.current = 0
      }
    }
    const heartbeat = setInterval(() => flush('heartbeat'), 10_000)
    el.addEventListener('timeupdate', onTimeUpdate)
    el.addEventListener('seeking', onSeeking)
    el.addEventListener('pause', () => flush('pause'))
    el.addEventListener('ended', () => flush('ended'))
    window.addEventListener('beforeunload', () => flush('unload')) // paired with sendBeacon in onFlush's impl

    return () => {
      clearInterval(heartbeat)
      el.removeEventListener('timeupdate', onTimeUpdate)
      el.removeEventListener('seeking', onSeeking)
    }
  }, [audioRef, onFlush])
}
```

### Anti-Patterns to Avoid

- **A `setInterval` timer that runs "while `playing === true`":** This is exactly the "naive timer" the phase watch-out prohibits — it can't distinguish a paused-but-state-stale render, a backgrounded tab where the interval is throttled/drifts, or (critically) doesn't verify the audio is actually AT a new position each tick. Always derive elapsed time from `audio.currentTime` deltas, never from `Date.now()` deltas alone.
- **Trusting the client's own `deltaSeconds` without a server-side cap:** A malicious client could POST `{deltaSeconds: 999999}` once. The engagement route must clamp/reject any single delta above a sane per-heartbeat ceiling (e.g., 15s, matching the heartbeat interval), exactly as migration 117 added a DB-level cap trigger on top of the app-level rate limit for reactions.
- **Re-deriving the Playbook seeded topics list from the DB:** D-31.2-07 is explicit — the 31.1 `SEEDED_GAME_PLAN_TOPICS` constant stays a code constant; authored Topics are a SEPARATE source merged at read time. Do not migrate the seed list into `playbook_entries` — that would silently change 31.1's tested default behavior.
- **Putting `leadership` into the room-grants table:** Would reintroduce the exact self-lockout risk the "last-admin protection" guardrail exists to prevent. Keep leadership's access hardcoded/structural, never row-data.
- **Gating Rail2 visibility only, and trusting that as the access authority:** Every Phase-33 IT-room page already demonstrates the correct discipline (inline `requireStaffPage` self-guard) — 31.2 must preserve this for every new data-driven room, not rely on the nav hide alone.

## Common Pitfalls

### Pitfall 1: Confusing "elapsed wall-clock time" with "audible playback time"
**What goes wrong:** A `setInterval`-based or `Date.now()`-delta-based timer keeps ticking during a paused track, a backgrounded/throttled tab, or while the user is scrubbing the seek bar — inflating listen time.
**Why it happens:** It's the obvious naive implementation, and it's explicitly called out as the phase's watch-out for exactly this reason.
**How to avoid:** Derive elapsed time exclusively from consecutive `audio.currentTime` readings on `timeupdate` events, discard any delta that isn't small-and-positive (a seek/scrub produces a large jump, or the `seeking` flag is set), and never accumulate anything while `audio.paused`.
**Warning signs:** Recorded audible seconds exceed the track's actual duration for a single play session; a user reports a qualified listen recorded after only skimming/scrubbing through a track.

### Pitfall 2: Trusting client-reported deltas without a server-side ceiling
**What goes wrong:** A public, unauthenticated (or lightly-authed via cookie) route accepts `{deltaSeconds}` from the browser with no bound — a single crafted request could fabricate hours of "listen time" for a track, corrupting the AE's engagement readout and the leadership rollup.
**Why it happens:** The client player is the natural place to compute the delta, but "client-computed" doesn't mean "server-trusted."
**How to avoid:** Cap each accepted delta to a sane per-heartbeat maximum (matching the client's own flush interval, e.g., ≤15s for a 10s heartbeat), reject/clamp anything larger, and apply the SAME `checkRateLimit` + DB-level-cap-trigger doctrine already proven for `selects_reactions` (migrations 116/117).
**Warning signs:** A single viewer's cumulative audible seconds for one track exceeds a multiple of the track's actual duration.

### Pitfall 3: Reusing `SELECTS_VIEWER_COOKIE` for attribution without acknowledging its known spoofability
**What goes wrong:** The existing guest-viewer cookie (`funun_svk`) is client-minted and rotatable by a determined caller — there's an OPEN, non-blocking todo (`2026-08-20-selects-reaction-signed-viewer-cookie.md`) tracking exactly this gap for reactions. Reusing it verbatim for telemetry inherits the same "distinct-viewer count can be nudged within the rate-limit/cap bounds" weakness — arguably a bigger deal for telemetry (a sales signal leadership will act on) than for reaction counts.
**Why it happens:** It's the path of least resistance — the cookie already exists and the SSR route already hydrates it.
**How to avoid:** Reuse the cookie for MVP (matches the phase's "staff-only, standard B2B posture" framing — D-31.2-14 — this is not client-facing data), but explicitly flag in the plan that the same rate-limit + DB-cap defenses applied to reactions must ALSO wrap the new engagement-write route, and cross-reference the deferred signed-cookie hardening todo as a candidate follow-up once telemetry fidelity matters to leadership.
**Warning signs:** Engagement counts for a Selects spike disproportionately relative to its `sent_at` recency or the org's typical activity.

### Pitfall 4: Migrating the seeded Game-Plan topics into the DB instead of merging two sources
**What goes wrong:** D-31.2-07 explicitly requires BOTH the 31.1 seeded starters AND authored Playbook Topics to appear together — replacing the seed constant with a DB-backed "seeded" room would silently break 31.1's tested `buildDefaultGamePlanTopics()` behavior and its 0-topic/empty-state edge coverage.
**Why it happens:** Once Topics become a real authored asset type, it's tempting to "unify" everything into one source for simplicity.
**How to avoid:** Keep `SEEDED_GAME_PLAN_TOPICS` as the existing code constant, untouched; add a new query for published `playbook_entries` where `entry_type='topic'`; concatenate the two lists at the point `loadGamePlan`'s caller builds the picker's option set — never inside `buildDefaultGamePlanTopics()` itself (that function's contract, per its own 31.1 doc comment, is "no game_plans row exists yet" seeding, unrelated to the picker's option menu).
**Warning signs:** 31.1's existing Game-Plan tests (topic-covered-summary, 0-of-N edge) start failing after this phase's changes land.

### Pitfall 5: Letting the access-editor matrix accidentally strip a room-lead's own OR leadership's implicit access
**What goes wrong:** If the matrix UI naively persists "every role's checked state" including leadership's row, an admin could uncheck leadership for a room, locking every other leadership member out of managing it (the exact "last-admin" failure mode).
**Why it happens:** A truly generic matrix component doesn't know leadership is special without an explicit carve-out.
**How to avoid:** Per Pattern 1 above — never render or persist a leadership row in the matrix at all; leadership access is structural, not data. If room-lead is ALSO meant to be immune from self-removal (a room-lead removing their own room-lead-ness), add an explicit guard in the room-lead-assignment endpoint (Team admin surface), not the room×role matrix (room-lead is a per-room assignment, D-31.2-02, separate from the role×room view-grant matrix).
**Warning signs:** A saved access-editor state leaves zero roles with edit/admin capability over the Playbook itself.

### Pitfall 6: Building a second "who has access to what room" check inside individual Playbook pages that drifts from the matrix
**What goes wrong:** Phase 33 shipped 5 IT-room pages each with their OWN inline `requireStaffPage(['leadership','it'])` call — a hardcoded array literal repeated 5 times. If 31.2 converts the room list to data-driven but leaves those 5 literals untouched, the access editor's matrix becomes cosmetic (it wouldn't actually control the IT room's real gate).
**Why it happens:** The safest-looking incremental change is "add the matrix UI, leave the enforcement alone" — but that fails D-31.2-01's actual goal (making Phase 33's hardcoded gates data-driven).
**How to avoid:** Explicitly re-point all 5 existing IT-room page guards (and the `PlaybookLayout`'s `canSeeItRoom` computation) through the new `requireRoomAccessPage('it-team')` helper, seeding `playbook_rooms`/`playbook_room_role_grants` with the IT room's CURRENT `['leadership','it']` grant so behavior is unchanged on day one, then verified by a migration-content test (mirroring the `migration-128.test.ts`/`migration-129.test.ts` pattern) asserting the seed matches today's hardcoded behavior.
**Warning signs:** The access editor UI shows a room's grants can be edited, but toggling a role in the UI has no effect on that room's actual page-level access.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Client-forged engagement deltas inflating listen-time/qualified-listen signals leadership acts on | Tampering | Server-side per-delta ceiling + `checkRateLimit` (per token+viewer) + a DB-level per-row/per-track cap trigger, mirroring migrations 116/117 exactly (Common Pitfalls #2, Code Examples) |
| Guest viewer-cookie rotation to inflate distinct-viewer counts | Spoofing | Inherited, tracked risk (`2026-08-20-selects-reaction-signed-viewer-cookie.md`) — accept for 31.2 (bounded by the caps above), explicitly cross-reference the deferred signed-cookie hardening as a candidate follow-up once telemetry fidelity matters (Common Pitfalls #3) |
| Access-editor self-lockout (leadership removes its own room access) | Denial of Service (against staff, not users) | Structural: leadership access is hardcoded, never entered into `playbook_room_role_grants` (Pattern 1, Pitfall 5) |
| Room-lead or regular member escalating a draft directly to `published` by crafting the PATCH body | Elevation of Privilege | Server derives `isApprover` from the caller's session-resolved role + `playbook_room_leads` membership — NEVER reads a client-supplied "am I an approver" flag (Pattern 2) |
| A staff member with NO grant for a sensitive room (IT/Leadership) reaching its content via direct API call despite nav hiding it | Information Disclosure | Every room/sub-group/entry route independently re-checks `requireRoomAccess` server-side — nav visibility is UX only (Pitfall 6, mirrors Phase 33's proven discipline) |
| Engagement/attribution data leaking to the public/client-facing `/selects/[token]` player | Information Disclosure | D-31.2-14 hard requirement — `resolvePlayerData` in `app/selects/[token]/page.tsx` must never select from the new engagement tables; verify via a contract test asserting the SSR player payload shape excludes engagement fields |
