# Phase 31.2: Code Review Report

**Reviewed:** 2026-08-24
**Depth:** standard

## Summary

The access-control substrate for this phase is solid: every playbook/plays/engagement admin route re-derives authority server-side (`requireRoomAccess`/`requireRoomAccessPage`/`requireStaff`/`verifyAdmin`), leadership is structurally excluded from the grantable-role CHECK constraint and from `GRANTABLE_ROLES`/`isGrantableRole` at the code layer, the hide-not-filter discipline for the leadership tower and engagement rollup is machine-verified (`lib/admin/gate.test.ts`), own-book scoping for Plays eligibility and the AE's Today's Play banner is correctly threaded through `loadBook`/`assembleRows`/`plays-eligibility.ts`, and the public engagement-telemetry write path (token resolution → dual rate limit → zod `.strict()` → scoped track lookup → server-side `clampDelta`) mirrors the existing `react` route's proven shape with no widening of the deferred viewer-cookie spoofability. The audible-time delta math (contiguity ceiling, seek/scrub exclusion, negative-delta rejection) is correct and well covered by `audible-accumulator.test.ts`. The read-time seeded+authored Game-Plan topic merge (`buildPickerTopics`) is a pure, non-mutating concatenation as documented.

One functional defect was found in the Plays → Client Partners deep-link (the "View clients" action on `TodaysPlayBanner` never actually filters anything at the destination), and one copy/labeling defect was found in the Game Plan picker for Playbook-authored topics. Both are traced end-to-end below with concrete reproduction paths.

## Critical Issues

### CR-01: Plays "View clients" deep-link is non-functional — the destination page never reads the health/stage filter it encodes

**File:** `lib/client-partners/plays-eligibility.ts:53-59` (`buildAssignmentDeepLink`), consumed by `components/admin/TodaysPlayBanner.tsx:143-150` and `lib/client-partners/room-data.ts:110-111`

**Issue:** D-31.2-09a's stated contract is: "The AE deep-links into My Client Partners filtered to those clients." `buildAssignmentDeepLink` correctly builds `/admin/client-partners?health=<band>&stage=<key>`, and `TodaysPlayBanner` correctly renders it as the "View clients" link for every `client_targeted` assignment. But the destination — `app/(admin)/admin/client-partners/page.tsx` — is a Server Component whose signature only destructures `{ params }`; it never reads `searchParams`, and neither `components/admin/ClientPartnersRoom.tsx` nor `components/admin/ClientPartnersList.tsx` reads `window.location.search` or a `useSearchParams()` hook anywhere in this room. Confirmed by direct search across the room's page/room/list components — zero references to `searchParams`, `health=`, or `stage=` outside `plays-eligibility.ts` itself.

Practical effect: an AE who clicks "View clients" on a Today's Play banner assignment lands on the unfiltered My Client Partners list (their whole book), not the subset of clients matching the assignment's `healthBand`/`pipelineStageKey` — the exact clients the play is asking them to act on. The "N in your book" count next to the button is correct (computed server-side via `matchingClientCount`), which makes the broken filter more misleading, not less: the AE sees an accurate count promising a filtered view, then gets the full list. `lib/client-partners/plays-eligibility.test.ts` only asserts the URL string `buildAssignmentDeepLink` produces — it never asserts the destination applies it, so this integration gap wasn't caught by the test suite.

**Fix:** Either (a) make `app/(admin)/admin/client-partners/page.tsx` accept `searchParams: Promise<{ health?: string; stage?: string }>` and thread an initial filter into `ClientPartnersRoom`/`ClientPartnersList` (client-side filter over the already-loaded own-book rows is sufficient — no new query), or (b) if filtering is deliberately deferred, downgrade the banner's affordance so it doesn't promise a filtered view it can't deliver (e.g., drop the query string / rename the button) until the destination actually consumes it.

## Warnings

### WR-01: Playbook-authored Game Plan topics are mislabeled as "From Selects" and display a raw internal UUID as their source badge

**File:** `components/admin/GamePlanPanel.tsx:296-306` (suggestion-pill copy), `components/admin/GamePlanPanel.tsx:232-240` (persisted-topic badge)

**Issue:** `buildPickerTopics` (`lib/client-partners/game-plan.ts:87-104`) tags authored Playbook Topics with `source: \`playbook:${entry.id}\`` (a UUID), correctly distinct from `'seeded'` and from the `'selects:<name>'` convention used for Selects-context suggestions. This is threaded end-to-end: `app/(admin)/admin/clients/[personId]/page.tsx:147` calls `buildPickerTopics(SEEDED_GAME_PLAN_TOPICS, authoredTopics)` and passes it to `ClientWorkspace` → `GamePlanPanel` as `pickerTopics`, so a real Playbook Topic reaches this component in production, not just in tests.

Two rendering bugs follow from this:
1. In the "Suggested topics" pill list (line 304), the label logic is `s.source === 'seeded' ? 'Seeded default' : 'From Selects'` — any non-seeded source (including every Playbook-authored topic) is unconditionally labeled "From Selects," which is factually wrong for a Playbook Topic.
2. Once an AE clicks a Playbook-sourced suggestion, `addSuggested` copies `source: s.source` verbatim into the topic list. The persisted-topic badge (lines 232-240) only special-cases `'seeded'` and a `'selects:'` prefix; anything else (i.e., `playbook:<uuid>`) falls through to rendering the raw string, so the AE-facing UI shows a badge reading literally `playbook:3f9a1c22-...` — an internal entry id leaked into user-facing copy instead of a friendly label.

**Fix:** Add an explicit `source.startsWith('playbook:')` branch in both places (mirroring the existing `'selects:'` branch), e.g. render `'Playbook'` for the suggestion-pill subtitle and `'Playbook'` (optionally with the room/entry title, not the id) for the persisted-topic badge.

## Info

### IN-01: `listEntries` alone never surfaces other authors' pending drafts to a room-lead

**File:** `lib/playbook/entries.ts:118-142` (`listEntries`)

**Issue:** `listEntries` scopes `status='draft_pending'` rows to `author_id = viewerId`, so if it were ever called directly to build an approver's view (e.g., a future consumer of `GET /api/admin/playbook/entries`), a room-lead/leadership caller would not see other members' pending drafts to approve. This is currently *not* a live bug — `app/(admin)/admin/playbook/[room]/page.tsx:47-58` explicitly works around it with a second, unscoped query merged in for approvers, and the `EntryEditor` component only consumes that merged `initialEntries` prop (it never calls the GET route). Flagging as Info because the underlying `GET /api/admin/playbook/entries` route (`app/api/admin/playbook/entries/route.ts`) is a valid, tested HTTP surface that returns an incomplete approver view if any future caller (external integration, a different UI, manual testing) relies on it directly instead of the page's workaround — the fix belongs in `listEntries`'s contract, not in every caller.

**Fix:** Consider adding an `isApprover` (or `includeAllPending`) parameter to `listEntries` so the "approver sees every pending draft in the room" rule lives in one place, and have both the route and the page call it the same way — rather than the page re-implementing the merge inline.
