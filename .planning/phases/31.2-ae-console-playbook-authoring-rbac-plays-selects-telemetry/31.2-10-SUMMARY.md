## Accomplishments
- AE per-Selects engagement route (`GET /api/admin/client-partners/selects/[id]/engagement`) — own-Selects-scoped (loadSelectsInScope, 404 not 403), returns per-track `{ title, audibleSeconds, qualifiedListens, replayCount }` + a Selects-level summary, computed via plan-02's `aggregateTrack`/`aggregateSelectsRollup`.

- The Client Partners leadership tower (`ClientPartnersRoom.tsx`'s All tab) now shows an "Engagement — who's getting listens" section: per-AE totals (opens, qualified listens, audible time, replays) plus a per-Selects breakdown — computed server-side only inside the RSC page's `isLeadership` branch, so the whole-book engagement read is never invoked for a non-leadership caller.

## Decisions Made
- Extracted `lib/selects/engagement-rollup.ts` rather than inlining the aggregate in the route: a Next.js route module may only export HTTP method handlers, so the leadership tower's RSC page (which needs the same aggregate without an internal HTTP round-trip) requires a shared lib function — same pattern as `lib/selects/tracks-query.ts`'s `resolveTracksWithRightsReady`.
- The AE panel (Task 1) self-fetches client-side (mirrors `CrateRequestsFeed`/`TipsAdmin`'s existing pattern), while the leadership rollup (Task 3) is computed server-side inside the RSC page's `isLeadership` branch. This split exists because the leadership hide-not-filter guarantee (T-31.2-27) needs to be machine-testable the exact way `allData`'s already is (`lib/admin/gate.test.ts`'s D-31.1-01 suite asserts `loadWholeBookWithCoverage` is never called for ae/bd) — a client-side-only guard around a `useEffect` fetch would not be provable the same way, since effects don't run under the repo's `testEnvironment: 'node'` component-test convention.
