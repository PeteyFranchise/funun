# Plan 44-02: Chat doctrine, schema, RLS, and server contract

## Objective

Author—not apply—a minimal persistent room-chat model after the owner resolves retention/moderation
choices. Preserve room authorization at the database and route layers.

## Human decision gate

Before SQL, record: retention period; edit/delete window; tombstone behavior; visibility after removal;
owner moderation powers; block behavior; reply/reaction scope; mention notification defaults; metadata
audit; export/legal-hold stance. No unanswered item may be silently delegated to implementation.

## Tasks

1. Preflight all migrations, untracked files, quick work, and the roadmap ledger. Migration 228 is
   unavailable. Select a number only then; never apply it in this plan.
2. Model work-bound messages, replies, minimal reactions if approved, edits/tombstones, mentions, and
   read cursor/unread state. Store authoritative author identity; clients cannot choose it.
3. Add RLS and direct privilege revokes proving only current authorized room members may read/write.
   Explicitly encode removal/block/moderation/retention decisions and service-role boundaries.
4. Add allowlisted, bounded routes/presenters with pagination, rate limits, idempotency, safe errors, and
   no `select('*')`. Chat content never enters summary logs/audits/notifications.
5. Test two-account access, revoked access, block, stale writes, reply integrity, pagination, rate limit,
   XSS/render safety, deletion/tombstone, mention validation, and migration structure.

## Acceptance

- Chat cannot write or imply rights/credits/splits/approvals.
- No user can read history merely because they once had access unless the approved policy explicitly says
  so and the UI explains it.
- Migration remains marked NOT APPLIED until owner-run application and remote RLS verification.
