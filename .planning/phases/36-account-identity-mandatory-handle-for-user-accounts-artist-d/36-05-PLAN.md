<objective>
Fix the pre-existing case-sensitivity defect on the public profile route and give retired handles
somewhere to land, both through migration 133's resolver.

Purpose: D-04 promises that `@MayaReyes` and `@mayareyes` are the same handle, but the public
profile page has always filtered on an exact-case equality against the URL segment — so today
`/u/MayaReyes` 404s even though the profile exists and the unique index is case-insensitive. The
database guarantee was built correctly in migration 010 and this one read path was never updated to
match. That is a live bug, not a nice-to-have, and this plan is already opening the same query
block to add D-07's retired-handle fallback.

Doing both through one resolver call means the fix and the redirect share a single round trip, and
`handle_history` stays fully revoked from anon and authenticated.
Output: one pure resolver module with tests, plus the page wiring.
</objective>

  <behavior>
    - A URL segment matching a live handle exactly → `{ kind: 'current', profileId, handle }`
    - A URL segment matching a live handle in different casing → `{ kind: 'current', ... }`, and `handle` carries the STORED casing, not the URL's
    - A URL segment matching only a retired handle → `{ kind: 'redirect', profileId, handle }` where `handle` is the owner's CURRENT handle
    - A URL segment matching nothing → `{ kind: 'none' }`
    - An empty or whitespace-only segment → `{ kind: 'none' }` and the RPC is never called
    - A segment longer than 64 characters → `{ kind: 'none' }` and the RPC is never called
    - The RPC returning an error → `{ kind: 'none' }`, never a throw
    - The RPC returning an empty array → `{ kind: 'none' }`
    - The RPC is invoked exactly once per call, with the trimmed segment as `p_handle`
  </behavior>
  <action>
    Create `lib/handles/resolve.ts` exporting a `HandleResolution` discriminated union
    (`{ kind: 'none' }` | `{ kind: 'current'; profileId: string; handle: string }` |
    `{ kind: 'redirect'; profileId: string; handle: string }`) and an async
    `resolveHandle(client, raw)`.

    Type `client` as the minimal structural shape it actually needs — an object with an `rpc` method
    returning `{ data, error }`. Injecting the client rather than constructing one is what makes this
    testable with a plain object literal; this repo has no jsdom and no Supabase test harness, and it
    is the same "extract the decision, inject the dependency" move `loadClientPartnersRoomData` used.

    Behaviour: trim the segment; return `none` immediately for an empty value or anything over 64
    characters, without spending a round trip on a garbage URL. Otherwise call
    `client.rpc('resolve_profile_by_handle', { p_handle: trimmed })`. Map an error or an empty result to
    `none`. Map a returned row to `redirect` when its `redirected` column is true and `current` when it
    is false, carrying `profile_id` and `current_handle` through.

    Do NOT gate the segment on `isValidHandle()`. The format rule governs what may be CLAIMED, not what
    may be LOOKED UP — coupling the public read path to it would 404 any handle that predates the rule.
    The resolver is an exact lowered equality inside the database, so a malformed segment simply finds
    nothing.

    Add a comment recording why this goes through an RPC at all: PostgREST cannot express a lowered
    column comparison, and the obvious alternative — a pattern-match filter — is wrong here because an
    underscore is simultaneously a legal handle character under D-05 and a single-character wildcard, so
    `/u/a_c` would resolve to `abc`, or match two rows and 404 a real profile.

    Write `lib/handles/resolve.test.ts` with a hand-rolled client whose `rpc` is a jest mock, covering
    every behavior line including the two "the RPC is never called" cases.
