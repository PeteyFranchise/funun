<objective>
Build the write path for a handle: a dedicated `PATCH /api/profile/handle` route that changes a
handle, records the retired one in `handle_history`, and surfaces the database's rejection rather
than trusting any earlier check — plus the settings-page field that exercises it.

Purpose: this answers the first open question research flagged. D-07 is a locked decision and the
phase's scope statement lists "handle changes with old-URL redirects" explicitly, but
`handle_history` has no other write path — without this route, nothing in the phase can ever put a
row in it, and D-07 ships unexercisable. The route is also the shared write path plan 06's hard
gate posts to, so building it in wave 2 unblocks wave 3. `handle` is deliberately absent from the
generic profile PATCH allowlist today; that is not an oversight to fix, it is the established
signal that this field needs its own route (the `/api/profile/visibility` precedent).
Output: one API route, one pure submit-decision module, one settings form, two test files.
</objective>

  <name>Task 1: PATCH /api/profile/handle — the dedicated handle write route (D-07, D-08, D-14)</name>
  <files>app/api/profile/handle/route.ts, __tests__/profile-handle-route.test.ts</files>
  <behavior>
    - No session → 401 with `{ error: 'Unauthorized' }`, and no database call is made
    - Body with a malformed handle → 400 carrying the shared format message, and no update is attempted
    - Body with a handle whose lowered form equals the current handle's lowered form → 200, the update
      IS performed (so the new casing persists), and NO handle_history row is written
    - Body with a genuinely new handle, update succeeds → 200 returning the new handle, and exactly one
      handle_history row is inserted carrying the OLD handle and the caller's profile id
    - Caller currently has no handle at all, update succeeds → 200 and NO history row (there is nothing
      to retire)
    - Update fails with the Postgres unique-violation code → 409, and no history row is written
    - Update fails with the guard's reserved/retired raise → 400, and no history row is written
    - The history insert rejecting → still 200; the handle change is not rolled back and no error is
      surfaced to the caller
    - Exceeding the per-user change rate limit → 429 before any database write
  </behavior>
  <action>
    Create `app/api/profile/handle/route.ts` exporting `PATCH`, modelled directly on
    `app/api/profile/visibility/route.ts` — this repo's template for a profile field whose write needs
    server-side logic beyond a plain column update. Lead the file with a section-header comment
    explaining why it is not in the generic allowlist: this write must also record the retired handle
    atomically with the change, and the field is the account's public identity.

    Flow:
    1. `createApiClient()` then `auth.getUser()`. No user → 401.
    2. Rate limit the change itself with `checkRateLimit` from `@/lib/security/rate-limit`, keyed
       `handle-change:<user.id>` with an explicit generous window — five changes per 24 hours. Do not
       use the default window. Justify it in a comment: D-08 makes every change permanently burn a
       name, so an unbounded change loop is a name-exhaustion vector; five a day is far above any
       legitimate rebranding cadence. Over the limit → 429 with the same message shape
       `check-invite` uses.
    3. Read `body.handle` defensively (`typeof === 'string'` then trim, per this repo's convention of
       reading loosely with type guards). Run `handleFormatError()` from `@/lib/handles/validate`;
       non-null → 400 with that exact message. Do not re-implement the format rule here.
    4. `createServiceClient()`, read the caller's current handle with
       `.select('handle').eq('id', user.id).maybeSingle()`.
    5. Compare with `normalizeHandleForCompare()`. If the lowered forms match, this is a casing change,
       not an identity change — perform the update so the stored casing reflects what the person typed
       (D-04 is case-preserving), skip the history write entirely, and return 200. Comment that a
       casing-only change breaks no URL because every lookup compares lowered.
    6. Otherwise update `user_profiles.handle` scoped `.eq('id', user.id)`, selecting back `id, handle`.
       Store the trimmed value exactly as typed — never lowercased.
    7. On error, map it: the unique-violation code `23505` → 409; anything else (including migration
       133's guard raise, which arrives as a plain message) → 400. Return a single non-specific message
       for both, so the response does not distinguish "someone has it" from "it is reserved" from "it
       was retired". Comment that per D-14 this rejection is the authority and the availability check
       is never proof.
    8. On success, and only when a previous handle existed and was not merely a casing variant, insert
       `{ profile_id: user.id, old_handle: <previous handle> }` into `handle_history` via the service
       client. Wrap it best-effort in the repo's established "swallow the secondary write, never fail
       the primary action" idiom. Comment the consequence honestly: a missed history row means an old
       link 404s instead of redirecting — degraded, not broken.
    9. Order matters and needs a comment: the update runs FIRST and the history row second. The reverse
       order would close a brief window where the retired handle is claimable, but at the cost of
       leaving a stray history row if the update then failed — and under migration 133's universal
       block that row would permanently burn the person's own current handle. The brief window is the
       cheaper failure.
    10. Return `NextResponse.json({ data: { handle } })`.

    Write `__tests__/profile-handle-route.test.ts` in the style of `__tests__/profile-privacy-api.test.ts`:
    `jest.mock('@/lib/supabase/server', ...)` for both client factories, a `jsonRequest()` helper, a
    fixed owner UUID, and one assertion per behavior line above. Mock `@/lib/security/rate-limit` so
    the limiter does not need a database. Assert the negative cases by proving the relevant mock was
    NOT called — for the 401 and 400 cases assert `createServiceClient` was never invoked, and for
    every non-success case assert no insert into `handle_history` occurred.
