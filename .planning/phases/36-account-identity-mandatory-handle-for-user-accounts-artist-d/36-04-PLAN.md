<objective>
Make the create-account form ask who someone is: add the handle field to signup's `allowed`
branch, carry it on the `signUp()` call so migration 133's trigger writes it atomically with the
profile row, and back it with a public, rate-limited availability endpoint that reads all three
sources uniqueness now spans.

Purpose: this is the decision the whole phase turns on — D-02 put the handle on the create-account
form rather than after email verification precisely so there is never a window where a User Account
exists without one. The availability check exists to stop someone typing a name that is already
gone, and nothing more: D-14 makes the database the sole authority, and D-15 already guarantees a
lost race costs a NULL handle rather than the account.

This plan also answers research's second open question. The availability check gets its own route
and its own rate-limit keyspace rather than folding into the invite pre-check, because the two
guard different resources — a debounced handle-typing session firing on every keystroke would
otherwise eat the budget the admission check depends on.
Output: one public API route, one pure field-state module, the signup form change, two test files.
</objective>

  <name>Task 1: GET /api/handles/available — public, own-keyspace availability check (D-14)</name>
  <files>app/api/handles/available/route.ts, __tests__/handle-available-route.test.ts</files>
  <behavior>
    - Missing or empty `handle` query param → 200 with `{ available: false, reason: 'invalid' }` and no database call
    - Malformed handle → 200 with `{ available: false, reason: 'invalid' }` and the shared format message, no database call
    - Handle that resolves to a live profile → 200 with `{ available: false, reason: 'unavailable' }`
    - Handle that resolves only through the retired-handle fallback → 200 with `{ available: false, reason: 'unavailable' }`
    - Handle present in the reserved list → 200 with `{ available: false, reason: 'unavailable' }`
    - Handle matching none of the three → 200 with `{ available: true, reason: null }`
    - Casing is irrelevant: a request for a mixed-case spelling of a taken handle is reported unavailable
    - Over the per-IP rate limit → 429 before any database call
    - A database error on either read → 200 with `{ available: null, reason: null }` — unknown, never a false verdict
  </behavior>
  <action>
    Create `app/api/handles/available/route.ts` exporting `GET`, modelled on
    `app/api/signup/check-invite/route.ts`'s posture (public, unauthenticated, called from a form,
    rate-limited, non-throwing).

    Put it at `/api/handles/available` rather than under `/api/profile/`: it is unauthenticated and is
    called both from signup (no session at all) and from the signed-in gate, so nesting it inside the
    authenticated profile namespace would misrepresent its auth posture. Say so in the header comment.

    Flow:
    1. `getClientIp(request)`, then `checkRateLimit` with the key `handle-check:ip:<ip>` and EXPLICIT
       options — roughly sixty attempts per five minutes. Comment both choices. The separate `handle-check:`
       prefix is deliberate: sharing `check-invite`'s `ip:` keyspace would let a debounced typing session
       exhaust the budget that guards signup admission, and the two checks protect different resources.
       The default five-per-fifteen-minutes ceiling would make the field unusable after two words typed.
    2. Read the handle from the query string, trim it. Run `handleFormatError()` from
       `@/lib/handles/validate`; non-null → return the invalid shape immediately, without a database call.
       Include the message so the caller can render it.
    3. `createServiceClient()`. Do two reads in parallel:
       - `.rpc('resolve_profile_by_handle', { p_handle: <trimmed> })` — migration 133's resolver, which
         covers BOTH a live handle and a retired one in a single exact lowered comparison. Any returned row
         means unavailable. Comment why the RPC rather than a filter: PostgREST cannot express a lowered
         column comparison, and an underscore is both a legal handle character and a single-character
         pattern wildcard, so a pattern-match filter would produce wrong matches.
       - `reserved_handles` `.eq('handle', <lowered>)` — that table stores its values lowercased per
         migration 037's own header, so a direct equality on the lowered input is exact.
    4. Collapse taken, retired and reserved into one `'unavailable'` reason. Do not distinguish them —
       matching the single-message posture of plan 03's PATCH route, so the endpoint never confirms
       whether a specific name is merely reserved or actually held by a person.
    5. If either read errors, return `{ available: null, reason: null }`. An honest "unknown" is correct;
       reporting a free handle as taken would be a worse failure than reporting nothing.

    Write `__tests__/handle-available-route.test.ts` mocking `@/lib/supabase/server` and
    `@/lib/security/rate-limit`, one assertion per behavior line, including an assertion that the
    service client is never constructed for a malformed input or a rate-limited request.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Anonymous internet → `GET /api/handles/available` | Fully public, unauthenticated read path callable at typing speed |
| Browser signup form → Supabase Auth `signUp()` → `auth.users` | Attacker-controlled `user_metadata` crossing into a SECURITY DEFINER trigger |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-36-17 | Denial of Service | Availability endpoint called at keystroke rate | medium | mitigate | Durable per-IP rate limiting on its own `handle-check:` keyspace with an explicit window, plus a client-side debounce and a client-side format pre-filter so no token is spent on a locally-invalid value. |
| T-36-18 | Denial of Service | Availability traffic exhausting the invite pre-check's budget | high | mitigate | Separate keyspace, separate limits. This is the direct reason research recommended a separate route over folding into `check-invite`, and it is why they must not share a prefix. |
| T-36-19 | Information Disclosure | Handle enumeration through the availability endpoint | low | accept | Handle-taken status is inherently public — anyone can visit the public profile URL to learn it. Unlike the invite pre-check's email-enumeration concern, no response-shape masking is warranted; abuse-rate protection is the appropriate control. Taken, reserved and retired are still collapsed into one reason so the endpoint does not distinguish them. |
| T-36-20 | Spoofing | Reserved or retired handle submitted through the signup form | high | mitigate | Not mitigated here and must not be attempted here. Migration 133's `BEFORE INSERT` guard is the enforcement; the form's check is a courtesy and the trigger's fallback turns a rejection into a NULL handle rather than a failed signup (D-15). |
| T-36-21 | Tampering | Forged `user_metadata` on the signUp call | medium | accept | A self-serve signup fully controls its own `user_metadata`, so it can present any handle string it likes — which is exactly what the field is for. The trigger validates it against the reserved list, the retired list and the unique index before it is stored, so a forged value gains nothing. Admission remains governed by the unchanged invite gate. |
| T-36-22 | Tampering | Out-of-order availability responses | low | mitigate | A monotonic request counter held in a ref; any response that is not the latest is discarded, so a slow early response cannot overwrite the verdict for a newer value. |
| T-36-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task in this plan or anywhere in Phase 36 — RESEARCH.md's Package Legitimacy Audit records "not applicable, zero new dependencies". |
