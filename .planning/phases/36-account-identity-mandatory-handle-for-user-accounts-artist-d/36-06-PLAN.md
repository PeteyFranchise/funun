<objective>
Build D-09's hard gate: a signed-in User Account that has a profile row but no handle sees one
unskippable choose-a-handle screen until it picks one.

Purpose: this is the mechanism that converts the existing handle-less accounts, and it is the
precondition for the `NOT NULL` constraint in plan 07 — without it, "mandatory" is a promise the
database cannot keep. It is also the single most dangerous piece of application code in the phase.
Both of its layers look correct in review and both pass every time you test with an artist account,
which is exactly how a lockout ships. Research corrected the original framing here: middleware's
protection check tests only whether someone is signed in and does not check their role, so a signed-in
Client Partner who navigates directly to the vault DOES render the artist layout. The route group is
not a wall. The absent-profile-row branch is the real protection, and the only way to know it holds is
an automated assertion that the gate never fires for a staff or a buyer identity.
Output: a pure gate resolver with a four-case test, the blocking screen, and the layout mount.
</objective>

  <behavior>
    - `shouldGateForHandle({ user: null, profile: null })` is false — no session, nothing to ask
    - `shouldGateForHandle({ user: { id: 'staff-1' }, profile: null })` is false — a Team Member has no profile row
    - `shouldGateForHandle({ user: { id: 'buyer-1' }, profile: null })` is false — a Client Partner has no profile row
    - `shouldGateForHandle({ user: { id: 'u1' }, profile: { handle: 'maya-reyes' } })` is false
    - `shouldGateForHandle({ user: { id: 'u1' }, profile: { handle: null } })` is true
    - `shouldGateForHandle({ user: { id: 'u1' }, profile: { handle: '   ' } })` is true — a blank handle is not a handle
    - `resolveHandleGate` with a Team Member identity: returns null AND the injected `renderGate` callback was never called
    - `resolveHandleGate` with a Client Partner identity: returns null AND `renderGate` was never called
    - `resolveHandleGate` with a User Account that has a handle: returns null AND `renderGate` was never called
    - `resolveHandleGate` with a User Account that has a profile row and no handle: returns the callback's value AND `renderGate` was called exactly once with that user's id
    - `resolveHandleGate` with no user: returns null, `renderGate` never called, and `loadProfile` never called either
  </behavior>
  <action>
    Create `lib/handles/gate.ts` with two named exports and a section-header comment stating the rule in
    one sentence: the gate exists to collect a handle from someone who should have one, and an absent
    profile row means "not my business", never "block".

    `shouldGateForHandle(input: { user: { id: string } | null; profile: { handle: string | null } | null }): boolean`
    returns true only when there is a user AND `profile` is non-null AND its handle is null, empty, or
    whitespace. Write the profile-presence test as an explicit non-null check and comment that it is
    load-bearing: a Team Member's identity lives in the staff table and a Client Partner has no profile
    row at all, so `null` is the structural signal for "not a User Account". Anything that reduces this
    to a truthiness check on the user is the D-10 trap.

    `resolveHandleGate<T>(input: { user: { id: string } | null; loadProfile: (userId: string) => Promise<{ handle: string | null } | null>; renderGate: (userId: string) => T }): Promise<T | null>`
    short-circuits to null when there is no user (without calling `loadProfile`), otherwise loads the
    profile, applies `shouldGateForHandle`, and returns `renderGate(user.id)` only when it is true.
    Injecting both the loader and the renderer is what lets the test prove the gate is not merely
    "false" for staff and buyers but is genuinely never constructed for them.

    Write `lib/handles/gate.test.ts` in the shape of `lib/admin/gate.test.ts` — typed fixtures at the
    top, explicit per-identity assertions rather than a table. Build the staff and buyer fixtures from
    realistic identities so the test reads as the account model it is defending: a staff fixture carrying
    an `app_metadata.staff_roles` array with `loadProfile` resolving to null, and a buyer fixture carrying
    `app_metadata.role = 'buyer'` with `loadProfile` resolving to null. Use `jest.fn()` for `renderGate`
    and assert `not.toHaveBeenCalled()` for cases 1, 2 and 3, and `toHaveBeenCalledTimes(1)` with the
    right id for case 4.

    Add a comment above the staff and buyer cases recording WHY they are the load-bearing ones: an artist
    account passes every version of this code including the broken one, so a test that only exercises an
    artist proves nothing. Add a second comment recording that the buyer case is a reachable path, not
    defence in depth — the middleware protection check tests only for a signed-in user, so a buyer can
    navigate directly to the vault and render this layout.
  </action>
