  <files>supabase/migrations/134_handle_format_and_backfill.sql, __tests__/migration-134.test.ts</files>
  <action>
    Create `supabase/migrations/134_handle_format_and_backfill.sql` following migration 133's header
    conventions, including the standing human-gated line.

    **Section 1 — fixture sweep.** A single guarded update assigning a deterministic value to any row
    that still has no handle:
    `UPDATE public.user_profiles SET handle = 'user-' || left(replace(id::text, '-', ''), 12) WHERE handle IS NULL;`

    Comment it precisely. This is NOT a general backfill and it is NOT the owner's "prompt, never
    auto-generate" rule being quietly reversed. By the time this migration runs, plan 06's gate has been
    collecting handles from real humans for the whole phase, and the owner has confirmed at this plan's
    checkpoint that every remaining NULL belongs to a test or demo fixture — the demo account, the EPK
    and drop test accounts, and the codex test rows named in CONTEXT.md's D-09. The generated value is
    derived from the row's own primary key so it cannot collide, and it satisfies the format rule below
    (five letters, one internal hyphen, twelve hex characters, seventeen total). It will not collide with
    the reserved list either.

    **Section 2 — format constraint.**
    `ALTER TABLE public.user_profiles ADD CONSTRAINT user_profiles_handle_format_chk CHECK (handle IS NULL OR (handle ~ '<pattern>' AND length(handle) BETWEEN 3 AND 30));`

    Open `lib/handles/validate.ts` and copy its pattern character for character into `<pattern>`, and use
    its two length constants as the literal bounds. If the application rule and the database rule differ
    by even one character, one of them will accept a handle the other rejects and the disagreement will
    surface as a confusing 400 much later. PostgreSQL's advanced regular expressions support
    non-capturing groups, so the pattern transfers directly; if the push rejects it, that is a clear,
    immediate error and the human gate is where it gets caught.

    Keep the `handle IS NULL OR` disjunct even though it looks redundant after the sweep. A CHECK
    constraint is satisfied by NULL anyway, and writing it explicitly makes the statement safe to run
    before, after, or independently of any NOT NULL decision, and re-runnable.

    **Do NOT add `ALTER COLUMN handle SET NOT NULL` to this file.** Task 2 explains why and puts the
    decision where it belongs.

    End with `NOTIFY pgrst, 'reload schema';`.

    Write `__tests__/migration-134.test.ts` asserting: the sweep is scoped to rows with no handle and
    derives its value from the row's own id; the constraint exists with the NULL-tolerant disjunct and
    the length bounds; the SQL pattern string, read out of the migration, is IDENTICAL to the pattern
    read out of `lib/handles/validate.ts` with its regex delimiters stripped — read both files and
    compare, rather than hardcoding the pattern in the test, so the two can never drift; the file
    contains no NOT NULL alteration of the handle column; the header carries the human-gated line; and
    the file ends with the schema reload.
  </action>

  <context>
    D-13 is a locked owner decision: NOT NULL is the only true database-level guarantee, sequence it last
    once the gate has drained the handle-less accounts. The draining part is done. But the constraint as
    written cannot be applied without breaking production, for a reason that has nothing to do with the
    backfill, and the planner has no authority to quietly drop a locked decision.

    Reading migration 105's live `handle_new_user()` alongside `lib/accounts/provisionIntent.ts` makes it
    concrete. On this Supabase instance `app_metadata` is NOT visible to the trigger at INSERT — that is
    the finding from the Phase 27 cutover diagnostic that cost two failed cutovers. Consequently the
    curator, buyer, staff and industry branches, all of which read `raw_app_meta_data`, cannot fire at
    INSERT. Every account creation path on this instance therefore falls through to the default branch,
    and the helper that provisioned the account deletes or updates the row afterwards. Only a self-serve
    artist signup carries a handle in `user_metadata`.

    That means a NOT NULL column would reject the profile insert for:
    - buyer provisioning
    - staff provisioning
    - industry provisioning (which is also how curators are created, per D-01)
    - the D-15 collision fallback — whose entire purpose is to insert a row with no handle so a lost race
      costs a handle rather than an account. A NOT NULL violation raised inside that exception handler
      propagates, aborts the trigger, and rolls back the signup: exactly the failure D-15 was written to
      eliminate, reintroduced through a different door.

    There is also a third locked decision in the way. D-10b fixes the gate's condition as a plain
    "profile row exists and has no handle" test, so a placeholder-handle scheme — the usual way to satisfy
    NOT NULL — would require changing a decision that plan 06 spent an entire test suite defending.

    Worth stating plainly: a NULL handle is not a corrupt state in this system. It means "a User Account
    exists and has not chosen a handle yet", which is precisely the state D-09's gate exists to resolve,
    and which the gate now resolves on the person's very next page load. The durable guarantees that
    actually shipped this phase are the lowered unique index (uniqueness), migration 133's trigger
    (reserved and retired names, on both write paths), and migration 134's format constraint.
