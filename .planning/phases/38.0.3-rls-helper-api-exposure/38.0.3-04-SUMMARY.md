# Phase 38.0.3 Plan 04: Decouple placement activation from the `no_block` RPC — Summary

**The Green Room placement activation gate now reads `public.blocks` directly with the service client instead of calling the `no_block` RPC over PostgREST, removing the application's last dependency on that route so plan 05 can relocate the function out of the exposed schema — behaviour-neutral today, independently deployable, and fail-closed on error.**

## Performance

- **Duration:** 26 min
- **Started:** 2026-09-09T19:51Z (approx)
- **Completed:** 2026-09-09T20:17Z
- **Tasks:** 2 of 2
- **Files modified:** 5 (1 source, 1 test created, 3 tests updated)

## Accomplishments

- **Removed the RPC dependency.** `checkViewerBlock` no longer issues `service.rpc('no_block', …)`. `grep -rn "rpc('no_block'" app lib components` returns nothing. Because `.rpc()` is an HTTP request routed by PostgREST against the schemas in its `db-schemas` config, a function in an unexposed schema has no route at all regardless of who holds EXECUTE — routing and privilege are different questions, and the INVENTORY's "relocatable" note answered only the second one.
- **Preserved every behaviour of the gate.** Bidirectional (a block in either direction hides the destination, matching `no_block`'s symmetric definition in migration 035), fail-closed on error, no query at all for an anonymous or self viewer, and a bounded single-pair lookup. `isDestinationVisible` and all five of its call sites are untouched.
- **Kept the 13-03 audit guard alive.** The content pin that text-locked the RPC call was re-pointed at the security property rather than deleted, and now also asserts that no `rpc('no_block'` remains.
- **Turned the relocation precondition into a test.** Assertion (d) of `rls-helper-callsites.test.ts` now proves `no_block` has zero application `.rpc()` call sites — which is exactly what plan 05 needs to be true before it moves the function.

## The one real risk, and how it was handled

The fail-closed requirement was the failure mode most likely to be introduced silently. The obvious refactor is to reuse `loadBlockedIds` from `lib/green-room/discover.ts`, but that helper destructures only `data` and discards `error`, so a database error would yield an empty block set and return `true` — flipping a security gate from fail-closed to fail-open with no visible symptom.

Per the orchestrator's instruction, this was proven rather than asserted:

1. The error-case test was written first and run against the unchanged RPC implementation. **RED** (5 of 7 failed; the 2 that passed were the early-return cases, which never reach the RPC).
2. A **deliberately fail-open** implementation was then written — identical to the final one except `if (error) return true`.
3. Result: **exactly one test failed** — `FAILS CLOSED: a query error hides the destination` — with the other 6 green. The guard fires, and it fires precisely on the mutation it exists to catch.
4. Only then was `if (error) return false` written.

`loadBlockedIds` was neither reused nor modified.

## Review finding — a fail-open security regression, found AFTER this plan was marked complete

This is recorded as it happened. The plan shipped with a defect; review caught it; a follow-up fix closed it. Nothing below has been rewritten to look like it went right the first time.

### What was wrong

`checkViewerBlock`'s first parameter was **named** `service`. On the only path that actually reaches its query, it receives a **user-scoped, RLS-bound** client:

```
app/api/green-room/feed/route.ts:20   const supabase = await createApiClient()   // createRouteHandlerClient — cookie session, RLS APPLIES
  -> loadGreenRoomFeed(supabase, user.id, ...)          lib/green-room/feed-query.ts:181
  -> loadPlacementCards(supabase, viewerId, tab)        feed-query.ts:341
  -> filterVisiblePlacementRows(supabase, viewerId, …)  feed-query.ts:362
  -> isDestinationVisible(supabase, …, viewerId)        feed-query.ts:387
  -> checkViewerBlock(supabase, viewerId, ownerId)      placements-admin.ts
```

`supabase/migrations/035_connections_blocks.sql:103`:

```sql
-- A member sees ONLY their own blocklist, never who blocked them
-- (T-08-03: enumeration of "who blocked me" is an information-disclosure risk)
CREATE POLICY "blocks_select_own" ON blocks FOR SELECT
  USING (blocker_id = auth.uid());
```

Of the two `.or()` disjuncts:

| Disjunct | Under `blocks_select_own` on a user-scoped client |
|---|---|
| `blocker_id=viewer AND blocked_id=owner` | visible — works |
| `blocker_id=owner AND blocked_id=viewer` | **hidden by RLS — always returns nothing** |

Zero rows → `length === 0` → `true` → **the placement is shown to the person the owner blocked.** Fail open, in the direction that matters.

The RPC form this plan removed did **not** have the bug. `no_block` is `SECURITY DEFINER` with `GRANT EXECUTE ... TO authenticated` (035:147) precisely so a user-scoped caller gets a bidirectional answer without being able to read the rows. Replacing the *query* while dropping the *privilege* is what broke it.

Scope: only the Green Room feed path was affected. The two admin routes (`app/api/admin/green-room/placements/route.ts:40`, `[id]/route.ts:60`) pass no `viewerId`, so `checkViewerBlock` early-returns before querying.

### Why this plan's tests could not catch it

**Every test in this repo's suite mocks the Supabase client, and a mock has no RLS.** The plan's block-check battery was mutation-tested and each assertion was proven to fail against a broken implementation — but every mutation it tested was a mutation of the *query*, and the defect was in the *privilege of the connection issuing it*. No amount of behaviour mocking on a single client reproduces a policy that filters rows server-side. This is a known limitation of the suite, not a failure of the mutation testing.

It is also worth naming the proximate cause plainly: **the parameter name lied.** `service` in the signature is what made "this runs with the service role" read as true at every call site, in review, and in the tests.

### How it was closed

- `checkViewerBlock` now obtains a client from `createServiceClient()` (`@/lib/supabase/server`) and issues the `blocks` read on that. Service role bypasses RLS — the privilege equivalent of the SECURITY DEFINER function it replaced. This does not widen disclosure: the helper takes one specific `(viewer, owner)` pair and returns a boolean, so no row content escapes and the T-08-03 enumeration oracle is not reinstated.
- The client is **memoized at module scope**, created lazily on first use. `filterVisiblePlacementRows` calls `isDestinationVisible` for every row via `Promise.all`; a per-call `createClient` would build one client per placement per feed request.
- `isDestinationVisible`'s `is_public` / `status` / `active` reads **still use the caller's client** — deliberately unchanged. There, RLS hiding a destination row correctly resolves to "not visible", which fails closed.
- The parameter is renamed `service` → `client` in **both** `checkViewerBlock` and `isDestinationVisible`, with comments stating that callers pass a user-scoped client and that the block read therefore must not use it. The `client` parameter is retained in `checkViewerBlock`'s signature (unused, `void client`) so the hazard stays visible at the call site rather than disappearing.
- Both early returns and the `if (error) return false` fail-closed branch are unchanged. A new fail-closed branch covers an unconstructable service client (`SUPABASE_SERVICE_ROLE_KEY` unset makes `createClient` throw synchronously) — it returns `false` rather than letting the exception escape and 500 the whole feed request.

## The final implementation

```typescript
// Memoized service-role client, created lazily on first block check.
//
// filterVisiblePlacementRows fans isDestinationVisible out across every
// placement row with Promise.all, so constructing a client per call would
// build one per placement per feed request. One module-scoped instance is
// enough: it is stateless and holds no session (persistSession: false).
let blockReadClient: SupabaseClient | null = null

function getBlockReadClient(): SupabaseClient | null {
  if (blockReadClient) return blockReadClient
  try {
    blockReadClient = createServiceClient()
  } catch {
    // SUPABASE_SERVICE_ROLE_KEY (or the URL) unset — createClient throws
    // synchronously. Return null so the caller FAILS CLOSED rather than
    // throwing out of the whole feed request.
    return null
  }
  return blockReadClient
}

// Bidirectional block gate for a placement destination.
//
// This used to call the `no_block` SECURITY DEFINER RPC. It now reads
// `public.blocks` directly WITH THE SERVICE ROLE. Three things to know, and
// all three matter:
//
//   1. Routing. Owner decision D4 relocates `no_block` out of the
//      PostgREST-exposed schema, because an exposed symmetric helper is an
//      oracle answering "did X block me?" for any pair — threat T-08-03,
//      which migration 035 closed at the table level. PostgREST introspects
//      and routes only to the schemas in its `db-schemas` config, so once
//      the function moves there is no RPC route at all, whatever EXECUTE
//      grants `service_role` holds. Routing and privilege are different
//      questions.
//   2. Why the passed-in `client` MUST NOT be used for this read. Callers
//      pass a user-scoped, RLS-bound client on the only path that reaches
//      this query (the Green Room feed). Policy `blocks_select_own`
//      (migration 035) restricts SELECT to `blocker_id = auth.uid()`, so
//      under RLS the "OWNER blocked the VIEWER" disjunct below returns
//      NOTHING — the query silently degrades to zero rows and the gate
//      FAILS OPEN toward exactly the person the owner blocked. This was a
//      real regression, caught in review of 38.0.3 plan 04. The service
//      role bypasses RLS and is the privilege equivalent of the
//      SECURITY DEFINER function it replaced.
//   3. Why bypassing RLS here does not widen disclosure. The helper takes
//      one specific (viewer, owner) pair and returns a boolean. No row
//      content leaves this function, so it is not the T-08-03 enumeration
//      oracle the table policy exists to prevent.
//
// The check is FAIL-CLOSED on error, deliberately, matching the RPC form.
// Do NOT reuse `loadBlockedIds` from lib/green-room/discover.ts: it
// discards its `error` and would flip this gate fail-open.
async function checkViewerBlock(
  client: SupabaseClient,
  viewerId: string | undefined,
  ownerId: string
): Promise<boolean> {
  // `client` is intentionally unused — see reason 2 above. It stays in the
  // signature to make it explicit at every call site that the caller's
  // client is the wrong instrument for this particular read.
  void client

  if (!viewerId || viewerId === ownerId) return true

  const service = getBlockReadClient()
  if (!service) return false

  const { data, error } = await service
    .from('blocks')
    .select('blocker_id')
    .or(
      `and(blocker_id.eq.${viewerId},blocked_id.eq.${ownerId}),` +
        `and(blocker_id.eq.${ownerId},blocked_id.eq.${viewerId})`
    )
    .limit(1)

  // FAIL CLOSED. The RPC form returned false on error and that must not
  // regress — a database hiccup hides the destination rather than surfacing
  // a blocked party's content.
  if (error) return false
  return ((data as unknown[] | null) ?? []).length === 0
}
```

## Notes for Future Phases

- **Plan 05** may now relocate `no_block` out of the PostgREST-exposed schema. The application-side precondition is met and tested. Note that `no_block` is still referenced by RLS *policies* inside the database (migrations 038, 044, 059, 060) — those are policy call sites, not HTTP routes, and are unaffected by relocation, but they do mean EXECUTE grants still matter for the querying role.
- **`loadBlockedIds` remains fail-open** in `lib/green-room/discover.ts`. It was deliberately left alone here (four callers, differing error tolerances), but it is worth an explicit decision in a later plan: `lib/trust-safety/block-check.ts` and `lib/deals/catalog-query.ts` both consume it in contexts where a swallowed error means a blocked party's content becomes visible.
- **A direct read replacing a SECURITY DEFINER function must inherit its PRIVILEGE, not just its query.** This is the single most transferable lesson from this plan, and it cost a fail-open security bug to learn. Plans 05 and 06 will remove or relocate more helpers; for each one, ask separately: (a) what does this function compute, and (b) *what can it see that its caller cannot?* SECURITY DEFINER exists to answer (b). Any replacement that ignores (b) fails silently under RLS rather than erroring.
- **Audit every helper whose client parameter is named `service`.** The name is load-bearing in review and it lied here. Worth a `grep -rn "service: SupabaseClient" lib/` pass in a later plan to see whether any other helper reached from more than one call site has the same latent mismatch.

It reinforces the existing memory note about production behavioural verification: for anything where a POLICY determines correctness, a text/mock test is not evidence. Two mitigations are available today and both are used above — encode the policy into the test double, and assert structurally which client issued which query.
- **Test-double coupling is a recurring planning blind spot in this phase.** When a plan removes a call, the `files_modified` list should be derived from `grep` over test mocks as well as over source.
