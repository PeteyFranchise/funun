# Phase 38.0.3 Plan 04: Decouple placement activation from the `no_block` RPC — Summary

**The Green Room placement activation gate now reads `public.blocks` directly with the service client instead of calling the `no_block` RPC over PostgREST, removing the application's last dependency on that route so plan 05 can relocate the function out of the exposed schema — behaviour-neutral today, independently deployable, and fail-closed on error.**

## Performance

- **Duration:** 26 min
- **Started:** 2026-09-09T19:51Z (approx)
- **Completed:** 2026-09-09T20:17Z
- **Tasks:** 2 of 2
- **Files modified:** 5 (1 source, 1 test created, 3 tests updated)

## Accomplishments

- **Removed the RPC dependency.** `checkViewerBlock` no longer issues `service.rpc('no_block', …)`. `grep -rn "rpc('no_block'" app lib components` returns nothing. Because `.rpc()` is an HTTP request routed by PostgREST against the schemas in its `db-schemas` config, a function in an unexposed schema has no route at all regardless of who holds EXECUTE — routing and privilege are different questions, and the INVENTORY's "relocatable" note answered only the second one.
- **Preserved every behaviour of the gate.** Bidirectional (a block in either direction hides the destination, matching `no_block`'s symmetric definition in migration 035), fail-closed on error, no query at all for an anonymous or self viewer, and a bounded single-pair lookup. `isDestinationVisible` and all five of its call sites are untouched.
- **Kept the 13-03 audit guard alive.** The content pin that text-locked the RPC call was re-pointed at the security property rather than deleted, and now also asserts that no `rpc('no_block'` remains.
- **Turned the relocation precondition into a test.** Assertion (d) of `rls-helper-callsites.test.ts` now proves `no_block` has zero application `.rpc()` call sites — which is exactly what plan 05 needs to be true before it moves the function.

## The one real risk, and how it was handled

The fail-closed requirement was the failure mode most likely to be introduced silently. The obvious refactor is to reuse `loadBlockedIds` from `lib/green-room/discover.ts`, but that helper destructures only `data` and discards `error`, so a database error would yield an empty block set and return `true` — flipping a security gate from fail-closed to fail-open with no visible symptom.

Per the orchestrator's instruction, this was proven rather than asserted:

1. The error-case test was written first and run against the unchanged RPC implementation. **RED** (5 of 7 failed; the 2 that passed were the early-return cases, which never reach the RPC).
2. A **deliberately fail-open** implementation was then written — identical to the final one except `if (error) return true`.
3. Result: **exactly one test failed** — `FAILS CLOSED: a query error hides the destination` — with the other 6 green. The guard fires, and it fires precisely on the mutation it exists to catch.
4. Only then was `if (error) return false` written.

`loadBlockedIds` was neither reused nor modified.

**Mutation 4 detail, as the plan asked to be recorded.** It failed on the *no-query* assertion, not on a wrong boolean:

```
expect(received).not.toContain(expected) // indexOf
Expected value: not "blocks"
Received array:     ["user_profiles", "blocks"]
```

This matters. Against a mock builder there is no uuid validation, so the query "succeeds" and the boolean stays correct — the real production failure mode (`invalid input syntax for type uuid`, the pitfall recorded in `lib/deals/catalog-query.test.ts`) is unreproducible in a unit test. The test therefore pins the *precondition* — that no query is issued at all for an anonymous viewer — which is the correct proxy and the thing that actually prevents the production error. A test asserting only the returned boolean would have passed here and been unfit for purpose.

**Mutation 5 confirms the tests are not merely boolean-checking.** The recorded-arguments assertion is what catches a query filtering on the wrong pair.

## Deviations from Plan

### 1. [Rule 3 - Blocking] Three test files beyond `files_modified` were mechanically coupled to the RPC removal

**Found during:** Task 1 (one file) and post-task full-suite verification (two more).

**Issue:** The plan's `files_modified` listed three files, and the orchestrator restated that as a hard constraint. But five test files — not two — expressed "this viewer is blocked" by mocking `service.rpc` to return `false`, or supplied a query-builder mock without `.or()`/`.limit()`. Removing the RPC made those mocks structurally unable to express the condition they were testing. The plan's own `<verify>` block for Task 1 names `__tests__/green-room-placements-admin.test.ts` and expects it green, and the plan's `<verification>` block requires `npm test` to exit 0, so leaving them red would have failed the plan's own definition of done.

This is a planning gap, not a design problem: the planner traced the source dependency but not the test-double dependency.

## The final implementation

```typescript
async function checkViewerBlock(
  service: SupabaseClient,
  viewerId: string | undefined,
  ownerId: string
): Promise<boolean> {
  if (!viewerId || viewerId === ownerId) return true

  const { data, error } = await service
    .from('blocks')
    .select('blocker_id')
    .or(
      `and(blocker_id.eq.${viewerId},blocked_id.eq.${ownerId}),` +
        `and(blocker_id.eq.${ownerId},blocked_id.eq.${viewerId})`
    )
    .limit(1)

  // FAIL CLOSED. The RPC form returned false on error and that must not
  // regress — a database hiccup hides the destination rather than surfacing
  // a blocked party's content.
  if (error) return false
  return ((data as unknown[] | null) ?? []).length === 0
}
```
