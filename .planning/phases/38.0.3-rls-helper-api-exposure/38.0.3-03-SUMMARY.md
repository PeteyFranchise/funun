## THE `pg_policies` EXPECTATION IS GENERATED, AND THAT IS CHECKABLE

A hand-typed list only proves somebody typed it. The 44 tuples in Part A's
`repo_pol` CTE were produced by **the wave-1 parser itself** —
`__tests__/rls-helper-callsites.test.ts` — via a temporary reporting `describe`
appended to that file, run once, then removed. The test was restored and
verified **byte-identical to `HEAD`** (`diff` clean, SHA256
`4a5fc1fe…`), and the generator script lives in the session scratchpad and is
**not committed**.

Two things were added on top of the parser's own output, both operating on the
parser's results rather than replacing them:

1. **A DROP POLICY fold.** Statements are replayed in filename order and, within
   a file, in character-offset order; `CREATE`/`ALTER POLICY` sets the
   authoritative text for `(table, policy)`, `DROP POLICY` removes it. The
   expectation is therefore the **final** state of the corpus, not every policy
   ever written. Without it, superseded policies would read as `MISSING` and
   bury a real finding in noise.
2. **Case-insensitive joining** on table and policy name, so a policy created
   with an unquoted (folded) identifier still matches.

**The corroboration worth recording:** the fold produces exactly **11 live
`no_block` policy sites** — which is plan-check's own independently-derived
number, and *not* the 15 that owner decision D4 quoted loosely (15 is the
pre-fold historical count that the wave-1 test locks as `> 0`). Two parsers
written from different starting points agreeing on a non-obvious number is the
only reason to believe either. Totals: **208 live policies, 44 of them naming an
in-scope helper, across 48 call sites.**

Tier 1 contributes **zero** tuples, deliberately — that zero is the entire
justification for migration 208 — so any Tier-1 name appearing in production's
policy set lands in `UNEXPECTED` and fails loudly.

### M3 — the one that did not go red, reported as such

The plan's mutation 3 says removing one `RESET ROLE` "MUST drop the printed
count below the number of role-changing assertions." **It does not.** The count
goes 28 → 27, and there are **13** role-changing blocks, so 27 is still
comfortably above the threshold. The reason is that the file is *deliberately*
redundant: every role-changing block carries `RESET ROLE` on **both** the
success path and the exception path, which is the actual safety property. A raw
count cannot distinguish "28 because both paths are covered thirteen times" from
"28 because one block has three and another has none."

So the guard was replaced rather than the result massaged. The structural audit
parses the `DO` block, pairs `BEGIN`/`END;`, and for every sub-block containing
`SET LOCAL ROLE` asserts a `RESET ROLE` in **both** the pre-`EXCEPTION` segment
and the handler segment. Clean run: `13 role-changing blocks, 0 offenders`.
Under M3b it names the offending block by line. **The `grep -c 'RESET ROLE'`
number in the plan's verify command is a weak guard and should be read as one.**

### M6 — converted from "by inspection" to a mechanical result

The plan's items 5 and 6 say to confirm by inspection "since the query cannot be
run." That is true of the *SQL*, but item 6's assertion is a **regex applied to
a function definition**, and migration 209's real bodies are on disk. So the
exact Part A regex — `(?<![A-Za-z0-9_])<ident> = \(SELECT auth\.uid\(\)\)`,
Postgres `\m` emulated as a zero-width negative lookbehind — was run against all
thirteen extracted bodies:

```
bodies parsed: 13   functions failing their own ident check: 0
M6 mutated table (p_uid) against the CORRECT body           : False   <- goes red on a correct function
M6 mutated table (p_uid) against a WRONGLY-bound body        : True    <- would report PASS on a broken function
correct table  (p_viewer) against that wrongly-bound body    : False   <- the correct table catches it
substring hazard: naive containment of "uid = (SELECT auth.uid())" in a p_uid-bound body: True
                  word-boundary regex with ident="uid" on that same body                : False
```

**The per-function parameter table is the assertion's load-bearing input**, and
Part A's `tier2` CTE carries a comment saying exactly that. The last two lines
are the behavioural counterpart of wave 2's mutation 2 finding — `uid` is a
substring of `p_uid`, and only the word-boundary anchor is not fooled.
