## 1. `resolve_profile_by_handle(TEXT)` — FINDING, no action this phase

**Evidence:** `supabase/migrations/133_handle_identity.sql:388-415`.

**What it is.** `RETURNS TABLE (profile_id UUID, current_handle TEXT,
redirected BOOLEAN)`, `LANGUAGE plpgsql STABLE SECURITY DEFINER SET
search_path = ''`. It lowercases a handle, looks for a live match in
`public.user_profiles`, and if there is none falls back to
`public.handle_history` for the D-07 retired-handle redirect. It returns at
most one row; zero rows means 404.

**Nothing to bind.** It takes ONE parameter, `p_handle TEXT`. There is no
caller-supplied identity argument, so the Tier-2 remedy this phase applies
to thirteen other helpers is not even expressible here. It is structurally
outside the bind/relocate/revoke taxonomy.

**Its `anon` grant is deliberate, not a default-privilege accident.** Line 415
is an explicit `GRANT EXECUTE ... TO anon, authenticated, service_role`,
preceded by `REVOKE ALL ... FROM PUBLIC`. That distinguishes it from every
other function in this phase, all of which were exposed by Supabase's *default*
grants that a `FROM PUBLIC`-only revoke never touched. `/u/<handle>` is a
public route that must resolve without a session; removing `anon` breaks
public profile pages. Migration 133's own header states the reasoning at
length — PostgREST cannot express `lower(col) = lower($1)`, and the
pattern-match alternative makes `_` both a legal handle character and a
wildcard, so `/u/a_c` would silently resolve to `@abc`.

**What it discloses.** A handle-to-`profile_id` mapping, *including for
profiles that are not public*, plus whether a handle is retired and what it
redirects to. It applies no `is_public` filter and no block check.

**Weighed against:** handles are public identifiers by construction. `/u/<handle>`
is a public URL; the resolver returns only an opaque uuid and the canonical
handle. The page itself still applies `is_public` and bidirectional-block
checks before rendering anything, and `handle_history` remains fully revoked
from `anon` and `authenticated` — the caller learns a profile id, never a
history row.

**Recommendation (owner's call, NOT work this phase performs):** leave the
`anon` grant in place. The residual is a **handle-enumeration oracle**: an
attacker can confirm that a given handle is taken and obtain its `profile_id`
even when the profile is private. That is a rate-limiting concern, not a
privilege concern, and it is the same fact `/api/handles/available` already
exposes by design. If it is ever tightened, the right remedy is a rate limit
on the resolver, not a revoke.

## 2. The two REVIEW functions that dropped out of scope

`38.0.3-INVENTORY.md` listed five REVIEW functions; three are handled by
migration 208, and two dropped out. Recording the evidence so the drop-out is
auditable:

| Function | In `38.0.3-LIVE-EXPOSED.txt`? | Conclusion |
|---|---|---|
| `transfer_vault_project_custody` | **absent** | `anon`/`authenticated` cannot reach it in production |
| `calculate_vault_readiness` | **absent** | same |

`38.0.3-LIVE-EXPOSED.txt` is the 53-row list of functions actually reachable by
`anon` or `authenticated` in production. Neither name appears in it.

### CORRECTION to the INVENTORY — the repo is NOT silent

`38.0.3-INVENTORY.md` records the repo grants for both of these as
**"(none stated)"**, and plan 01's Task 3 repeats that
`transfer_vault_project_custody` "has no grant statement in any migration".
**Both statements are wrong.** Explicit revokes exist:

- `supabase/migrations/190_vault_projects_user_id_immutable.sql:166-167` —
  `REVOKE EXECUTE ON FUNCTION public.transfer_vault_project_custody(UUID, UUID, UUID)`
  `FROM PUBLIC, anon, authenticated;`
- `supabase/migrations/070_readiness_definer_privilege_sweep.sql:206` —
  `REVOKE EXECUTE ON FUNCTION public.calculate_vault_readiness(uuid) FROM PUBLIC, anon, authenticated;`
  with the comment "Revoke, no re-grant."

Migration 190's statement is **wrapped across two lines** — the `FROM` clause
sits on line 167. That is almost certainly why the inventory's single-line
grant regex missed it. It is a third defect in the same family as the two the
INVENTORY already documents (trailing modifiers after the body; a comment
inverting the grant posture), and it is worth recording because it failed in
the *safe* direction this time — reporting a locked-down function as
ungoverned — whereas the comment defect failed in the dangerous one.

**Net effect: none.** Both functions are correctly locked down in the repo AND
in production, and the repo and the live database agree. **No migration in this
phase issues a statement for either.** Plan 03's Part A should still report
their live grant rows so the corrected record is evidenced rather than inferred
from this note.

## 3. HAZARD for plan 03's Part A — `public.zz_verify_b_results`

Phases 38.0.1 and 38.0.2 created a results table `public.zz_verify_b_results`
in production for their behavioural harnesses **and left it there**.

A table in `public` with no RLS is a PostgREST-exposed table, readable and
possibly writable by `anon` — the same class of default-exposure defect this
phase exists to close, created by this phase's own predecessor.

**Required of plan 03's Part A:** report whether the table still exists, and
whether RLS is enabled on it.

**Do NOT attempt to drop it from a migration in this phase.** It is the
owner's to remove, and the drop is already tracked at
`.planning/todos/pending/2026-09-08-drop-zz-verify-b-results-public-table.md`
so it does not close silently with the phase. 38.0.3's own harnesses use
`TEMP` tables (plans 03 and 06 both assert this).
