## G3 was my assertion, not the database

The gate located the function with

```sql
AND pg_get_function_identity_arguments(p.oid) = 'uuid, uuid'
```

`pg_get_function_identity_arguments` **keeps parameter names**. Production
returns `a uuid, b uuid` (length 14), so the equality failed on a function that
is present and healthy. A follow-up diagnostic over every schema returned one
row, and every attribute matches migration 035:

| attribute | live value |
|-----------|-----------|
| schema.name | `public.no_block` |
| identity args | `a uuid, b uuid` |
| `prosecdef` | true |
| `provolatile` | `s` |
| `proconfig` | `search_path=""` |
| `anon` EXECUTE | false |
| `authenticated` EXECUTE | **true** |

That last row is the live confirmation of the exposure Tier 3 closes: any
logged-in user can execute the symmetric block oracle today.

**This is the third instance of the same failure shape in this phase** — the
twelve false `search_path` FAILs in 38.0.2 Part A, the `%public.%` pattern that
matched `graphql_public.`, and now this. Every one was a hand-written predicate
compared against a rendering the author assumed rather than checked. The lesson
is the same each time: **resolve objects by identity, not by string equality on
a rendered form.**

The plan-05 agent's own gate, quoted in `38.0.3-05-SUMMARY.md`, does not have
this defect — it uses `to_regprocedure('public.no_block(uuid,uuid)')`, which
resolves by type signature and is immune to how names and spacing render. That
is the form to reuse.
