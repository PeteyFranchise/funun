# Phase 38.0.3 — RLS Helper API Exposure

## How this was found

A production sweep of `SECURITY DEFINER` functions in `public`, run 2026-09-08
while applying migration 200, returned **100+ rows** and showed that `anon` and
`authenticated` hold `EXECUTE` on a large set of functions that were never
designed to be called by a client.

The trigger was `apply_to_opportunity_atomic`: migration 047 revoked it `FROM
PUBLIC`, but Supabase grants `anon`/`authenticated` **directly**, and a
PUBLIC-only revoke does not remove a direct grant. That single function is
handled separately (migration 200 + an immediate owner-run REVOKE) because it
is the **only** exposed helper that performs writes. This phase is everything
else.

## What is actually wrong

PostgREST exposes any function in `public` that the requesting role can
execute. So ~18 read-only authorization predicates are live RPC endpoints:

```
custody_transfer_visible          workspace_agreement_evidence_visible
green_room_can_view_post          workspace_attachment_visible
green_room_post_matches_custom_audience   workspace_audit_visible
is_green_room_eligible            workspace_grant_lineage_live
is_split_sheet_initiator          workspace_grant_visible_to_member
is_split_sheet_party              workspace_member_role
is_workspace_owner                workspace_project_permission
no_block                          workspace_roster_relationship_is_live
ownership_transfer_visible        is_project_owner / is_work_owner /
                                  project_member_role / work_member_tier
```

**None of them write** — verified by reading every body. The exposure is
**information disclosure of the authorization graph**: anyone holding the
public anon key can ask *"what role does user X have in workspace Y", "did A
block B", "can viewer V see post P", "is user U a party to split sheet S"*.

Migration 185's own comment already stated the intent —
*"Intended for RLS policy USING clauses wrapped as (SELECT ...), not a
client-invoked RPC."* The intent was right. Nothing enforced it.

## THE TRAP — do not blanket-revoke

**Revoking `EXECUTE` from `authenticated` would take large parts of the app
down.** RLS policy expressions are evaluated **as the querying role**, and these
helpers are called from inside policy `USING` clauses. Migration 197 line 1258:

```sql
OR (SELECT public.workspace_member_role(workspace_id, auth.uid())) IN ('owner', 'admin')
```

Revoke that grant and every policy calling it fails with permission denied —
breaking reads on `workspace_audit_log`, `workspace_roster_relationships`,
split sheets, the Green Room feed, and blocks.

Any plan that opens with "REVOKE from anon, authenticated" is wrong and must be
rejected at plan-check.

## Two remedies, not one

The scoping insight: these helpers split into two groups with **different**
correct fixes.

### Group A — pure policy helpers → relocate to a non-exposed schema

Never called by application code. Move to a `private` schema; grant `USAGE` +
`EXECUTE` to `anon`/`authenticated` so policies still work, but PostgREST never
exposes them (it only introspects configured schemas, `public` by default).

This is the standard Supabase pattern and the structurally correct fix: the
endpoint stops existing rather than being guarded.

### Group B — helpers the app genuinely calls → bind `p_uid` to `auth.uid()`

Four are called from application code. **Two of them use a user-scoped client
and cannot be relocated without breaking features:**

| Helper | Call site | Client | Consequence |
|---|---|---|---|
| `green_room_can_view_post` | `lib/trust-safety/reports.ts:179` | `service` | relocatable |
| `no_block` | `lib/green-room/placements-admin.ts:353` | `service` | relocatable |
| **`is_work_owner`** | `lib/catalogue/access.ts:161` | **user-scoped** | **6 producer-handoff routes + the works page break** |
| **`work_member_tier`** | `lib/catalogue/access.ts:166` | **user-scoped** | same |

Both user-scoped call sites pass `p_uid: user.id` taken from `auth.getUser()`,
so binding `AND p_uid = (SELECT auth.uid())` inside the function is
behaviour-preserving for them and closes impersonation — exactly the fix
migrations 193/194 applied to the `workspace_read_*` family in 38.0.1.

**Every helper must be classified A or B before anything moves.** A helper
assumed to be Group A but actually called with a user-scoped client is a
production outage.

## Constraints

- **Migrations are HUMAN-GATED.** Numbers 201–202 belong to Codex's Playbook
  workstream; 203–204 to Phase 38.2. This phase claims from **205**.
- **No live-DB test harness exists.** Text-lock tests cannot prove any of this.
  A behavioural harness in the shape of 38.0.2's Part A + Part B is
  **mandatory**, not optional — see [[project-migration-behavioural-verification]].
- Policies must move in lockstep with their helpers, per table group, so no
  intermediate state has a policy calling a function that no longer exists.
- D-56 is OFF and workspace tables are empty, but **Green Room, split sheets,
  projects and works are LIVE with real user data.** Unlike 38.0.1/38.0.2, this
  phase cannot rely on empty tables for safety.

## Suggested staging

1. **Classify** all ~18 helpers A or B, evidenced by call-site grep, not
   assumption. Output is a table with a client type per call site.
2. **Group B first** — bind `p_uid` to `auth.uid()`. Small, independently
   valuable, no relocation risk.
3. **Create `private` schema** + grants; recreate Group A helpers there
   alongside the `public` ones. Nothing breaks; both exist.
4. **Rewrite policies** per table group to call `private.*`, in batches, each
   batch its own migration.
5. **Drop the `public.*` copies** only once a query proves nothing references
   them.
6. **Behavioural verification** after 2, 4 and 5.

## OWNER DECISIONS — 2026-09-08 (locked)

**D1. This phase BLOCKS BETA.** All of it ships before D-56 goes on. The owner
chose the full fix over a partial one, knowing it is the largest blast radius in
Phase 38 and touches live Green Room / split-sheet / works data. Plan
accordingly: no "ship the easy half" shortcuts, and the behavioural harness is
not optional.

**D2. `discover_profile_id_by_email` — CHECKED 2026-09-08, NO ACTION.** It was
already correct and is the model this phase should copy. Migration 149 revokes
`FROM PUBLIC, anon, authenticated` and grants only `authenticated` — naming the
roles explicitly, which is precisely what migration 047 omitted. Its body sets
`search_path = ''`, qualifies every reference, and uses `auth.uid()` DIRECTLY
rather than trusting a caller-supplied id. It returns only a profile that is
already public to the viewer, unblocked, and not themselves. Out of scope.

**D3. SCOPE IS EVERY FUNCTION OF THIS KIND**, not just the ~18 confirmed
authorization predicates. The full inventory of `SECURITY DEFINER` functions in
`public` must be enumerated and classified before planning. 97 migrations
contain definers; the live sweep returned 100+ rows and was truncated, so the
true count is not yet known.

### What D3 requires before this phase can be planned

1. A complete inventory of `SECURITY DEFINER` functions in `public` — from the
   migrations (what exists, what it does, whether it binds `auth.uid()`) AND
   from the live database (actual grants, which the repo does NOT reliably
   reflect — migration 047 is the proof).
2. Each classified: **A** relocate, **B** bind `p_uid`, **C** already correct
   (149's shape), **D** service-role only, already unreachable.
3. Call-site evidence per function — grep, not assumption. The
   `is_work_owner` / `work_member_tier` finding shows why: both are invoked
   with a USER-SCOPED client and would have broken six routes if relocated.
