call sites and its two SECURITY DEFINER-body callers, and drop the `public` copy under PostgreSQL's

> "A member sees ONLY their own blocklist, never who blocked them (T-08-03: enumeration of 'who
> blocked me' is an information-disclosure risk mitigated by restricting SELECT to

Binding would re-open a threat this repo deliberately closed. Owner decision D4 chose to keep it
closed. This is the one function in the whole phase that genuinely needs a schema move, and at 1
function × 11 policies it is a tractable, bounded piece of work — not the 17 × 73 the SCOPE feared.

## What relocation does and does not buy — state it honestly in the migration header

- PostgREST introspects and routes to only the schemas in its `db-schemas` configuration. A function
  outside that set has **no RPC route**; a request naming an unlisted schema fails with `PGRST106`.
  That is a real control, not obscurity: it is not a matter of guessing a name.
- It does **not** remove a privilege. For a policy on a `public` table to call a helper in another
  schema, the querying role must hold `USAGE` on that schema and `EXECUTE` on the function. So
  `authenticated` retains EXECUTE — it simply has no HTTP route to reach it.
- It is a **configuration** boundary, not a privilege boundary, and it is one dashboard toggle away
  from being undone. The migration itself writes the first half of Supabase's own "how to expose a
  custom schema" recipe. Say so in the header so nobody later completes the recipe by accident.

## The hazard that follows you into the new schema

PostgreSQL grants `EXECUTE` to `PUBLIC` by default on **every** function it creates, in every schema.
The moment `USAGE` on the new schema is granted to `authenticated`, every function in it becomes
executable by `authenticated` through that default — exactly as in `public`. This is a confirmed,
open Supabase issue (functions in custom API schemas receiving EXECUTE for `anon`/`authenticated`
even when only `GRANT USAGE` was issued, and even when `ALTER DEFAULT PRIVILEGES` had revoked it).
`ALTER DEFAULT PRIVILEGES` is not a dependable prophylactic — it is scoped to the creating role, and
the issue reporter found it did not prevent the grants.

**The only dependable control is the explicit per-function revoke naming the roles**, which is owner
decision D2's model (migration 149). Write it.
