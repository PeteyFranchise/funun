# Phase 38.0.3 — RLS Helper API Exposure — Research

**Researched:** 2026-09-08
**Domain:** PostgreSQL RLS policy evaluation, SECURITY DEFINER privilege model, PostgREST schema exposure, Supabase grant defaults
**Confidence:** HIGH on Q1 (exhaustive repo enumeration), HIGH on Q2/Q4 (PostgreSQL primary sources), MEDIUM on Q3/Q5 (Supabase docs + an open Supabase bug report; live confirmation still needed)

---

## Summary

**Q1 collapses the phase.** Every single RLS-policy call site of every in-scope helper passes
`auth.uid()` as the uid argument. Across all 200 migrations there are **zero** policies that pass a
different user's id. That means the caller-identity binding already used in this repo
(migrations 174, 193, 194) closes the disclosure **with no relocation, no `private` schema, no
policy rewrites, and no `DROP FUNCTION`**. The 73 policy call sites that the SCOPE feared having to
migrate in lockstep do not need to be touched at all.

A second finding shrinks it further. Four of the eighteen helpers have **zero policy call sites** —
they are only ever called from inside other `SECURITY DEFINER` bodies, which execute as the
function owner and therefore do not need the caller to hold `EXECUTE`. Those four can simply be
`REVOKE`d, the migration-149 way, with literally no blast radius.

The phase therefore resolves into three tiers instead of the SCOPE's two:

| Tier | Count | Remedy | Blast radius |
|---|---|---|---|
| **T1 — Revoke** | 4 | `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated` | none — no policy names them |
| **T2 — Bind** | 13 | add `p_uid = (SELECT auth.uid()) OR (SELECT auth.role()) = 'service_role'` | none — every policy already passes `auth.uid()` |
| **T3 — Relocate** | 1 (`no_block`) | move to a non-exposed schema | 15 policy call sites |

`no_block` is the one genuine exception and it is not a technicality: binding it leaves an oracle
for *"did user X block me"*, which migration 035 explicitly identified as threat **T-08-03** and
deliberately closed at the table-policy level. Binding `no_block` would re-open a threat this repo
already decided to close. That single function is the only thing in the phase that actually needs a
schema move.

**Primary recommendation:** Ship T1 (revoke ×4) and T2 (bind ×13) as two small migrations, verified
by a **100% read-only** Part B probe that impersonates JWT claims — an idiom already proven twice
against this production database. Decide `no_block` separately: relocate it, or accept the
self-scoped oracle with the owner's explicit sign-off. Do **not** build a `private` schema for the
other seventeen — on Supabase it would be obscurity, not a privilege boundary (see Q3/Q5).

## Q2 — Can an RLS policy on a `public` table call a definer in a non-exposed schema?

**Yes, and the privilege requirement is exactly two grants held by the querying role: `USAGE` on
the schema and `EXECUTE` on the function.**

PostgreSQL, *Row Security Policies*:

> "Policy expressions are run as part of the query and with the privileges of the user running the
> query, although security-definer functions can be used to access data not available to the
> calling user."

`[CITED: postgresql.org/docs/current/ddl-rowsecurity.html]`

So the policy expression is evaluated as `authenticated` (or `anon`), and the function-call
privilege check is therefore made against `authenticated`. That is precisely why the TRAP is real.

PostgreSQL, *Privileges*, on `USAGE`:

> "For schemas, allows access to objects contained in the schema (assuming that the objects' own
> privilege requirements are also met). Essentially this allows the grantee to 'look up' objects
> within the schema. Without this permission, it is still possible to see the object names, e.g., by
> querying system catalogs. Also, after revoking this permission, existing sessions might have
> statements that have previously performed this lookup, so this is not a completely secure way to
> prevent object access."

and on `EXECUTE`:

> "Allows calling a function or procedure, including use of any operators that are implemented on
> top of the function. This is the only type of privilege that is applicable to functions and
> procedures."

`[CITED: postgresql.org/docs/current/ddl-priv.html]`

**Both are required.** `EXECUTE` without schema `USAGE` fails at name resolution; `USAGE` without
`EXECUTE` fails at the privilege check. And note the doc's own caveat that revoking `USAGE` is *"not
a completely secure way to prevent object access."*

**The corollary that decides the recommendation.** Because the querying role must hold
`USAGE` + `EXECUTE` for a relocated helper to work inside a policy, relocation does **not** remove
any privilege. `authenticated` can still execute `private.no_block` — it simply has no HTTP route to
do so. Relocation removes the *endpoint*, not the *permission*. That is a real and worthwhile
reduction (it is defence in depth), but it is a weaker guarantee than binding, which makes the
function return the correct answer even to an attacker who reaches it.

**And one more corollary that creates Tier 1.** A `SECURITY DEFINER` function executes with the
privileges of its owner, so a definer body calling another function needs the **owner** to hold
`EXECUTE`, not the caller. That is why the four zero-policy helpers can be revoked from
`authenticated` outright without breaking their eleven definer-body callers. `[VERIFIED: PostgreSQL
SECURITY DEFINER semantics + repo call-site enumeration]`

## Q3 — Does PostgREST expose functions outside its configured schemas?

**No — but on Supabase this is a configuration boundary, not a privilege boundary, and it is
flippable from the dashboard by anyone with project admin.**

- PostgREST introspects and exposes only the schemas listed in `db-schemas`
  (`PGRST_DB_SCHEMAS`). A function in a schema not on that list has no RPC route. Requests naming
  an unlisted schema fail with `PGRST106: "The schema must be one of the following…"`.
  `[CITED: supabase.com/docs/guides/troubleshooting/pgrst106-the-schema-must-be-one-of-the-following-error-when-querying-an-exposed-schema]`
- Supabase's default exposed set is `public` and `graphql_public` for local/self-hosted; the hosted
  platform additionally permits `storage`. A custom schema is reachable only after being added to
  **API settings → Exposed schemas**. `[CITED: supabase.com/docs/guides/api/using-custom-schemas]`
- Supabase's own hardening guidance endorses the pattern: *"A dedicated schema adds another
  boundary around your Data API. Objects in a schema such as `api` define the API surface. Internal
  tables and helper functions remain in schemas that aren't exposed."*
  `[CITED: supabase.com/docs/guides/database/hardening-data-api]`

**Is it a real security boundary here? Partly.** Three properties matter:

1. It is **not obscurity** in the pejorative sense — PostgREST genuinely refuses to route to an
   unlisted schema; it is not a matter of guessing a name.
2. It **is** a single mutable setting. `private` becoming exposed is one dashboard toggle or one
   `.env` edit away, and the migration this phase would write (`GRANT USAGE ON SCHEMA private TO
   authenticated`) is precisely the second half of Supabase's own "how to expose a custom schema"
   recipe. Half the exposure work would already be done and committed to the repo.
3. It **does not reduce privilege at all** (Q2). The role keeps `EXECUTE`.

`[ASSUMED — reasoning, not a citation]` — the judgement that this makes relocation a *weaker*
control than binding for this specific threat is mine, not a documented Supabase or PostgreSQL
position. It should be confirmed with the owner rather than treated as settled.

## Q4 — Transition safety: coexistence, and does `DROP FUNCTION` self-verify?

### Coexistence: yes, trivially.

`public.f` and `private.f` are distinct objects. Every function in this repo sets
`search_path = ''` and fully qualifies every reference, so there is no resolution ambiguity and no
window in which a call could bind to the wrong one. Policies can be migrated in batches. `[VERIFIED:
INVENTORY — "proconfig is search_path='' on every single row"]`

### Does PostgreSQL record a dependency from an RLS policy to a function? YES.

From PostgreSQL's own source, `src/backend/commands/policy.c`, in `CreatePolicy` (and repeated in
`AlterPolicy`):

```c
/* Record Dependencies */
recordDependencyOnExpr(&myself, qual, qual_pstate->p_rtable,
                       DEPENDENCY_NORMAL);
...
recordDependencyOnExpr(&myself, with_check_qual,
                       with_check_pstate->p_rtable, DEPENDENCY_NORMAL);
```

Both the `USING` and `WITH CHECK` expressions record `DEPENDENCY_NORMAL` entries.
`[VERIFIED: github.com/postgres/postgres — src/backend/commands/policy.c]`

`DROP FUNCTION`'s default is `RESTRICT`:

> "**RESTRICT** — Refuse to drop the function if any objects depend on it. This is the default."

`[CITED: postgresql.org/docs/current/sql-dropfunction.html]`

**So the drop step IS self-verifying with respect to policies.** `DROP FUNCTION public.no_block(uuid, uuid);`
without `CASCADE` will fail with `2BP01` and a `DETAIL:` line naming every policy that still
references it. That is a genuinely good property and the planner should exploit it: the drop is the
proof, not a step that needs a separate proof.

### The caveat that makes it only *half* self-verifying — and this is the dangerous half.

Dependencies are recorded for **policy expressions**, which are parsed at creation. They are **not**
recorded for references inside a string-literal function body. PostgreSQL's `CREATE FUNCTION` docs:

> "This form is parsed at function definition time, the string constant form is parsed at execution
> time; therefore this form cannot support polymorphic argument types and other constructs that are
> not resolvable at function definition time. **This form tracks dependencies between the function
> and objects used in the function body, so `DROP … CASCADE` will work correctly, whereas the form
> using string literals may leave dangling functions.**"

`[CITED: postgresql.org/docs/current/sql-createfunction.html]`

**Every function in this repo uses the string-literal `AS $$ … $$` form.** `[VERIFIED: grep — zero
`BEGIN ATOMIC` bodies in supabase/migrations]`

Therefore:

| Reference type | Dependency recorded? | `DROP FUNCTION` (RESTRICT) behaviour |
|---|---|---|
| RLS policy `USING` / `WITH CHECK` | **yes** | **fails loudly** — safe |
| Another function's `$$ … $$` body | **no** | **succeeds silently**, leaving a caller that raises `42883 function does not exist` on its next invocation |
| Trigger `WHEN` clause | yes (expression) | fails loudly |
| CHECK constraint / index expression | yes | fails loudly |
| Application `.rpc()` call | no (not a DB object) | succeeds silently, breaks at runtime |

This matters enormously for the four Tier-1 functions, which are called **only** from function
bodies. If a relocation-style plan ever dropped `public.workspace_access_enabled()`, PostgreSQL
would allow it, and eleven RPCs — including `workspace_create` and
`workspace_change_member_role_or_status` — would start failing at their first call, in production,
with no prior warning. This is the migration-198 `ON CONFLICT` failure mode exactly.

**Never use `DROP … CASCADE` on any of these.** With RLS enabled and a policy cascaded away, the
table falls to default-deny — fail-closed rather than fail-open, but a silent, total outage of that
table's reads for every non-owner role.

## Q5 — Supabase-specific hazards

### The root cause is PostgreSQL, not Supabase, and it follows you into `private`.

> "PostgreSQL grants privileges on some types of objects to `PUBLIC` by default when the objects are
> created. No privileges are granted to `PUBLIC` by default on tables, table columns, sequences,
> foreign data wrappers, foreign servers, large objects, schemas, tablespaces, or configuration
> parameters. For other types of objects, the default privileges granted to `PUBLIC` are as follows:
> `CONNECT` and `TEMPORARY` … for databases; **`EXECUTE` privilege for functions and procedures**;
> and `USAGE` privilege for languages and data types."

`[CITED: postgresql.org/docs/current/ddl-priv.html]`

That is the whole mechanism. Every function created anywhere is `EXECUTE`-able by `PUBLIC` on
creation. `anon` and `authenticated` hold `USAGE` on `public`, so every new function in `public` is
immediately an RPC endpoint. Migration 035's own header already said so in 2024: *"Revoke the
blanket PostgREST RPC exposure every function in the public schema gets by default."*

**The trap this creates for the relocation approach.** The moment you run the grant relocation
requires —

```sql
GRANT USAGE ON SCHEMA private TO authenticated;
```

— every function you create in `private` becomes `EXECUTE`-able by `authenticated` via the default
`PUBLIC` grant, exactly as in `public`. You have not removed a privilege; you have removed a route.
And this is a live, open, confirmed Supabase bug report: functions in custom API schemas receive
`EXECUTE` for `anon`/`authenticated` *"even when only `GRANT USAGE` was granted on the schema"* and
*"`ALTER DEFAULT PRIVILEGES` explicitly revoked execution rights."* The reporter's own words:
*"this can lead to sensitive RPC endpoints being accessible unintentionally, because this is a
really unsafe and unexpected default."* Their workaround was an event trigger that revokes after
every function creation. `[CITED: github.com/supabase/supabase/issues/43884 — open]`

### Does migration 047's failure mode recur on a new schema?

Migration 047's specific defect was `REVOKE … FROM PUBLIC` not removing a **direct** grant to
`anon`/`authenticated`. On a brand-new `private` schema there would be no direct grants unless the
migration created them — so the 047 shape does not recur. But the *outcome* does, via the default
`PUBLIC` grant above. The fix is the same either way and it is D2's model: **name the roles
explicitly in the revoke.**

```sql
REVOKE EXECUTE ON FUNCTION public.f(...) FROM PUBLIC, anon, authenticated;
GRANT  EXECUTE ON FUNCTION public.f(...) TO authenticated;   -- only if a policy needs it
```

### Is there an event trigger that re-grants?

Supabase installs event triggers owned by `supabase_admin` that fire on `ddl_command_end` /
`sql_drop`, principally to `NOTIFY pgrst` for schema-cache reload (`pgrst_ddl_watch`,
`pgrst_drop_watch`) and to grant access to specific **extensions** (`grant_pg_cron_access`,
`grant_pg_net_access`, `grant_pg_graphql_access`). None of them is documented as granting
`EXECUTE` on user-defined functions. `[ASSUMED — Supabase does not publish the full installed
event-trigger list; this is inferred from the platform image documentation and community
descriptions. Part A must confirm it directly.]`

**Required Part A check (cheap, read-only, closes the assumption):**

```sql
SELECT evtname, evtevent, evtenabled, p.proname AS handler
FROM pg_event_trigger e JOIN pg_proc p ON p.oid = e.evtfoid
ORDER BY evtname;
```

If any handler's body contains `GRANT`, the phase's revokes are not durable and the plan needs a
different mechanism. This is the single highest-value unknown left in the phase.

### `ALTER DEFAULT PRIVILEGES` is not a reliable prophylactic here

Per issue 43884, `ALTER DEFAULT PRIVILEGES … REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` did not
prevent the grants for that reporter. Default privileges are also scoped to the *creating role*, and
on Supabase migrations run as `postgres` while dashboard SQL may run as something else. Treat
per-function explicit revokes as the only dependable control. `[CITED: github.com/supabase/supabase/issues/43884]`

## The recommended approach

### Three tiers, in ship order

#### T1 — REVOKE (4 functions, zero blast radius)

These have **no policy call site anywhere in the repo**. Their only callers are `SECURITY DEFINER`
bodies, which execute as the owner and do not need the caller to hold `EXECUTE` (Q2 corollary).

| Function | Policy sites | Definer-body callers | Action |
|---|---:|---|---|
| `workspace_access_enabled()` | 0 | 11 (`workspace_project_permission`, `workspace_catalogue_page`, `workspace_audit_page`, `workspace_roster_page`, `workspace_access_permitted`, `workspace_create`, `workspace_nominate_owner`, `workspace_change_member_role_or_status`, `workspace_respond_ownership_nomination`, `workspace_revoke_invitation`, `workspace_transition_roster_relationship`) | `REVOKE … FROM PUBLIC, anon, authenticated` |
| `workspace_grant_lineage_live(uuid)` | 0 | 2 (`workspace_project_permission`, `workspace_catalogue_page`) | same |
| `green_room_post_matches_custom_audience(uuid,uuid)` | 0 | 1 (`green_room_can_view_post`) | same |
| `workspace_roster_relationship_is_live(uuid,uuid)` | 0 | **0 — dead code** | same; consider `DROP FUNCTION` (RESTRICT will confirm nothing depends on it) |

This is the D2 / migration-149 posture applied verbatim. It is the *only* place in this phase where
a revoke is correct, and plan-check must be told that so it does not reject it under the TRAP rule.

`[VERIFIED: repo enumeration, latest-definition-wins]`

#### T2 — BIND (13 functions, zero policy edits)

Add the caller-identity binding to the body. Every policy already passes `auth.uid()`, so the bound
branch is tautologically true on the policy path — the behaviour of every existing policy is
unchanged *by construction*, not by test.

**Recommended predicate** (call it the 174-B idiom):

```sql
(p_uid = (SELECT auth.uid()) OR (SELECT auth.role()) = 'service_role')
```

Applied as a leading conjunct for `BOOLEAN` returns, or as the `WHEN` guard of a `CASE` for
`TEXT`-returning helpers — matching migration 174's two shapes exactly.

The thirteen: `workspace_project_permission`, `workspace_member_role`, `is_workspace_owner`,
`green_room_can_view_post`, `workspace_audit_visible`, `custody_transfer_visible`,
`ownership_transfer_visible`, `workspace_attachment_visible`,
`workspace_agreement_evidence_visible`, `workspace_grant_visible_to_member`,
`is_split_sheet_initiator`, `is_split_sheet_party`, `is_green_room_eligible`.

**Why `auth.role() = 'service_role'` is required and not optional.** Two application call sites use
the service client and pass a viewer who is not the caller:
- `lib/trust-safety/reports.ts:179` → `service.rpc('green_room_can_view_post', …)`
- `lib/green-room/placements-admin.ts:353` → `service.rpc('no_block', { a: viewerId, b: ownerId })`

On a service connection `auth.uid()` is `NULL`, so a strict migration-194-style bind
(`p_uid = (SELECT auth.uid())` alone) would silently break both. `[VERIFIED: grep of app/, lib/,
components/ — these are the only two application call sites among all eighteen helpers]`

**Why `pg_trigger_depth() > 0` should be OMITTED.** Migration 174 includes it. It is not needed
here — no trigger function currently calls any of these eighteen (§Q1). Omitting it removes the
weakest branch of the idiom: `pg_trigger_depth() > 0` is an unauthenticated, un-identity-bound
escape that any write which fires a trigger enters. Add a text-lock test asserting that no trigger
function calls a bound helper, so the omission stays true.

**Deliberate consequence to state plainly:** after binding, an authenticated caller can still ask
these functions about **themselves** — *"what is my role in workspace W"*, *"can I see post P"*.
That is self-information and is equivalent to what a normal `SELECT` already returns. It is not a
disclosure. The disclosure being closed is the cross-user one.

#### T3 — `no_block` is the exception, and it needs a decision

`no_block` is the only helper where binding leaves a **real** disclosure, and the repo already said
so. Migration 035's own comment above `blocks_select_own`:

> "A member sees ONLY their own blocklist, never who blocked them (**T-08-03**: enumeration of 'who
> blocked me' is an information-disclosure risk mitigated by restricting SELECT to
> `blocker_id = auth.uid()`)."

Because `no_block(a, b)` is symmetric, any binding that permits the policy path (`a = auth.uid()`)
necessarily permits `no_block(me, X)` — which answers *"did X block me?"* for any `X`. That is
T-08-03, re-opened through an RPC, having been closed at the table.

`no_block` has 15 policy call sites, so it cannot be revoked. Three options, in order of preference:

| Option | Effect on T-08-03 | Cost |
|---|---|---|
| **A. Relocate to `private`** | Closed — no RPC route | 1 new schema, 1 grant pair, 15 policy rewrites (a policy per table, each `DROP POLICY` + `CREATE POLICY`), plus the drop step. **The only part of this phase that needs the SCOPE's original machinery.** |
| **B. Bind + accept** | Open — self-scoped block oracle | Zero. Requires explicit owner sign-off that T-08-03 is acceptable at beta. |
| **C. Bind + rate-limit / audit** | Mitigated, not closed | Needs a write path from a `STABLE` function — not viable. Rejected. |

**Recommendation: A, but scoped as its own plan, and only after T1 and T2 have shipped and been
verified.** Relocating one function with 15 policy sites is a tractable, bounded piece of work.
Relocating seventeen with 73 was the phase the SCOPE feared.

### What ships, concretely

| Migration | Contents | Risk |
|---|---|---|
| `20N+0` | T1 revokes ×4 (+ optional `DROP FUNCTION workspace_roster_relationship_is_live` under RESTRICT) | minimal |
| `20N+1` | T2 binds ×13, each `CREATE OR REPLACE` with grants restated (`CREATE OR REPLACE` preserves grants but says nothing about them — migration 196/197's own doctrine) | low, provable by enumeration |
| `20N+2` | T3 `no_block` relocation: `CREATE SCHEMA private`, grants, `private.no_block`, 15 policy rewrites, `DROP FUNCTION public.no_block` under RESTRICT as the self-verifying step | moderate — the only real risk in the phase |

### D1 and honest scope framing

D1 says the phase blocks beta and forbids shipping half. That decision was made on the SCOPE's model
of the work — 15 relocations, 73 policy rewrites, staged over five steps. The evidence changes the
model, and the planner should surface that to the owner rather than silently re-scoping:

> The stated defect — *anyone with the anon key can query the authorization graph about other
> users* — is **fully closed by T1 + T2**, which touch no policy and no application code. T3 closes a
> different and narrower residual (a self-scoped block oracle, T-08-03). If the owner wants
> everything before beta, ship all three; T3 is one function, not fifteen. If beta timing is tight,
> T1 + T2 is not "the easy half" — it is the whole of the disclosure fix, and T3 is a distinct
> finding that was not in the original problem statement.

Present it as a decision, not as a fait accompli. D1 stands until the owner moves it.

## Common Pitfalls

### Pitfall 1: plan-check rejecting the T1 revokes under the TRAP rule
**What goes wrong:** The SCOPE says "any plan that opens with REVOKE is wrong and must be rejected."
T1 opens with a revoke.
**Why:** The TRAP was written before the zero-policy-call-site class was known.
**Avoid:** The plan must carry the per-function policy-call-site count as evidence, and the
plan-check instruction must be amended to *"a revoke is permitted only where the policy call-site
count is proven zero."*
**Warning sign:** A reviewer citing the TRAP without citing a call-site count.

### Pitfall 2: writing the bind as migration 194's strict form
**What goes wrong:** `p_uid = (SELECT auth.uid())` alone breaks `reports.ts:179` and
`placements-admin.ts:353`, silently — both are service-client calls where `auth.uid()` is `NULL`.
**Avoid:** Use the 174-B idiom with the `service_role` branch.
**Warning sign:** A migration diff for `green_room_can_view_post` or `no_block` with no
`auth.role()` reference.

### Pitfall 3: copying migration 174's `pg_trigger_depth() > 0` branch by reflex
**What goes wrong:** It is dead weight for these eighteen and is the branch an attacker would look
at first.
**Avoid:** Omit it; add a text-lock test that no trigger function calls a bound helper.

### Pitfall 4: `DROP FUNCTION … CASCADE`
**What goes wrong:** Cascades away the depending policies. RLS-enabled table with zero policies =
default deny = total read outage for that table.
**Avoid:** Never write `CASCADE`. Rely on RESTRICT's failure as the verification (Q4).

### Pitfall 5: assuming a drop is self-verifying for function-body callers
**What goes wrong:** Dependencies are recorded for policy expressions only. Dropping a function
still called from another `$$ … $$` body succeeds silently and fails at runtime with `42883`.
**Avoid:** Before any drop, run the call-site enumeration over `pg_proc.prosrc` as well as
`pg_policies`, and make that a Part A check.

### Pitfall 6: `CREATE OR REPLACE FUNCTION` and grants
**What goes wrong:** `CREATE OR REPLACE` preserves existing grants but the migration text then says
nothing about them, so the file stops being an authority on the posture — which is how migration
047's defect stayed invisible.
**Avoid:** Restate `REVOKE … FROM PUBLIC, anon, authenticated;` and the intended `GRANT` after every
replace. Migrations 196 and 197 already do this and say why.

### Pitfall 7: `NOTIFY pgrst, 'reload schema'`
**What goes wrong:** PostgREST caches the schema. A revoke without a reload leaves the endpoint
apparently live until the cache turns over.
**Avoid:** End every migration with `NOTIFY pgrst, 'reload schema';` — every migration in this repo
already does.

### Pitfall 8 (repo-wide, discovered while researching): migration numbers 201–206 are already taken
**What goes wrong:** The SCOPE says *"Numbers 201–202 belong to Codex's Playbook workstream; 203–204
to Phase 38.2. This phase claims from 205."* That is stale. The working tree contains **untracked**
test files `__tests__/migration-201-202-playbook.test.ts`, `migration-204-playbook-reviews.test.ts`,
`migration-205-playbook-updates.test.ts`, and `migration-206-playbook-enablement.test.ts`, while
`supabase/migrations/` stops at `200`. The Playbook workstream has consumed **through 206** in a
parallel session.
**Avoid:** This phase must claim from **207**, and the planner must re-verify immediately before
writing the files — the parallel workstream may have advanced again. This is the
[[parallel-sessions-stale-state]] failure mode exactly: the artifact was true when written and is
false now.
**Warning sign:** `ls supabase/migrations | tail` disagreeing with `ls __tests__ | grep migration-`.
`[VERIFIED: git status, filesystem, 2026-09-08]`

### The behavioural harness — and why this phase's is *easier*, not harder

The SCOPE and the brief both warn that this phase cannot rely on empty tables. That is true, and it
disqualifies the 38.0.1/38.0.2 Part B shape, whose safety rested on a pre-flight that **aborts if
`workspace_members` / `workspace_invitations` / `workspace_audit_log` is non-empty**. Green Room,
split sheets, works and projects will never satisfy that.

**But a bind-only change does not need to seed anything.** What must be proven is that a function
returns a different answer depending on whose id is passed — and that can be observed on existing
production rows, read-only, by impersonating JWT claims:

```sql
DO $$
DECLARE v_self UUID; v_other UUID; v_result BOOLEAN;
BEGIN
  -- pick two real ids by READING, never writing
  SELECT id INTO v_self  FROM public.user_profiles ORDER BY created_at LIMIT 1;
  SELECT id INTO v_other FROM public.user_profiles WHERE id <> v_self ORDER BY created_at LIMIT 1;

  PERFORM set_config('request.jwt.claims',
    json_build_object('sub', v_self::text, 'role', 'authenticated')::text, true);
  EXECUTE 'SET LOCAL ROLE authenticated';

  -- cross-user probe MUST be false/NULL after the bind
  SELECT public.is_workspace_owner('<real workspace id>', v_other) INTO v_result;
  -- ... record result row ...

  RESET ROLE;
  PERFORM set_config('request.jwt.claims', NULL, true);
END $$;
```

**This idiom is already proven twice against this exact production database.** It is used at
`38.0.1-VERIFY-B-PRODUCTION-SINGLE.sql:169-201` and at
`38.0.2-VERIFY-B-PRODUCTION-SINGLE.sql:465-857` — the same `set_config('request.jwt.claims', …)` /
`SET LOCAL ROLE authenticated` / `RESET ROLE` pattern, with `RESET ROLE` in the exception handler so
one failure does not poison the rest of the transaction. `[VERIFIED: repo]`

Properties that make it safe on live data:
- **No INSERT, UPDATE, DELETE, TRUNCATE, DDL, GRANT or REVOKE anywhere.** It is a pure read.
- **No population precondition.** It does not care whether tables are empty; it prefers them not to
  be, because real rows make the assertions meaningful.
- **No kill-switch flip.** It does not touch D-56.
- Still one `DO` block = one statement = one transaction, with per-assertion subtransactions and a
  guaranteed `RESET ROLE`, exactly as the two prior files.

The T3 relocation, if it ships, needs one additional behavioural assertion that *is* harder: that a
rewritten policy still admits the same rows. That is still achievable read-only — impersonate a real
Green Room author and `SELECT count(*)` from the affected tables before and after — but it must be
run in the same transaction window as the policy swap, which means a human running the migration and
the probe back to back.

### Known threat patterns for this stack

| Pattern | STRIDE | Standard mitigation |
|---|---|---|
| Caller-supplied subject id trusted by a `SECURITY DEFINER` function (IDOR / horizontal privilege escalation) | Elevation of Privilege | Bind the parameter to `auth.uid()`; the parameter may name the caller or nobody (migration 194's doctrine) |
| Authorization-graph enumeration via auto-exposed RPC | Information Disclosure | Revoke where no policy needs it; bind where a policy does; relocate where a bound answer is still a disclosure |
| `REVOKE … FROM PUBLIC` failing to remove a direct role grant | Elevation of Privilege | Name `anon` and `authenticated` explicitly (D2 / migration 149) |
| Default `EXECUTE` to `PUBLIC` on every new function | Information Disclosure | Explicit per-function revoke; do not rely on `ALTER DEFAULT PRIVILEGES` (Supabase issue 43884) |
