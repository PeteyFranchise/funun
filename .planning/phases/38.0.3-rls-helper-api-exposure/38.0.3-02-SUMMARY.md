# Phase 38.0.3 Plan 02: Tier 2 — Caller-Identity Binds Summary

**Thirteen `SECURITY DEFINER` authorization predicates that PostgREST hands to
every authenticated caller now refuse to answer a question about anybody but
the caller — and they do it without a single RLS policy being touched, because
all 58 policy call sites already pass `auth.uid()` and the added conjunct is
therefore tautologically true wherever a policy evaluates it.**

## DEVIATION 2 — plan assertion 10 cannot be implemented as written

**The plan's Task 2 assertion 10 says "`no_block` appears nowhere in the
file". Taken as raw text that is impossible, and it contradicts the plan's own
Task 1.**

Task 1 requires `green_room_can_view_post`'s body be copied **verbatim** from
migration 076. That body calls `public.no_block(p_viewer, p.author_id)` — the
plan's own `key_links` say so in terms. A literal absence grep could only be
satisfied by editing a body the drift guard exists to prove unedited.

**Implemented as what it means**, which is strictly stronger than the literal
reading:

1. `no_block` is not **defined** here (no `CREATE [OR REPLACE] FUNCTION`).
2. It is not **revoked**, **granted** or **dropped** here.
3. **Exact-count lock**: `no_block` occurs **exactly once** in the
   comment-stripped text, and that occurrence is the call inside
   `green_room_can_view_post`'s body.

The count lock is what makes this stronger than absence-grep: it fails on a
*second* appearance of any kind, not merely on a definition. **The plan's own
mutation for this assertion (add a `no_block` replace to the file) goes RED**
— on both the definition check and the count lock. Verified as mutation 9.

Owner decision D4 is untouched: `no_block` is relocated in plans 04-06
(migration 210), not bound, because `no_block(a, b)` is symmetric and any bind
permitting the policy path also answers *"did X block me?"* — threat T-08-03,
which migration 035 closed at the table.

### The finding from mutation 2 — a positive assertion is not enough

**`uid` is a substring of `p_uid`.** So the positive check
`body.contains('uid = (SELECT auth.uid())')` **still passed** on a
`is_split_sheet_party` bound against `p_uid` — a name it does not have, which
would make the bind a no-op that reads as a fix, the exact defect
`T-38.0.3-02-04` names.

What caught it was the **negative** assertion added alongside — "this function
does not bind a parameter name it does not have" — with a word-boundary regex
that excludes a leading `_` or letter. **Without that negative, assertion 2
would have been half-blind on precisely the two functions the plan flagged as
most dangerous.** Mutations 11-13 were added for the same reason: an assertion
that no mutation has broken is a claim, not a proof.
