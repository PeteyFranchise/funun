## Why the repo alone was not enough

**This describes the REPO, and the repo lies about grants.** Migration 047
revoked `apply_to_opportunity_atomic` `FROM PUBLIC` and the repo therefore
looked correct — while production had direct grants to `anon` and
`authenticated` that the PUBLIC-only revoke never touched. That is how a
write-capable bypass survived unnoticed.

The same divergence exists right now in the other direction: this table shows
`apply_to_opportunity_atomic` as **class D**, because migration 200 (authored,
**not applied**) contains the explicit revoke. Production still has it exposed.

**This was cross-checked (see above) and came back clean.** The section is
kept because the reasoning stays true for any future change: the repo is not
authoritative about grants, and only the live database is.

## Live cross-check — run before planning

```sql
SELECT p.proname,
       coalesce(array_to_string(p.proconfig, ','), '(none)') AS proconfig,
       has_function_privilege('anon', p.oid, 'EXECUTE')          AS anon_exec,
       has_function_privilege('authenticated', p.oid, 'EXECUTE') AS authed_exec,
       has_function_privilege('service_role', p.oid, 'EXECUTE')  AS service_exec
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public'
  AND p.prosecdef
  AND p.prorettype <> 'trigger'::regtype
  AND NOT EXISTS (SELECT 1 FROM pg_depend d WHERE d.objid = p.oid AND d.deptype = 'e')
ORDER BY anon_exec DESC, authed_exec DESC, p.proname;
```

Any function this table calls **C** or **D** that comes back with `anon_exec`
or `authed_exec` true is a repo-vs-live divergence of the 046 kind, and is
higher priority than anything in class A.

## Method, and one parser defect worth recording

Built by parsing every migration, latest definition winning. Two defects were
found and fixed while building it, both of which would have produced a
confidently wrong inventory:

1. **Trailing modifiers.** Functions written as
   `$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = public;` put their
   modifiers *after* the body. The first parser only read the header and
   excluded three functions — including `apply_to_opportunity_atomic`, the one
   that started all this.
2. **A comment inverted the grant posture.** The grant regex matched the word
   *"grant"* inside the comment `-- Migration 123's grant posture, NOT
   migration 046's.` and ran forward to the next real `ON FUNCTION`. The
   captured REVOKE then began with prose, failed a `startswith('REVOKE')` test,
   was filed as a GRANT, and the `anon, authenticated` in its `FROM` clause was
   reported as **granted**. Before the fix this document would have claimed
   every hardened Phase 38 RPC was wide open. Comments are stripped first now.
