<objective>
Remove the application's only dependency on the `no_block` RPC route, so that plan 05 can relocate
`no_block` out of the PostgREST-exposed schema without breaking the Green Room placement activation
gate.

Purpose: owner decision D4 relocates `no_block` because binding it would leave a symmetric oracle
answering *"did X block me?"* — threat T-08-03, which migration 035 explicitly closed at the table
level. Relocation removes the HTTP route. `lib/green-room/placements-admin.ts:353` uses that exact
HTTP route. This plan closes that dependency first, on its own, in a change that is behaviour-neutral
today and independently deployable.

Output: a direct-read block check in `placements-admin.ts`, its unit test, and an updated audit pin.

---

## Why this is its own plan, and why it comes first

`38.0.3-INVENTORY.md` lists this call site as *"relocatable"* because `service_role` can be granted
EXECUTE on the new schema. That is true and it is not sufficient. `service.rpc('no_block', …)` is a
supabase-js call that becomes an HTTP request to PostgREST, and **PostgREST introspects and routes
only to the schemas in its `db-schemas` configuration**. A function in an unexposed schema has no
RPC route at all — a request naming it fails with `PGRST106`, or simply 404s, no matter what grants
the caller holds. Routing and privilege are different questions and the INVENTORY answered only the
second one.

So the ordering is forced: decouple, deploy, then relocate. Doing it the other way round breaks
placement activation for every internal destination type on the first request after the migration is
applied — the migration-198 failure shape exactly, where the defect surfaces on the first live call
rather than at apply time.

Owner decision D4 also sequences all of Tier 3 **after Tier 1 and Tier 2 have shipped and been
verified**, which is why this plan sits behind plan 03 even though the change itself is safe at any
time.

    - The query filters on the specific pair, not on "every block involving the viewer" — a single-pair lookup, so the result set is bounded regardless of how many blocks a heavy user has.

| service client → `public.blocks` | The service role bypasses RLS, which is the only way to see the "owner blocked viewer" direction. |
