## Why this phase's Part B is EASIER than 38.0.1's and 38.0.2's, not harder

The SCOPE warns that unlike its predecessors this phase cannot lean on empty tables — Green Room,
split sheets, projects and works hold real user data. That is true, and it disqualifies the
38.0.1/38.0.2 Part B shape outright: both of those files **abort if `workspace_members` is
non-empty**, because they seed fixtures. No fixture strategy will ever satisfy that precondition on
these tables.

But a bind-only change **does not need to seed anything**. What has to be proven is that a function
returns a *different answer depending on whose id is passed*, and that is observable on rows that
already exist, by impersonating JWT claims and reading. The idiom —
`set_config('request.jwt.claims', json_build_object('sub', …, 'role', 'authenticated')::text, true)`
followed by `SET LOCAL ROLE authenticated`, with `RESET ROLE` in the exception handler so one
failure does not poison the rest of the transaction — is already proven twice against this exact
production database:

- `.planning/phases/38.0.1-workspace-authorization-remediation/38.0.1-VERIFY-B-PRODUCTION-SINGLE.sql`
  lines 169-201
- `.planning/phases/38.0.2-workspace-transactional-integrity-hygiene/38.0.2-VERIFY-B-PRODUCTION-SINGLE.sql`
  lines 465-857

**Copy it.** Do not invent a new one.

Properties that make it safe here: no INSERT, UPDATE, DELETE, TRUNCATE, DDL against any application
object, GRANT or REVOKE anywhere; no population precondition (it prefers the tables NOT to be empty,
because real rows make the assertions meaningful); no kill-switch flip; still one `DO` block = one
statement = one transaction, with per-assertion subtransactions and a guaranteed `RESET ROLE`.

## The one thing Part A must do that the predecessors did not

The whole Q1 analysis — and therefore the entire justification for not rewriting a single policy —
assumes that **every RLS policy in production originated from a migration file**. A policy created
by hand in the Supabase SQL editor would be invisible to a repo-side enumeration. That is research
assumption **A5**, flagged as *"the one thing that could still collapse Q1."*

Part A closes it by diffing production's `pg_policies` against the migration-derived expectation.
This is a required check, not an optional one.
