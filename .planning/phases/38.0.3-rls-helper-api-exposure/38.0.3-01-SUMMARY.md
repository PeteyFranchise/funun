# Phase 38.0.3 Plan 01: Tier 1 — Targeted Revokes Summary

**Three exposed authorization-graph RPC endpoints are closed at the grant level and a fourth dead one is dropped, with zero blast radius — and the zero-policy-call-site finding that makes that safe is now a standing repo test rather than a claim in a plan.**

---

## THE TRAP EXEMPTION — stated here for the third time, by design

`38.0.3-SCOPE.md` says, in capitals: **do not blanket-revoke.** Any plan that
opens with "REVOKE from `anon`, `authenticated`" is wrong and must be rejected.

**That rule is correct, and this plan did not weaken it.** It applies to a
helper **if and only if an RLS policy names that helper** — policy expressions
run with the privileges of the querying role, so revoking a helper a policy
calls produces `42501 permission denied for function` on every read that policy
gates. That is why plan 02 **binds** thirteen helpers instead of revoking them,
and why none of those thirteen appears in migration 208.

The four functions in this plan are named by **zero** policies. Their only
callers are other `SECURITY DEFINER` bodies, which execute with the privileges
of the function **owner** — so the caller needs no `EXECUTE` grant for those
calls to keep working.

**The restated rule, which is stronger than the original:**

> **No blanket revoke. A revoke is permitted only for a function whose policy
> call-site count is PROVEN ZERO BY A TEST IN THE REPO, not by a claim in a
> plan.**

That exemption is now stated in **three places that outlive this plan**:

1. `supabase/migrations/208_definer_helper_targeted_revokes.sql` — the header,
   with the per-function evidence table and all fourteen definer-body callers
   named, so the safety argument is re-derivable without leaving the file.
2. `__tests__/rls-helper-callsites.test.ts` — assertion (b)'s failure message,
   which says in terms that a non-zero count means the revoke became wrong
   retroactively, and instructs the reader **not** to "fix" it by deleting the
   helper from `TIER1` but to revert the revoke and bind instead.
3. This SUMMARY.

## What shipped

### 1. `__tests__/rls-helper-callsites.test.ts` — 38 tests

The single most valuable artifact this phase leaves behind. It re-derives, on
every `npm test`, the finding the whole three-tier design rests on. It reads
`supabase/migrations/*.sql` with `readdirSync` and excludes nothing, so a
migration added tomorrow is picked up automatically.

**Parser, in dependency order** — line comments stripped first and
unconditionally (the `38.0.3-INVENTORY.md` defect where the word "grant" inside
a prose comment inverted the reported grant posture of every hardened RPC in
the repo); dollar-quoted regions mapped so a call site is classified
*inside a function body* vs *top level*; `CREATE`/`ALTER POLICY` statements
line-anchored and scanned to their terminating semicolon outside string
literals; balanced argument extraction splitting on top-level commas only
(`dmt_insert_participant` passes a `CASE … END` expression, so `split(',')`
would be wrong); function definitions with return type and body.

**The stripper tracks single-quote state within each line**, with SQL's `''`
escape self-cancelling. Without that, `--` inside the repo's long `COMMENT ON`
prose bodies would truncate real SQL.

**Assertions and the numbers they produced:**

| Assertion | Result |
|---|---|
| (a) every policy call site passes `auth.uid()` at the identity index | **0 offenders** across `TIER2` + `no_block` |
| (a) per-helper exact counts | 18 / 13 / 12 / 6 / 1×8 — **58 Tier-2 sites**, plus **15** `no_block` = **73** total |
| (b) Tier-1 helpers named by policies | **0 for all four** |
| (c) current trigger functions calling a Tier-2 helper | **0**, over 20+ `RETURNS TRIGGER` functions |
| (d) application `.rpc()` call sites | **exactly 2**, both service-client |

**Every one of those counts independently reproduces `38.0.3-RESEARCH.md` §Q1
on the first run**, from a parser written from the plan's description rather
than from the research's scripts. That is corroboration, not restatement.

Identity-argument indices are recorded per helper because they are **not
uniform**: index 1 for the eleven two-argument helpers and the one
three-argument helper, index 0 for `is_green_room_eligible`, and index 0 for
`no_block` — which takes the **viewer first**. Getting one wrong is precisely
how this test would pass while proving nothing.

### 2. `supabase/migrations/208_definer_helper_targeted_revokes.sql`

Three `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated`, three replacement
`COMMENT ON FUNCTION` statements describing the now-**enforced** state, one
modifier-free `DROP FUNCTION`, and `NOTIFY pgrst, 'reload schema';` last.
**Zero grants. Zero `CREATE OR REPLACE FUNCTION`.** It changes reachability,
never behaviour.

`anon` and `authenticated` are named explicitly because Supabase grants them
**directly** and `REVOKE … FROM PUBLIC` does not remove a direct grant — the
exact defect that let `apply_to_opportunity_atomic` stay open from migration
047 until 2026-09-08 while the repo looked correct. This is owner decision D2's
posture (migration 149's shape) applied verbatim.

**On the drop.** The brief asked for `DROP FUNCTION … RESTRICT`. The plan
specified **no modifier at all**, and its paired test asserts the absence of
both modifier keywords. These are the same thing — **`RESTRICT` is
PostgreSQL's default** — so the brief's intent (PostgreSQL confirms nothing
depends on it) is fully satisfied. `RESTRICT` is left unwritten so a future
reader cannot mistake the default for an oversight and "helpfully" change it.
The header states in prose that the recursive modifier must never be used here:
with RLS enabled, cascading a policy away leaves the table **default-deny** — a
silent total read outage, not an opening.

**Static verification that the drop is safe.** `workspace_roster_relationship_is_live`
has zero callers of any kind anywhere in the repo — zero policies (assertion
(b)), zero function bodies, zero application code. Every surviving textual
reference is prose: two comments in migration 183, one comment in
`app/api/workspaces/[workspaceId]/roster/route.ts:97`, and two neighbouring
tests that assert it is *not* redefined. It was created by migration 183 for
migration 186's three-hop helper; 192 (v2) and 197 (v3) rewrote that helper and
inlined the check, leaving the predicate behind. **The revoke fallback was
therefore not needed** — but it is documented verbatim in the header for the
owner to apply by hand if the live drop refuses with `2BP01`.

**Residual risk, stated in the header rather than hidden:** the default
restrictive mode is self-verifying for **policy** references only. This repo
writes every body as a string-literal `AS $$ … $$` block, and PostgreSQL's
`CREATE FUNCTION` docs say that form "may leave dangling functions". A
body-level caller would **not** block the drop — it would succeed cleanly and
raise `42883` on first call. That is why plan 03's Part A `pg_proc.prosrc`
enumeration is a mandatory pre-run gate and why research assumption A7 closes
there, not here.

### 3. `__tests__/migration-208-definer-revokes.test.ts` — 22 tests

Text-lock plus a **signature-fidelity** guard: for each of the four names, the
argument list written in 208 is compared character-for-character (lowercased,
whitespace-normalised) against the argument list in that function's most recent
**prior** `REVOKE`/`GRANT`, and the source migration of each is anchored:

| Function | Prior signature source | Args |
|---|---|---|
| `workspace_access_enabled` | `186_workspace_rls_extension.sql` | `()` |
| `workspace_grant_lineage_live` | `192_workspace_project_permission_v2.sql` | `(uuid)` |
| `green_room_post_matches_custom_audience` | `060_green_room_block_visibility_and_audience_roles.sql` | `(uuid, uuid)` |
| `workspace_roster_relationship_is_live` | `183_workspace_roster_relationships.sql` | `(uuid, uuid)` |

**A revoke against a signature that does not exist is a silent no-op, and a
silent no-op is the exact failure mode this phase exists to fix.**

The suite also carries an explicit anti-vacuity test proving the header
*really does* contain the forbidden constructs in prose (`RESTRICT`, a
commented-out fallback `REVOKE`) while the stripped text does not — so the
stripping is demonstrably doing work rather than the header happening to be
clean.
