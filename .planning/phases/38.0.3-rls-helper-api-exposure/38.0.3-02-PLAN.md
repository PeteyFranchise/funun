## Why this needs no policy rewrites, and why that is a finding rather than an assumption

`38.0.3-SCOPE.md` planned for the hard version of this: relocate the helpers to a non-exposed
schema, rewrite ~73 policy call sites in lockstep per table group, then drop the originals. That
plan was correct for the model of the problem the SCOPE had.

The research falsified the model. Every `public.<helper>(` occurrence across all 200 migrations was
located with line comments stripped and dollar-quoted regions mapped, each match classified as
inside-a-function-body versus inside a `CREATE POLICY`, and the balanced argument list extracted
verbatim. **Every single policy call site of every one of these helpers passes `auth.uid()` as the
identity argument. Zero exceptions.** So the added conjunct `p_uid = (SELECT auth.uid())` is
tautologically true wherever a policy evaluates it. The policies do not change because they do not
need to.

Plan 01 turned that finding into `__tests__/rls-helper-callsites.test.ts` assertion (a), which runs
on every `npm test`. This plan is downstream of that test, not downstream of a paragraph.

## The ordering constraint — bind all thirteen in ONE migration

Several of the thirteen call each other, forwarding their own `p_uid`:
`workspace_agreement_evidence_visible` calls `is_workspace_owner(r.workspace_id, p_uid)`;
`workspace_audit_visible`, `ownership_transfer_visible` and `workspace_attachment_visible` all call
`workspace_member_role(..., p_uid)`.

Once all thirteen are bound, that chain is transitively safe: the entry point constrains `p_uid`,
and every interior call forwards the already-constrained value.

A **partial** rollout is the dangerous state, and it does not fail loudly. If the inner function is
bound and the outer is not, an attacker calling the outer with somebody else's uid reaches an inner
call whose `p_uid` is now not `auth.uid()`, so the inner returns `false`/`NULL`, so the outer
returns a **wrong answer** — a confident "no" where the truth is "yes". Nothing raises. Nothing
logs. This is the class of defect that shipped twice in this repo already.

So: one file, thirteen replaces, applied as one statement batch. Do not split this migration.

## The idiom, exactly

Two shapes only, matching migration 174's two shapes, with `(SELECT …)` wrapping as migrations 193
and 194 use it:

- **BOOLEAN returns (twelve of the thirteen)** — a leading conjunct:
  the bound predicate `(p_uid = (SELECT auth.uid()) OR (SELECT auth.role()) = 'service_role')`
  becomes the first operand of an `AND` in front of the existing body expression.
- **TEXT return (`workspace_member_role` only)** — the `WHEN` guard of a `CASE`, with the existing
  body as the `THEN` scalar subquery and `NULL` as the `ELSE`.

**The `auth.role()` branch is required, not decorative.** Two application call sites use the service
client and pass a viewer who is not the caller:
`lib/trust-safety/reports.ts:179` calls `green_room_can_view_post` and
`lib/green-room/placements-admin.ts:353` calls `no_block`. On a service connection `auth.uid()` is
NULL, so a strict migration-194-style bind (`p_uid = (SELECT auth.uid())` alone) would silently
break both. A diff for `green_room_can_view_post` with no `auth.role()` reference in it is the
warning sign.

**The trigger-depth branch is deliberately omitted.** Migration 174 carries
`pg_trigger_depth() > 0` as a third disjunct. It is dead weight for these thirteen — no trigger
function currently calls any of them — and it is the weakest branch of the idiom: an
unauthenticated, un-identity-bound escape that any write firing a trigger enters. Plan 01's
`__tests__/rls-helper-callsites.test.ts` assertion (c) asserts that no trigger function calls a
bound helper, using latest-definition-wins semantics, so the omission stays true rather than
becoming true once and rotting. **Do NOT remove that branch from migration 174 itself** —
migrations 146 and 160 have trigger-side callers that still depend on it. Migration 174 is not
edited by this plan.

## The deliberate residual, stated plainly

After binding, an authenticated caller can still ask these functions about **themselves** — *"what
is my role in workspace W"*, *"can I see post P"*. That is self-information, equivalent to what a
normal `SELECT` already returns them. It is not a disclosure. The disclosure being closed is the
cross-user one.

`no_block` is the one helper where that reasoning does NOT hold, because `no_block(a, b)` is
symmetric: any bind permitting the policy path (`a = auth.uid()`) also permits `no_block(me, X)`,
answering *"did X block me?"* — which migration 035 named as threat T-08-03 and closed at the table
level. Owner decision D4 is therefore RELOCATE, not bind, and it is plans 04-06. **`no_block` must
not appear in migration 208.** The test asserts its absence.

|----------|-------------|

| helper → helper (`p_uid` forwarding) | Interior calls inherit the entry point's constraint — only once ALL entry points are bound. |
