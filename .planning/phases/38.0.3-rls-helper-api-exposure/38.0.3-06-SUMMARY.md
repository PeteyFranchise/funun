## B2-5: the one thing that is expected to change

Plan 03's row B12 recorded `SQLSTATE 42501: permission denied for function no_block` for an anonymous read of `release_comments`. `rc_select_public` carries no `TO` clause so `anon` evaluates it, and `anon` has never held EXECUTE on the helper — so anonymous reads already failed before this phase, and the assertion is that they fail **the same way**.

The **SQLSTATE must match**; the **message is expected to differ**. The barrier moved from a missing EXECUTE grant on `public.no_block` to a missing USAGE grant on schema `private`, which `anon` was deliberately not given, so the text may now read "permission denied for schema private". 42501 is what determines the HTTP status PostgREST hands an anonymous caller, and that is the observable behaviour being preserved. The row prints both codes, the raw message and its length, has a PASS branch for 42501, a `PASS (with a note)` branch for 3F000, and — importantly — **a FAIL branch for the read SUCCEEDING**, because a count coming back would mean anonymous reads now work where they did not, which nothing in migration 210 sanctioned.

A 42883 there is a hard FAIL with its own diagnosis: it would mean a stray `public.no_block` survives in `rc_select_public`'s predicate, which would break the authenticated read of that table too.

## The Supabase SQL editor paste hazard

The editor scans pasted text for `INTO <name>` **ignoring string literals and comments**, then fails with `relation "<name>" does not exist`. Prose is enough to break a paste.

Both files were grepped with `grep -niE "into[[:space:]]+[a-z]"` and every hit reworded or classified:

- **Part A2: zero occurrences.** Matching migration 210. One prose hit was found and reworded ("collapsing it with a healthy state into one row" → "collapsing it together with a healthy state on one row").
- **Part B2: 41 occurrences, every one a real SQL `INTO`** — 25 `INSERT INTO verify_b2_38_0_3` and 16 `SELECT … INTO` / `EXECUTE … INTO` target lists. Literal zero is unattainable in a PL/pgSQL harness: there is no other syntax for either. One prose hit was found and reworded ("a partially populated INTO must be cleared by hand" → "partially populated target variables have to be cleared by hand"), which mattered because `INTO must` is exactly the `INTO <name>` shape the editor mis-parses. `38.0.3-VERIFY-B-PRODUCTION-SINGLE.sql` uses the same real-SQL forms and pasted successfully in this editor against this database.

## Disagreements recorded rather than complied with silently

**Part B2 keeps `CREATE TEMP TABLE`, against the instruction "do not create a scratch results table; return results as a single `SELECT` result set".**

The harm behind that instruction is real and this phase paid for it: `public.zz_verify_b_results` was left in production with no RLS and had to be dropped by hand. A `pg_temp` table cannot reproduce it — PostgREST does not introspect `pg_temp`, no other session can see it, and it is destroyed when the connection closes.

And it is the only mechanism available. Every assertion in Part B2 must `SET LOCAL ROLE` and reset, which requires PL/pgSQL; a `DO` block returns no result set; and PL/pgSQL variables do not survive the block. There is no syntax for accumulating rows across role changes and emitting them without somewhere to put them. The plan itself mandates the TEMP table in two places and its automated verify greps for it.

Results **are** returned as a single `SELECT` at the foot of the file, which is the other half of the instruction. The header states the write count, states that writes to application tables are zero, and explains the `pg_temp` guarantee explicitly so no reader has to take it on trust.

The alternative considered and rejected: accumulate a JSON array in a session GUC via `set_config('funun.b2', …, false)` and unpack it with `json_to_recordset` in the closing SELECT. That creates no table at all and would satisfy the instruction literally. It was rejected because it is a novel, never-run mechanism in a file that gets pasted at production once, and the single clearest lesson of this phase — four predicate errors, all the same shape — is to reuse the proven idiom rather than invent a cleverer one.

**A second, smaller one:** the plan's `must_haves` say Part A2's pre-apply run "is a GATE on plan 05". It was, and it passed. Presenting it that way now would be misleading, so the file presents it as a standing enumeration with a recorded result. That is a change of framing, not of coverage — every check the plan asked for is present.
