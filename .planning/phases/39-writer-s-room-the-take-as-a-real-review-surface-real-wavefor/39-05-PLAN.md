<objective>
Give a private pin a server. A pin is a bookmark, not a letter: a position on one take, wordless,
visible to nobody but whoever dropped it, notifying nobody, and never carried to another take.

Purpose: the friction this removes is having to compose a sentence while you are still listening.
That only works if dropping one is free and if the writer is certain nobody else can see it — so
the enforcement point is row-level security on a table with exactly one access rule, not a filter
in a route handler that a future export or a second surface could forget to apply.

Output: two route files, a behaviour test, and a doctrine test that fails the build if a pin ever
learns how to talk to the room.
</objective>

Create `app/api/works/[workId]/versions/[versionId]/pins/route.ts` exporting `GET` and `POST`.

Shared preamble for both, copied from the comments route: resolve the promised params, create the
API client, get the user or return 401, then `resolveWorkAccess(..., 'contribute')` and return the
refusal's own status and reason when it is not granted. Room membership is verified here and only
here — the database's single policy answers "is this row yours", never "are you in this room".

GET: select `id, timestamp_ms, created_at` from `work_version_pins` filtered by
`.eq('work_id', workId).eq('version_id', versionId)`, ordered by `timestamp_ms` ascending, with a
`.limit(200)`. Map to `WorkVersionPinView` (`{ id, timestampMs, createdAt }`) and return
`{ data }`. Add an `.eq('author_user_id', user.id)` filter as well, and place a comment directly
above it stating that it is a redundant narrowing for query planning and readability, never the
safeguard — if that line were deleted the endpoint must still return only the caller's rows,
because the policy is what filters. Do not write the endpoint in a way that would leak if the
filter were removed.

POST: a `PinBodySchema = z.object({ timestampMs: z.number().int().min(0).max(86400000) }).strict()`
— no body field of any kind, because D-10 makes a pin wordless. Apply `checkRateLimit` with a key
of `work-version-pin:${user.id}`, generous enough for first-listen use (for example 300 attempts
per 15 minutes) since dropping pins in a run is the intended behaviour. Declare
`const MAX_PINS_PER_VERSION = 100` and, before inserting, count the caller's existing pins on this
version with a head-count select; return 409 with a short user-facing message when the ceiling is
reached. Then insert `{ work_id: workId, version_id: versionId, author_user_id: user.id,
timestamp_ms: parsed.data.timestampMs }`, select `id, timestamp_ms, created_at`, and return the
mapped view with status 201.

Create `app/api/works/[workId]/versions/[versionId]/pins/[pinId]/route.ts` exporting `DELETE`.
Same preamble. Validate `pinId` as a UUID and return 400 otherwise. Delete from
`work_version_pins` with `.eq('id', pinId).eq('version_id', versionId)` and `.select('id')`; when
no row comes back return 404 with a neutral message. Returning 404 rather than 403 is deliberate
and matches this repo's own-scope convention: a pin belonging to someone else must be
indistinguishable from a pin that does not exist, or the status code itself becomes a disclosure
channel.

Two things must be true of every line in both files. First, nothing here touches authorship,
credits, splits, rights, approvals, delivery state or membership. Second, neither file imports
`WriterRoomPresence`, opens a Supabase realtime channel, or emits any event onto the
`writers-room:{workId}:presence` channel — a pin adds zero events to the union that channel
carries. Do not write a code comment in either file naming the realtime API, so that the doctrine
test in Task 3 stays a meaningful signal rather than matching its own warning.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → pins routes | An authenticated room member creates, lists and deletes pins |
| Postgres row-level security | The only thing deciding which pin rows a request can see |
| realtime presence channel | A shared broadcast surface every other Writer's Room write rides, and pins must not |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-39-01 | Information Disclosure | pin visibility to other room members | critical | mitigate | A dedicated table with one `author_user_id = auth.uid()` policy and no membership branch (plan 39-01); the route's own author filter is documented as redundant so its removal could not open a leak; plan 39-11 proves the boundary with a two-account smoke against a real Postgres role |
| T-39-02 | Information Disclosure | a pin path reusing a room-activity helper | high | mitigate | Task 3's doctrine test fails on any realtime call, notification call, presence import or `writers-room:` literal in a pin route, and asserts the presence channel still registers exactly five events, none of them pin-shaped |
| T-39-14 | Information Disclosure | status code as an oracle | medium | mitigate | The delete route returns 404 for a pin that is not the caller's, never 403; a behaviour test asserts the 403 path does not exist |
| T-39-15 | Spoofing | caller-supplied `author_user_id` | high | mitigate | `PinBodySchema` is `.strict()` and carries only `timestampMs`; the route sets the author from the session, and a test asserts the inserted author equals the authenticated user |
| T-39-16 | Denial of Service | unbounded pin creation | medium | mitigate | `checkRateLimit` on the POST plus a `MAX_PINS_PER_VERSION` ceiling of 100 enforced before insert, both covered by tests |
| T-39-17 | Elevation of Privilege | service-role client near the pins table | high | mitigate | Task 3 asserts neither route imports `createServiceClient`; row-level security is never bypassed for a pin |
| T-39-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is added by this plan |
</threat_model>
