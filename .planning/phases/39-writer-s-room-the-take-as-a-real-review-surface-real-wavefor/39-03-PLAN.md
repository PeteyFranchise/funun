<objective>
Make every creation path persist a real waveform, and make the server refuse anything that is not
a well-formed peaks array. This is D-01 as amended: peaks are computed client-side for every take
including plain uploads, because the browser is already holding the exact bytes it is about to
send and the real Writer's Room ceiling is 50MB (`MAX_BYTES`, `lib/catalogue/audio-mime.ts:13`),
not Sound Vault's 250MB.

Purpose: a writer who just made a take must never see a placeholder. Everything that predates
this phase heals later through the same PATCH endpoint this plan adds.

Output: a peaks-aware upload client, two peaks-accepting routes with a real rejection test, and
the record-over studio reusing the buffer it already decoded.
</objective>

for callers that already hold a decoded `AudioBuffer` and must not decode a second time.

Inside `uploadWorkVersion`, after the existing size and MIME guards pass and before or alongside
the upload step, resolve the peaks to send:

  - if the caller supplied `input.peaks`, accept it only when `isValidPeaksPayload` says so,
    otherwise treat it as absent;
  - otherwise call `extractPeaksFromBlob(input.file)` inside a `try`/`catch` and fall back to
    `null` on any throw. A decode failure must never surface to the writer and must never abort
    the upload — the take is still saved, its `peaks` column stays null, and the player heals it
    on first open. Do not log, do not set an error state, do not add a phase.

Add `peaks` to the JSON body of the `POST /api/works/${workId}/versions/complete` call alongside
the existing `versionId`, `path`, `source`, `duration` and `label` keys.

Place the decode after the signed-URL upload has been requested rather than before it, so the
decode's few seconds overlap the network transfer instead of delaying the take appearing at all.

  - a caller-supplied, correctly shaped array is forwarded verbatim in the complete-call body;

    `peaks: null`;
  - with no caller-supplied array, the upload still resolves and the complete-call body carries
    `peaks: null`. This case exercises the decode fallback for free: there is no `AudioContext`
    in this Jest environment, so `extractPeaksFromBlob` throws and the catch is the code path

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /versions/complete` | An authenticated room member supplies a peaks array with the take record |
| browser → `PATCH /versions/[versionId]` | Any room member may write a waveform back for any take in the room |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-39-03 | Tampering / Denial of Service | client-supplied peaks array | high | mitigate | Fixed-cardinality Zod schema on both routes, per-value integer range 0..100, `.strict()` object shapes; Task 1's route test proves five malformed shapes each return 400 with no database write. The migration's `work_versions_peaks_shape` CHECK is the second line of defence |
| T-39-08 | Tampering | a room member overwriting another member's take waveform via PATCH | low | accept | `peaks` is a rendering aid derived deterministically from the take's own stored audio; it carries no authorship, credit, split, right, approval or delivery meaning. Any room member with `contribute` access can already archive and rename takes. Corruption is self-healing: the next open re-derives from the real audio |
| T-39-09 | Denial of Service | server-side audio processing | medium | transfer | No server-side decode exists. Extraction runs in the uploader's own browser against a blob capped at 50MB by `MAX_BYTES`; the cost lands on the client, not the platform. An ffmpeg or job-queue design is explicitly out of scope and its absence is asserted by a grep in Task 1 |
| T-39-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is added. A grep gate in Task 1 fails the plan if an ffmpeg or child-process dependency appears in either route |
