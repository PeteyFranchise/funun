<objective>
Carry a span through the API layer end to end: accept it, validate it at the edge, hand it to the
validated RPC, read it back, and present it — including the "needs a new position in this take"
flag D-07 requires and the "carried from" provenance D-09 asks the UI to show.

Purpose: "lower the guitars through this section" currently has nowhere to live, because
`timestamp_ms` is a single integer. After this plan the data path exists; plan 39-08 draws it.

Output: a span-aware comments route, a span-aware presenter, and tests for both.
</objective>

  <action>
Extend `COMMENT_COLUMNS` with `end_timestamp_ms` and `needs_reposition`. This single constant
feeds both the version's own comments query and the carry-offer's source query, so both gain the
span in one edit. The columns are readable because plan 39-01 added them to the table's
`GRANT SELECT` list; a column missing from that list comes back undefined rather than erroring,
which is exactly the silent failure to watch for.

Extend `CommentBodySchema` with `endTimestampMs: z.number().int().min(1).max(86400000).nullable()
.optional()`, then attach a `.superRefine` (or `.refine` on the object) rejecting any payload
where `endTimestampMs` is a number not strictly greater than `timestampMs`. Keep the object
`.strict()`. The edge check is a fast, clear 400; the database CHECK and the RPC guard remain the
authority — do not restate the duration bound here, since only the database knows the take's
duration.

Pass `p_end_timestamp_ms: parsed.data.endTimestampMs ?? null` in the `supabase.rpc(
'create_work_version_comment', {...})` argument object.

Fix the error classification while you are in it, because the new failure modes need it. The
current block assigns a constant string to `message` and then tests `message.includes(...)`,
which can never match — every RPC failure becomes a 500 today. Classify on the actual
`error.message` returned by Supabase instead: map a message containing `comment_thread_resolved`
to 409; map a message containing any of `timestamp`, `invalid_comment_end_timestamp` or
`comment_end_timestamp_out_of_range` to 400; everything else stays 500. Keep the user-facing
string generic — do not leak a raw Postgres error to the browser. Widen the 400 copy to name the
span, for example that a timed comment needs a valid track position, an optional end position
after it, and 1-2000 characters.

Update the POST-success path's rate limit key, notification title and deep link only if the span
changes their meaning — it does not, so leave them alone: a range comment notifies at its
in-point, which is where the deep link should land.

Extend `__tests__/writer-room-timed-track-comments-api.test.ts` with a new `it` block asserting
the route source contains `end_timestamp_ms` inside `COMMENT_COLUMNS`, contains

`p_end_timestamp_ms`, and still contains `supabase.rpc('create_work_version_comment'`. Add a
negative assertion that the route source contains no `.from('work_version_comments')` followed by

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → comments route | Untrusted span endpoints arrive with a comment body |
| route → `SECURITY DEFINER` RPC | The RPC runs elevated and owns every comment invariant |
| Postgres → browser | The column `GRANT SELECT` list decides what a room member can read |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-39-10 | Tampering | span endpoints on POST | high | mitigate | Zod bounds plus an `end > start` refinement at the edge; the `create_work_version_comment` guard and the `work_version_comments_end_after_start` CHECK behind it. Three independent layers, none of them the client |
| T-39-11 | Tampering | a second validation layer drifting from the database | medium | mitigate | The route deliberately does not restate the take-duration bound — only the trigger knows `duration_seconds`. The route's checks are a strict subset of the database's, so they can reject more but never admit more |
| T-39-12 | Information Disclosure | raw Postgres error text reaching the browser | medium | mitigate | Classification reads `error.message` to pick a status code but the response body keeps the existing generic user-facing string |
| T-39-13 | Elevation of Privilege | direct table write bypassing the RPC | high | mitigate | Task 1 adds a negative assertion that the route contains no `.insert(` or `.update(` against `work_version_comments`; the table has no INSERT or UPDATE grant for `authenticated` in any case |
| T-39-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is added by this plan |
</threat_model>
