# Plan 45-02: Device authorization and resumable upload control plane

## Objective

Author—not apply—the server/device boundary required for Bridge, with storage attribution and admission
bound before any automated large-file ingestion.

## Before SQL

Confirm the storage-attribution ledger/admission repair selected after migration 227 is applied and
verified. Scan migrations, untracked files, quick work, and the roadmap ledger; migration 228 remains
unavailable. Stop if quota ownership for shared work paths is unresolved.

## Tasks

1. Implement the approved device authorization/refresh/revocation model with minimal scopes, hashed or
   otherwise safely stored credential material, OS/device display metadata, expiry, rotation, and audit.
2. Add Bridge APIs for authorized target-room listing, upload intent, TUS token/config, progress/status,
   cancel, idempotent completion, and protected pull intent. Revalidate membership/block at each boundary.
3. Extend source/provenance vocabulary only through human-gated schema and type updates; server derives
   user/device/work/path. Clients cannot choose actor, storage path, owner attribution, or rights state.
4. Enforce approved class/format/size/count/byte/concurrency quota before minting; reserve/admit bytes
   transactionally; reconcile completion/cancel/expiry/orphans; fail closed when admission is unavailable.
5. Verify stored size/type by content rather than filename alone, bind checksum/idempotency, and retain
   immutable new object paths. Do not overwrite an existing take.
6. Test stolen/revoked/expired device, cross-account/work, removed/block, forged path/metadata/checksum,
   duplicate/retry/race, abandoned upload, quota exhaustion, service outage, and TUS replay.

## Human gates

Security reviews auth/token/key handling and storage admission. Owner applies any migrations and performs
remote two-account/RLS/privilege verification. Until recorded, Bridge production APIs remain disabled.
