# Phase 38.0.1 Plan 16: Wire the Consent Route to the Ask Table Summary

`decidePermissionRequest` now has a caller: the Member's consent route reads pending asks from
`public.workspace_permission_requests`, approving moves the matching row out of `pending` after the
consent lands, and declining records the refusal without touching `workspace_grants` at all.

## READ FIRST — cross-plan notes

**GET response shape is unchanged, byte for byte.** No key was added, removed or retyped;
`requested` is still `toPermissionRows(...)`, still in catalogue matrix order, still
`{ permission, tier, sensitive }`. Plan 12 needs no reconciliation on this.

**Plan 12 has its own copy of the defect to avoid.** Plan 12's task 2 instructs its route to resolve
"the requested-but-ungranted set from the workspace's pending grant requests." If plan 12 copied
plan 07's derivation (dead-lineage grant rows) rather than reading
`workspace_permission_requests`, its aggregate list will silently disagree with the per-relationship
list this route now returns — plan 12's page would omit exactly the first-time asks WSR-27 exists to
show. The correct read is `listRequestsForWorkspace(service, { workspaceId, relationshipId, states:
['pending'] })`. This route's `loadPendingAsks` is the reference shape.

**Plan 13's client contract holds as written.** Plan 13 says "Approve and Decline post to
`/api/roster/relationships/{relationshipId}/consent` with a one-element `permissions` array." Both
do. Approve needs no body change at all. Decline adds one key: `{ permissions: [p], decision:
'declined' }`.

**Nothing outside this plan's two files was touched.** No neighbour's file was edited, and no
neighbour's test was run as a gate (plans 11 and 12 are not in this worktree).

## What Was Built

### Task 1 — the pending list comes from the real table

`resolveOutstandingRequests` no longer walks the grant chain. It now sits on a new
`loadPendingAsks`, which calls `listRequestsForWorkspace` for `state = 'pending'` on this
relationship and keys the result by permission.

Why this matters, restated because it is the whole point of the plan: the old definition was "a
delegated grant row whose lineage is dead." A row like that can only exist *beneath* a Member
consent root (migration 191's `workspace_grants_consent_root_or_lineage_check`), so the set could
only ever populate after a consent-then-revoke. A workspace asking for the first time — zero grant
rows in existence — was structurally invisible. There is now a test that seeds an ask with an empty
`workspace_grants` table and asserts it appears.

Three imports died with the derivation: `loadRelationshipGrantChain`, `isGrantChainLive` and
`MEMBER_CONSENT_SOURCE`. The route reads no grant rows for the requested set at all any more.

The stale comment asserting "There is no `workspace_permission_requests` table in this schema" is
gone, along with the block documenting the derived definition. A file that makes security decisions
should not carry a confident falsehood about its own schema.

`loadPendingAsks` matches the ask's project scope **exactly**. A relationship-wide consent does not
answer a project-scoped ask and vice versa — the unanswered question stays on the Member's list,
which is honest, because nobody answered it.

### Task 2 — approve moves the row; decline is a new act, not a repurposed one

POST now has three readings, and the file header states them as a table:

| Request | Meaning | Grant rows touched |
|---|---|---|
| `POST { permissions }` | the Member grants | consent issued; a matching ask is also moved to `approved` |
| `POST { permissions, decision: 'approved' }` | the Member answers an ask | consent issued; the ask must exist |
| `POST { permissions, decision: 'declined' }` | the Member refuses an ask | **none** |
| `DELETE { permissions }` | the Member revokes | consent rows stamped revoked |

**Why POST for decline rather than a new verb.** Three reasons, in order of weight. (1) Plan 13, the
consumer, already specifies that Approve and Decline both post to this path with a one-element
`permissions` array — a different verb would have broken a plan that depends on this one. (2) The
route's verbs are already partitioned by *what is written*: POST writes forward-looking consent
state, DELETE takes something away. A decline writes forward-looking state, so it is a POST. (3)
Putting decline on DELETE would have been the exact confusion the plan warned against: it would sit
one `if` away from the revoke path forever.

**Decline touches no grant.** `declineAsks` calls `decidePermissionRequest` with `'declined'`, which
never reaches `issueMemberConsent` and never reads `workspace_grants`. Two tests pin this: one
asserts no grant row is written, and one seeds a *live consent for the very same permission* and
asserts it is still live and unrevoked after the decline.

**Decline deliberately runs no consent pre-flight.** Consent requires an accepted relationship;
saying no does not. A Member with a merely `proposed` relationship can still close the question, and
there is a test for it. Requiring consent-eligibility to decline would trap the ask open.

**Ordering was not reimplemented.** The route calls `decidePermissionRequest` and lets it own the
sequence. Nothing in this route stamps a row and then issues.

**Fail-closed on a decision with nothing to decide.** When `decision` is present, every named
permission must have an open ask on this relationship at this scope, or the whole request is refused
409 before any write. Being told "declined" about a question nobody asked, or "approved" about one
already answered, is being told something untrue. When `decision` is absent the request is a plain
grant, so a missing ask is simply nothing to move — the pre-R-19 contract, unchanged.

Identity is checked twice, as this codebase does everywhere (D-49): `openConsentContext` proves the
relationship names the caller, and `decidePermissionRequest` independently re-compares the request
row's own `member_user_id`. A test seeds a drifted `member_user_id` (unstorable in the real schema
thanks to migration 195's trigger) and asserts the second check refuses it.

### Deviation — the all-or-nothing pre-flight (Rule 2, missing critical correctness)

Approving splits a permission set across two writers: asked permissions go through
`decidePermissionRequest`, unasked ones through `issueMemberConsent`. `issueMemberConsent` is
all-or-nothing *across the set it is handed* — so once the set is split, a batch of
`['view_metadata' (asked), 'approve_releases' (unasked, authority-tier on an operational
relationship)]` would write the first before the second was refused. That is a partial write of
authority the Member never completed, and it is reachable: a workspace can ask for an authority-tier
permission on an operational relationship.

`preflightConsentSet` restores the property by running `assertMemberMayConsent` — the *same*
assertion both writers use, not a second opinion — over the whole set before anything is written. It
can only turn a would-be write into a refusal; it approves nothing and both writers still re-run the
assertion on their own inputs. Because it is the same function, every existing refusal message and
status code is byte-identical to before (the structural-exclusion, unrecognised-permission and
authority-tier tests all pass unchanged). Covered by a new test asserting a mixed set writes nothing
and leaves the ask pending.

### Task 3 — tests

23 new cases. The in-memory Supabase stand-in gained `in()`, `order()` and an injectable insert
failure (`installClients(store, user, { failInsertOn: 'workspace_grants' })`), which is how the
"consent write did not land" case is exercised honestly rather than by proxy.

Coverage of the plan's required list:

| Required case | Test |
|---|---|
| approve issues consent AND moves the row | `issues the consent AND moves the request row out of pending` |
| approve leaves the row pending when the consent write fails | `leaves the ask pending when the consent write does not land` |
| decline records the decline and writes no grant | `records the decline and writes no grant row of any kind` |
| decline of an already-decided request is refused | `refuses a decline of an already-decided request and leaves it as it was` |
| a request naming a different Member is refused | `refuses an ask whose member_user_id names somebody else` (approve and decline) |
| a first-time ask with zero grants appears in the list | `shows a first-time ask with zero pre-existing grant rows of any kind` |

Plus: a plain grant clears a matching ask; an explicit approve of an unasked permission is refused;
an approve of a non-pending ask is refused; a mixed refusable set writes nothing; a decline works on
a `proposed` relationship; a workspace owner is refused on the decline path; `decision: 'withdrawn'`
is a 400; only `pending` rows appear in the list (approved/declined/withdrawn do not); an ask on
another relationship does not appear; an already-granted permission is not re-asked; a revoke leaves
pending asks untouched; a `decision` key on DELETE is a 400.

## Deviations from Plan

**1. [Rule 2 — missing critical correctness] All-or-nothing pre-flight on approve**
- **Found during:** Task 2
- **Issue:** Splitting an approve across two writers loses `issueMemberConsent`'s all-or-nothing
  guarantee for the set; a mixed set could partially write.
- **Fix:** `preflightConsentSet` runs the canonical `assertMemberMayConsent` over the whole set
  before any write. Refusal-only; no authorization is granted by it.
- **Files modified:** `app/api/roster/relationships/[relationshipId]/consent/route.ts`
- **Commit:** f392f9e5

**2. [Interpretation] `decision` on DELETE is a 400, not ignored**
- The plan did not ask for this. DELETE already refuses `projectId` rather than dropping it
  silently, on the reasoning that a caller must never believe they narrowed an act they did not.
  The same reasoning applies to a caller who believes they declined when they revoked, so DELETE
  keeps the narrower schema and a `decision` key is a 400.

No acceptance criterion in this plan was stated as an exact grep count, so the
mis-specification escape hatch did not apply.

## Notes for the Verifier

- The decline path writes **one** audit row (`workspace.permission_request.declined`, from
  `decidePermissionRequest`) and no second one from the route. A second entry would say the same
  thing twice under a different name. The approve path writes **two** and they are not duplicates:
  `workspace.permission_request.approved` (the question was answered) and
  `workspace.consent.granted` (access was issued). Those are genuinely different facts.
- Approve returns the permissions **newly written by this call**, unchanged from before. Approving a
  permission the Member had already consented to returns `permissions: []` with a 200 and still
  moves the ask — a no-op success, not a failure, exactly as re-consenting has always behaved.
