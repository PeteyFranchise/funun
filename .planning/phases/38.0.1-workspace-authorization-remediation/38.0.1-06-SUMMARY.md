# Phase 38.0.1 Plan 06: Grant Authority I/O Services (F6 Fix) Summary

**Broke the F6 bootstrap deadlock: `assertGrantIssuable` now derives a workspace admin's authority from the Member's live consent root (new `consent-service.ts` + `grant-lineage-service.ts`) instead of circularly from the admin's own grant rows, so a workspace can issue its first grant for the first time since ship.**

## Accomplishments

- **`lib/workspaces/grant-lineage-service.ts`** (new) — the I/O half of the delegation-lineage walk. `loadRelationshipGrantChain` loads a relationship's entire `workspace_grants` row set in one query (including revoked rows, which the walker needs to see). `resolveLivePermissionsForRelationship` re-derives, on every call, the set of permissions whose lineage chain is live per the pure `isGrantChainLive` walker (plan 03). `resolveConsentRootPermissions` returns only the permission set carried by the relationship's own live `member_consent` root rows — this is what `assertGrantIssuable` now uses as `granterHolds`.
- **`lib/workspaces/consent-service.ts`** (new) — the sole writer of a `source = member_consent` row in the codebase. `issueMemberConsent` loads the relationship, resolves its authority tier, calls the pure `assertMemberMayConsent` (plan 03), and on approval writes one row per approved permission with `parent_grant_id = null`; a refusal writes nothing for any permission in the request (all-or-nothing); re-consenting to an already-live permission is a no-op success rather than a duplicate row. `revokeMemberConsent` sets `revoked_at`/`revoked_by` on the Member's own root rows and never deletes — a revocation kills every delegated descendant at the next read via `isGrantChainLive`, with no cascade job.
- **`lib/workspaces/grant-service.ts`** (modified) — the actual F6 fix. `assertGrantIssuable`'s `granterHolds` is now sourced from `resolveConsentRootPermissions` instead of the old circular call to `resolveEffectivePermissions(..., actorUserId: granterUserId)`. `resolveEffectivePermissions`'s Step 4 was re-sourced from a direct `workspace_grants` read to `resolveLivePermissionsForRelationship`, so a grant whose lineage chain is dead is dropped on every call. The header doctrine gained a numbered item (5) documenting the F6 correction. No "empty means allow" branch was added anywhere — refusal is still the default when no consent root exists.

## Decisions Made

- **`resolveConsentRootPermissions` excludes delegated rows on purpose.** Only live `source = member_consent` rows contribute to `granterHolds` — a delegated grant relays the Member's consent onward but is never itself a further source of authority a second admin could re-delegate from. This matches D-21's exactly-two-tiers model.
- **`issueMemberConsent` returns only newly-written permissions.** A re-consent request where some permissions are already live returns `ok: true` with only the subset actually inserted in that call (possibly empty) — read literally from the plan's "return the written permissions" instruction, and verified by the no-op re-consent test.
- **Followed the schema_state directive's migration numbering over the plan body's stale references.** The plan's `<context>` and Task 1 `read_first` list cite `supabase/migrations/193_workspace_consent_lineage_schema.sql` and describe migration 194 as the SQL twin; the repository's actual highest-applied-relevant migration is `191_workspace_consent_lineage_schema.sql` (matching the prompt's explicit `<schema_state>` instruction), and `grant-lineage.ts`'s own shipped header names migration 192 as the SQL twin. Both new modules' header comments cite migration 191 (schema) and 192 (SQL twin) accordingly, per the authoritative sources rather than the plan's stale numbering.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `grant-service.test.ts`'s pre-existing `workspace_grants` query stub no longer matched the real query shape**
- **Found during:** Task 3
- **Issue:** The existing fake Supabase client's `workspace_grants` mock chained `.eq().eq().is('revoked_at', null)`, matching the OLD direct query `resolveEffectivePermissions` used to issue. The new implementation delegates that read to `grant-lineage-service.ts`'s `loadRelationshipGrantChain`, which issues `.eq().eq()` with no `.is()` (revoked rows must reach the pure walker, not be filtered out by the query). Left unchanged, the old fake's second `.eq()` would return a plain object instead of an awaitable, and existing grant fixtures (bare `{permission, project_id}` shape) would resolve to `revokedAt: undefined`, which the lineage service's `!== null` check treats as "revoked" — silently zeroing every existing test's expected result.
- **Fix:** Rewrote the fake's `workspace_grants` builder to the real two-`.eq()` shape, and re-fixtured every existing test's grant rows to the full `GrantChainRow` shape (`id`, `parent_grant_id: null`, `source: MEMBER_CONSENT_SOURCE`, `revoked_at: null`, `relationship_id`) via a `rootRow()` helper, preserving each test's original intent (membership/relationship/tier gating, project scoping, D-39/D-49 semantics).
- **Files modified:** lib/workspaces/grant-service.test.ts
- **Verification:** `npx jest lib/workspaces` — 317/317 tests pass (446/446 including the structural-exclusions suite)
- **Committed in:** e249a728 (Task 3 commit)
