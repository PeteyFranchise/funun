# Phase 38.0.1 — UI Design Contract

> Visual and interaction contract for **WSR-27 only**: the minimal Member-facing consent surface
> where a Member reviews pending workspace permission requests, approves or declines each
> permission individually, and revokes previously granted permissions. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope discipline:** this phase is a security remediation, not a UX phase. Everything below
> covers exactly one surface. Workspace chrome, the active-workspace switcher, the Roster/Activity
> room, roster cards, the catalogue view, contracts surfaces, audit surfaces, and the "Appears on"
> shelf belong to Phase 38.1 and are deliberately absent here.
>
> **Design system note:** Funūn has a mature, hand-rolled dark Tailwind design system (38 phases
> deep) — no shadcn, no component library. `components.json` does not exist in this repo and this
> is not proposed for this phase: introducing a component system at 38.0.1, into a security
> remediation phase with zero new dependencies otherwise, would fragment the design language and
> add unreviewed surface area to a phase whose entire point is *reducing* risk. Every token, class,
> and interaction pattern below is derived from shipped precedent (`components/collaborators/*`,
> `components/split-sheets/SplitApprovalView.tsx`, `components/settings/*`,
> `app/(artist)/vault/page.tsx`'s "Appears on" badge, Phase 27's invite/waitlist surfaces) — no new
> tokens are introduced.

Applies the authenticated in-app surface's established tokens directly: `bg-ink`, `text-lav` /

(`components/admin/console-theme.ts`), which governs staff surfaces only and must never be reused
here (a Member-facing screen must look like the artist app).

## Placement & Entry Points

**Route:** `/settings/permissions` — a fourth entry in the existing Settings tab bar
(`components/settings/SettingsTabs.tsx`), alongside "Rights & contracts," "Public profile," and
"Payouts." Tab label: **"Permissions."**

**Why a tab, not a new nav item:** the existing `ArtistNav.tsx` top-level list is a deliberately
short, stable set (Ideas, Sound Vault, Contract Locker, Deals, Sync Library, Collaborators, The
Green Room, Antenna, PitchPlug, Benchmarks, Launchpad, Rights Coach, Earnings, Settings) — adding a
thirteenth top-level item for a beta-cohort, currently-disabled feature (kill switch is OFF per
R-03) is disproportionate. Settings already gathers "things about your rights and your account" —
this is one more.

**Implementation note for the planner (not a visual decision, flagged here because it constrains
the interaction contract):** `SettingsTabs.tsx` drives save-on-switch through
`settings.saversForTab(activeTab)` — every existing tab is a form. This surface has no fields to
save; it is an action list. `saversForTab('permissions')` must return `[]` so switching to or away
from this tab is instant, with **no "Saving…" label and no dirty-state prompt** — the tab-bar
visual (`border-lav` active state, `text-white/40` inactive, `-mb-px border-b-2 px-3 py-2.5
text-sm font-semibold`) is reused unchanged; only its save-coupling is bypassed for this one tab.

**Secondary entry point (discretion, not required for WSR-27):** a workspace permission request is
a natural fit for the existing `NotificationBell` / `NotificationPanel` pattern (deep-link to
`/settings/permissions`). Recommended, not required — do not block this phase on wiring a new
notification type if it adds scope; the tab is reachable and sufficient on its own.

## Spacing Scale

Declared values (must be multiples of 4) — matches the codebase's existing informal scale, no new
values introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Tag-to-label gaps, chip internal padding |
| sm | 8px | Row-internal gaps (checkbox/button to label), `gap-2` |
| md | 16px | Card padding (`p-4`), spacing between rows within a card |
| lg | 24px | Card padding on the page shell (`p-6`), gaps between cards (`gap-6`) |
| xl | 32px | Gap between "Pending requests" and "Active permissions" sections |
| 2xl | 48px | Empty-state vertical padding (`py-12`) |

Exceptions: none. Every tappable control (Approve, Decline, Remove access, the two-step confirm
buttons) clears the 44px touch-target minimum via the existing `px-4 py-2` / `px-3 py-1.5` button
padding convention — do not introduce a smaller control on this surface, which asks people to make
real decisions about real authority.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0a0a0f` (`ink`) | Page background |
| Secondary (30%) | `#0E0D1E` (`card`) with `border-hair` | Every request card and active-permission card |
| Accent (10%) | Brand gradient `bg-grad` (`linear-gradient(105deg,#818CF8 0%,#D946EF 100%)`) | **Reserved for exactly one element on this surface: the per-row "Approve" button.** This is the doctrine's real center of gravity — the Member's affirmative act of granting authority — so it gets the same visual weight Phase 27 reserved for "Send invite." Never used for "Decline," "Cancel," page chrome, or any tag. |
| Destructive | `rose-500` family (`border-rose-500/30 bg-rose-500/10 text-rose-200`, confirm button `bg-rose-500/90 hover:bg-rose-500`) | **Reserved for "Remove access" (revocation) only** — matches `CollaboratorForm`'s delete-confirm exactly. Declining a *request* is not destructive (nothing existing is being removed) and must never use this color; revoking an *active* grant removes real, relied-upon access and should read with that weight. |
| Authority-tier tag | `brandindigo` at low opacity (`border-brandindigo/30 bg-brandindigo/10 text-brandindigo`) | The exact treatment already shipped for the "Appears on" badge in `app/(artist)/vault/page.tsx` — reused verbatim for the "Needs a signed agreement" tag on authority-tier permission rows. Informational, never a button. |
| Never-bundled / sensitive tag | `money`/`money2` amber (`border-money/30 bg-money/10 text-money2`) | Reserved for the three D-40 permissions (clean-master download, private rights identifiers, earnings visibility) — the "Granted one at a time · every use logged" tag. Distinct from both the accent gradient and the authority-tier indigo, so a sensitive permission is never visually confusable with an ordinary or merely-authority one. |

Accent reserved for: the per-row Approve button, nothing else on this surface. There is no
"select all," "approve all," or bulk-grant control anywhere on this page — every permission is its
own decision, made and rendered individually. This is a structural rule, not a style preference:
it is what makes it impossible for a future edit to accidentally sweep a D-40 sensitive permission
into a one-click bulk action.

## Copywriting Contract

Voice: plain, confident, non-corporate (Funūn's established artist-facing register — "We got you,"
not SaaS-speak). Never the word "verified" for a stored document (D-37) — use provenance language
("attached," "uploaded") instead. No permission is ever shown by its database slug.

| Element | Copy |
|---------|------|
| Tab label | "Permissions" |
| Page heading | "Workspace permissions" |
| Page subhead | "See exactly what a workspace is asking to do with your work — and decide, one permission at a time." |
| Pending section heading | "Pending requests" |
| Active section heading | "Active permissions" |
| Empty state (nothing pending, nothing active) | Heading: "No workspace has asked for access yet." Body: "When a team or label wants to work on your catalogue, you'll see exactly what they're asking for here — and nothing happens until you say yes." |
| Empty state (pending only, no active grants) | Section "Active permissions" is simply omitted — never shown empty with placeholder copy underneath a populated "Pending requests" section. |
| Pending request card header | "{Workspace name} wants access" |
| Authority-tier row document link | "They've attached a signed agreement for this — [View it]" |
| Sensitive-permission row tag | "Granted one at a time · every use logged" |
| Authority-tier row tag | "Needs a signed agreement" |
| Approve action (per row) | "Approve" |
| Decline action (per row) | "Decline" |
| Row resolved — approved | "Approved" (quiet green `text-emerald-300` label replacing the two buttons) |
| Row resolved — declined | "Declined" (quiet `text-white/40` label replacing the two buttons; workspace may ask again later) |
| Active permission row | Plain-language label + "Granted {relative date}" meta line |
| Revoke action | "Remove access" |
| Revoke confirm step | "Remove {workspace}'s access to {permission, lowercase}? They'll lose it immediately." + solid `bg-rose-500/90` "Yes, remove" + text-only "Cancel" — mirrors `CollaboratorForm`'s delete-confirm exactly |
| Revoke success | Row disappears from "Active permissions" immediately; no separate success toast needed (the row's absence is the confirmation, matching this codebase's inline-swap convention) |
| Structural-exclusion footnote (page-bottom, once, muted) | "Payout and tax details are never part of any workspace request — there's no permission for it, here or anywhere in Funūn." Rendered once, `text-xs text-white/30`, at the very bottom of the page. Not repeated per-card: stating an absence nobody asked about, on every card, would be noise rather than reassurance. |

## Surfaces & Interaction States

### 1. `/settings/permissions` — page shell

Reuses the Settings page shell exactly (`app/(artist)/settings/layout.tsx`'s heading + tab-bar
container). Below the tab bar: subhead, then "Pending requests" section (if any pending rows
exist for the signed-in Member), then "Active permissions" section (if any active grants exist),
then the structural-exclusion footnote. If both sections are empty, render the empty state instead
of two empty section headers.

### 2. Pending request card

One card per requesting workspace with at least one undecided permission request. Card shell:
`rounded-card border border-hair bg-card p-6`. Header row: workspace name (card-heading weight) +
optional relationship context line ("Roster relationship since {date}" — reuses whatever the
roster relationship's accepted-date already is, no new field).

Each requested permission renders as its own row inside the card:

- Plain-language label (Body style, from the table above) on the left.
- Tag(s) immediately after the label where applicable: authority-tier indigo tag and/or
  sensitive-permission amber tag. A permission is never both — an authority-tier permission that
  is *also* one of the three D-40 names does not exist in the current catalogue (`request_signatures`,
  `edit_rights_information`, `approve_releases`, `deliver_assets`, `act_on_behalf` are the only
  authority-tier values, and none overlaps the three D-40 sensitive names), so no dual-tag case
  needs to be designed.
- If authority-tier: the document link line renders directly beneath the label
  ("They've attached a signed agreement for this — [View it]"), using an ordinary text link style
  (`text-brandindigo underline-offset-2 hover:underline`) — opens the attached document via
  whatever the Contract Locker's existing document-view route already is; this phase does not add
  a new document viewer.
- Right-aligned: two text buttons, **"Approve"** (accent gradient, `bg-grad` pill,
  `rounded-lg px-4 py-2 text-sm font-semibold text-white`) and **"Decline"**
  (`text-sm font-medium text-white/50 hover:text-white/80`, no border, no fill).
- On action, the row's buttons are replaced in place by the resolved-state label ("Approved" /
  "Declined") — no page reload, no toast, no modal. This is a per-row, immediate, non-blocking
  action: a Member may approve two permissions and leave a third pending in the same card: **there
  is no "submit" step and no requirement to resolve every row before leaving the page.**
- A card whose every row has been resolved (approved or declined) is removed from "Pending
  requests" on next load (or immediately, if simpler to implement client-side — planner's call);
  approved rows move into "Active permissions."

### 3. Active permissions

Grouped by workspace, same card shell as pending requests but without the Approve/Decline
machinery. Each row: plain-language label, same tags where applicable, "Granted {relative date}"
meta line, and a right-aligned **"Remove access"** text button
(`text-sm font-medium text-white/50 hover:text-rose-300`).

Clicking "Remove access" expands an inline two-step confirm in place of that one row (does not
affect sibling rows), matching `CollaboratorForm`'s delete-confirm pattern exactly:

```
Remove {workspace}'s access to {permission}? They'll lose it immediately.
[Yes, remove]  Cancel
```

`Yes, remove` is a solid `bg-rose-500/90 hover:bg-rose-500` button; `Cancel` is text-only and
collapses the confirm back to the normal row. On success, the row disappears from the list — no
separate success state, matching the codebase's established inline-swap convention (Phase 27's
denial/waitlist replace-in-place precedent).

### 4. Empty state

Centered within the page content area (reuses `CollaboratorRoster`'s empty-state layout: centered
heading + one-line body, no icon needed — see icon note above, this surface uses none), `py-12`
vertical padding.
