<objective>
The HTTP surface for R-01 / WSR-01: the Member's own consent endpoint. D-21 always said the Member
is the root of authority; the Member's side was never built, which is why F6 left the layer inert.

**Placement is a security decision, not a filing decision.** This route sits under
`app/api/roster/relationships/**`, beside the existing Member-side roster surface, and is gated with
`requireMemberApiAccount` plus a `member_user_id === caller` comparison. It must NOT live under
`app/api/workspaces/**` and must NOT call `requireWorkspaceAccess` — the consent act belongs to the
Member, who is deliberately not a member of the claiming workspace and must be able to act without
ever entering its context (the same reasoning `app/api/roster/relationships/route.ts` already
records in its own header).

Purpose: give the Member an API they can actually reach, so the authority model this phase builds is
exercisable rather than theoretical.

Output: a three-verb route (GET pending/active, POST approve, DELETE revoke) over
`consent-service.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `/api/roster/relationships/{id}/consent` | Untrusted body and path; the identity that matters is the session's, never the body's. |
| workspace admin -> the Member's consent | The admin must not be able to grant on the Member's behalf; this is the forgery surface the whole endpoint creates. |
| this route -> `workspace_grants` | Service-role write, only after the Member-identity comparison. |
