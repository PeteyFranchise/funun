**BEFORE UPDATE trigger closes the pre-existing R-17/WSR-25 custody-seizure hole with a SECURITY-DEFINER-function structural exemption, not a service_role allow-list — but the legitimate custody-transfer route must be updated to call that function before this migration is safe to push.**

## Accomplishments

- Authored `supabase/migrations/190_vault_projects_user_id_immutable.sql`: a `BEFORE UPDATE FOR EACH ROW` trigger, `guard_vault_projects_user_id_immutable()`, that raises `insufficient_privilege` whenever `NEW.user_id IS DISTINCT FROM OLD.user_id` and `current_user` is not the database superuser (`postgres`) — refusing the change from the project's own owner, a Phase 21 `co-owner`/`editor`, and a workspace `edit_metadata` grant holder alike, regardless of which RLS branch on migration 186's `vault_projects_update_owner_or_editor` policy admitted the statement.
- Implemented the D-PF-01 resolution's mandated mechanism exactly: the exemption is **structural**, not role-based. `public.transfer_vault_project_custody(p_project_id, p_from_user_id, p_to_user_id)` is a new `SECURITY DEFINER` function, owned by `postgres` (this project's confirmed superuser role per PREFLIGHT.md P1), that performs the actual `UPDATE` internally. Because `SECURITY DEFINER` changes `current_user` to the function's owner for the duration of its execution (and any trigger it fires), the guard trigger's exemption is available only to code that calls through this specific function — a raw `service_role` `.update()` anywhere else, today or in the future, stays refused.
- Authored `__tests__/migration-190.test.ts`: 25 text-lock assertions covering both functions' shapes, the trigger's idempotent create, the single-element `current_user NOT IN ('postgres')` exemption (explicitly asserting it is NOT a `service_role`/`authenticated`/`anon` allow-list), the negative guarantees (zero `CREATE POLICY`/`DROP POLICY`/`WITH CHECK`, no other table touched), and housekeeping (HUMAN-GATED marker, numbering, citation, schema-cache reload).
- `npx jest __tests__/migration-190.test.ts` — 25/25 passing. `npx tsc --noEmit` — clean.
- Edits no policy anywhere: migration 186's `vault_projects_update_owner_or_editor` policy is byte-for-byte untouched, confirmed by grep and by the test suite's negative assertions.

## Decisions Made

- **Followed the D-PF-01 resolution, not the plan's original (pre-resolution) task text.** `38.0.1-02-PLAN.md`'s Task 1 `<action>` still describes the rejected design (`current_user IN ('authenticated', 'anon')` role block-list, from RESEARCH.md Pattern 5's original sketch, written before the owner resolved D-PF-01 on 2026-09-06). Per this plan's dispatch objective ("D-PF-01 IS RESOLVED — read this before authoring"), the actual migration implements the resolved decision instead: the trigger refuses `user_id` changes from **all** ordinary traffic, and the D-29 custody transfer is exempted **structurally** (a SECURITY DEFINER function owned by `postgres`), never by naming `service_role` in an allow-list. This also means the plan's original Task 1 acceptance-criteria line "the role literal(s) appearing in the trigger's `current_user IN (...)` list match D-PF-01" is satisfied in spirit (the single role literal, `postgres`, matches D-PF-01's confirmed superuser identity from PREFLIGHT.md P1) but not in the literal `IN (...)`-as-refuse-list shape that stale criterion assumed — the construct is `current_user NOT IN ('postgres')`, a one-element **permit**-list of the superuser, which is exactly what the binding resolution required instead of a role-based refuse-list.
- **Named the exemption function `public.transfer_vault_project_custody()`** rather than inventing a name from RESEARCH.md's `accept_custody_transfer` sketch, because its scope is deliberately narrower than a full transactional accept RPC (RESEARCH's Pattern 3/5 sketch folds in more responsibility than this migration's scope covers) — it does exactly one thing: the filtered `UPDATE`, reproducing `app/api/vault/custody-transfers/route.ts`'s existing double filter verbatim.

## Deviations from Plan

### D-PF-01 escape hatch — surfaced, not silently worked around

**This is the one deviation from a literal reading of the plan, and it is deliberate, per the D-PF-01 resolution's own binding instruction ("If the legitimate custody-transfer path cannot cleanly move into a SECURITY DEFINER function ... STOP and surface it. Do NOT silently fall back...").**

- **Found during:** Task 1, while designing the structural exemption.
- **The technical move is clean.** `app/api/vault/custody-transfers/route.ts`'s accept branch (lines 296-302) is a single filtered `UPDATE` — `.from('vault_projects').update({ user_id: row.to_user_id }).eq('id', row.project_id).eq('user_id', row.from_user_id)` — with no interleaved application-layer checks that can't express in plpgsql. Moving it into `public.transfer_vault_project_custody()` and calling it via `service.rpc('transfer_vault_project_custody', { p_project_id, p_from_user_id, p_to_user_id })` is a one-call-site change following a pattern already used by roughly twenty other `service.rpc()` call sites in this codebase (e.g. `lib/security/upload-admission.ts`, `lib/jobs/queue.ts`, `lib/invites/mintInvite.ts`).
- **The obstacle is this plan's declared scope, not plpgsql expressiveness.** This plan's dispatch explicitly restricts file changes to `supabase/migrations/190_vault_projects_user_id_immutable.sql` and `__tests__/migration-190.test.ts` only ("you own ONLY..."; success criteria: "No modifications to STATE.md, ROADMAP.md, or any file outside the two declared"). `app/api/vault/custody-transfers/route.ts` is outside that declared scope.
- **What this means in practice:** as authored, this migration's trigger will refuse the *existing* (unmodified) accept branch's raw `.update()` call too — it runs as `service_role`, not `postgres`, so it gets the same `insufficient_privilege` refusal as any other caller. **If migration 190 is pushed to production without first (or atomically) updating `route.ts`'s accept branch to call the new RPC, the legitimate custody-transfer flow breaks** — Task 3 step 4's non-regression check (a real two-sided transfer) will fail.
- **What was NOT done:** the route.ts change itself, and NOT a silent fallback to a role-based allow-list (e.g. permitting `service_role` directly) that would have kept the existing route.ts working without any application change — that fallback was explicitly rejected by the D-PF-01 resolution as "the same shape as finding F1."
- **Recommendation to the owner:** either (a) expand this plan's scope by one file and land the one-call-site `route.ts` change alongside this migration before push, or (b) treat it as a fast-follow that must merge no later than the same deploy as this migration's push, since migration 190 is otherwise safe to push alone per Task 3's own framing ("Migration 190 is INDEPENDENT of everything else in Phase 38.0.1 and may be pushed alone, first"). Do not push migration 190 without that companion change landing first or in the same deploy.
