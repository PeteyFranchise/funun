# Phase 38.0.1 Plan 12: Member Consent Surface — Data and Copy Summary

Gave WSR-27 its two missing halves: a plain-language vocabulary that translates all nineteen grantable permissions into sentences a musician reads without a glossary, and a read-only aggregate endpoint that hands the client the Member's own pending asks and live grants, grouped by workspace, with no second mutation surface anywhere near it.

## What Was Built

**Task 1 — `lib/workspaces/permission-copy.ts` (131 lines, pure, zero I/O)**

- `PERMISSION_PLAIN_COPY: Record<WorkspacePermission, string>` — all nineteen sentences, copied verbatim from the approved UI-SPEC's "Plain-Language Permission Copy" table. Typed as a *full* record deliberately: adding a permission to the catalogue without adding copy is now a `tsc` failure, which is what makes `npx tsc --noEmit` (not a hand-counted test) the real proof the table is complete.
- `AUTHORITY_TIER_TAG` (`Needs a signed agreement`), `SENSITIVE_PERMISSION_TAG` (`Granted one at a time · every use logged`) and `STRUCTURAL_EXCLUSION_FOOTNOTE` exported as named constants, verbatim from the Copywriting Contract, so no component inlines approved wording.
- `describePermissionForMember(permission)` returns `{ permission, copy, tier, sensitive, tags }`, composing tier from `PERMISSION_TIER` and sensitivity from `isBundleExcluded` rather than restating either axis. Never throws.
- Header comment records, in order: that `PERMISSION_LABELS` is the ops/admin label set and stays exactly as it is; that this module is the Member-facing vocabulary for WSR-27; that the strings are verbatim and must not be paraphrased in a component; that no surface may show a slug or an ops label; and the D-37 rule that "verified" is never used about a stored document.

**Task 2 — `app/api/settings/permissions/route.ts` (242 lines, `GET` only)**

- `requireMemberApiAccount` first, then `isWorkspaceAccessEnabled` returning 503.
- Roster relationships read through the RLS-scoped session client filtered on the authenticated user id, then filtered a second time in application code.
- Pending asks from `listRequestsForMember(service, { memberUserId, states: ['pending'] })`.
- Active grants from `resolveConsentRootPermissions` per relationship, `projectId: null`.
- Workspace display fields (name, type) via the service client after the gate, memoised per workspace id for the request.
- Response: `{ pending: WorkspaceConsentGroup[], active: WorkspaceConsentGroup[] }`. A group with no permissions is omitted; `active` is `[]` rather than absent. Permission rows are built by walking `WORKSPACE_PERMISSION_VALUES` (catalogue matrix order), so a value outside the grantable catalogue cannot reach a response regardless of what a row carries; both structurally excluded names are filtered a third time defensively.
- No email, no member id (not even the caller's own), no document reference in the response.

## The Pending Source (R-19) — What Changed and Why It Matters

The plan's READ FIRST block is the load-bearing instruction here, and it is now satisfied: `pending` is rows in `public.workspace_permission_requests` with `state = 'pending'`. The older derivation — non-consent grant rows whose chain is dead — was checked and deliberately not used. It cannot express a first-time ask at all, because migration 191's `workspace_grants_consent_root_or_lineage_check` forbids a non-`member_consent` row without a `parent_grant_id`; the set only ever populates after a consent-then-revoke. Reading it here would have shipped a "{Workspace} wants access" card that could never appear for a workspace that had not already been granted and then revoked, which is the exact inversion of the story WSR-27 exists to tell.

## Deviations from Plan

### 1. [Rule 2 — missing critical functionality] Project-scoped asks are omitted, not flattened

**Found during:** Task 2.
**Issue:** A `workspace_permission_requests` row may carry a `project_id`. The plan's declared group shape carries no project field, so a project-scoped ask flattened into a group would be indistinguishable from a relationship-wide one. A client approving it would POST to the consent route without a `projectId` and issue a **relationship-wide** consent — strictly more authority than the workspace asked for. That is an elevation-of-privilege bug introduced by a display decision.
**Fix:** The route surfaces only asks with `project_id IS NULL`, matching exactly the `projectId: null` scope the active list resolves. Documented in the route header and covered by a test (`omits a project-scoped ask rather than presenting it as relationship-wide`).
**Trade-off, stated plainly:** a project-scoped ask is currently invisible on this surface and stays pending until 38.1 carries project scope end to end. Invisible-and-ungranted is the fail-closed side of this choice; visible-and-over-granted is not.
**Files:** `app/api/settings/permissions/route.ts`.
**Commit:** `eebb7da9`.

### 2. Gate ordering differs from the plan-07 consent route (as the plan instructed)

The consent route consults the kill switch *before* authentication; this route gates with `requireMemberApiAccount` first, per this plan's explicit action text, which is also what makes the behaviour bullets consistent (401 for an unauthenticated caller, 503 only for a gated Member). Noted so the difference reads as deliberate rather than as drift between two neighbouring files.

No auto-fixed bugs, no blocking issues, no architectural changes. No acceptance criterion was mis-specified: every grep count in the plan was satisfiable idiomatically and none required contorting code.

That is a one-line, additive change and I left it out rather than pre-empting plan 16's contract from a concurrent worktree. Flagging it so the reconciliation is a decision, not a discovery.

3. **Plan 13's component contract.** `WorkspaceConsentGroup`, `ConsentPermissionRow`, `PERMISSION_PLAIN_COPY`, `describePermissionForMember`, the two tag constants and `STRUCTURAL_EXCLUSION_FOOTNOTE` are all exported and stable. The component resolves copy client-side from `permission-copy.ts`; it is deliberately not embedded in the API response, so the copy table has exactly one home.

4. **STATE.md and ROADMAP.md are deliberately NOT touched from this worktree.** Plans 11 and 16 are executing concurrently off the same base and all three would collide on those shared files. The orchestrator owns them — same convention plans 14 and 15 recorded.

5. **No database was contacted.** Migrations 190–195 remain authored-but-unapplied and push together at plan 11's checkpoint. No `supabase db push`, `db reset`, `migration up` or `db query` was run.
