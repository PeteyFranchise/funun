## What this establishes

**A1 is the headline.** The `p_uid` caller bind is present in all four
`workspace_read_*` functions **in the deployed database**, not merely in the
source and its text-lock test. The read-impersonation hole plan 11 found — any
authenticated caller passing another user's uuid — is confirmed closed in
production.

**A3 confirms the blast-radius reduction.** `vault_projects` is now the only
table whose RLS policies name a workspace helper. A future policy bug in this
family has a radius of one table, not five.

**A9 confirms zero exposure for the whole phase.** Every workspace table is still
empty. Nothing was ever reachable through the defects Codex found, and nothing is
reachable through them now.

**A10 restates S1 rather than fixing it.** `service_role` retains TRUNCATE,
DELETE and UPDATE on `workspace_audit_log`, so the audit log is not append-only.
Expected and deliberately deferred to Phase 38.0.2 as WSR-26.

## What this does NOT establish

Part A proves the migrations produced the objects they were reviewed as
producing. It proves **shape, not behaviour**. Specifically unproven:

- that a workspace actually loses access the moment custody transfers (WSR-06)
- that an expired-but-active seat is refused identically by RLS and the API gate (WSR-17)
- that a revoked ancestor grant actually kills its descendants at read time (WSR-02)
- that a `view_summaries` holder actually receives only the allowlisted columns (WSR-03/04)
- the six-account adversarial matrix and the D-56 disable drill (`38-RLS-SMOKE-CHECKLIST.md`)
- `EXPLAIN ANALYZE` showing no SQLSTATE 42P17 and index scans under a live grant

All of those need the kill switch ON and seeded data, which A9 confirms does not
exist. They are Part B.

## Part B — blocked, and why

38.0.1's behavioural verification requires the kill switch on. This phase's own
binding condition (R-03, R-07) requires it off until Phase 38.0.2 lands. That is
a genuine circular dependency, not an oversight.

Three ways out, for the owner:

1. **Supabase preview branch** — seed freely, switch on freely, discard.
   Recommended: the only option that verifies 38.0.1 without contradicting its
   binding condition or touching production while beta users onboard.
2. **A controlled production window** — switch on briefly with seeded test
   accounts, then off. Fastest; contradicts the deferral argument.
3. **Fold into 38.0.2's verification** — check both phases together once the
   switch can legitimately go on. Slowest, no contradiction.

Until Part B runs, no requirement row may be marked fully Verified.

## What is now proven behaviourally, not just structurally

- **B9 — the read-impersonation fix works.** An outsider calling
  `workspace_read_tracks(project, <owner's uuid>)` received **0 rows**. Part A
  proved the `p_uid` bind is present in the deployed SQL; B9 proves it bites.
- **B5 — delegation lineage is live.** Revoking the consent root killed its
  delegated descendant on the very next read, nothing cached.
- **B2/B2b — WSR-17 holds.** An `status='active'` seat with a past `expires_at`
  is refused, and `workspace_member_role` returns NULL for it. Both layers agree.
- **B12 — the kill switch actually kills.**
- **B10 — custody is immutable to a direct UPDATE.**

## B3 is a defect in the TEST, not the code

B3 asserted that a workspace member holding a seat but no grant "naming them"
must be refused. That expectation is wrong: **grants in this schema are issued
per RELATIONSHIP, not per member.** `workspace_grants.relationship_id` is the
key; there is no member column. `workspace_project_permission` hop 2 joins
`workspace_members` on `status` and `expires_at` only — verified, there is no
role filter anywhere in the function.

So the workspace as an organisation holds the permission, and any active member
exercises it. The guest reaching the project is the design working as written,
not membership leaking access. The assertion encoded an assumption the data
model never made.

## But it surfaced a real design question (OPEN, for the owner)

`workspace_members.role` — owner, admin, member, contractor, guest — **does not
gate project access at all**. A guest has exactly the same reach into an
attached project as the owner. Role currently affects only workspace
administration and R-12's proposal visibility.

That may be intended: the workspace holds the access, its staff use it. But it
means "guest" is not a lesser tier for a Member's project data, which is not
obvious from the word. Two options if it should be:

1. Add a role floor to the helper (e.g. exclude `guest`), or
2. Keep as is and rename/document the tier so nobody assumes containment.

Not a defect against any WSR requirement as written — no requirement claims role
gates project access. Raised as a product question, not a bug.
