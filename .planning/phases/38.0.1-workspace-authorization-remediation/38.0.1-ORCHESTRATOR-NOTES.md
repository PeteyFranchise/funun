## 1. Kill-switch ordering in the consent route — DONE 2026-09-08

**File:** `app/api/roster/relationships/[relationshipId]/consent/route.ts`,
`openConsentContext`.

**Finding.** It consults the D-56 kill switch BEFORE `auth.getUser()`. Measured
call-site order across every route that uses `isWorkspaceAccessEnabled`:

| Route | Order |
|---|---|
| `roster/relationships/route.ts` | auth-first |
| `roster/relationships/[relationshipId]/evidence/route.ts` | auth-first |
| `workspaces/route.ts` | auth-first |
| `workspaces/invitations/accept/route.ts` | auth-first |
| **`roster/relationships/[relationshipId]/consent/route.ts`** | **switch-first — the only one** |

Plan 07 wrote it this way because its own plan said "consults the D-56 kill
switch first / before any other work", and it correctly flagged the alternative
for a reviewer rather than silently choosing.

**Why change it.** Three small reasons, none urgent:
- consistency — it is the lone outlier among five routes;
- an unauthenticated caller currently triggers a `createServiceClient()` DB read
  before any authentication happens;
- it discloses one global boolean (whether workspace access is enabled) to
  unauthenticated callers.

**Why it was NOT changed when found.** Plan 16 owns this exact file and was
mid-flight. Editing it concurrently would have created the merge conflict this
phase has been careful to avoid.

**The change.** Move the `isWorkspaceAccessEnabled` block to sit after the
`requireMemberApiAccount` gate. Two-line move. Plan 07's tests assert an
unauthenticated caller gets 401 while the switch is enabled — that stays true;
add a case asserting 401 (not 503) for an unauthenticated caller while the
switch is DISABLED, which is the behaviour that actually changes.

**Not a vulnerability.** The switch is still consulted before any workspace work.
This is hygiene and consistency, not a hole.

**APPLIED 2026-09-08** (quick `260908-consent`). `createServiceClient()` and the
`isWorkspaceAccessEnabled` block now sit after the `requireMemberApiAccount`
gate and before `loadRelationship`. Two tests added — an unauthenticated caller
gets 401 (not 503) on GET and on POST while the switch is DISABLED. Both were
mutation-proved: reverting to switch-first fails exactly those two, while the
four pre-existing kill-switch tests stay green, which is precisely why they
could never have caught this.

**A second defect was found while applying it.** The file's header comment
justified switch-first as "copying
`app/api/workspaces/invitations/accept/route.ts`." That precedent was FALSE —
that route authenticates at line 193 and consults no switch beforehand, as do
the other three routes using the helper. The consent route was the lone outlier
among five while its own comment claimed to be following them. The comment has
been rewritten to state the real rule and to record that its cited precedent
was wrong, so the false justification cannot be re-derived from the file.

## 4. Project-scoped asks are creatable but not renderable — RESOLVED 2026-09-07

**Owner chose option 1 on 2026-09-07: refuse project-scoped asks for now.**
Shipped by quick task `260907-0t2-refuse-project-scoped-permission-request`.

`createPermissionRequest` in `lib/workspaces/request-service.ts` now refuses a
non-null `projectId` with 400 and an explanatory message, alongside its other
early refusals and before it reads the relationship. The route keeps `projectId`
in its `.strict()` Zod schema deliberately, so a caller that sends one gets that
explanation rather than a generic Zod "unrecognized key" error; the service is
the single source of the rule and the route does not reword the refusal.

**No migration.** Migrations 186-195 are all applied in production and this
change adds none. The `project_id` column and the partial unique index over
`coalesce(project_id, ...)` STAY exactly as migration 195 wrote them — they are
the forward-compatible shape for when per-project asks are supported, and there
is no database CHECK. The refusal is application-layer only, which is
proportionate: a permission request grants nothing and no authorization path
reads that table, so this is a "do not accept input you cannot honour"
correctness fix, not a security fix.

`app/api/settings/permissions/route.ts` was NOT touched. Its omission of
project-scoped rows is correct and stays.

**What lifts this:** the Member-facing surface being able to render a per-project
row on its own terms — plan 12's endpoint returning it and plan 13's UI naming
the project. Deleting the check is then the whole change; parameter, column and
index are already the right shape.

The original finding is preserved below.

### Original finding (2026-09-06)

**Finding.** `app/api/workspaces/[workspaceId]/permission-requests/route.ts`
(plan 15) accepts `projectId` and stores a project-scoped ask.
`app/api/settings/permissions/route.ts` (plan 12) deliberately OMITS
project-scoped rows from the Member view, on a documented fail-closed argument:
its group carries no project, so flattening one in would make a client issue a
relationship-WIDE consent — broader than what was actually asked for. That
reasoning is correct.

The consequence is a dead end. Such an ask is accepted, stored, invisible to the
Member, never approvable, and the partial unique index on
`(relationship_id, permission, COALESCE(project_id, ...)) WHERE state='pending'`
then blocks re-asking for that same pair.

**Severity: low, and latent.** No client sends `projectId` today — the UI does
not exist until plan 13 — so nothing is stuck in production. This is an API
surface accepting a parameter nothing yet supplies.

**Three ways to close it, for the owner to pick:**
1. **Refuse project-scoped asks for now** (400 from plan 15's route, naming the
   reason). Smallest, and honest: do not accept an ask that cannot be rendered.
   Consistent with WSR-27 being explicitly "minimal".
2. **Surface them** in plan 12's endpoint and plan 13's UI as their own
   per-project rows. Correct long term, but widens the surface WSR-27 scoped
   down, and needs a project name lookup the aggregate endpoint does not do.
3. Leave it and document the limitation. Not recommended — it leaves an API that
   silently accepts input that can never resolve.

**Do not silently pick.** This is consent-surface behaviour, which the owner
asked to be consulted on. Raise it before plan 13 ships the UI.

*(Resolved: the owner picked option 1 on 2026-09-07. See the header above.)*

## 5. `requestId` on the pending row — RESOLVED 2026-09-06, no change needed

Plan 12's `ConsentPermissionRow` carries no `requestId`, because approve
(`POST {permissions}`) and revoke (`DELETE`) key on relationship + permission.

If plan 16's **decline** verb keys on `workspace_permission_requests.id` instead,
plan 13 will need one additive field (`requestId` on pending rows) and plan 12's
endpoint must supply it. Plan 12 left it out rather than pre-empting plan 16's
contract from a concurrent worktree — the right call.

Check plan 16's decline signature at merge and reconcile before dispatching 13.

**RESOLVED.** Plan 16 landed and keys decline on the permissions array, not on
`workspace_permission_requests.id`: Approve is `POST { permissions: [p] }`,
Decline is `POST { permissions: [p], decision: 'declined' }`. No `requestId` is
needed anywhere, plan 12's response shape is sufficient as built, and plan 16
confirmed the GET shape is byte-for-byte unchanged. Plan 13's contract holds.

Separately verified at merge: plan 16 warned that plan 12 might have copied the
dead-lineage derivation. It did not — `app/api/settings/permissions/route.ts`
imports `listRequestsForMember` from `request-service` and never imports
`loadRelationshipGrantChain` or `isGrantChainLive`. Plan 12's own SUMMARY was
accurate; the warning was speculative and is dismissed.
