## 1. Kill-switch ordering in the consent route — APPLY AFTER PLAN 16 MERGES

**File:** `app/api/roster/relationships/[relationshipId]/consent/route.ts`,
`openConsentContext`.

**Finding.** It consults the D-56 kill switch BEFORE `auth.getUser()`. Measured
call-site order across every route that uses `isWorkspaceAccessEnabled`:

| Route | Order |
|---|---|
| `roster/relationships/route.ts` | auth-first |
| `roster/relationships/[relationshipId]/evidence/route.ts` | auth-first |
| `workspaces/route.ts` | auth-first |
| `workspaces/invitations/accept/route.ts` | auth-first |
| **`roster/relationships/[relationshipId]/consent/route.ts`** | **switch-first — the only one** |

Plan 07 wrote it this way because its own plan said "consults the D-56 kill
switch first / before any other work", and it correctly flagged the alternative
for a reviewer rather than silently choosing.

**Why change it.** Three small reasons, none urgent:
- consistency — it is the lone outlier among five routes;
- an unauthenticated caller currently triggers a `createServiceClient()` DB read
  before any authentication happens;
- it discloses one global boolean (whether workspace access is enabled) to
  unauthenticated callers.

**Why it was NOT changed when found.** Plan 16 owns this exact file and was
mid-flight. Editing it concurrently would have created the merge conflict this
phase has been careful to avoid.

**The change.** Move the `isWorkspaceAccessEnabled` block to sit after the
`requireMemberApiAccount` gate. Two-line move. Plan 07's tests assert an
unauthenticated caller gets 401 while the switch is enabled — that stays true;
add a case asserting 401 (not 503) for an unauthenticated caller while the
switch is DISABLED, which is the behaviour that actually changes.

**Not a vulnerability.** The switch is still consulted before any workspace work.
This is hygiene and consistency, not a hole.

## 4. Project-scoped asks are creatable but not renderable — DECIDE BEFORE PLAN 13 SHIPS

**Finding.** `app/api/workspaces/[workspaceId]/permission-requests/route.ts`
(plan 15) accepts `projectId` and stores a project-scoped ask.
`app/api/settings/permissions/route.ts` (plan 12) deliberately OMITS
project-scoped rows from the Member view, on a documented fail-closed argument:
its group carries no project, so flattening one in would make a client issue a
relationship-WIDE consent — broader than what was actually asked for. That
reasoning is correct.

The consequence is a dead end. Such an ask is accepted, stored, invisible to the
Member, never approvable, and the partial unique index on
`(relationship_id, permission, COALESCE(project_id, ...)) WHERE state='pending'`
then blocks re-asking for that same pair.

**Severity: low, and latent.** No client sends `projectId` today — the UI does
not exist until plan 13 — so nothing is stuck in production. This is an API
surface accepting a parameter nothing yet supplies.

**Three ways to close it, for the owner to pick:**
1. **Refuse project-scoped asks for now** (400 from plan 15's route, naming the
   reason). Smallest, and honest: do not accept an ask that cannot be rendered.
   Consistent with WSR-27 being explicitly "minimal".
2. **Surface them** in plan 12's endpoint and plan 13's UI as their own
   per-project rows. Correct long term, but widens the surface WSR-27 scoped
   down, and needs a project name lookup the aggregate endpoint does not do.
3. Leave it and document the limitation. Not recommended — it leaves an API that
   silently accepts input that can never resolve.

**Do not silently pick.** This is consent-surface behaviour, which the owner
asked to be consulted on. Raise it before plan 13 ships the UI.
