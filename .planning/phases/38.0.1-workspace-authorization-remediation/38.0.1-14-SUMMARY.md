# Phase 38.0.1 Plan 14: Workspace Date Input Validation Summary

Wired the two remaining workspace date inputs — the roster relationship's access window and the workspace project release date — to `lib/workspaces/date-schemas.ts`, so there is one implementation of ISO date validation on the workspace surface rather than three, and added POST/PATCH ordering guards that refuse an inverted access window with a message naming both fields.

## What Was Built

**Task 1 — roster route (`app/api/workspaces/[workspaceId]/roster/route.ts`)**

- `ProposeRosterSchema.effectiveFrom` / `.terminatesOn` and `PatchRosterSchema.effective_from` / `.terminates_on` now use `optionalIsoDate` instead of `z.string().optional()` / `z.union([z.string(), z.null()]).optional()`. `optionalIsoDate` is `.nullish()`, so PATCH keeps the ability to send an explicit `null` and clear a bound.
- POST calls `assertDateOrdering` immediately after parsing, before `createServiceClient()` — a malformed or inverted window never reaches a query.
- PATCH calls `assertDateOrdering` on the **merged** pair: incoming values (present keys, including explicit nulls) laid over the stored row's values. A request naming only `terminates_on` can still invert the window against the stored `effective_from`, which is exactly the case the merge closes (T-38.0.1-14-02).
- `loadTargetRelationship` now selects `effective_from, terminates_on` in addition to its four existing columns, and `RosterRelationshipRow` gained the two fields. This was required by the merge — without the stored values there is nothing to merge against.
- Both guards carry a comment stating they mirror migration 183's own CHECK (`terminates_on IS NULL OR effective_from IS NULL OR terminates_on > effective_from`) to turn a constraint violation into a readable message, not to replace the database rule.
- `checkRateLimit`, the `canManageRoster` gate, `pickRosterFields`, the notification call and the audit call are byte-identical.

**Task 2 — workspace projects route (`app/api/workspaces/[workspaceId]/projects/route.ts`)**

- `releaseDate: z.string().optional()` → `optionalIsoDate`, with a comment naming R-14 / WSR-22 and stating that `vault_projects.release_date` is a DATE column, so the date schema and not the datetime schema applies. Nothing else in the file changed.

**Tests** — two new route suites in the style of `roster/evidence/route.test.ts`: the real handlers driven against in-memory Supabase stubs, asserting on actual HTTP status codes and on the exact row handed to `.insert()` / `.update()`.

## Mis-specified Acceptance Criteria

Two criteria are stated as exact grep counts that the correct code does not hit literally. Per the sanity rule, satisfied idiomatically and flagged rather than contorted:

1. **`grep -c 'date-schemas' roster/route.ts` returns 1** — it returns **2**. One hit is the import; the second is a prose reference inside the explanatory comment above `ProposeRosterSchema` (`goes through lib/workspaces/date-schemas.ts`). Removing the comment's module name to hit the literal count would delete the pointer that tells the next reader where the rule lives — the opposite of the criterion's intent, which is "exactly one import, not three re-derived rules". Import count is 1.
2. **`npx jest "app/api/workspaces/[workspaceId]/roster/route"`** — jest treats a positional arg as a regex, so `[workspaceId]` is a character class matching one character and the pattern matches nothing. The brackets must be escaped: `npx jest "app/api/workspaces/\[workspaceId\]/roster/route.test.ts"`. This affects every criterion in this phase that greps or runs jest against a bracketed Next.js dynamic path.
