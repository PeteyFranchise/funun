## User Constraints (from CONTEXT.md)

### Locked Decisions

**Authorization model**
- **R-01 (F6):** The subject Member is the root of authority, always. Build a Member-side consent endpoint where the relationship's `member_user_id` issues operational permissions to the workspace. Workspace admins may re-delegate only what the Member already granted, tracked through an immutable `parent_grant_id` lineage. `resolveEffectivePermissions` must re-validate the Member's consent AND every delegation link at use time. This is what D-21 already says; the code never built the Member's side. Bootstrap resolves because the Member is the root.
- **R-02 (F2/F3):** Remove the workspace branch from `tracks`, `vault_assets`, `vault_documents` and `tool_outputs` entirely. Workspace reads go through SECURITY DEFINER RPCs with explicit column allowlists. Only `vault_projects` keeps a direct branch, narrowed. Storage paths must never be returned to a workspace caller. Blast radius of any future policy bug drops to one table.
- **R-04 (F4):** Bind access to custody inside the helper — `workspace_project_permission` joins `vault_projects` and requires `p.user_id = r.member_user_id`. Access then follows custody automatically; no cleanup step to forget, no cron.
- **R-08 (F8):** Workspace proposes, subject confirms. A workspace may draft evidence (genuine admin help), but it stays `proposed` and confers nothing until the relationship's `member_user_id` confirms. `document_id` is mandatory for authority tier. Verify the document belongs to the subject. Enforce `effective_from <= now` at use time — it is currently stored and ignored.

**Escalation and state integrity**
- **R-05 (F5):** Only owners may promote to owner; admins may not edit or remove owner rows; no self-promotion. Ownership transfer becomes two-sided — the owner nominates, the successor accepts — mirroring D-29 custody transfer. Enforced in the database/RPC, not route logic.
- **R-06 (F9/F11/F15/F16/F14):** Transactional SECURITY DEFINER RPCs for every consequential state change — custody acceptance, invitation redemption, ownership and owner-floor changes, roster transitions. Each does `SELECT ... FOR UPDATE`, revalidates preconditions, mutates, and writes the audit row in the same transaction. This closes all four races and F14's best-effort audit together: a consequential mutation can no longer succeed without its audit record.

**Containment**
- **R-03:** Flip the kill switch OFF in production immediately, before this phase is built. Costs nothing (F6 makes the feature non-functional anyway) and closes F5/F8 exposure, which need no grants. Also exercises the D-56 control for real, satisfying smoke-checklist 8a/8b.
- **R-07 (F17):** The D-55 cohort gate is a release requirement, not a 38.2 item. Server-side cohort eligibility in workspace creation and `requireWorkspaceAccess`, following the Song Passport pilot pattern. Re-enabling without it means going from "off" to "every Member."
- **R-11 (F12):** One canonical live-membership definition. `workspace_member_role` and `is_workspace_owner` must check `expires_at`, and `resolveEffectivePermissions` and the catalogue must stop selecting `status` alone. Prefer a single SQL helper both layers call.
- **R-12 (F13):** A `proposed` relationship is visible only to the named Member and the owner/admin proposal-management surface — not to ordinary members, contractors or guests. D-05 says the workspace sees nothing until acceptance; the current policy contradicts it.
- **R-13 (F14):** No restricted PII in the broadly readable `changes` JSON (invitation emails are currently exposed to every workspace member). Introduce viewer-class-redacted audit reads.

**Quality**
- **R-10 (F18):** Fold the N+1 into R-02. Resolve permitted project summaries for one actor and workspace in a single set-based, paginated RPC, preserving live authorization semantics inside the SQL rather than caching. Same for the roster GET's per-row evidence tier.
- **R-09 (F20):** "Appears on" requires an explicit contributor or roster relationship naming the caller. Delegated workspace access is not contribution credit — the same principle as D-43 one layer up. Fix `workspaceIdByProjectId` silently overwriting multi-workspace attachments.
- **R-14 (F19):** Strict ISO date/datetime schemas on `effectiveFrom`, `terminatesOn`, `expiresAt`, `releaseDate`, plus ordering validation, before any mutation.
- **R-15 (F21):** Remove the `created_by = auth.uid()` fallback in `workspaces_select_member`, or condition it on live membership. Make workspace creation atomic so the fallback is unnecessary.
- **R-16 (F22):** `relationship_id` becomes NOT NULL on `workspace_attachments` and `workspace_grants`. Do not encode "all" as a nullable security foreign key. Audit production for existing NULL rows before adding the constraint.

**Pre-existing, separate**
- **R-17 (F3, pre-existing half):** The `vault_projects` UPDATE policy never constrains `user_id` in `WITH CHECK`, so custody can be seized by UPDATE. This is inherited from migration 078 and a Phase 21 `co-owner`/`editor` can exploit it today, independent of workspaces. It gets its own migration 188 and its own review, fixing all branches (owner, co-owner/editor, workspace). Owner decision 2026-09-06.

## Summary

Phase 38 shipped a workspace layer whose two root defects are both independently verifiable in the
current tree, not theoretical: **(1)** `lib/workspaces/grant-service.ts`'s `assertGrantIssuable`
derives a granter's authority entirely from `resolveEffectivePermissions`, which itself reads
`workspace_grants` rows filtered to the same relationship — with zero grant rows in production
(confirmed: F6 guarantees this), every possible first grant request evaluates `granterHolds` as
empty and is refused, forever, for any workspace/relationship pair. Nothing in the current codebase
can seed that first row. **(2)** Migration 186's `workspace_project_permission()` — the sole gate on
`vault_projects`/`tracks`/`vault_assets`/`vault_documents`/`tool_outputs` — resolves attachment →
membership → relationship → grant but never re-reads `vault_projects.user_id`, so an attachment
survives a custody transfer to a different Member (F4) and `edit_metadata` maps onto `FOR ALL`
policies that also cover `vault_projects.user_id` itself (F3, inherited from migration 078).

Every other finding in scope (F5, F8, F9/F11/F14/F15/F16, F12, F13, F17-F22, S1) is similarly
concrete and located: `members/route.ts`'s PATCH handler gates role changes on
`canManageWorkspaceMembers` (owner OR admin) with no owner-only branch for promotion or protection
of existing owner rows (F5); `roster/evidence/route.ts` accepts `documentId` as optional and inserts
evidence with no subject-confirmation state, and `evidence.ts`'s `isLiveQualifyingEvidence` never
reads `effectiveFrom` (F8); `catalogue.ts` calls `resolveEffectivePermissions` — itself four
sequential queries — once per project in a loop (F18, the ~400-query claim for 100 projects is
exact: 4 queries × 100); `workspace_audit_log`'s only privilege lockdown is
`REVOKE ... FROM PUBLIC`, which does not touch `service_role`'s directly-granted privileges in
Supabase's default schema setup (S1).

The fixes are almost entirely mechanical once the two root causes are named correctly: R-01 needs a
genuinely new authority source (a Member-issued grant that does not derive from
`resolveEffectivePermissions`) rather than a patch to the existing function; R-02's column-allowlist
RPCs are a well-precedented Postgres pattern (`SECURITY DEFINER`, explicit `SELECT` list, no
`SELECT *`); R-17's `WITH CHECK`-cannot-see-OLD problem is a documented PostgreSQL limitation with a
standard trigger-based resolution, made simpler here because the one legitimate custody-mutation
path (`app/api/vault/custody-transfers/route.ts`) already runs entirely through `createServiceClient()`,
never through the RLS-governed `authenticated` role.

**Primary recommendation:** Treat R-01 (consent bootstrap) and R-02/R-04/R-17 (RLS/column-allowlist
rework) as one tightly-coupled security-critical unit that must land and soak together before R-06's
transactional RPCs are built on top of it — the transactional RPCs' `SELECT ... FOR UPDATE` bodies
will themselves need to call the corrected `workspace_project_permission`/grant-resolution logic, so
sequencing R-06 second avoids rebuilding it once R-02 changes the authorization surface it depends
on. Split the phase in two (see Slice/Split Recommendation below): the same boundary this repo used
for Phase 38 itself (permission model + its RLS consumer in one security review) applies again here.

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| SECURITY DEFINER column-allowlist function (R-02) | `security_barrier` VIEW with explicit column list | A view cannot accept a caller-supplied `p_permission` argument to vary the allowlist per requested capability, and cannot easily perform the four-hop join with STABLE caching the way a function can; a function is also directly callable via `supabase.rpc()` without PostgREST's view-based `select=` column-name coupling. Rejected — see Priority Item 1 analysis below. |
| BEFORE UPDATE trigger for `user_id` immutability (R-17) | Self-referential subquery inside `WITH CHECK` | PostgreSQL's RLS `WITH CHECK` clause is evaluated only against the proposed NEW row; there is no OLD reference available inside it, and a same-table subquery's visibility of the row's own pending change within one command is unspecified/fragile. Rejected in favor of a trigger, which has guaranteed, documented OLD/NEW access. See Pitfall 5. |

### Pattern 1 — Consent + Delegation Model (R-01, R-02's hop 6, WSR-01/02/27)

**What:** A Member-issued grant is the *only* thing that can be a chain root. A workspace
admin's grant to another relationship-scoped actor must carry a non-null `parent_grant_id`
pointing at an ancestor grant, and the ancestor chain must terminate at a `source =
'member_consent'` row that is itself still live (not revoked, relationship still accepted).

**Why the current code cannot bootstrap (verified):** `assertGrantIssuable` in
`lib/workspaces/grant-service.ts` computes `granterHolds` by calling
`resolveEffectivePermissions(supabase, { actorUserId: granterUserId, subjectMemberId:
relationship.member_user_id, ... })`. That function's Step 4 reads
`workspace_grants` rows `.eq('relationship_id', relationshipRow.id)`. With zero rows
in that table for a brand-new relationship — the only state F6 makes possible in
production — `granterHolds` is always the empty set, so `assertGrantIsIssuable`
refuses every request at the "exceeds what the granter holds" check
(`lib/workspaces/grants.ts` line 121-123). There is no code path anywhere in this
codebase that inserts a `workspace_grants` row without going through this same
check first. This is a closed loop with no seed.

**The fix:** `resolveEffectivePermissions`'s notion of "does the granter hold X" must be
answered two different ways depending on who is asking:
1. **The Member consenting for the first time** does not need to "hold" anything —
   they are the rights holder consenting to grant it. A new, separate assertion
   function (`consent.ts`) governs this case: it only checks that `permission` is a
   recognized `WorkspacePermission`, is not structurally excluded (D-42), and — for
   authority-tier permissions — that the relationship is currently document-supported
   (D-16). It does **not** call `resolveEffectivePermissions` at all.
2. **A workspace admin delegating** still calls `assertGrantIsIssuable`, but
   `granterHolds` must now be the set of permissions reachable by walking UP the
   `parent_grant_id` chain from the admin's own delegated grants (or, if the admin
   is delegating for the first time from the Member's root grant directly, the
   admin's "holds" set is simply the Member-root's live permission set for that
   relationship — an admin does not need a *personal* grant row to relay the
   Member's own root consent onward, matching D-21's "workspace admins may
   re-delegate only what the Member already granted").

**When to use:** Any grant-issuance code path. This is not optional discretion — R-01
requires it for every grant in the system, not just the first one.

**Self-FK vs. closure table (Claude's Discretion, with a recommendation):**
- **Self-FK (`workspace_grants.parent_grant_id UUID REFERENCES workspace_grants(id)`)** —
  recommended. The chain depth here is bounded and shallow by design: D-21 describes
  exactly two tiers of authority (the Member's root consent, and a workspace's
  re-delegation of a subset of it) — there is no product requirement for admin→admin→admin
  chains of arbitrary depth. A recursive CTE (`WITH RECURSIVE`) validating a 2-3 hop
  chain inside a `STABLE SECURITY DEFINER` function is cheap and matches the "one
  function body, no cross-table EXISTS in a policy" recursion doctrine this repo already
  established in migration 186 for the *access* chain — the *lineage* chain can use the
  identical technique.
- **Closure table** — would earn its complexity only if arbitrarily deep re-delegation
  chains become a real product requirement (e.g., a label workspace re-delegating to a
  sub-team workspace, which does not exist in this phase's scope, D-01/D-02 keep
  workspaces as one flat entity type). Rejected for this phase; flag as a note for
  38.1/38.2 if multi-level workspace hierarchies are ever discussed.

**Revocation cascade at READ time (not a cron job):** Because `resolveEffectivePermissions`
already re-derives everything on every call with nothing cached (a documented, deliberate
design decision, see `grant-service.ts` header comment items (1)-(2)), a parent grant's
revocation cascades "for free" — the lineage-walk function simply finds a `revoked_at IS NOT
NULL` ancestor and returns false for every descendant in the same call, with no cascade job,
matching D-49's "re-checked on use" requirement and this repo's existing anti-caching
philosophy.

```sql
-- Source: derived from lib/workspaces/grant-service.ts's existing recursion-safety
-- doctrine (migration 186 header) applied to the NEW lineage dimension.
CREATE OR REPLACE FUNCTION public.workspace_grant_lineage_live(p_grant_id UUID)
RETURNS BOOLEAN
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = ''
AS $$
  WITH RECURSIVE chain AS (
    SELECT id, parent_grant_id, revoked_at, source
    FROM public.workspace_grants
    WHERE id = p_grant_id
    UNION ALL
    SELECT g.id, g.parent_grant_id, g.revoked_at, g.source
    FROM public.workspace_grants g
    JOIN chain c ON g.id = c.parent_grant_id
  )
  SELECT
    -- every link in the chain must be unrevoked ...
    NOT EXISTS (SELECT 1 FROM chain WHERE revoked_at IS NOT NULL)
    -- ... and the chain must terminate at a member_consent root
    AND EXISTS (SELECT 1 FROM chain WHERE parent_grant_id IS NULL AND source = 'member_consent')
$$;
```

### Pattern 2 — Column-Allowlist SECURITY DEFINER RPC (R-02, WSR-03/04)

**What:** Replace the additive `OR (SELECT public.workspace_project_permission(...))`
branch on `tracks`, `vault_assets`, `vault_documents`, `tool_outputs` (migration 186,
lines 332-444) with **removal** of that branch entirely, and add four new
`SECURITY DEFINER` set-returning functions, one per table, each with a hard-coded
`SELECT` column list that a workspace caller is permitted to see.

**Why a function, not a `security_barrier` VIEW:** A view's column list is fixed at
creation time and does not vary per requested permission — but the D-40 exclusion
rules (clean-master path, private rights identifiers) mean *which* columns are safe
to expose depends on which permission the caller currently holds, not just on the
caller's role. A function can branch internally (`CASE WHEN
public.workspace_project_permission(...) THEN ... ELSE NULL END`) to null out a
column the caller's specific grant does not cover, while still returning one row per
matching record — a view cannot parameterize on a caller-supplied permission
argument the way a function invoked via `supabase.rpc('workspace_read_tracks', {
p_project_id, p_permission })` can. Views are also read through PostgREST's
`select=` query-string mechanism, which cannot easily vary the *set* of exposed
columns per caller in one declared view; a function's return type is the contract
and callers cannot request columns outside it, which is the entire point of R-02.

**Structural guarantee against a storage-path leak (custody D-01/D-09):** The
function's `RETURNS TABLE (...)` clause must never include `audio_file_url`,
`document_data`, or any other column shown in the codebase to hold a signed/raw
storage path or URL. This is enforced the same way migration 186's own header
enforces the "no vault_projects/tracks/etc. read inside the helper" rule: a text-lock
test (`__tests__/migration-19X.test.ts`) asserts the literal column list in the
migration file, and a second suite (mirroring
`__tests__/workspace-structural-exclusions.test.ts`) walks every module that signs a
storage URL and asserts none of them ever calls one of these new RPCs.

```sql
-- Source: pattern derived from migration 186's existing three-hop helper, narrowed
-- to an explicit column allowlist and parameterized on p_permission per D-40.
CREATE OR REPLACE FUNCTION public.workspace_read_tracks(
  p_project_id UUID,
  p_uid UUID
)
RETURNS TABLE (
  id UUID,
  project_id UUID,
  title TEXT,
  track_number INT,
  duration_seconds NUMERIC
  -- NEVER: audio_file_url, isrc (unless view_private_rights_identifiers is held —
  -- branch internally per-row, do not add a second unconditional column)
)
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = ''
AS $$
  SELECT t.id, t.project_id, t.title, t.track_number, t.duration_seconds
  FROM public.tracks t
  WHERE t.project_id = p_project_id
    AND public.workspace_project_permission(p_project_id, p_uid, 'view_summaries')
$$;

REVOKE EXECUTE ON FUNCTION public.workspace_read_tracks(uuid, uuid) FROM PUBLIC, anon;
GRANT  EXECUTE ON FUNCTION public.workspace_read_tracks(uuid, uuid) TO authenticated;
```

**Migration-ordering hazard:** dropping the four `OR workspace_project_permission(...)`
branches from `tracks`/`vault_assets`/`vault_documents`/`tool_outputs` MUST happen in
the SAME migration/push as standing up the replacement RPCs and updating every
TypeScript caller (`catalogue.ts` and any other module reading those tables through a
workspace-scoped client) — a staged rollout that removes the RLS branch before the
RPCs exist, or ships the RPCs before removing the RLS branch, either breaks the
feature (former) or leaves both paths live simultaneously with no test coverage of
which one actually executes (latter, a false sense of remediation).

### Pattern 3 — Transactional SECURITY DEFINER RPC (R-06, WSR-09..13)

**What:** For custody acceptance, invitation redemption, ownership/owner-floor changes,
and roster transitions: a single `plpgsql` `SECURITY DEFINER` function that performs
`SELECT ... FOR UPDATE`, revalidates every precondition against the now-locked row(s),
mutates, and inserts the `workspace_audit_log` row — all inside the function's own
implicit transaction (a single top-level SQL statement, i.e. one `CALL`/`SELECT` of the
function, is one transaction unless the function itself uses subtransactions).

**Locking discipline / deadlock avoidance:** Order locks by a fixed, deterministic key
across every RPC in this family to prevent a lock-order inversion between, e.g., a
concurrent custody-transfer-accept and a roster-transition on the same project/workspace
pair:
1. Lock `vault_projects` row (by `id`) first, whenever the RPC touches custody at all.
2. Lock `workspace_members` / `workspace_roster_relationships` rows second, ordered by
   `id` ascending when locking more than one row (e.g., a roster transition that also
   checks the owner floor across multiple `workspace_members` rows should
   `SELECT ... FOR UPDATE ORDER BY id`).
3. Never lock `workspace_audit_log` — it is insert-only and append-only; an insert does
   not need a preceding row lock and audit inserts must never be a source of a
   deadlock in this family.

This ordering matches the existing precedent in
`app/api/vault/custody-transfers/route.ts` (already using `.eq('user_id',
row.from_user_id)` as an optimistic-concurrency guard rather than an explicit lock) —
moving this into a `SELECT ... FOR UPDATE` pessimistic lock inside a `plpgsql` function
is a strict tightening of the same mechanism, not a new one.

**Surfacing a typed failure from plpgsql to TypeScript:** Use `RAISE EXCEPTION`
with a distinct `ERRCODE` (Postgres allows custom `PXXXX`-class SQLSTATE codes) per
failure reason, and have the TypeScript RPC wrapper switch on `error.code`
(`PostgrestError.code` surfaces the SQLSTATE) to produce the same `{ ok: false,
status, error }` shape every other module in this codebase already returns — this
preserves the "never throws" convention at the TypeScript boundary even though the
underlying SQL does raise.

```sql
-- Source: pattern combining this repo's SELECT...FOR UPDATE precedent
-- (app/api/vault/custody-transfers/route.ts's optimistic guard, tightened to
-- pessimistic locking) with the transactional-audit requirement (R-06/WSR-13).
CREATE OR REPLACE FUNCTION public.accept_custody_transfer(
  p_transfer_id UUID,
  p_actor_uid UUID
)
RETURNS public.workspace_custody_transfers
LANGUAGE plpgsql SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  v_transfer public.workspace_custody_transfers;
  v_project  public.vault_projects;
BEGIN
  SELECT * INTO v_transfer
  FROM public.workspace_custody_transfers
  WHERE id = p_transfer_id AND state = 'offered'
  FOR UPDATE;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Transfer not found or already resolved'
      USING ERRCODE = 'P0001';
  END IF;

  IF v_transfer.to_user_id <> p_actor_uid THEN
    RAISE EXCEPTION 'Only the offer recipient may accept'
      USING ERRCODE = 'P0002';
  END IF;

  SELECT * INTO v_project
  FROM public.vault_projects
  WHERE id = v_transfer.project_id
  FOR UPDATE;

  IF v_project.user_id <> v_transfer.from_user_id THEN
    RAISE EXCEPTION 'Custodian changed since this transfer was offered'
      USING ERRCODE = 'P0003';
  END IF;

  UPDATE public.vault_projects
  SET user_id = v_transfer.to_user_id
  WHERE id = v_transfer.project_id;

  UPDATE public.workspace_custody_transfers
  SET state = 'accepted', responded_at = now()
  WHERE id = p_transfer_id
  RETURNING * INTO v_transfer;

  IF v_transfer.workspace_id IS NOT NULL THEN
    INSERT INTO public.workspace_audit_log
      (workspace_id, actor_user_id, subject_member_id, action, target_type, target_id, changes)
    VALUES
      (v_transfer.workspace_id, p_actor_uid, v_transfer.to_user_id,
       'custody.transfer.accepted', 'workspace_custody_transfer', v_transfer.id,
       jsonb_build_object('projectId', v_transfer.project_id));
  END IF;

  RETURN v_transfer;
END;
$$;
```

### Pattern 5 — BEFORE UPDATE Trigger for Column Immutability (R-17, WSR-25)

See Pitfall 5 below for the full analysis and citation. Summary: RLS `WITH CHECK`
cannot compare a row's proposed new value against its stored old value — this is a
documented PostgreSQL limitation, not a gap in this codebase's policy authoring. The
correct tool is a `BEFORE UPDATE FOR EACH ROW` trigger, which has direct, guaranteed
access to both `OLD` and `NEW`.

```sql
-- Source: CITED, PostgreSQL RLS limitation confirmed via project mailing-list
-- discussion (postgresql.org/message-id/20151216231504.GJ26804%40moraine.isi.edu);
-- trigger-based column-immutability is the documented workaround.
CREATE OR REPLACE FUNCTION public.guard_vault_projects_user_id_immutable()
RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = ''
AS $$
BEGIN
  -- current_user is 'authenticated' for every ordinary RLS-governed client
  -- request (PostgREST) and 'anon' for unauthenticated ones. It is
  -- 'service_role' for the app's service-role client (the ONE legitimate
  -- path today — app/api/vault/custody-transfers/route.ts's accept branch)
  -- and 'postgres' (or the migration-owning role) for a SECURITY DEFINER
  -- transactional RPC such as accept_custody_transfer above, which is
  -- OWNED by that privileged role. Blocking only 'authenticated'/'anon'
  -- and allowing everything else is the correct boundary: it is exactly
  -- the RLS-governed-client boundary this repo already treats as the
  -- security perimeter everywhere else (078, 136, 182-186's REVOKE
  -- ... FROM authenticated, anon posture).
  IF NEW.user_id IS DISTINCT FROM OLD.user_id
     AND current_user IN ('authenticated', 'anon') THEN
    RAISE EXCEPTION
      'vault_projects.user_id cannot be changed directly -- record custody moves only through the two-sided custody-transfer flow (D-29)'
      USING ERRCODE = 'insufficient_privilege';
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_guard_vault_projects_user_id_immutable
BEFORE UPDATE ON public.vault_projects
FOR EACH ROW
EXECUTE FUNCTION public.guard_vault_projects_user_id_immutable();
```

This closes R-17/WSR-25 for **all three** WITH CHECK branches (owner, co-owner/editor,
workspace) in one stroke, without needing to touch the `WITH CHECK` clauses themselves
at all — the trigger fires regardless of which RLS branch admitted the UPDATE. The
existing `vault_projects_update_owner_or_editor` policy (migration 078, restated
verbatim by migration 186) can be left exactly as-is; migration 188 need only add the
trigger. This is a materially simpler migration than rewriting the policy, and it is
strictly *more* correct than a WITH-CHECK-only fix, because it also protects the owner's
own ordinary "edit metadata" path (an owner directly UPDATE-ing their own row to smuggle
in a `user_id` change), which a `co-owner/editor`-scoped WITH CHECK fix alone would
not.

**Verify before authoring 188:** confirm the actual Postgres role name Supabase's
PostgREST layer uses for authenticated requests in this project (`current_user` should
read `authenticated`, matching every REVOKE statement already in this repo's
migrations, e.g. migration 182 line 239-242) and confirm that
`createServiceClient()` truly executes as `service_role` at the Postgres session
level, not merely at the PostgREST API-key level — do this with a one-line runtime
probe (`SELECT current_user;` executed through each of the two client types) before
writing the trigger, in case a connection pooler role-mapping differs from assumption.

### Anti-Patterns to Avoid
- **Patching `resolveEffectivePermissions` to special-case "if no grants exist, allow
  everything"** — this is the tempting, wrong fix for F6. It reopens exactly the
  "grants nothing until acceptance" doctrine (D-05) and the "no grant may exceed what
  the granter holds" doctrine (D-49) the moment a workspace has zero grant rows for
  any reason (including right after a revocation), not just at bootstrap.
- **Adding a second, parallel "is this the Member" check inside
  `workspace_project_permission`'s existing four-hop body without also updating
  `resolveEffectivePermissions`** — the two must stay in lockstep (migration 186's own
  comment already states this: "matching lib/workspaces/grant-service.ts's
  resolveEffectivePermissions, which filters grants ... exactly this way"). Any R-02/R-04
  change to the SQL helper needs a parallel TypeScript change in the same plan, verified
  by a shared test fixture exercising both.
- **Using `SELECT *` or an ORM-style "just return the row" shape from a column-allowlist
  RPC** — defeats the entire point of R-02; every new RPC's `RETURNS TABLE` clause is
  itself the security contract and must be reviewed as carefully as an RLS policy.
- **Trying to solve R-17 with a `WITH CHECK` subquery self-join** — see Pitfall 5.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Comparing a row's old vs. new value under RLS | A `WITH CHECK` subquery that tries to read the row's "current" value mid-statement | A `BEFORE UPDATE FOR EACH ROW` trigger with `OLD`/`NEW` | Documented Postgres limitation (CITED below) — this is not a case where "just write a clever query" is a legitimate option |
| Deep permission-lineage validation | A TypeScript loop that walks `parent_grant_id` client-side across N round-trips | A `WITH RECURSIVE` SQL function, `STABLE SECURITY DEFINER`, called once | Matches this repo's own established doctrine — the same reasoning migration 186 gives for doing all 4 authorization hops inside one function body applies identically to the lineage hop |
| Atomic "check-then-mutate-then-audit" | Sequential `.from(...).select()` / `.update()` / `.insert()` Supabase client calls wrapped in a try/catch | A single `plpgsql` SECURITY DEFINER RPC called via `supabase.rpc()` | The JS client has no cross-statement transaction primitive; each `.from()` call is its own autocommit statement unless it is itself one `rpc()` invocation of a function whose body is one transaction |
| N+1 permission resolution over a project list | Caching `resolveEffectivePermissions`'s result across the loop | A set-based SQL RPC that resolves the whole page in one query, preserving the identical live-authorization logic (R-10 explicitly forbids caching — it must remain a single query, not a cached repeated one) | Caching reintroduces exactly the staleness D-49 exists to prevent; folding into one SQL statement gets both the performance fix and zero staleness |

**Key insight:** every "Don't Hand-Roll" case above has the same shape — the current
code correctly identified that these decisions must be evaluated live and cannot be
cached, but implemented that correctness one row/one round-trip at a time. The fix is
never "compute it once and remember it" (which would violate D-49); it is always "make
the single already-correct computation happen inside one database round trip instead of
N."

## Common Pitfalls

### Pitfall 1: `workspace_project_permission` never re-validates custody (F4)
**What goes wrong:** Migration 186's helper (lines 218-252) resolves attachment →
membership → relationship → grant, but never reads `vault_projects.user_id` at all.
Its own header (lines 42-55) explicitly documents the four hops it performs and states
"it does not read vault_projects ... at all" as a *deliberate anti-recursion design
choice*. That design choice is exactly what leaves F4 open: if a project's custody
transfers to a different Member (via the shipped, correctly two-sided
`custody-transfer.ts` flow) while an old workspace attachment/relationship/grant chain
still exists for the *previous* custodian, the helper has no way to notice — it was
never checking who currently holds the project in the first place.
**Why it happens:** The anti-recursion doctrine (no cross-table EXISTS re-entering RLS)
was correctly applied to the four workspace tables, but the doctrine's rationale
("SECURITY DEFINER functions bypass RLS when reading a table they don't own via a
policy re-entry") does **not** actually forbid reading `vault_projects` directly —
a `SECURITY DEFINER` function owned by a role that bypasses RLS on `vault_projects`
(the standard Supabase migration-owner setup) does not trigger RLS re-evaluation by
reading that table with a plain `SELECT`; it only would recurse if it went back
through a *policy*, which a direct table read inside a SECURITY DEFINER body does
not do. The exclusion of `vault_projects` from the helper's reads was over-cautious,
not load-bearing for recursion safety.
**How to avoid:** Add the join described in R-04/WSR-06 (`JOIN public.vault_projects p
ON p.id = p_project_id AND p.user_id = r.member_user_id`) directly inside the helper
body. Verify with an `EXPLAIN` that this remains an index-only/index-range lookup
(there is already a `vault_projects` primary-key index on `id`; `user_id` should
already be indexed from the base schema — confirm before assuming).
**Warning signs:** Any adversarial test where custody is transferred away from a
Member mid-relationship and the old workspace retains project access — this MUST be
in the smoke checklist for this phase.

### Pitfall 2: Owner promotion/protection has no owner-only gate (F5)
**What goes wrong:** `app/api/workspaces/[workspaceId]/members/route.ts`'s PATCH
handler gates on `requireWorkspaceRole(access, canManageWorkspaceMembers, ...)`, and
`canManageWorkspaceMembers` returns true for **both** `owner` and `admin`
(`lib/workspaces/membership.ts` line 63-65). There is no separate check preventing an
`admin` from setting `role: 'owner'` on any member row, including their own, and no
check preventing an `admin` from editing/suspending an existing `owner` row (beyond
the owner-floor count check, which only fires when the change would demote/deactivate
the LAST owner — it does not fire for demoting one of several owners, and does not
distinguish "who is allowed to touch an owner row" from "would this break the floor").
**Why it happens:** `canManageWorkspaceMembers` was written for the general
membership-management capability (invite, suspend, remove) without a narrower
predicate for the specific "touches an owner row" or "sets role to owner" cases.
**How to avoid:** Add two new pure predicates in `membership.ts`: `canPromoteToOwner
(actorRole: WorkspaceRole): boolean` (owner only) and `canModifyOwnerRow(actorRole:
WorkspaceRole): boolean` (owner only). Call both from the PATCH handler before the
existing floor check, in addition to it, not instead of it. Also add a same-user
guard (`if (target.user_id === gated.userId && role === 'owner') return 403` is
redundant once `canPromoteToOwner` exists, but keep the explicit self-promotion
message for a clearer error).
**Warning signs:** Any test where an `admin`-role actor successfully sets a role to
`owner`, or successfully suspends/removes/demotes an `owner` row while other owners
remain, should fail after the fix.

### Pitfall 3: Evidence has no confirmation gate and ignores `effective_from` (F8)
**What goes wrong:** `app/api/workspaces/[workspaceId]/roster/evidence/route.ts`'s
`RecordEvidenceSchema` makes `documentId` `.optional()`, and the route is gated only by
`canManageRoster` (owner/admin) — a workspace admin can insert a
`workspace_agreement_evidence` row with a `declaredScope` and no document at all, and
it becomes immediately live authority-tier evidence the instant
`resolveAuthorityTier`/`isLiveQualifyingEvidence` (`lib/workspaces/evidence.ts`) next
evaluates it — there is no `proposed`/`confirmed` state anywhere in the schema
(migration 183's `workspace_agreement_evidence` table has no such column) or in the
pure-logic module. Separately, `isLiveQualifyingEvidence` (lines 39-53) checks
`declaredScope`, `expiresAt`, and `supersededAt`, but never reads
`row.effectiveFrom` at all — a future-dated agreement (e.g., uploaded today,
effective next month) is treated as live immediately.
**Why it happens:** The evidence ladder was built assuming the workspace-side upload
was itself sufficient consent, missing the D-36 requirement that the rights holder
declares the scope — the workspace can draft, but only the Member's declaration
should activate it.
**How to avoid:** Add a `confirmed_by_subject_at TIMESTAMPTZ` (or a `state` enum
`'proposed' | 'confirmed'`) column to `workspace_agreement_evidence`; require
`document_id NOT NULL` for any row intended to support authority tier (WSR-14
explicitly requires this); verify server-side that the referenced `vault_documents`
row's owner (`user_id`) equals the relationship's `member_user_id` before treating a
document as valid support (a workspace must not be able to point at *someone else's*
document); add `row.effectiveFrom` to `isLiveQualifyingEvidence`'s check
(`if (row.effectiveFrom && new Date(row.effectiveFrom).getTime() > now) return false`).
**Warning signs:** A test asserting a freshly-inserted, unconfirmed evidence row does
NOT raise the relationship's authority tier; a test asserting a future-dated
`effectiveFrom` does NOT count as live evidence today.

### Pitfall 4: Membership/ownership helpers omit `expires_at` (F12)
**What goes wrong:** `workspace_member_role()` and `is_workspace_owner()` (migration
182, lines 260-279) both filter on `status = 'active'` only — neither checks
`expires_at`. `requireWorkspaceAccess` (`lib/workspaces/access.ts`, lines 88-106)
separately DOES check `expires_at` at the API layer. This is a real, exploitable gap:
an expired Contractor-role seat (`status` still `'active'` because nothing has run a
cron to flip it to `'expired'` — this schema uses a stored status the app must
transition, not a computed one) still satisfies every RLS policy that calls
`workspace_member_role`, even though the SAME actor would be refused by
`requireWorkspaceAccess` at the API layer. This produces an inconsistency where a
direct PostgREST/RLS-governed read might succeed for an expired contractor while an
API route call fails, or vice versa depending on which check a given surface uses.
**Why it happens:** The two implementations (SQL helper, TypeScript gate) were written
independently at different plans within Phase 38 and drifted.
**How to avoid:** Per R-11, prefer ONE canonical definition. The cleanest fix: since
Postgres SQL functions can freely reference `now()`, add
`AND (expires_at IS NULL OR expires_at > now())` to both `workspace_member_role` and
`is_workspace_owner`'s `WHERE` clauses directly — this makes the DB-layer definition
the single source of truth, and `requireWorkspaceAccess`'s existing TypeScript check
becomes redundant-but-harmless defense in depth (do not remove it; two independent
enforcement layers agreeing is the established pattern in this codebase, not
duplication to eliminate).
**Warning signs:** A test seeding an `active`-status, past-`expires_at` contractor
membership, then asserting BOTH the RLS-governed read AND the API gate refuse it
identically.

### Pitfall 5: RLS `WITH CHECK` cannot compare OLD and NEW (R-17, F3 pre-existing)
**What goes wrong:** `vault_projects_update_owner_or_editor`'s `WITH CHECK` clause
(migration 078, restated verbatim by migration 186) only asserts who is allowed to
perform the update (`auth.uid() = user_id OR project_member_role(...) IN
('co-owner','editor') OR ...`) — it places no constraint on what the NEW row's
`user_id` value may be relative to the OLD row's value, so any of those three
actor classes can UPDATE `vault_projects SET user_id = <anything>` and the policy
admits it.
**Why it happens:** This is a documented, structural PostgreSQL limitation, not an
authoring oversight this codebase is unusual in having: "With PostgreSQL's WITH CHECK
condition in RLS policies, you can only compare old values to session state in the
USING condition and new values to session state in the CHECK condition, but never
consider old and new values simultaneously" — confirmed via a project maintainer's
own explanation on the `pgsql-hackers` mailing list
(postgresql.org/message-id/20151216231504.GJ26804%40moraine.isi.edu, and the
associated thread), and echoed in current Postgres RLS commentary (dev.to,
Medium — see Sources).
**How to avoid:** Use a `BEFORE UPDATE FOR EACH ROW` trigger, which has native,
guaranteed `OLD`/`NEW` access (see Pattern 5 above for the full worked example).
Confirmed compatible with this codebase's existing legitimate custody-mutation path:
`app/api/vault/custody-transfers/route.ts`'s accept branch already calls
`createServiceClient()`, which authenticates to Postgres as `service_role`, not
`authenticated` — so a trigger that blocks the change only for `current_user IN
('authenticated','anon')` does not need any new bypass mechanism for that route to
keep working.
**Warning signs:** A test performing an ordinary "edit metadata" PATCH (through the
RLS-governed session client, as an owner, a co-owner/editor, or a workspace
`edit_metadata` grant holder) that attempts to also change `user_id` in the same
request body — before the fix this silently succeeds; after the fix it must be
rejected with `insufficient_privilege`.

### Pitfall 6: Restricted PII lives in the broadly-readable audit `changes` column (F14)
**What goes wrong:** `app/api/workspaces/[workspaceId]/invitations/route.ts:198` logs
`changes: { role, email: normalizedEmail }`. `workspace_audit_log`'s only SELECT
policy (migration 186 section (e), `workspace_audit_log_select`) admits any caller for
whom `workspace_audit_visible()` returns true — which includes **any active member of
the workspace** (`workspace_member_role(l.workspace_id, p_uid) IS NOT NULL`), not just
the owner/admin who sent the invitation. A `Guest`- or `Contractor`-role member can
therefore read every email address ever invited to that workspace.
**Why it happens:** `logWorkspaceAction`'s `changes` parameter is an unconstrained
`Record<string, unknown>` — nothing in its type or the calling convention flags which
keys are viewer-class-restricted.
**How to avoid:** Introduce a redaction layer (`audit-redaction.ts`, pure module) with
an explicit per-`action` (or per-key) restricted-field map, applied when the read path
resolves rows for a viewer whose role does not clear the threshold (e.g., `email` is
owner/admin/actor/subject-only; ordinary members see `{ role }` with `email` stripped).
Apply this at the READ path (a wrapper around the existing SELECT, or inside the RPC if
audit reads move to one), not by refusing to log the data at write time — the
owner/admin still needs the full record for their own audit review.
**Warning signs:** A test asserting a `member`-role (non-owner/admin) caller reading
the audit log for an `invitation.sent` action sees `role` but not `email`.

### Pitfall 7: N+1 permission resolution in the catalogue (F18)
**What goes wrong:** `lib/workspaces/catalogue.ts`'s `loadWorkspaceCatalogue` calls
`resolveEffectivePermissions` once per project inside a `for` loop (line 177-186).
`resolveEffectivePermissions` itself performs up to 4 sequential Supabase queries
(membership, relationship, evidence via `loadRelationshipTier`, grants). For a
100-project workspace catalogue, this is up to 400+ round trips in one HTTP request —
confirmed exactly matching the CONTEXT's "~400 sequential queries for 100 projects"
claim.
**Why it happens:** `resolveEffectivePermissions` was correctly built as the single
use-time authority with an explicit "never cache" design mandate (its own header
comment (2)) — but that mandate was interpreted as "call it once per row" rather than
"fold the whole computation into one query so nothing needs caching in the first
place."
**How to avoid:** Per R-10, build ONE set-based, paginated SQL RPC that performs the
same live-authorization logic — attachment → membership → relationship → grant, plus
the Pitfall 1 custody binding and Pattern 1 lineage check — as a single query joining
`workspace_attachments` to `vault_projects` and `workspace_grants` for the whole
requested page, returning already-filtered rows with already-resolved field
visibility flags. This is not caching (the query still runs fresh, with live data, on
every call); it collapses N+1 queries into 1.
**Warning signs:** A test/benchmark asserting the catalogue endpoint issues a bounded,
small number of SQL statements (e.g., ≤3) regardless of the number of attached
projects, verified via `EXPLAIN ANALYZE` or a query-count assertion in the test
harness.

### Pitfall 8: `REVOKE ... FROM PUBLIC` does not touch `service_role` (S1)
**What goes wrong:** Migration 182 line 251 runs
`REVOKE UPDATE, DELETE ON public.workspace_audit_log FROM PUBLIC;` with the comment
"the audit log additionally may never be UPDATEd or DELETEd by ANY application role,
including service_role reached through PostgREST." In standard PostgreSQL privilege
semantics, `PUBLIC` is a pseudo-role every role implicitly belongs to; revoking a
privilege `FROM PUBLIC` only removes privileges that were granted to `PUBLIC` itself
(or the implicit default). It does **not** revoke a privilege that a role holds via a
**direct** `GRANT ... TO service_role` or via `ALTER DEFAULT PRIVILEGES ... GRANT ALL
... TO service_role` — and Supabase's standard project bootstrap does exactly the
latter (the `service_role` Postgres role is commonly granted broad table privileges
directly, separate from `PUBLIC`, precisely so the service key can bypass RLS and
perform administrative writes).
**Why it happens:** `FROM PUBLIC` reads as "from everyone" in casual English, but is a
specific, narrower Postgres privilege-system construct.
**How to avoid:** Run the verification query below against the actual project
database (this is the concrete "runtime check" S1 asks for):
```sql
SELECT grantee, privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'public'
  AND table_name = 'workspace_audit_log'
  AND grantee = 'service_role';
```
If `UPDATE` or `DELETE` appear for `service_role`, the exposure is confirmed. Fix with
an explicit `REVOKE UPDATE, DELETE ON public.workspace_audit_log FROM service_role;`
**and** a rejecting trigger (`BEFORE UPDATE OR DELETE ... RAISE EXCEPTION`) as
defense-in-depth — the trigger matters because Supabase can re-apply its own default
grants to `service_role` on schema changes in ways an explicit `REVOKE` in an old
migration would not automatically re-assert; the trigger holds even if a future
schema change silently re-grants the privilege.
**Warning signs:** The verification query above returning any row for
`service_role` is itself the warning sign — this should be run BEFORE writing the fix
migration, not assumed.

## Open Questions

1. **Does the delegation lineage need to support an admin re-delegating a NARROWER
   subset per-project, distinct from the relationship-wide root grant?**
   - What we know: D-20 already allows a grant to be "narrowed or widened per
     project," and `workspace_grants.project_id` already supports this today
     (nullable = relationship-wide, non-null = project-scoped).
   - What's unclear: whether a delegated (non-root) grant's `project_id` scoping
     needs its own subset check against its PARENT's `project_id` scoping (e.g., can
     a project-scoped delegated grant have a parent that was relationship-wide? Yes,
     that should be fine — narrowing. Can a delegated grant's `project_id` be OUTSIDE
     what the parent covers? No, that must be rejected).
   - Recommendation: `grant-lineage.ts`'s validation function should include a
     project-scope-subset check, not just a permission-subset check, when the
     descendant grant has a non-null `project_id`.

2. **Should the never-zero-owners floor check and the new owner-only promotion gate
   (R-05) live inside a transactional RPC (R-06) or stay as separate route-level
   checks?**
   - What we know: R-06 explicitly lists "ownership and owner-floor changes" as one
     of the four transactional RPC targets (WSR-11), which suggests it should move
     into the same `SELECT ... FOR UPDATE` pattern as custody acceptance.
   - What's unclear: whether R-05's simpler promotion/protection checks (which are
     pure role predicates, no race condition risk on their own) need the full
     transactional-RPC treatment, or whether only the owner-floor-count check (which
     DOES have a genuine TOCTOU race between the count query and the update) needs it.
   - Recommendation: fold BOTH into one `transfer_workspace_ownership`-style RPC per
     WSR-08's two-sided nominate/accept model — the promotion gate, the floor check,
     and the two-sided acceptance state machine are all part of the same
     consequential state change and should share one lock scope.

## Slice/Split Recommendation (explicitly requested)

**Recommendation: split into two phases, mirroring the exact boundary Phase 38 itself used.**

Evidence for this:
1. **Scope comparability is real, not just asserted.** Phase 38 itself needed 13 plans
   across 7 waves for D-01..D-56 (a green-field build). This phase must (a) diagnose
   and fix two genuinely novel, non-mechanical design problems (R-01's consent
   bootstrap, R-02/R-04's RLS rework) that did not exist as "known quantities" going
   into Phase 38's own plans, AND (b) retrofit 6 transactional RPCs, a redaction layer,
   a cohort gate, and ~9 smaller hygiene fixes on TOP of that reworked foundation. That
   is not less design work than Phase 38's original build — verified concretely above:
   R-01 alone requires a new grant-provenance model with a schema change, a new pure
   module, a new I/O module, and a re-derivation of `resolveEffectivePermissions`'s
   core algorithm; R-02 alone requires 4 new SECURITY DEFINER functions plus removing
   live policy branches plus rewriting `catalogue.ts`.
2. **The natural dependency boundary is identical to Phase 38's own A-D/E-G/H-I split
   rationale ("the permission model and its RLS consumer stay in one security
   review").** Here: **Slices A (consent model) + B (RLS rework) + R-04's custody
   binding are one inseparable security-critical unit** — R-06's transactional RPCs
   (Slice C) call INTO the corrected authorization surface Slice A/B produce, so
   building C before A/B lands means rebuilding C's authorization calls once A/B
   change them. E (migration 188) is independent and can ship any time, first if
   convenient, exactly as CONTEXT already states.
3. **Recommended split:**
   - **Phase 38.0.1** — R-17 (migration 188, standalone) + R-01 + R-02 + R-04 + R-11
     (Slices A, B, E from CONTEXT, plus F12's expires_at fix since it directly touches
     the same helpers R-02/R-04 modify) — the security-critical RLS/consent rework,
     let it soak with its own adversarial smoke pass before anything is built on top,
     matching migration 186's own "pushed alone, own review" precedent.
   - **Phase 38.0.2** (new, or renumber as this phase's continuation) — R-05, R-06,
     R-07, R-08, R-09, R-10, R-12, R-13, R-14, R-15, R-16, S1 (Slices C, D from
     CONTEXT) — the transactional RPCs and hygiene fixes, built against the now-stable
     corrected foundation, plus WSR-27's consent UI (which depends on WSR-01 existing
     from the first sub-phase).
   - This keeps WSR-27 (the UI) in the SECOND sub-phase, since it needs WSR-01's
     endpoint to exist and be stable, not mid-rework.
4. **Counter-consideration:** if the owner prefers a single phase for a single
   coherent security narrative (one adversarial review commissioned the whole set of
   19 findings; splitting risks losing that narrative coherence across two
   `/gsd-verify-work` passes), a single phase with ~14-18 plans across 5-6 waves
   (A/B/E first wave-group, C/D second) is defensible — this is explicitly the
   planner's/owner's call to make at plan time, not something this research should
   force. The evidence above is offered to make that call informed, not to preempt it.
