## P1 — Postgres role identity

**Requirement:** WSR-25. **Assumption settled:** RESEARCH.md Assumption A2 (medium risk, verify
at planning time), Pattern 5's `guard_vault_projects_user_id_immutable()` trigger.

**What this is for:** Migration 190 adds a `BEFORE UPDATE` trigger on `vault_projects` that
refuses a `user_id` change when `current_user` is in a hard-coded refuse-list. That list must
name the Postgres role Supabase's PostgREST layer actually uses for ordinary authenticated
requests — not an assumed name. The one legitimate direct custody-mutation path in this codebase
(`app/api/vault/custody-transfers/route.ts`'s accept branch) runs through `createServiceClient()`
and must NOT be blocked by this trigger, so its role identity must also be observed, separately.

**Run it twice, through two different client types:**

```sql
SELECT current_user, session_user;
```

1. **Ordinary authenticated session** — run this via any authenticated request path that
   executes SQL through PostgREST under a normal user session (the session-scoped Supabase
   client, i.e. the same client type every RLS-governed API route and every direct
   PostgREST/`supabase-js` browser call uses). Record the two values returned.
2. **Service-role client** — run this via a code path that uses `createServiceClient()` (the
   same client type `app/api/vault/custody-transfers/route.ts`'s accept branch, and
   `app/api/admin/workspaces/access/route.ts`, use). Record the two values returned.

**Interpretation:**
- Migration 190's trigger blocks a `user_id` change only for the role name(s) observed on the
  **authenticated** run above.
- The **service-client** run MUST return a DIFFERENT role name than the authenticated run.
  - If it does: the trigger's refuse-list names only the authenticated role, and the
    service-role path is exempt by construction. GO for authoring migration 190 as designed.
  - If it does NOT (i.e. both runs report the same `current_user`): the trigger as designed
    would also block `app/api/vault/custody-transfers/route.ts`'s legitimate accept branch. Do
    not author migration 190 as designed — the trigger's exemption condition needs
    reconsideration before authoring, and this is an architectural question for plan 02, not
    something plan 02 should silently work around.

## P4 — Audit-log privilege reality

**Requirement:** WSR-26 / S1 (captured now, actioned in Phase 38.0.2 — costs one read now to
avoid re-asking the owner later).

**What this is for:** Migration 182 runs `REVOKE UPDATE, DELETE ON public.workspace_audit_log
FROM PUBLIC;`. In standard PostgreSQL privilege semantics, revoking `FROM PUBLIC` does not touch
a privilege a role holds via a **direct** grant — and Supabase's standard project bootstrap
commonly grants `service_role` broad table privileges directly, separate from `PUBLIC`. This
probe determines, for real, whether that exposure exists in this project.

```sql
SELECT grantee, privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'public'
  AND table_name = 'workspace_audit_log'
  AND grantee = 'service_role';
```

**Interpretation:**
- **No `UPDATE` or `DELETE` row for `service_role`** → migration 182's `REVOKE ... FROM PUBLIC`
  was sufficient in this project's specific privilege setup. Record "no exposure" verbatim.
- **A row naming `UPDATE` or `DELETE`** → confirms migration 182's `REVOKE FROM PUBLIC` did not
  reach `service_role`. Phase 38.0.2 must author an explicit
  `REVOKE UPDATE, DELETE ON public.workspace_audit_log FROM service_role;` plus a rejecting
  `BEFORE UPDATE OR DELETE` trigger as defense-in-depth.

Record the result verbatim in the "Carried to Phase 38.0.2" section below so that phase can be
planned without re-running this query.

**Requirement:** WSR-06. **Assumption settled:** RESEARCH.md Assumption A4.

**What this is for:** Migration 192 adds a join on `vault_projects (id, user_id)` inside

evaluation on `vault_projects` and its child-table RPC reads. If the supporting indexes are
missing in production, the plan-09 `EXPLAIN` gate for that migration becomes a real performance
blocker rather than a formality — this probe finds out now, not mid-review.

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public' AND tablename = 'vault_projects';
```

**Interpretation:**
- An index covering the primary key on `id` (expected: the implicit primary-key index) AND an
  index named `idx_vault_projects_user_id` (or any index whose `indexdef` covers `user_id` as a
  leading column) both appear in the result → GO. The join migration 192 adds should be an
  index-based lookup, not a sequential scan, and plan-09's `EXPLAIN` gate should pass as a
  formality.
- Either is missing → record which one, and say so as a flag for plan 09: the `EXPLAIN` gate on
  that migration becomes a real blocker, not a formality, and an index-adding migration may need
  to land before or alongside migration 192.

## Derived decisions

### D-PF-01 — migration 190 trigger role list: **UNRESOLVED**

P1 returned `postgres` because it ran through the management endpoint. That is *not* the role
ordinary traffic presents as, so it cannot be used as the trigger's block list.

**This must be settled before migration 190 is authored.** The trigger has to reject a `user_id`
change from client traffic (`authenticated`, and `anon` if reachable) while NOT breaking the
legitimate service-role custody-transfer path, which changes `user_id` by design. Blocking
`service_role` outright would break custody transfer; blocking only `postgres` would block nothing
real. Plan 02 must resolve this explicitly rather than inherit an assumption.

### D-PF-02 — migration 191 `NOT NULL`: **GO**

Both NULL counts are 0. The unconditional `NOT NULL` on `relationship_id` is safe against current
production data. Re-verify immediately before the push, since these are live tables.

## D-PF-01 — STILL UNRESOLVED, and it is a DESIGN decision, not a probe result

P1 cannot settle this. It returned `postgres` because the management endpoint runs as `postgres`,
and no authenticated application session was available to observe without creating production
state. Running it again would not help: the roles are architecturally known, and the real question
is which of them the trigger should refuse.

In this stack: PostgREST client traffic arrives as `authenticated` (or `anon`); server routes using
the service key arrive as `service_role`; migrations and the dashboard arrive as `postgres`.

The tension migration 190 must resolve: **the F3 exploit is a client `PATCH` arriving as
`authenticated`, but the legitimate custody-transfer path changes `user_id` through `service_role`
by design.** So a naive "block everything" breaks custody transfer, and "block only `authenticated`"
leaves any service-role path able to move custody outside the D-29 two-sided flow.

Plan 02 must choose explicitly and record the choice. See the orchestrator's note in
`38.0.1-02-PLAN.md` handling.
