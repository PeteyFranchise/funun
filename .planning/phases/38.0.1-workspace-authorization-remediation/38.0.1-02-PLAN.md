<objective>
Close R-17 / WSR-25: the `vault_projects` UPDATE policy inherited from migration 078 never
constrains `user_id`, so a Phase 21 `co-owner`/`editor` — live for weeks, entirely independent of
workspaces — can seize record custody with an ordinary metadata UPDATE.

**Mechanism, corrected at planning:** this is NOT a `WITH CHECK` change. A PostgreSQL RLS
`WITH CHECK` clause is evaluated against the proposed NEW row only and has no access to OLD
(RESEARCH Pitfall 5, cited to the pgsql-hackers thread). The fix is a `BEFORE UPDATE FOR EACH ROW`
trigger, which has guaranteed OLD/NEW access. **No `WITH CHECK` clause anywhere is edited.**

Purpose: custody moves only through the D-29 two-sided transfer, whoever is asking — including the
owner's own direct UPDATE. This is strictly more correct than a co-owner/editor-scoped policy fix.

Output: migration 192 (independent of everything else in this phase; it may be pushed first, alone,
with its own review) and its text-lock test.
</objective>
