# Phase 38.0.1: Workspace Authorization Remediation - Context

**Gathered:** 2026-09-06
**Status:** Ready for planning
**Decisions:** 17 (R-01..R-17)

<domain>
## Phase Boundary

Phase 38 shipped a workspace layer whose **doctrine is right and whose enforcement is not**. An
external adversarial review (Codex, 2026-09-06) found 22 defects; three P0s were fixed and shipped
in the 2026-09-06 hotfix (migration 187). This phase closes the remaining 19.

**This phase changes no doctrine.** All 56 Phase 38 decisions (D-01..D-56) stay locked. Every
change here makes the code do what those decisions already say.

### The two-sentence problem statement

The permission catalogue names 19 granular capabilities, but row-level RLS grants **whole rows** —
so `view_summaries` hands over `tracks.audio_file_url`, `vault_documents.document_data`, lyrics and
ISRCs, while `edit_metadata` maps onto `FOR ALL` policies and becomes delete-and-overwrite
authority including direct mutation of `vault_projects.user_id`.

Simultaneously, the grant model has **no consent origin**: `assertGrantIssuable` derives the
granter's authority from existing grants, so with zero rows every first grant is refused and
nothing seeds one. The layer is **both over-powerful and non-functional**.

<decisions>
## Implementation Decisions

### Authorization model
- **R-01 (F6):** **The subject Member is the root of authority, always.** Build a Member-side
  consent endpoint where the relationship's `member_user_id` issues operational permissions to the
  workspace. Workspace admins may re-delegate **only what the Member already granted**, tracked
  through an immutable `parent_grant_id` lineage. `resolveEffectivePermissions` must re-validate
  the Member's consent AND every delegation link at use time. This is what D-21 already says; the
  code never built the Member's side. Bootstrap resolves because the Member is the root.
- **R-02 (F2/F3):** **Remove the workspace branch from `tracks`, `vault_assets`, `vault_documents`
  and `tool_outputs` entirely.** Workspace reads go through SECURITY DEFINER RPCs with **explicit
  column allowlists**. Only `vault_projects` keeps a direct branch, narrowed. Storage paths must
  never be returned to a workspace caller. Blast radius of any future policy bug drops to one table.
- **R-04 (F4):** **Bind access to custody inside the helper** — `workspace_project_permission`
  joins `vault_projects` and requires `p.user_id = r.member_user_id`. Access then follows custody
  automatically; no cleanup step to forget, no cron.
- **R-08 (F8):** **Workspace proposes, subject confirms.** A workspace may draft evidence (genuine
  admin help), but it stays `proposed` and confers nothing until the relationship's
  `member_user_id` confirms. `document_id` is **mandatory** for authority tier. Verify the document
  belongs to the subject. Enforce `effective_from <= now` at use time — it is currently stored and
  ignored.

### Escalation and state integrity
- **R-05 (F5):** Only owners may promote to owner; admins may not edit or remove owner rows; no
  self-promotion. **Ownership transfer becomes two-sided** — the owner nominates, the successor
  accepts — mirroring D-29 custody transfer. Enforced in the database/RPC, not route logic.
- **R-06 (F9/F11/F15/F16/F14):** **Transactional SECURITY DEFINER RPCs for every consequential
  state change** — custody acceptance, invitation redemption, ownership and owner-floor changes,
  roster transitions. Each does `SELECT ... FOR UPDATE`, revalidates preconditions, mutates, and
  **writes the audit row in the same transaction**. This closes all four races and F14's
  best-effort audit together: a consequential mutation can no longer succeed without its audit
  record.

### Containment
- **R-03:** **Flip the kill switch OFF in production immediately**, before this phase is built.
  Costs nothing (F6 makes the feature non-functional anyway) and closes F5/F8 exposure, which need
  no grants. Also exercises the D-56 control for real, satisfying smoke-checklist 8a/8b.
- **R-07 (F17):** **The D-55 cohort gate is a release requirement**, not a 38.2 item. Server-side
  cohort eligibility in workspace creation and `requireWorkspaceAccess`, following the Song
  Passport pilot pattern. Re-enabling without it means going from "off" to "every Member".
- **R-11 (F12):** **One canonical live-membership definition.** `workspace_member_role` and
  `is_workspace_owner` must check `expires_at`, and `resolveEffectivePermissions` and the catalogue
  must stop selecting `status` alone. Prefer a single SQL helper both layers call.
- **R-12 (F13):** A `proposed` relationship is visible **only to the named Member and the
  owner/admin proposal-management surface** — not to ordinary members, contractors or guests.
  D-05 says the workspace sees nothing until acceptance; the current policy contradicts it.
- **R-13 (F14):** No restricted PII in the broadly readable `changes` JSON (invitation emails are
  currently exposed to every workspace member). Introduce viewer-class-redacted audit reads.

### Quality
- **R-10 (F18):** **Fold the N+1 into R-02.** Resolve permitted project summaries for one actor and
  workspace in a **single set-based, paginated RPC**, preserving live authorization semantics inside
  the SQL rather than caching. Same for the roster GET's per-row evidence tier.
- **R-09 (F20):** "Appears on" requires an explicit contributor or roster relationship **naming the
  caller**. Delegated workspace access is not contribution credit — the same principle as D-43 one
  layer up. Fix `workspaceIdByProjectId` silently overwriting multi-workspace attachments.
- **R-14 (F19):** Strict ISO date/datetime schemas on `effectiveFrom`, `terminatesOn`, `expiresAt`,
  `releaseDate`, plus ordering validation, before any mutation.
- **R-15 (F21):** Remove the `created_by = auth.uid()` fallback in `workspaces_select_member`, or
  condition it on live membership. Make workspace creation atomic so the fallback is unnecessary.
- **R-16 (F22):** `relationship_id` becomes **NOT NULL** on `workspace_attachments` and
  `workspace_grants`. Do not encode "all" as a nullable security foreign key. **Audit production
  for existing NULL rows before adding the constraint.**

### Pre-existing, separate
- **R-17 (F3, pre-existing half):** The `vault_projects` UPDATE policy never constrains `user_id`
  in `WITH CHECK`, so custody can be seized by UPDATE. **This is inherited from migration 078 and a
  Phase 21 `co-owner`/`editor` can exploit it today, independent of workspaces.** It gets **its own
  migration 190** and its own review. Owner decision 2026-09-06.

  **MECHANISM CORRECTED at planning (research, 2026-09-06):** the original wording said "constrain
  `user_id` in `WITH CHECK`". That is **not expressible** — a Postgres RLS `WITH CHECK` clause sees
  only the NEW row and cannot compare it against OLD. The correct fix is a **`BEFORE UPDATE`
  trigger** rejecting any statement that changes `user_id` when the caller is `authenticated` or
  `anon`. This is simpler than column-level privileges, requires **no change to the existing
  `WITH CHECK` clauses at all**, and correctly covers the owner's own path as well as
  co-owner/editor and workspace — custody must move only through the D-29 two-sided transfer,
  whoever is asking.

### Verification
- **S1:** Verify at runtime whether `REVOKE ... FROM PUBLIC` actually removed `service_role`'s
  UPDATE/DELETE on `workspace_audit_log`. Supabase commonly grants table privileges directly to
  `service_role`, which `FROM PUBLIC` does not touch. If so, revoke explicitly and add a rejecting
  trigger.

### Consent surface (added 2026-09-06, at planning)
- **R-18 (scope addition):** WSR-01's consent endpoint ships with a **minimal Member-facing consent
  surface** in this phase. Rationale: R-01 makes the Member the root of authority, and a Member
  cannot exercise authority through an API they cannot reach. Phase 38.1 owns workspace UX but is
  blocked on this phase, so without this the remediation would ship a correct security model that
  still leaves the feature unusable and the kill switch un-flippable.
  **Deliberately minimal — this is not 38.1's UX slice.** In scope: a Member sees pending workspace
  permission requests, reviews exactly which permissions are being asked for, and approves or
  declines per permission. Out of scope: workspace chrome, the switcher, the Roster/Activity room,
  and everything else in 38.1. Adds requirement **WSR-27**.
  A UI-SPEC is generated for this phase covering only this surface.

### Claude's Discretion
- RPC naming and file organisation under `lib/workspaces/`.
- Column allowlist composition per permission, provided it satisfies the D-40 exclusions.
- Whether the delegation lineage is a self-FK or a closure table.
</decisions>

## Recommended Slices

**A — Consent model (WSR-01, 02, 14, 15, 27).** The Member-side grant endpoint and delegation lineage.
Everything else depends on grants being issuable at all. **Do first.**

**B — RLS rework (WSR-03, 04, 05, 06, 20).** Child-table branch removal, column-allowlist RPCs, the
custody binding, and the set-based paginated reader. **Security-critical; let it soak.**

**C — Transactional integrity (WSR-09..13, 07, 08).** The RPCs and the ownership model.

**D — Containment + hygiene (WSR-16, 17, 18, 19, 21, 22, 23, 24, 26).**

**E — Separate: migration 190 (WSR-25).** Pre-existing, affects Phase 21. Own review, own push.
Can run independently of A–D and should not wait on them.

**Sizing note:** this is comparable to Phase 38's own scope. Expect a split; the planner should
assess A+B as one phase and C+D as another if the count exceeds ~15 plans.
</slices>

<risks>
## Risks

1. **R-02 rewrites live RLS policies again.** The same class of change that produced F2/F3.
   Requires the full adversarial smoke before AND after.
2. **R-16's NOT NULL constraint can fail on production data.** Audit for existing NULL rows first;
   a failed migration mid-push is worse than the latent risk.
3. **R-01 changes the consent model users may already have exercised.** Production has no grants
   (F6 guarantees it), so there is no data migration — but confirm that before planning.
4. **R-17 touches Phase 21 sharing that has been live for weeks.** Regression-test the
   "Shared with me" lane explicitly.
5. **The unrun smoke checklist is still outstanding** and now applies to production.
</risks>
