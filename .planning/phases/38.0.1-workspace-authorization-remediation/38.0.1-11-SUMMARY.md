# Phase 38.0.1 Plan 11: Set-Based Paginated Catalogue + Joint Push Summary

A workspace catalogue page now resolves in one live SQL statement with the same six-hop
authorization the per-row helper applies, instead of ~4 queries per project in a loop — and the
fix is a single query, not a cache, so nothing about D-49's "revocation takes effect on the very
next read" changes.

NOT been executed.** No `supabase db push`, `db reset`, `migration up` or `db query` was run. No
database connection of any kind was opened. `npm run build` was not run.

## What Was Built

### Task 1 — migration 194 (`78912e65`)

`public.workspace_catalogue_page(p_workspace_id UUID, p_uid UUID, p_limit INT, p_offset INT,
p_project_id UUID DEFAULT NULL)`, `LANGUAGE sql STABLE SECURITY DEFINER`, `SET search_path = ''`,
with an explicit 20-column `RETURNS TABLE`.

The body reproduces migration 192's resolution set-based for a whole page:

| Hop | Clause |
|---|---|
| 0 | `WHERE public.workspace_access_enabled()` — the D-56 kill switch, evaluated first |
| 1 | live attachment: `a.workspace_id = p_workspace_id AND a.detached_at IS NULL`, optionally narrowed to `p_project_id` |
| 2 | `workspace_members` active AND `(expires_at IS NULL OR expires_at > now())` |
| 3 | `workspace_roster_relationships` accepted, in date window, joined on `r.id = a.relationship_id` with no nullable fallback |
| 4 | `workspace_grants` unrevoked on that same relationship, no nullable fallback |
| 5 | `JOIN public.vault_projects p ON p.id = a.project_id AND p.user_id = r.member_user_id` — the custody binding |
| 6 | `AND public.workspace_grant_lineage_live(g.id)` |

Row visibility is `HAVING bool_or(g.permission = 'view_summaries')`, matching migration 193's
surviving `vault_projects_select_owner_or_member` branch exactly. The eleven metadata columns and
the UPC are each wrapped in `CASE WHEN <flag> THEN <column> ELSE NULL END`, so a withheld value
never leaves the database; two booleans (`can_view_metadata`,
`can_view_private_rights_identifiers`) are returned alongside so the reader can distinguish
"withheld" from "genuinely null" without a second query.

`LIMIT LEAST(GREATEST(COALESCE(p_limit, 50), 1), 200) OFFSET GREATEST(COALESCE(p_offset, 0), 0)`,
ordered `p.title ASC, p.id ASC` inside and `q.title ASC, q.project_id ASC` outside. No storage
path, signed URL, audio reference, document payload or lyric body appears in the declared list
under any permission, and there is no permission argument that could be widened into one.
`REVOKE ... FROM PUBLIC, anon` + `GRANT ... TO authenticated` (this one IS a client-invoked RPC,
unlike migration 192's policy helpers). No policy created or dropped. Ends with
`NOTIFY pgrst, 'reload schema'`.

`__tests__/migration-194.test.ts` — 40 assertions in the established text-lock style, including a
**drift guard** that reads `__tests__/migration-193.test.ts`, extracts its
`FORBIDDEN_RETURN_COLUMNS` array and asserts it is identical to this suite's duplicate. (Plan 10's
file is not mine to edit, so importing was not an option; the guard achieves the plan's
"cannot drift" requirement without touching it.)

### Task 2 — the reader, TDD (`53cbed68` RED, `f7478df7` GREEN)

`loadWorkspaceCatalogue` keeps its membership pre-check verbatim (a deliberate second fail-closed
gate), then issues ONE `supabase.rpc('workspace_catalogue_page', {...})` call, fails **closed** to
`[]` on any error or non-array payload, and keeps the single batched `.in('id', holderIds)`
holder-name lookup. `limit` and `offset` were added and are clamped to the same 200/50 window the
SQL clamps to (exported as `WORKSPACE_CATALOGUE_PAGE_MAX` / `_DEFAULT`). The per-project loop, the
`resolveEffectivePermissions` import and the now-dead `normalizeProjectRow` helper are gone. The
module header gains a fourth doctrine paragraph naming R-10 and D-49 and stating explicitly that a
cache here would reintroduce exactly the staleness the single-query fix avoids.

`hasMore` was **not** added: it cannot be produced without a second query, and the plan said not to
add it in that case.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — missing critical authorization] Bound `p_uid` to `auth.uid()` inside migration 194**
- **Found during:** Task 1, writing the function signature.
- **Issue:** `p_uid` is caller-supplied and the function is `SECURITY DEFINER`, so it bypasses RLS.
  Without a binding, any authenticated user could read any *other* user's permitted catalogue by
  passing that user's id — the definer would happily resolve the other user's memberships, grants
  and lineage. Nothing else in the call path would stop it: the module-level membership pre-check
  runs against the caller's own RLS-scoped client, but the RPC's own resolution would use whatever
  uid it was handed.
- **Fix:** `AND p_uid = (SELECT auth.uid())` in the WHERE clause, with a header section explaining
  why the parameter is kept (explicitness, signature symmetry with migration 193's read functions)
  and that a NULL `auth.uid()` — e.g. a service-role connection — matches nothing and returns zero
  rows, deliberately fail-closed. `auth.uid()` reads a per-transaction GUC that SECURITY DEFINER
  does not disturb, so it returns the caller's identity, not the definer's.
- **Files modified:** `supabase/migrations/194_workspace_catalogue_rpc.sql`,
  `__tests__/migration-194.test.ts` (two assertions).
- **Commit:** `78912e65`
- **This strengthens T-38.0.1-11-01** (the set-based function admitting something the per-row
  helper would deny) along an axis the threat register did not enumerate.

**2. [Rule 1 — dead code] Removed the `now?: number` argument**
- **Found during:** Task 2.
- **Issue:** `now` existed solely to be forwarded to the per-project permission resolver. With the
  resolver gone, the argument was dead — and worse, misleading: a caller passing it would
  reasonably expect it to affect the time-window evaluation, which now happens entirely in
  Postgres against `now()` / `CURRENT_DATE`.
- **Fix:** dropped from the signature. No caller passed it (`app/api/workspaces/[workspaceId]/
  attachments/route.ts` is the sole call site and does not).
- **Commit:** `f7478df7`

### Documented, not "fixed"

**3. Header wording corrected against the plan's literal instruction.** Task 1 said the header
should carry "the same PUSHED-WITH paragraph (191, 192, 193, 194 ... plans 04, 06, 08 and 11)" and
"the HUMAN-GATED paragraph naming ... 181-191". Both were stale by the time this ran. The header as
written states the **actual** push set — 190, 191, 192, 193, 194 and 195 with the TypeScript from
plans 04, 06, 07, 08, 11 and 15 — names `181-193` for the convention, and adds an explicit
CORRECTION paragraph recording that (a) migration 190 was *not* pushed separately as 191-193's
headers imply and (b) 195 did not exist when they were written. It also states the numbering
reservation **correctly** (196-197 for Phase 38.0.2, 198-199 for Phase 38.2) rather than repeating
the off-by-one "195-196 / 197-198" locked into 191-193, and points the reader at
`.planning/ROADMAP.md`'s LIVE LEDGER as authoritative. **Migrations 191, 192 and 193 were NOT
edited** — they are text-locked by their own suites and already reviewed and held.

**4. `holder_user_id` vs migration 193's forbidden-column list.** That list bans a bare `user_id`.
The catalogue function must return the custodian's id: the reader needs it for the single batched
display-name lookup, and joining `user_profiles` inside a SECURITY DEFINER body would bypass that
table's RLS for no good reason. The column is named `holder_user_id`, which the shared word-boundary
check correctly does not flag, and the migration header justifies it explicitly: hop 5 has already
proved `p.user_id = r.member_user_id`, so the value is the roster relationship's own subject
Member — someone the caller can already name. The id never reaches the returned entry; a test
asserts the holder uuid does not appear in the serialised entry.

## Cross-Plan Notes

1. **`p_uid` is unbound in migration 193's four read functions.** `workspace_read_tracks`,
   `workspace_read_assets`, `workspace_read_documents` and `workspace_read_tool_outputs` are all
   `SECURITY DEFINER` and all take a caller-supplied `p_uid` that is forwarded straight into
   `workspace_project_permission(p_project_id, p_uid, ...)` with nothing binding it to
   `auth.uid()`. An authenticated caller can therefore pass a *different* user's id and read
   whatever that user is permitted to read. Migration 194 closes this on its own function
   (deviation 1 above). **This is plan 10's file and was not touched.** Suggested fix, one line per

   `expect(block).toContain('AND p_uid = (SELECT auth.uid())')`. Worth settling **before** the
