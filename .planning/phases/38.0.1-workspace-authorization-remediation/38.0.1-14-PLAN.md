<objective>
Finish R-14 / WSR-22. Plan 08 built `lib/workspaces/date-schemas.ts` and applied it to the evidence
route, where a malformed date directly gates authority. This plan wires the two remaining workspace
date inputs to the same module, so there is one implementation rather than three.

**The defect.** `app/api/workspaces/[workspaceId]/roster/route.ts` accepts `effectiveFrom`,
`terminatesOn`, `effective_from` and `terminates_on` as bare `z.string()`, and
`app/api/workspaces/[workspaceId]/projects/route.ts` accepts `releaseDate` the same way. These
values become the relationship's live-access window, compared inside
`isWorkspaceAccessLive` and inside migration 194's helper. A malformed value is stored and then
either compared as `NaN` (which reads as no constraint) or rejected by a database CHECK with an
unreadable message.

Purpose: input validation on the one axis that decides how long a workspace's access lasts.

Output: two routes wired to the shared schemas, with ordering validation on the roster pair.
</objective>
