# Phase 38.0.1 Plan 13: Member Consent Surface Summary

**A Member can now reach `/settings/permissions`, read exactly what a workspace is asking for in plain language, and approve, decline or revoke each permission as its own decision — with no bulk control anywhere on the page.**

## Performance

- **Duration:** ~45 min
- **Tasks:** 3/3
- **Files modified:** 5 (3 created, 2 modified)
- **Commits:** 5

## Accomplishments

- **The Permissions tab exists and is uncoupled from save-on-switch.** `SettingsTabId` gains a `permissions` member and `SETTINGS_TABS` a fourth entry with the UI-SPEC's label, href and layout segment, positioned after Payouts. `fieldsForTab`, `buildTabPayload` and `buildSaversForTab` all name the tab explicitly rather than relying on a fall-through, so switching to or away from it is instant — no write attempt, no "Saving…" label, no dirty-state prompt (T-38.0.1-13-07). A regression test pins the three existing tabs to the saver counts they had before.
- **The consent surface renders per-permission decisions in plain language.** One card per requesting workspace, one row per permission, the plain sentence from `describePermissionForMember`, and the authority-tier or sensitive tag where it applies. Not one of the nineteen sentences and neither tag string is written out in the component.
- **There is no bulk control, and the test enforces it structurally.** The suite counts Approve controls against rows and asserts no control's name suggests acting on all of them, so an edit that adds one fails rather than ships (T-38.0.1-13-01).
- **Every mutation goes to the Member-gated consent route, one permission per request.** Approve is `POST { permissions: [one] , decision: 'approved' }`, decline is the same verb with `decision: 'declined'`, revoke is `DELETE` with `{ permissions: [one] }` and no `projectId` (the route refuses that key). The component contains no workspace-scoped API path at all (T-38.0.1-13-06).
- **Decline is not styled as revoke, and revoke needs two steps.** Declining an ask writes no grant and takes nothing away, so it gets no confirm and never wears the rose family. Revoking swaps that one row for the inline confirm — `CollaboratorForm`'s delete-confirm pattern, no modal, no toast — and the row's disappearance is the confirmation.
- **A refusal never reads as an approval.** A failed request leaves the row unresolved with both decisions still live and the server's own message printed beside them (T-38.0.1-13-05).
- **Only serialisable data crosses the server/client boundary,** with the production-only 500 that rule prevents named in a comment at the call site (T-38.0.1-13-04).

## Deviations from Plan

None of the auto-fix rules fired. Three judgment calls are worth recording, all of them omissions rather than additions:

**1. The authority-tier document link is not rendered.** The UI-SPEC's section 2 specifies a "They've attached a signed agreement for this — [View it]" line beneath an authority-tier row. Plan 12's `WorkspaceConsentGroup` carries no document reference, deliberately (T-38.0.1-12-04). Rendering a link with nothing behind it would be worse than omitting it. The plan's own `<behavior>` bullets do not list the link, so this matches the plan even where it diverges from the UI-SPEC. **Open for 38.1.**

**2. The per-row "Granted {relative date}" meta line is not rendered.** Same cause: the payload has `relationshipAcceptedAt` (when the relationship was accepted) but no per-grant timestamp. Presenting the relationship date as the grant date on a consent screen is exactly the T-38.0.1-13-02 failure mode in a different costume. The card header shows the accurate `Roster relationship since {date}` instead. **Open for 38.1.**

**3. Project-scoped asks are not surfaced,** per the plan's explicit instruction and plan 12's fail-closed argument. The page's own assembly skips them with the same reasoning recorded inline. Already tracked as an open item in `38.0.1-ORCHESTRATOR-NOTES.md`.
