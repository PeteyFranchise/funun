<objective>
Plan 15 added `workspace_permission_requests` (migration 195, R-19/WSR-28). Two seams were left
open by construction, both in this one file, and plan 15 correctly reported rather than reached
across to fix them:

1. **`resolveOutstandingRequests` derives "pending" from dead-lineage grant rows.** That was the
   only definition available before migration 195. It structurally cannot contain a first-time ask
   — it only ever populates after a consent-then-revoke — which is exactly the story WSR-27 exists
   to tell. Read the real table.

2. **Approving grants the permission but never moves the request row.** POST calls
   `issueMemberConsent` and stops. The ask therefore stays `pending` for ever: the Member's list
   never clears and the workspace's own ask list never resolves. `decidePermissionRequest` exists
   for precisely this and has no caller.

There is also a stale comment (~line 150) stating "There is no `workspace_permission_requests`
table in this schema" — true when plan 07 wrote it, false since migration 195. Remove it rather
than leaving a confident falsehood in a security-sensitive file.
</objective>

<task type="auto">
**Task 1 — read the pending list from the real table.**

Replace `resolveOutstandingRequests`'s dead-lineage derivation with a read of
`workspace_permission_requests` in state `pending` for this relationship. Delete the stale
"there is no such table" comment and the block comment documenting the derived definition.

Keep the response shape byte-identical if you can — plans 12 and 13 consume it. If the shape must
change, say so loudly in your SUMMARY, because plan 12 is running concurrently.
</task>

<task type="auto">
**Task 2 — approve moves the request row; add decline.**

POST (approve) must call `decidePermissionRequest` so the matching pending row becomes `approved`.
Ordering matters and is already handled inside `decidePermissionRequest`: the consent is issued
first and the row is only marked after it lands. Do NOT reimplement that ordering here, and do NOT
mark the row and then issue.

Add a decline path. **Decline is not revoke.** DELETE on this route already means "revoke a consent
I previously gave" and must keep meaning exactly that. Declining a pending ask issues nothing,
revokes nothing, and touches `workspace_grants` not at all — it only records the decline on the
request row. Choose the verb that fits this route's existing conventions and say which you chose
and why in your SUMMARY.

An approve or decline naming a request that does not exist, is not pending, or does not name the
calling Member must fail closed. Never silently no-op.
</task>

<task type="auto">
**Task 3 — tests.**

Cover, at minimum: approve issues consent AND moves the row; approve leaves the row pending when
the consent write fails; decline records the decline and writes no grant; decline of an
already-decided request is refused; a request naming a different Member is refused; the pending
list comes from the new table and contains a first-time ask with zero pre-existing grants — the
case the old derivation could not represent.
</task>
