# Plan 01 — Production pre-flight probes

## What this plan was for

Migrations 190 and 191 both make assumptions about production that could not be
checked from the repo: 190 adds a trigger whose role allowlist depends on which
role ordinary application traffic actually presents as, and 191 tightens two
columns to `NOT NULL`, which is unsafe if any pre-existing row holds a null.

Rather than guess, this plan authored six read-only probes for the owner to run
against production and recorded their literal results.

## Outcome

All six probes were run by the owner on 2026-09-06 and their results are
recorded verbatim in `38.0.1-PREFLIGHT.md` under the `RESULTS` heading.

The findings that changed later work:

- **P2 / P3 — every workspace table is empty.** Zero grants have ever been
  issued, zero attachments exist. This confirmed finding F6 empirically (the
  grant layer has never actually worked) and made **D-PF-02 a GO**: no backfill
  is needed for migration 191, or anywhere else in this phase.
- **P4 — `service_role` holds UPDATE, DELETE and TRUNCATE on
  `workspace_audit_log`.** The audit log is not append-only, confirming Codex
  finding S1. Carried into Phase 38.0.2.
- **P5 — the D-56 kill switch was found ON.** Combined with P2/P3 this means
  production exposure during the Phase 38 defect window was zero.
- **P6 — `idx_vault_projects_user_id` is present**, which is what makes
  migration 192 hop 5's custody-binding join index-backed.
- **P1 was INCOMPLETE by design.** Only the management-endpoint role reading
  (`current_user = postgres`) was obtainable; the ordinary-traffic role could not
  be observed without creating production state. D-PF-01 was therefore settled as
  a design decision rather than a probe result, delegated by the owner.

construction — an agent must never open a database connection in this repo). The

session. Because the executing agent had already stopped at the checkpoint, no
