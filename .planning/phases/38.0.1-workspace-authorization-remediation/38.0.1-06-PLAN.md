<objective>
The I/O half of R-01. Plan 03 built the decisions; this plan wires them to Supabase and rebuilds
`assertGrantIssuable`'s notion of "does the granter hold this".

**The current, verified defect (F6):** `assertGrantIssuable` calls `resolveEffectivePermissions`
with `actorUserId: granterUserId`, whose Step 4 reads `workspace_grants` filtered to the same
relationship. Zero rows means an empty `granterHolds`, which means
`assertGrantIsIssuable` refuses at its subset check. Every possible first grant is refused, forever.

**The fix:** two answers to "does the granter hold X", chosen by who is asking.
1. The subject Member consenting — governed by `assertMemberMayConsent` (plan 03), which consults no
   existing grant at all. The Member is the root; they hold the right by being the rights holder.
2. A workspace admin delegating — still governed by `assertGrantIsIssuable`, but `granterHolds` is
   now the live permission set reachable by walking the `parent_grant_id` chain up to the Member's
   consent root for that relationship. An admin does not need a personal grant row to relay the
   Member's own consent onward (D-21).

Purpose: this is the plan that makes the whole feature functional for the first time since ship.

Output: `consent-service.ts`, `grant-lineage-service.ts`, and a reworked `grant-service.ts`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workspace admin -> grant issuance | The admin may relay the Member's consent; the boundary is that they cannot exceed or originate it. |
| service-role client -> `workspace_grants` | The only write path; authority proven in application code before the client is constructed. |
| stored chain -> effective permission set | Re-derived on every call; a revoked ancestor must invalidate descendants with no job. |
