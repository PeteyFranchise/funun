<objective>
Build the two pure decision modules the corrected consent model needs (R-01 / WSR-01, WSR-02).

**The defect being closed (F6, verified in the current tree):** `assertGrantIssuable`
(`lib/workspaces/grant-service.ts`) computes `granterHolds` by calling
`resolveEffectivePermissions`, whose Step 4 reads `workspace_grants` filtered to the same
relationship. With zero rows — the only state production can be in — `granterHolds` is always empty
and `assertGrantIsIssuable` refuses every request at its "exceeds what the granter holds" check.
Nothing anywhere seeds the first row. The layer is non-functional by construction.

**The fix's logic half:** the subject Member is the root of authority. A Member's own consent is
governed by a NEW assertion that does not consult existing grants at all, and every delegated grant
carries a `parent_grant_id` whose chain must terminate at a live member-consent root.

Purpose: everything else in this phase depends on grants being issuable at all. These two modules
are the decision layer; plans 05 (schema), 06 (I/O) and 07 (route) hang off them.

Output: `lib/workspaces/consent.ts` and `lib/workspaces/grant-lineage.ts`, both pure and fully
unit-tested.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| request body -> `assertMemberMayConsent` | The requested permission set arrives as unvalidated strings; the module accepts `string`, not `WorkspacePermission`, so an untyped value is refused inside the function rather than trusted by its type. |
| stored grant rows -> `isGrantChainLive` | Rows may be stale, revoked, cyclic or incomplete; the walker must fail closed on all four. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-38.0.1-03-01 | Elevation of Privilege | A re-delegated grant outliving the Member's revoked root consent | critical | mitigate | `isGrantChainLive` refuses the whole chain when any ancestor carries a `revokedAt`; revocation cascades at read time with no job to fail. |
| T-38.0.1-03-02 | Elevation of Privilege | A delegated grant widening scope beyond its parent (permission or project) | high | mitigate | Per-hop containment checks on both `permission` and `projectId`; narrowing allowed, widening refused (RESEARCH Open Question 1). |
| T-38.0.1-03-03 | Elevation of Privilege | A structurally excluded capability (payouts/tax, D-42) entering through the new Member-consent path, which has no subset check to catch it | critical | mitigate | Check order in `assertMemberMayConsent` puts structural exclusion before anything else that could approve; a dedicated test asserts both excluded names are refused. |
| T-38.0.1-03-04 | Spoofing | Someone other than the named Member consenting on their behalf | critical | mitigate | The identity comparison (`consentingUserId` vs `relationshipMemberUserId`) is the FIRST check in the pure module, so the route layer cannot forget it. |
| T-38.0.1-03-05 | Elevation of Privilege | Re-introducing the F6 circularity by importing the resolver into the consent path | high | mitigate | A source-text guard test asserts `consent.ts` never imports `grant-service`; the module header states why. |
| T-38.0.1-03-06 | Denial of Service | A cyclic or unbounded chain hanging the walker | medium | mitigate | Visited-set cycle detection plus `MAX_GRANT_CHAIN_DEPTH`; both have dedicated tests. |
| T-38.0.1-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package install occurs; both modules use only existing repo imports. |
