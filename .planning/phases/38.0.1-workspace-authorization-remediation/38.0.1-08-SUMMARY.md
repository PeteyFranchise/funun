# Phase 38.0.1 Plan 08: Evidence Propose-Then-Confirm and Strict Date Validation Summary

Closed R-08 / WSR-14 and WSR-15 at the HTTP layer: a workspace can now only DRAFT agreement
evidence — with a mandatory document that must belong to the subject Member — and only the
relationship's named Member can turn that draft into live authority-tier evidence. Added
`lib/workspaces/date-schemas.ts` as the single home for ISO date validation and window ordering
(R-14 / WSR-22).

## What Was Built

### Task 1 — `lib/workspaces/date-schemas.ts` (commits `e878769a` RED, `cd5ab548` GREEN)

A pure, zero-I/O module. Five exports:

- `isoDateSchema` — `YYYY-MM-DD`, shape-checked AND calendar-checked. The calendar check
  round-trips through a date constructor and compares the normalised result back to the input, so
  `2026-02-30` and `2026-04-31` are refused rather than silently rolled forward into the next
  month. A regex-only validator accepts both.
- `isoDateTimeSchema` — a full ISO-8601 datetime. Rejects a bare `YYYY-MM-DD`, an impossible
  calendar date, and an out-of-range clock component.
- `optionalIsoDate` / `optionalIsoDateTime` — `.nullish()` wrappers, exported so no call site has
  to compose `.optional().nullable()` by hand and get the order wrong.
- `assertDateOrdering({ start, end, startLabel, endLabel })` — returns `{ ok: true }` when either
  side is absent, refuses an end at or before its start naming both labels, and refuses an
  unparseable bound rather than treating a NaN parse as absent. Mirrors migration 183's
  `terminates_on > effective_from` CHECK at the API layer so the caller sees a readable message
  instead of a constraint-violation string.

19 tests. The module imports no Supabase client.

### Task 2 — workspace evidence route hardened (commits `1056fd42` RED, `74d63b73` GREEN)

`app/api/workspaces/[workspaceId]/roster/evidence/route.ts`:

- `documentId` moved from `z.string().uuid().optional()` to required `z.string().uuid()`.
- `effectiveFrom` / `expiresAt` moved from bare `z.string().optional()` to `optionalIsoDate` /
  `optionalIsoDateTime`, matching the column types (`effective_from` is a DATE, `expires_at` is a
  TIMESTAMPTZ). `assertDateOrdering` runs immediately after parse, before any database read, so an
  inverted window is a 400 rather than a stored fact.
- `resolveWitnessedBySignature` became `resolveDocumentFacts`, returning `{ ownerUserId,
  witnessedBySignature }` from the SAME single `vault_documents` lookup the helper already made.
  POST refuses 403 unless `ownerUserId === relationship.member_user_id`. One identical generic
  message covers both "no such document" and "not the subject's document", so a workspace cannot
  use this route as a document-id enumeration oracle. Neither fact opens, parses or validates the
  file (D-36, D-37) — both are structured metadata columns.
- The insert writes `confirmed_by_subject_at: null` and `confirmed_by_subject: null` explicitly,
  and nothing on this route can set either. A comment names the Member-side route that can.
- POST and GET responses carry `isConfirmedBySubject` (a derived boolean, deliberately NOT the
  `confirmed_by_subject` identity column) and `confirmedBySubjectAt`. No response field carries
  document contents, a storage path, or a signed URL.
- The `canManageRoster` gate, the accepted-relationship precondition and the DELETE-supersedes
  behaviour are unchanged; the new suite pins all three.

12 tests, including one proving a third-party-owned document is refused 403 with the same message
as a nonexistent one.

### Task 3 — Member-side confirmation route (commits `1d16de0b` RED, `b15bb9a8` GREEN)

New `app/api/roster/relationships/[relationshipId]/evidence/route.ts`, sibling of
`app/api/roster/relationships/route.ts`:

- Gated by `requireMemberApiAccount` plus a `member_user_id === caller` comparison ONLY. No
  workspace-membership gate, no role predicate. A workspace owner or admin who is not the named
  Member gets the same generic 403 as anyone else.
- The evidence row is loaded filtered by BOTH its id AND the path relationship id, so a row
  belonging to a different relationship is unreachable through this path (404).
- `confirm` sets both confirmation columns through the service client. A row with `document_id`
  null is refused 409 with a message naming the document requirement (migration 191's CHECK
  enforces the same coupling; this is the readable version).
- `withdraw` nulls both columns. **Nothing in the file removes a row** — D-46's rule that a
  billing or relationship event must never destroy rights evidence applies equally to a change of
  mind about confirming one.
- Both branches call `logWorkspaceAction` with `actorId` and `subjectMemberId` both set to the
  Member, actions `workspace.evidence.confirmed` / `workspace.evidence.confirmation_withdrawn`,
  and `changes` carrying the evidence id and the declared scope only.
- GET uses `describeProvenance` unchanged and adds the confirmation state plus the document
  IDENTIFIER; it introduces no third state label (D-37).
- Every verb returns 503 when the D-56 kill switch is off.

11 tests, including the cross-relationship evidence id case.

## Deviations from Plan

### Auto-fixed / judgement calls

**1. [Rule 2 — correctness] `isoDateTimeSchema` requires an explicit time-zone designator**

- **Found during:** Task 1.
- **Issue:** The plan says "a full ISO-8601 datetime passes." An offset-less datetime
  (`2026-09-06T12:00:00`) is technically ISO-8601 but is interpreted as host-local time by both a
  JavaScript date constructor and a TIMESTAMPTZ column, so accepting one silently shifts an
  authority window by the deployment region's UTC offset — the same "reads as something the user
  never declared" failure class R-14 exists to close.
- **Fix:** The pattern requires a trailing `Z` or `±HH:MM`. Documented in the module header and
  covered by an explicit test.
- **Files:** `lib/workspaces/date-schemas.ts`, `lib/workspaces/date-schemas.test.ts`.
- **Commit:** `cd5ab548`.

**2. [naming] `resolveWitnessedBySignature` renamed `resolveDocumentFacts`**

- **Found during:** Task 2.
- **Issue:** The plan says to "extend that helper to return both facts." A helper named for one
  boolean that returns an owner id as well is a misleading name.
- **Fix:** Renamed, doc comment extended (it still states explicitly that neither fact involves
  opening or parsing the file). The symbol was module-local — a repo-wide grep confirms zero other
  references.
- **Files:** `app/api/workspaces/[workspaceId]/roster/evidence/route.ts`.
- **Commit:** `74d63b73`.

**3. [scope] `AgreementEvidenceFacts` left with optional confirmation fields**

Plan 04 deliberately declared `confirmedBySubjectAt` and `documentId` as `?: string | null` rather
than required, because tightening them broke the workspace GET handler. I did **not** tighten
them. The workspace GET still constructs a literal without both keys (a missing key reads
identically to explicit `null` at every fail-closed check); the new Member-side route passes both.
`lib/workspaces/evidence.ts` was not touched.

**4. [plan text vs. schema] The plan's `<read_first>` cites migration 193**

The consent-lineage migration is numbered **191** on this base
(`supabase/migrations/191_workspace_consent_lineage_schema.sql`), and its own header records the
renumbering (188/189 were claimed by unrelated Playbook work). I read 191. No migration was
authored, applied, or verified against a database — this plan is `migration: none`, and the
columns this code writes ship in the joint 190-192 push at plan 11's checkpoint.

**5. [design] PATCH no-ops produce no write and no audit row**

The plan requires "confirming an already-confirmed row is an idempotent success." I extended the
same treatment to withdrawing an already-unconfirmed row, and made both short-circuit before the
update: returning 200 with the current row, with no database write and no audit entry. Logging a
withdrawal that did not happen would put a false event in an append-only, both-sides-visible log
(D-50).
