<objective>
The visible half of WSR-27, built to the approved UI-SPEC and to nothing beyond it.

**Scope discipline.** This phase is a security remediation, not a UX phase. This plan builds exactly
one surface: a Member reviews pending workspace permission requests, approves or declines each one,
and revokes active ones. Workspace chrome, the active-workspace switcher, the Roster/Activity room,
roster cards, the catalogue view, contracts surfaces, audit surfaces and the "Appears on" shelf all
belong to Phase 38.1 and are deliberately absent.

**Two constraints that are not stylistic.** (1) There is no bulk-grant control of any kind. That is
structural, not aesthetic: it is what makes it impossible for a later edit to sweep a D-40 sensitive
permission into a one-click action. (2) A Server Component must never pass a function prop to a
Client Component — that produced a production-only 500 in this codebase before and is a documented
repo lesson.

Purpose: without this, the Member's root authority exists only as an API, the phase's central fix
cannot be verified by UAT, and the kill switch cannot responsibly go back on.

Output: a settings tab, a server page and a client component.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server page -> client component | Only serialisable data crosses; a function prop here is a known production-only failure. |
| client component -> API | Every mutation goes to the Member-gated consent route; the client never reaches a workspace-scoped endpoint. |
| rendered copy -> the Member's decision | Misleading copy is a security problem on this surface, because the Member's understanding is what the authority model rests on. |
