# Phase 38.0.1 Plan 15: The Ask (`workspace_permission_requests`) Summary

**A workspace can now ASK a Member for a permission before that Member has consented to anything — and the ask is a proposal object that confers nothing: it carries no `parent_grant_id`, no authorization path reads it, and approving it routes the actual grant through `issueMemberConsent`, which stays the sole writer of `member_consent` rows.**

## Accomplishments

### 1. `supabase/migrations/195_workspace_permission_requests.sql` (new) — the missing object

`public.workspace_permission_requests`, one row per permission a workspace has asked a Member for.

- **Columns:** `id`, `workspace_id`, `relationship_id`, `member_user_id`, `permission`, `project_id` (NULL = relationship-wide), `requested_by`, `requested_at`, `state`, `decided_at`, `decided_by`, `note`. All three foreign keys that identify WHO the ask is about are `NOT NULL` from birth — the F22/R-16 lesson applied at creation rather than corrected later.
- **`permission`** carries the full nineteen-value catalogue CHECK, byte-identical to migration 184's list, **plus** a separately named `workspace_permission_requests_structural_exclusion_check` naming `manage_payouts` and `view_tax_information`. The second is redundant against today's catalogue list on purpose: if a later migration widens the catalogue, a reviewer still has to delete a constraint whose name says "structural exclusion" to re-admit a D-42 capability. The migration states in prose that those two literals and `STRUCTURALLY_EXCLUDED_CAPABILITY_VALUES` must change together, and the test imports the TypeScript constant to prove it.
- **`state`** is `pending | approved | declined | withdrawn`, with a `decision_pair` CHECK making a half-recorded decision unstorable (pending carries neither decision column; decided carries both).
- **One open ask per scope:** a partial `UNIQUE` index on `(relationship_id, permission, (COALESCE(project_id, '00000000-...'::uuid))) WHERE state = 'pending'`. Terminal rows accumulate freely as history, so a workspace that was declined may ask again and both asks survive.
- **Two triggers, which are the real enforcement.** The table follows the house write-lockdown (`REVOKE INSERT, UPDATE, DELETE ... FROM authenticated, anon`), so every write is service-role — and service-role bypasses RLS but **not** triggers:
  - `workspace_permission_request_member_matches_relationship()` (BEFORE INSERT OR UPDATE) asserts the denormalised `member_user_id` **and** `workspace_id` equal the values on the relationship named by `relationship_id`. This is what makes the denormalisation safe, and the denormalisation is what lets the Member-side RLS policy filter on one local column with no join — no 42P17 recursion shape.
  - `workspace_permission_request_transition_guard()` (BEFORE UPDATE) makes the three non-pending states terminal and the subject of a request immutable. Both rules compare OLD against NEW, which a `WITH CHECK` clause cannot do — R-17's mechanism correction, reapplied.
  - Neither is `SECURITY DEFINER`; the migration adds no definer body at all, and the test asserts the string does not appear.
- **Five policies expressing four rules** (see the checkpoint section for the full text).
- **The header states the not-an-authorization-path property in capitals, first, before anything else**, and enumerates each way it is true.

### 2. `lib/workspaces/request-service.ts` (new)

I/O composition in `consent-service.ts`'s house shape — fetch, decide, mutate, tagged union, never throw.

- `createPermissionRequest` — the bootstrap case: succeeds with zero grant rows against a relationship with no consent root. `member_user_id` is read off the relationship and **there is no parameter through which a caller could supply one**. Every inserted column is named explicitly, never spread. Idempotent on `23505`.
- `withdrawPermissionRequest` — `pending -> withdrawn`, and it can reach no other state from any input.
- `listRequestsForMember` / `listRequestsForWorkspace` — the two reads, both fail-closed: a row whose `permission` is outside the grantable catalogue (or is a D-42 capability) is dropped rather than rendered to a Member as something to approve.
- `decidePermissionRequest` — the only decision path. Only the request's own `member_user_id` reaches it; a miss and a not-yours return one indistinguishable 403. **On approve, the consent is issued first and the decision recorded second.** If the consent write fails, the function returns that failure verbatim and the request stays `pending` — nothing recorded, nothing audited. The opposite residue (a landed grant beside a still-open ask) is harmless and self-healing, because `issueMemberConsent` treats a re-consent as a no-op success.
- Every mutation writes through `logWorkspaceAction` naming **both** the acting identity and the subject Member (D-22, D-50).

### 3. `app/api/workspaces/[workspaceId]/permission-requests/route.ts` (new)

`POST` asks, `GET` lists this workspace's own outbox, `DELETE` withdraws. All three are owner/admin only — matching migration 195's `workspace_permission_requests_workspace_select` policy exactly, including on `GET`, because who a workspace has asked for what is roster-management material rather than general workspace chrome (R-12's posture).

**This route can ask and it can stop asking. It cannot answer**, and the guarantee is structural in four independent ways: `decidePermissionRequest` is not imported by the file at all; `withdrawPermissionRequest` writes exactly one state; both schemas are `.strict()` and neither admits a `state`, a `workspaceId` or a `memberUserId` key; and the module exports exactly `POST`, `GET`, `DELETE`. Tests assert all four.

The D-56 kill switch is consulted first and fails closed with 503 — via `requireWorkspaceAccess`, whose own first statement it is (the F7 hotfix). It is deliberately **not** re-implemented in this file: a second independent kill-switch read would be a second thing to keep correct, and the point of funnelling every `/api/workspaces/**` verb through one gate is that there is exactly one.

`DELETE` withdraws rather than removes — the record that a workspace asked, and later retracted, survives.

## Deviations from Plan

### [Rule 2 - Missing critical functionality] The trigger also pins `workspace_id`, not only `member_user_id`

- **Found during:** Task 1
- **Issue:** The plan specified a trigger asserting `member_user_id` against the relationship. `workspace_id` is denormalised from the same relationship and had no such guard, so a buggy writer could file an ask under workspace A against workspace B's relationship — and workspace A's owners and admins would then read, and be able to withdraw, a row they have no standing on.
- **Fix:** The same trigger asserts both columns against the relationship, with its own error message.
- **Files:** `supabase/migrations/195_workspace_permission_requests.sql`
- **Commit:** 84456bdc

### [Rule 2 - Missing critical functionality] A full catalogue CHECK alongside the structural-exclusion CHECK

- **Found during:** Task 1
- **Issue:** The plan asked only for a CHECK excluding the two D-42 values. That leaves any arbitrary string storable in `permission`, which every downstream consumer then has to defend against.
- **Fix:** Added migration 184's full nineteen-value catalogue CHECK, and **kept** the structural-exclusion CHECK as a separately named constraint rather than folding it in, so D-42's guarantee survives a future widening of the catalogue list.
- **Files:** `supabase/migrations/195_workspace_permission_requests.sql`
- **Commit:** 84456bdc

### [Rule 2 - Missing critical functionality] Relationship-state gate on creating an ask

- **Found during:** Task 2
- **Issue:** Nothing in the plan restricted which relationship states may receive an ask. A refused, blocked or ended relationship would have accepted new asks, putting a question in front of a Member who already closed that door (D-51).
- **Fix:** `ASKABLE_RELATIONSHIP_STATES` = `{proposed, accepted}`; anything else is a 409. `proposed` is deliberately included so a workspace can ask alongside its roster proposal.
- **Files:** `lib/workspaces/request-service.ts`
- **Commit:** 3adfd201

### Note on the plan's `four RLS policies` phrasing (acceptance-criterion sanity)

Task 4 says "the four RLS policies". The plan's own Task 1 body lists **four rules** — Member SELECT, Member UPDATE, workspace owner/admin SELECT + INSERT + UPDATE-to-`withdrawn` — which require **five policy objects**, because Postgres policies are per-command and the workspace's create and withdraw rules are an INSERT and an UPDATE respectively. Written as five, idiomatically, rather than contorted into four. Not a defect in the plan; recorded so the checkpoint reviewer is not surprised by the count.

### The table shape

```
public.workspace_permission_requests
  id              UUID PK DEFAULT gen_random_uuid()
  workspace_id    UUID NOT NULL -> public.workspaces          ON DELETE CASCADE
  relationship_id UUID NOT NULL -> workspace_roster_relationships ON DELETE CASCADE
  member_user_id  UUID NOT NULL -> auth.users                 ON DELETE CASCADE   (denormalised, trigger-pinned)
  permission      TEXT NOT NULL  CHECK (one of the nineteen catalogue values)
  project_id      UUID           -> public.vault_projects     ON DELETE CASCADE   (NULL = relationship-wide)
  requested_by    UUID NOT NULL -> auth.users
  requested_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
  state           TEXT NOT NULL DEFAULT 'pending'
                  CHECK (state IN ('pending','approved','declined','withdrawn'))
  decided_at      TIMESTAMPTZ
  decided_by      UUID -> auth.users
  note            TEXT

  CONSTRAINT ..._decision_pair_check
    CHECK ((state='pending'  AND decided_at IS NULL     AND decided_by IS NULL)
        OR (state<>'pending' AND decided_at IS NOT NULL AND decided_by IS NOT NULL))
  CONSTRAINT ..._structural_exclusion_check
    CHECK (permission NOT IN ('manage_payouts','view_tax_information'))

  UNIQUE INDEX ..._open ON (relationship_id, permission,
                            (COALESCE(project_id,'00000000-0000-0000-0000-000000000000'::uuid)))
               WHERE state = 'pending'
  INDEX ..._member_state    ON (member_user_id, state)
  INDEX ..._workspace_state ON (workspace_id, relationship_id, state)

  RLS ENABLED
  REVOKE INSERT, UPDATE, DELETE FROM authenticated, anon

  TRIGGER ..._member_matches      BEFORE INSERT OR UPDATE  -> pins member_user_id + workspace_id to the relationship
  TRIGGER ..._transition_guard    BEFORE UPDATE            -> terminal states + immutable subject

  NO parent_grant_id COLUMN. NOT IN THE GRANT LINEAGE. READ BY NO AUTHORIZATION PATH.
```

### The RLS policies (four rules, five policy objects)

| # | Policy | Cmd | USING | WITH CHECK |
|---|---|---|---|---|
| 1 | `..._member_select` | SELECT | `member_user_id = (SELECT auth.uid())` | — |
| 2 | `..._member_decide` | UPDATE | `member_user_id = (SELECT auth.uid()) AND state = 'pending'` | `member_user_id = (SELECT auth.uid()) AND state IN ('approved','declined')` |
| 3 | `..._workspace_select` | SELECT | owner OR admin | — |
| 4 | `..._workspace_insert` | INSERT | — | (owner OR admin) `AND state = 'pending'` |
| 5 | `..._workspace_withdraw` | UPDATE | (owner OR admin) `AND state = 'pending'` | (owner OR admin) `AND state = 'withdrawn'` |

"owner OR admin" is `(SELECT public.is_workspace_owner(workspace_id, auth.uid())) OR (SELECT public.workspace_member_role(workspace_id, auth.uid())) = 'admin'` — every helper call wrapped as a scalar subselect per migration 192's recursion doctrine, and no policy body contains an `EXISTS` of any kind.

**What to look for in review:**

1. **`approved` and `declined` appear in exactly one policy — #2, the Member's.** Policies 3, 4 and 5 do not contain either word. A test asserts this on the raw SQL.
2. **`withdrawn` appears in exactly one policy — #5, the workspace's.** The Member cannot erase the record of having been asked.
3. The Member-side policies consult **no** workspace role helper and perform **no** join — that is the whole reason `member_user_id` is denormalised, and the trigger is what makes the denormalisation trustworthy.
4. Ordinary members, contractors and guests get **no** read path onto this table.
5. The policies are declarative given the write lockdown; the **triggers** are what a service-role writer actually meets. That split is deliberate and stated in the migration's section (b).
