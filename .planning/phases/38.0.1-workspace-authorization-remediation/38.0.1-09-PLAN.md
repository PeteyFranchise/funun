<objective>
Rebuild the single point at which a workspace can reach a Member's project.

**Two verified defects in migration 186's helper.** (1) F4: it resolves attachment -> membership ->
relationship -> grant and never reads `vault_projects.user_id` at all. Its own header states this as
a deliberate anti-recursion choice, but that rationale is over-cautious — a SECURITY DEFINER
function reading a table directly does not re-enter that table's policies. The consequence is that
when custody transfers to a different Member, the previous custodian's workspace attachment/
relationship/grant chain keeps working. (2) F12: `workspace_member_role` and `is_workspace_owner`
(migration 182) filter on `status = 'active'` only and ignore `expires_at`, while
`requireWorkspaceAccess` checks it — so an expired contractor seat is refused by the API and
admitted by RLS.

Purpose: bind access to custody structurally, so there is no cleanup step to forget and no cron to
fail; and give the codebase ONE canonical live-membership definition.

Output: migration 194, replacing 186's helper and 182's two membership helpers, and adding the
lineage function. Authored only; pushed at plan 11's joint checkpoint with 191/193/194.
</objective>
