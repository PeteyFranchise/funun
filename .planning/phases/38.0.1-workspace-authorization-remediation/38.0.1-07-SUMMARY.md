## Accomplishments

- **`app/api/roster/relationships/[relationshipId]/consent/route.ts`** (new) — the HTTP surface R-01/WSR-01 always implied and never had.
  - **GET** returns the workspace's display name and type (read through the service client after the gate, because the `workspaces` SELECT policy does not admit the named Member), the relationship's state and accepted date, the permissions currently granted through a live member-consent root (`resolveConsentRootPermissions`), and the permissions the workspace has an outstanding record of asking for. Every row carries its `WorkspacePermission` value, its `PERMISSION_TIER` tier and its `isBundleExcluded` sensitivity flag — the three fields the WSR-27 surface renders. Rows are built by walking `WORKSPACE_PERMISSION_VALUES`, so a value outside the grantable catalogue cannot reach a response no matter what a database row carries; a structural-exclusion filter runs over the same walk as a defensive second pass.
  - **POST** calls `issueMemberConsent` and returns the written permissions, then logs `workspace.consent.granted`.
  - **DELETE** calls `revokeMemberConsent` and returns the revoked permissions, then logs `workspace.consent.revoked`.
  - All three verbs share `openConsentContext`: kill switch → `requireMemberApiAccount` → load the relationship by path id → compare `member_user_id` to the session user. A refusal from the service layer travels back with its own status and reason unchanged; nothing is ever remapped to a 200 with an empty body.
- **`route.test.ts`** (new) — 25 cases. Only `createApiClient`/`createServiceClient` are mocked; the real `consent.ts`, `consent-service.ts`, `grant-lineage.ts`, `grant-lineage-service.ts`, `permissions.ts`, `roster-service.ts` and `member-api-gate.ts` all run against an in-memory Supabase stand-in that mirrors the real query shapes (`select/eq/is/insert/update/maybeSingle/single` plus a thenable terminal). A test that mocked `assertMemberMayConsent` would assert nothing about the forgery surface this endpoint creates.

## Decisions Made

- **An outstanding permission request is derived, not stored.** See the "Cross-Plan Notes" gap below. The route reports as `requested` those `workspace_grants` rows on the relationship that are non-`member_consent`, not themselves revoked, in scope, and whose lineage chain is NOT live — i.e. rows the workspace holds that currently confer nothing because the Member revoked (or never issued) the root above them. This is the only representation the committed schema admits, and it is documented in a dedicated block comment on `resolveOutstandingRequests` so a future reader does not mistake it for an arbitrary choice.
- **Kill switch before authentication.** The plan's `must_haves.truths` says the route "consults the D-56 kill switch first" and the behavior bullet says "before any other work," so the check precedes `auth.getUser()`. With the switch on, an unauthenticated caller still gets 401 (covered by a test). A platform-wide control's answer is identical for every caller, so ordering it first leaks nothing.
- **GET resolves relationship-wide scope (`projectId: null`).** GET takes no query parameters in this plan; a per-project consent view is a later surface's concern, and defaulting to the relationship-wide scope matches what `resolveConsentRootPermissions` treats as the unnarrowed set.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] DELETE refuses a `projectId` rather than silently ignoring it**
- **Found during:** Task 1
- **Issue:** The plan specifies one shared `ConsentBodySchema` carrying `projectId` for both mutating verbs, but `revokeMemberConsent` (plan 06, not in this plan's file scope) takes no `projectId` — its UPDATE matches on workspace, relationship, source and permission, clearing the named permissions across **every** project scope. Parsing a `projectId` on DELETE and dropping it would let a caller believe they had narrowed a revocation that in fact went wider than they asked. Silently ignoring a security-relevant input is a correctness problem, not a style one.
- **Fix:** DELETE returns 400 with an explicit message when the body carries a `projectId` key, and the reason is stated in a comment at the check. `ConsentBodySchema` itself is unchanged from the plan's literal text (POST honours `projectId` as specified).
- **Files modified:** `app/api/roster/relationships/[relationshipId]/consent/route.ts`
- **Verification:** `route.test.ts` — DELETE 'rejects a projectId on a revoke rather than silently ignoring it'

## Cross-Plan Notes (for the orchestrator at merge)

**1. GAP — there is no representation for a workspace's FIRST permission request. Affects plan 12 and plan 13, not just this plan.**

Both this plan's action block and plan 12's say to resolve "the requested-but-ungranted set from the workspace's pending grant requests." **No such table exists.** There is no `workspace_permission_requests` table in `supabase/migrations/`, and every plan in this phase that authors a migration (02→190, 05→191, 09→192, 10→193, 11→194) authors something else. Meanwhile migration 191's `workspace_grants_consent_root_or_lineage_check` requires every non-`member_consent` row to carry a non-null `parent_grant_id` — so a workspace **cannot** record an ask for a permission before the Member has consented to it at least once. The only derivable "outstanding request" is the post-revocation case this route implements (a delegated row orphaned above by a revoked root).

Consequence for the WSR-27 surface (plans 12 and 13): the "Pending requests" section can only ever populate for a relationship where the Member consented and then revoked. The UI-SPEC's primary story — "{Workspace name} wants access" for a workspace asking for the first time — is **not reachable** with the committed schema. This is a phase-level design gap, not a defect in any single plan; it needs either a new table (a migration nobody owns) or an explicit product decision to reframe the surface. Flagging rather than fixing, since a new migration is outside this plan's `migration: none` scope and outside its `files_modified`.
