<objective>
R-19 / WSR-28. A workspace currently has no way to ASK for a permission. Verified during
execution: no request table exists anywhere in the schema, and migration 191's
`workspace_grants_consent_root_or_lineage_check` requires every non-`member_consent` grant to
carry a non-null `parent_grant_id` — so a workspace physically cannot record an ask until a
Member consent root already exists. That is a chicken-and-egg that makes WSR-27's primary story
unreachable.

This plan adds the missing object. It is deliberately NOT part of the grant lineage: a request
is a proposal, it confers nothing, and no authorization path reads it.
</objective>

<task type="auto">
**Task 1 — Author migration 195.**

`public.workspace_permission_requests`:
- `id`, `workspace_id`, `relationship_id`, `member_user_id`, `permission`, `project_id` (NULL =
  relationship-wide), `requested_by`, `requested_at`, `state`, `decided_at`, `decided_by`, `note`.
- `state` CHECK in (`pending`, `approved`, `declined`, `withdrawn`); the last three terminal.
- CHECK that `permission` is not one of the two structurally excluded capability values — mirror
  the literals from `lib/workspaces/permissions.ts` and say in a comment that the two must change
  together.
- Partial UNIQUE index on `(relationship_id, permission, coalesce(project_id, '...'::uuid))
  WHERE state = 'pending'` — one open ask per permission per scope.
- A trigger asserting `member_user_id` equals the relationship's own `member_user_id`, so the
  denormalised column can never drift from its source.

RLS:
- Member SELECT: `member_user_id = auth.uid()`.
- Member UPDATE: only `pending -> approved | declined`, only their own rows.
- Workspace owner/admin SELECT + INSERT + UPDATE-to-`withdrawn`, via
  `(SELECT public.workspace_member_role(...))` wrapped as a scalar subselect.
- **No policy anywhere lets a workspace member move a row to `approved` or `declined`.**

Header must state, emphatically, that this table is NOT consulted by any authorization path.

**Do not push.** 195 joins 190-194 in plan 11's joint window.
</task>

<task type="auto">
**Task 2 — `lib/workspaces/request-service.ts`.**

`createPermissionRequest`, `withdrawPermissionRequest`, `listRequestsForMember`,
`listRequestsForWorkspace`, and `decidePermissionRequest`.

`decidePermissionRequest` on approve MUST delegate the actual grant to `issueMemberConsent` from
`lib/workspaces/consent-service.ts` and write only the request row's own decision fields. If the
consent write fails, the request stays `pending` — never record a decision whose grant did not
land. Every mutation writes through `logWorkspaceAction` with both acting identity and subject
Member (D-22, D-50).
</task>

<task type="auto">
**Task 3 — the workspace-side ask endpoint.**

`POST` creates an ask, `GET` lists the workspace's own asks, `DELETE` withdraws. Gated on
workspace owner/admin. Consults the D-56 kill switch first and fails closed with 503. It must be
impossible to reach an approve or decline through this route — that lives only on the Member-side
consent route.
</task>
