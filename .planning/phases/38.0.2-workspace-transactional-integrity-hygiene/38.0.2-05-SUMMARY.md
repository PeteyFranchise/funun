# Phase 38.0.2 Plan 05: Open Migration 197 Summary

Migration 197 is open, carrying the phase's SQL doctrine in its header plus two new tables and the
two `workspace_members` triggers WSR-07 and R-28 require — text-locked by 74 tests whose negative
assertions were each proved capable of failing.

**The three traps, handled explicitly:**

1. **WSR-07 needed a NEW trigger, not a reuse.** `guard_workspace_never_zero_owners`'s UPDATE branch
   requires `OLD.role = 'owner'`; promoting an admin has `OLD.role = 'admin'`, so it is skipped
   entirely and provides *zero* protection against promotion. Section (c) is new, is not
   `SECURITY DEFINER` (it tests `current_user`, and elevating it would make it always take the
   exemption branch and refuse nothing), and carries an INSERT branch so the postgres-owned
   `workspace_create` RPC can still seat the creator — which is why WSR-23 is a prerequisite for
   WSR-07, not an independent item.
2. **R-28 fixed on both sides.** The qualifying `OLD` test and the remaining-owners `COUNT(*)` both
   gained `expires_at`, and the UPDATE branch now also fires on
   `NEW.expires_at IS NOT NULL AND NEW.expires_at <= now()`, so the last owner cannot be de-ownered
   by expiry while the floor looks away.
3. **`WORKSPACE_OWNER_FLOOR_MESSAGE` preserved byte-for-byte.** Not retyped — the sentence is
   asserted from the imported constant, so drift fails the suite rather than production.

**Migration numbering** is taken from `.planning/ROADMAP.md`'s LIVE LEDGER, and the header says so,
says the ledger supersedes every migration-file header including its own, names the six stale-number
incidents, and marks **201–202 as reserved for the Playbook rich-content workstream — DO NOT TAKE
THESE**. 199–200 are named as Phase 38.2's.

## Deviations from Plan

### Auto-fixed / adjusted

**1. [Rule 3 — Blocking] `lib/workspaces/ownership-transfer.ts` does not exist in this tree.**

- **Found during:** Task 3.
- **Issue:** The plan's acceptance criterion says the suite must *import*
  `OWNERSHIP_TRANSFER_STATE_VALUES` from `@/lib/workspaces/ownership-transfer`. That module is
  authored by **plan 01, which runs concurrently off the same base commit**. A static import fails
  `npx tsc --noEmit` with TS2307 and fails the suite outright — in exactly the tree plan 05 executes
  in, by construction. Plan 05's frontmatter is `depends_on: []`, so this is not a sequencing error
  I could wait out.
- **Fix:** The literals are read from that module's **source text** via `existsSync` +
  regex when it is present, falling back to the canonical set the custody analogue already uses
  (RESEARCH §7.1: "same state set" — `offered`/`accepted`/`declined`/`withdrawn`) when it is not.
  The drift guard is real either way: once plan 01 lands, a change to its array that is not mirrored
  in the SQL `CHECK` fails here. A dynamic `require` was rejected because avoiding its lint would
  need an `eslint-disable` naming a `@typescript-eslint/*` rule, which is forbidden.
- **Files:** `__tests__/migration-197.test.ts`. **Commit:** `14ffafd5`.

**2. [Rule 2 — Missing critical] Added three harness sanity tests.** See above. Without them the
suite's negative half could pass vacuously — the exact failure mode this plan's verification
instructions warn about.

**3. Tasks 1 and 2 landed in one commit (`b90ddfb2`).** They author a single file, and task 2's
owner-floor replacement is only coherent alongside task 1's header (which states the
promote-then-demote rule the replaced trigger enforces). Splitting them retroactively would have
produced an artificial intermediate state that was never real.

### Mis-specified acceptance criteria (flagged, not contorted)

Per the sanity rule, these were satisfied idiomatically rather than to the letter:

- **The transition-guard name.** The criterion asks for `guard_ownership_transition` "(or the exact
  transition-guard name chosen)". The plan's own action text says
  `guard_ownership_transfer_transition()`, which is what was built and what the suite asserts. The
  chosen name does not contain the substring `guard_ownership_transition`; the parenthetical clause
  is what governs.
- **"`expires_at` appears at least three times".** It appears **8 times** in the replaced owner-floor
  body, which is what a correct three-part fix requires. Rather than assert a bare count, the suite
  asserts the decomposition term by term: ≥2 `OLD.expires_at` guards (DELETE branch and UPDATE
  branch), the `NEW.expires_at <= now()` expiry-push clause, and the `COUNT(*)` filter — plus ≥3
  comparisons against `now()`. A count alone would pass even if all 8 occurrences sat in the wrong
  clause.
- **"at least 25 tests"** → **74**.

### Not deviations, but worth recording

- Migrations **190, 196, 182, 190–193's headers are untouched.** The role-scoped-exemption
  discrepancy is *recorded* in 197's header, per the locked decision, not fixed by churning reviewed
  applied migrations.
- The file uses **no `DROP TRIGGER IF EXISTS`** before its `CREATE TRIGGER`s, departing from the
  house idiom in 185/187/195. Both new tables are new, so the drop is unnecessary, and the plan's
  acceptance criteria forbid `DROP TRIGGER` in this file. Section (d) deliberately does *not* drop
  and recreate migration 182's trigger: `CREATE OR REPLACE FUNCTION` suffices and dropping would
  open a window in which the floor is unenforced.
