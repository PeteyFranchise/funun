# Phase 38.0.2 Plan 03: Owner-management and project-access role predicates Summary

Two composable role predicates added to the pure `lib/workspaces/membership.ts`
module: owner-only owner management (R-05 / WSR-07) and the guest-excluding
project-access role floor (R-20 / WSR-29), the latter deliberately shaped so it
is applied *on top of* the existing workspace gate rather than inside it.

## What was built

### `canManageOwners(role)` — R-05 / WSR-07

True for `owner` only. Added immediately after `canConfigureWorkspace`, **beside**
`canManageWorkspaceMembers`, which is untouched and still returns true for
`owner` and `admin`. Narrowing the existing predicate would have taken ordinary
member management away from admins, which no decision asks for; the two
predicates are meant to disagree on `admin`, and that disagreement *is* WSR-07.

The doc comment names migration 197's `guard_workspace_owner_role_change`
trigger (plan 05) as the independent database layer expressing the same rule.

### The project-access role floor — R-20 / WSR-29

A new `// ─── Project-access role floor (R-20 / WSR-29) ───` section holding:

- `WORKSPACE_PROJECT_ACCESS_ROLES: readonly WorkspaceRole[]` —
  `['owner','admin','member','contractor']`. One exported set, commented as the
  TypeScript twin of the conjunct migration 197 adds to
  `workspace_project_permission` hop 2's `workspace_members` join (plan 09), with
  WSR-17 named as the reason it is a twin rather than a deduplication.
- `canReachWorkspaceProjects(role)` — membership in that set, backed by a
  `ReadonlySet` lookup following the existing `KNOWN_MEMBERSHIP_STATES` precedent.
- `WORKSPACE_PROJECT_ROLE_FLOOR_MESSAGE` — the single refusal sentence, exported
  in the same idiom as `WORKSPACE_OWNER_FLOOR_MESSAGE`.

### The composability requirement, handled explicitly

R-20 pulls in two directions: the API gate "must be given the same floor", *and*
"guests keep everything that is not project data". A branch inside
`requireWorkspaceAccess` would satisfy the first and violate the second, because
that gate also covers workspace chrome routes guests legitimately reach.

The resolution is that `canReachWorkspaceProjects` is a **standalone predicate
with the exact signature `requireWorkspaceRole` already accepts**
(`(role: WorkspaceRole) => boolean`). Plan 13 wires it as:

```ts
requireWorkspaceRole(access, canReachWorkspaceProjects, WORKSPACE_PROJECT_ROLE_FLOOR_MESSAGE)
```

No change to `lib/workspaces/access.ts` was made or needed — `requireWorkspaceRole`
already composes a `WorkspaceAccessResult` with any role predicate. The module
comment states in full why the floor is deliberately NOT inside the gate, so a
later reader does not "fix" the apparent omission.

### Header correction

The module header claimed this module governs the workspace "and NEVER project
access". That became half true with R-20: the module still *grants* no project
access, but it now defines the role floor *beneath* it. Both the file header and
the role-capability section header were corrected rather than left stale — the
plan cites migration 139's wrong parenthetical as the precedent for why a stale
doctrine comment is treated as a defect here.
