# Phase 38.0.2 Plan 07: Audit Trail Lockdown, PII Guard and Non-Bypassable Audit Summary

Migration 197 gains four sections that make the workspace audit trail append-only to every
application role, refuse restricted PII at any JSON depth, refuse to let a consequential
change commit unaudited, and hand ordinary members a bounded, caller-bound, allowlist-redacted
read instead of the raw table.

**No database connection of any kind was opened, no migration was applied, and no
`supabase db push`, `db reset`, `migration up` or `db query` was run.** The file remains
deliberately incomplete; plan 09 closes it and carries the owner review checkpoint.

---

## What was built

### Section (e) — the audit lockdown (S1 / WSR-26)

Three layers, each with what it actually binds written beside it.

**Layer 1 — privileges.** `REVOKE UPDATE, DELETE, TRUNCATE ON public.workspace_audit_log
FROM PUBLIC, anon, authenticated, service_role;`. `service_role` is named because 38.0.1
Part A check A10 proved on production on 2026-09-07 that it holds all three, and that
migration 182's `REVOKE ... FROM PUBLIC` removed nothing from it — Supabase's
`ALTER DEFAULT PRIVILEGES ... GRANT ALL ON TABLES TO ... service_role` is a direct grant,
which a revoke from `PUBLIC` never touches. INSERT and SELECT are deliberately retained and
this file issues no REVOKE against either: revoking INSERT would silence the trail, revoking
SELECT would delete D-50's read.

**Layer 2 — triggers.** One unconditional `public.guard_workspace_audit_log_append_only()`
raising `insufficient_privilege`, installed by **two** triggers: a
`BEFORE UPDATE OR DELETE ... FOR EACH ROW` and a separate
`BEFORE TRUNCATE ... FOR EACH STATEMENT`. The second is not a duplicate — a row-level
trigger never fires for TRUNCATE, so without it the one privilege check A10 found that
migration 182 never even named would walk straight past the guard. The function has no
branch, no `current_user` test and no exemption.

**Layer 3 — restrictive policies, scoped honestly.** Documented in the SQL as
forward-insurance against a future non-BYPASSRLS role receiving a grant, explicitly *not*
as the enforcement, because `service_role` carries `BYPASSRLS` and no policy constrains it.
CONTEXT.md's S1 wording ("revoke ... and add a rejecting policy") is called out in the file
as half right.

**The limitation, in its own paragraph.** None of this constrains the database owner.
`postgres` can drop the triggers, `ALTER TABLE ... DISABLE TRIGGER`, or set
`session_replication_role` to `'replica'`. The defensible claim written into the file is
**"append-only to every application role"**, not "immutable", and the file says that must
not be overstated in D-50's wording or in any audit-trail UI copy.

### Section (f) — the restricted-PII write guard (R-13 / WSR-19)

`BEFORE INSERT` guard refusing ten restricted keys — `email`, `phone`, `contact_email`,
`contact_phone`, `address`, `tax_id`, `token`, `token_hash`, `ipi`, `isni` — **at any
depth**, via `jsonb_path_exists(NEW.changes, '$.**."<key>"'::jsonpath)` rather than `?|`.
Research Pitfall 11 is the reason: `?|` inspects top-level keys only, and this codebase
already writes nested before/after diffs (`{"status": {"before": ..., "after": ...}}` on the
invitation-revoked path) that would walk straight past it. Raises `check_violation` naming
the offending key.

The two things it does not claim are written into the SQL: it is a **key-name guard, not a
content classifier**, so a restricted value under an innocuous key still gets through; and
its cost on the write path **has not been measured**, because the table holds zero rows and
no agent opened a database connection.

### Section (g) — the deferred audit-assertion triggers (R-06 / WSR-13)

`public.assert_workspace_change_is_audited()` plus four `CREATE CONSTRAINT TRIGGER`s, each
`DEFERRABLE INITIALLY DEFERRED ... FOR EACH ROW` and each column-scoped:

| Trigger | Event |
|---|---|
| `assert_workspace_member_change_audited` | `AFTER UPDATE OF role, status ON public.workspace_members` |
| `assert_workspace_roster_relationship_change_audited` | `AFTER UPDATE OF state ON public.workspace_roster_relationships` |
| `assert_workspace_invitation_change_audited` | `AFTER UPDATE OF status ON public.workspace_invitations` |
| `assert_workspace_custody_transfer_change_audited` | `AFTER UPDATE OF state ON public.workspace_custody_transfers` |

The SQL states, at the function, that R-06 makes the audit non-**partial** and not
non-**bypassable**; why `now()` is a sound in-this-transaction test
(`created_at` DEFAULTs to `NOW()` = `transaction_timestamp()`); the contract this imposes on
every writer, naming `app/api/workspaces/invitations/accept/route.ts`'s
`targetId: pendingSeat?.id ?? null` as the one call site that already fails it; the MEDIUM
confidence and plan 17 as the proof; and the `logWorkspaceAction`-throws fallback, labelled
a fallback and not the design.

### Section (h) — the redacted audit read (R-13 / R-27 / WSR-19)

`public.workspace_audit_page(p_workspace_id, p_uid, p_limit, p_offset)` returning ten
declared columns. All three migration 194 properties preserved and commented: the
`p_uid = (SELECT auth.uid())` caller bind check B9 proved bites, the
`LIMIT LEAST(GREATEST(COALESCE(p_limit, 50), 1), 200)` clamp, and a declared column list
rather than `SELECT *`. Redaction is **allowlist-based** — `'{}'::JSONB`, never a `changes -`
subtraction — with `changes_redacted` returned as a boolean.

`workspace_audit_log_select` is dropped and recreated as actor-or-subject-or-owner/admin,
with `workspace_audit_visible` narrowed in lockstep. The D-50 tension is stated in the SQL
rather than glossed, R-27's confirmation is recorded, and the file notes that no app surface
reads `workspace_audit_log` today so nothing breaks.

## Deviations from Plan

### 1. [Rule 1 — Bug] Layer 3 is two command-scoped policies, not one `FOR ALL` policy

- **Found during:** Task 1, while writing the SQL.
- **Issue:** RESEARCH §6.3 and this plan both specify
  `CREATE POLICY "workspace_audit_log_no_mutation" ... AS RESTRICTIVE FOR ALL TO authenticated, anon USING (false) WITH CHECK (false);`.
  A RESTRICTIVE policy is AND-ed with the permissive policies for **every command it covers**,
  and `FOR ALL` covers **SELECT**. That single policy would have made `workspace_audit_log`
  unreadable to `authenticated` — silently destroying D-50's both-sides read *and* the
  `workspace_audit_log_select` policy this very file recreates in section (h), while the
  redacted definer function kept working because it runs as `postgres`. The failure would
  have been invisible in a text-lock suite and would have surfaced only in production.
- **Fix:** Two policies, `workspace_audit_log_no_update` (`FOR UPDATE`, `USING (false)
  WITH CHECK (false)`) and `workspace_audit_log_no_delete` (`FOR DELETE`, `USING (false)` —
  a DELETE policy takes no `WITH CHECK`). PostgreSQL accepts exactly one command per
  `CREATE POLICY`, so two is the minimum. TRUNCATE is not an RLS-controlled command at all
  and is covered by layer 1 and the statement-level trigger. The correction is written into
  the SQL beside the policies, and a test asserts no `AS RESTRICTIVE FOR ALL` exists on this
  table so nobody can "restore" it.
- **Files modified:** `supabase/migrations/197_workspace_structural_integrity.sql`,
  `__tests__/migration-197.test.ts`
- **Commit:** `6c8f14f3`

### 2. [Rule 3 — Blocking] One plan-05 assertion narrowed: reading the kill switch is not flipping it

- **Found during:** Task 2 — the only plan-05 test that went red, and the only one changed.
- **Issue:** Plan 05 wrote `it('does not flip the D-56 kill switch', ...)` asserting
  `expect(executable).not.toMatch(/workspace_access_enabled/)`. Correct for a file that never
  touched the switch. Section (h)'s redacted reader **must call**
  `public.workspace_access_enabled()` — reading the switch is exactly what makes that reader
  fail closed while the switch is off, and every workspace read surface in the codebase reads
  it (migrations 186, 192, 194). The assertion as written forbids the correct behaviour.
- **Fix:** Narrowed to what it was always meant to catch — a **write** to
  `workspace_access_config`, or a **redefinition** of the predicate — plus a new companion
  test asserting every appearance of `workspace_access_enabled` is a call and never a
  definition. The reasoning is written in the test file, not only here. The narrowed test is
  strictly stronger than the original against an actual flip; it is weaker only against a
  read, which is mandatory. Mutation M17 proves it still catches a redefinition.
- **Files modified:** `__tests__/migration-197.test.ts`
- **Commit:** `6c8f14f3`

### 3. [Rule 1 — Bug] `COALESCE(..., FALSE)` on `full_view`

- **Found during:** Task 2, reviewing the LATERAL before splicing.
- **Issue:** RESEARCH §10.1's snippet computes `full_view` as a bare three-way OR.
  `subject_member_id` is nullable (migration 182: NULL whenever the action is about the
  workspace rather than a roster Member) and `workspace_member_role()` returns NULL for a
  caller with no live seat, so the OR evaluates to **NULL**, not FALSE, for perfectly
  ordinary rows. `NOT v.full_view` would then return NULL as `changes_redacted` — telling the
  reader neither "withheld" nor "shown", which is the exact ambiguity the boolean exists to
  remove.
- **Fix:** `COALESCE(<three-way OR>, FALSE)`. Unknown means redacted; it fails closed. The
  reasoning is in the section comment.
- **Commit:** `6c8f14f3`

### 4. [Scope, stated not hidden] `workspace_audit_visible` narrowed as well

The plan's Task 2 `read_first` names "the existing `workspace_audit_log_select` policy and
`workspace_audit_visible` helper being narrowed", but the action body only specifies the
policy. Both were narrowed. The policy now expresses its predicate directly (no self-reference
means no 42P17 risk, so migration 186's definer indirection buys nothing, and delegating would
have made the "broad branch is gone" assertion vacuously true); the helper is narrowed in
lockstep because it remains `EXECUTE`-able by `authenticated`, and a helper whose answer
disagrees with the policy is the WSR-17 class of drift this repo exists to avoid.

### 5. Tasks 1 and 2 landed in one commit

Both append to the same file and were spliced in one operation. `6c8f14f3` carries sections
(e) through (h); `632c6786` carries the suite. Two commits, not three.

## Mis-specified acceptance criteria, flagged rather than contorted around

Per the sanity rule, exact counts were treated as "at least one" and satisfied idiomatically.

1. **Task 1: `AS RESTRICTIVE` and the named policy `workspace_audit_log_no_mutation`.** The
   criterion greps only for `AS RESTRICTIVE`, which is satisfied twice. But the action body
   specifies a single `FOR ALL` policy that is **actively wrong** — see Deviation 1. This is
   not a count problem; it is a correctness problem in the plan text and in RESEARCH §6.3, and
   it should be corrected in the research document before any future plan copies that snippet.

2. **Task 3: "contains a recursive path for each restricted key".** Implemented as one
   recursive path *template* (`'$.**."' || v_restricted_key || '"'`) evaluated over a static
   ten-element key array in a `FOREACH` loop, rather than ten literal path strings. Every key
   is covered by a recursive path, the exception message names the offending key, and the
   suite iterates the ten keys with a per-key `it.each` so a dropped key fails by name. Ten
   copy-pasted `jsonb_path_exists` calls would have been strictly worse to review and would
   not have produced a per-key error message.

3. **Task 3: "the total should rise by at least 20".** It rose by 39 (74 → 113). Reported as
   an actual number rather than steered toward.

## Carry-forwards — these MUST reach later plans

1. **PLANS 08, 10, 11 (migration 198) — every RPC must set `target_id` to the mutated row's
   own id.** Not the workspace, not the parent invitation, not null. The deferred constraint
   triggers now abort the whole transaction at COMMIT if no audit row matches
   `target_id = NEW.id AND created_at = now()`. This is the highest-consequence carry-forward
   from this plan.

2. **PLAN 14 (WSR-10) — two separate fixes on the invitation paths, both now enforced by the
   database.**
   - `app/api/workspaces/invitations/accept/route.ts` writes
     `targetId: pendingSeat?.id ?? null`. Null fails the section (g) assertion.
   - `app/api/workspaces/[workspaceId]/invitations/route.ts` writes
     `changes: { role, email: normalizedEmail }`. The section (f) guard now **refuses that
     INSERT outright** with `check_violation`, so the issuance path will start failing the
     moment 197 lands unless the key is removed. `changes` should carry the role and nothing
     else; the address lives on `workspace_invitations.email`, owner/admin-only, reachable
     from the audit row through `target_id`.

3. **PLAN 17 — three harness hazards, two of which this plan created.**
   - The audit table is append-only to **every** role, so teardown cannot `DELETE` its
     fixture audit rows without disabling the triggers first.
   - The four constraint triggers fire at COMMIT on any **direct** fixture UPDATE of a
     consequential column, so seed and teardown must route through the RPCs or disable the
     triggers — and the assertions must run with them **enabled**, or WSR-13 is not being
     tested.
   - The Part A probe must count `workspace_audit_log` explicitly (check A9 counted five
     tables and not this one), because WSR-19 and WSR-26 both assume it is empty, and after
     this migration lands **nothing can delete a row from it**.

4. **PLAN 09 — the header contract holds.** Append above the `NOTIFY` line. The
   "creates or alters no table" assertion still enumerates exactly
   `workspace_cohorts` and `workspace_ownership_transfers`; add any new table to that list.
   Two new module-scope harness helpers are available to reuse: `statementBlock(header)`,
   which slices one statement to its terminating semicolon, and `returnColumnList(header)`,
   copied from the migration 194 suite.

5. **RESEARCH §6.3 should be corrected before it is copied again.** Its recommended
   `AS RESTRICTIVE FOR ALL ... USING (false)` policy would break SELECT on the table. It is
   quoted verbatim in this plan's action body, so the next reader of either document inherits
   the bug. See Deviation 1.
