# Phase 38.0.2 — orchestrator notes

## Planner decisions reviewed and ACCEPTED (2026-09-07)

**1. Two cohort env vars, default CLOSED — accepted.** Song Passport uses three
rungs; workspaces already have a database kill switch (D-56), so a second
env-based one would be two stop buttons that can disagree. This repo has already
shipped a bug from exactly that shape — WSR-17 exists because the RLS helper and
the API gate disagreed about `expires_at`. Fewer authorities, not more. Default
closed is what R-07 demands: without it, re-enabling goes from "off" to "every
Member".

**2. The R-20 API floor is a separate composable helper — accepted, and it caught
a contradiction in my own decision.** R-20 as I wrote it says both "the API gate
must be given the same floor" *and* "guests keep everything that is not project
data". A blanket floor inside `requireWorkspaceAccess` would satisfy the first
and violate the second, because that gate also covers chrome routes. Scoping
`requireWorkspaceProjectAccess` to the attachments and projects routes is the
correct reading. Plan 13's test asserting a guest still reaches a chrome route is
what stops the floor from quietly becoming a ban.

**3. Blocking checkpoints only on 09, 11 and 17 — accepted.** A checkpoint after
"part 1 of 3" of a migration file reviews an incomplete artifact, which is
review theatre. The three that exist land on complete files.

## Backlog, not this phase

- **Migration `046_atomic_opportunity_apply.sql` has no `REVOKE` at all**, so
  `PUBLIC` and `anon` hold `EXECUTE` on a `SECURITY DEFINER` function. Pre-existing,
  unrelated to workspaces, and out of scope here. File it; do not fix it inside a
  remediation phase for a different subsystem.

- **Migrations 190 and 196 document their exemption as function-scoped when it is
  role-scoped.** `current_user IN ('postgres')` is true inside any postgres-owned
  definer function. Not exploitable today — no existing definer function writes
  `vault_projects.user_id` — and this phase avoids widening it by having the
  custody RPC call `transfer_vault_project_custody()`. Both files are text-locked
  and already applied; record the discrepancy rather than churning them.

## Carried into plan 17 — verification harness hazards

Two hazards this phase *creates* that do not exist in 38.0.1's harness. Either
would abort the verification run after 197 lands, in production:

1. The audit log becomes append-only **to every role**, so teardown cannot
   `DELETE` its fixture audit rows without disabling those triggers first.
2. The deferred constraint triggers fire **at COMMIT** on any direct fixture
   UPDATE of a consequential column — so seed and teardown must route through the
   RPCs or disable the triggers, while the assertions must run with them
   **enabled**, or WSR-13 is not actually being tested.

Plan 17 requires both solved explicitly and asserts every trigger was re-enabled.

It also flips B3 (a guest is now refused) and adds **B3b** — the seeded admin must
still pass. A floor that accidentally excluded everyone would pass B3 alone.
