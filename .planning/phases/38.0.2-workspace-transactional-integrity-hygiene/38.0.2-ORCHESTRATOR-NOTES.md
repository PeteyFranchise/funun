## 1. `apply_to_opportunity_atomic` has no EXECUTE lockdown — BACKLOG, NOT THIS PHASE

**What was checked.** `supabase/migrations/046_atomic_opportunity_apply.sql`
was read in full while building migration 198's grant posture, because 046 is
this phase's *behavioural* template (its outcome-code discriminator is the
shape plans 12–16 map to HTTP statuses).

**The finding.** 046 creates `public.apply_to_opportunity_atomic(...)` as
`LANGUAGE plpgsql SECURITY DEFINER` and issues **no `REVOKE` at all**. Supabase
grants `EXECUTE` on new functions to `PUBLIC` by default, so `PUBLIC` — and
therefore `anon` — holds `EXECUTE` on a definer function. It additionally uses
`SET search_path = public` with unqualified table names (`vault_projects`,
`opportunities`, `opportunity_matches`, `submissions`), which is the opposite of
the house `SET search_path = ''` posture that migrations 123, 190, 192, 194 and
196 all use.

**The fix, in one sentence.** Add the migration 123 pair —
`REVOKE EXECUTE ON FUNCTION public.apply_to_opportunity_atomic(UUID, UUID, UUID, TEXT) FROM PUBLIC, anon, authenticated;`
then `GRANT EXECUTE ... TO service_role;` — and schema-qualify the four table
references while `search_path` is tightened to `''`.

**Why it is NOT done here.** Unrelated blast radius (the Antenna opportunity
subsystem, not workspaces), an unrelated test suite, and this phase is already
carrying two migrations through one human-gated push window. Fixing an
unrelated subsystem inside a remediation phase for a different subsystem is
exactly how a review window stops being reviewable.

**When it can be acted on.** Any time after 38.0.2's push window closes. It is
a standalone one-migration change with no dependency on this phase.

**Why it is recorded here at all.** So nobody reading 046 as the behavioural
template copies that half. Migration 198's header and its section (a) template
both say this explicitly: take the outcome-code shape from 046 and the security
posture from 123, never the reverse.

## 2. Migrations 190 and 196 describe a FUNCTION-scoped exemption their code enforces as ROLE-scoped

**What was checked.** Both guard function bodies were read directly this
session, alongside their headers.

**The finding.** Both test the same predicate:

- migration 190 — `IF NEW.user_id IS DISTINCT FROM OLD.user_id AND current_user NOT IN ('postgres') THEN RAISE`
- migration 196 — `IF NEW.user_id IS DISTINCT FROM OLD.user_id AND NOT (TG_TABLE_NAME = 'vault_projects' AND current_user IN ('postgres')) THEN RAISE`

`current_user` is `postgres` for the duration of **any** postgres-owned
`SECURITY DEFINER` function, not only `transfer_vault_project_custody()`. But
migration 190's header says the exemption is *"available ONLY to code that
calls that specific function"* and migration 196's says *"only this one
function's execution context... is permitted."* Those two sentences describe an
intent the code does not enforce.

**Exposure today: none.** No existing definer function writes
`vault_projects.user_id`. The exposure is forward-looking: every new
`SECURITY DEFINER` function this phase adds silently joins the exemption set.

**The phase's answer.** No RPC in migration 198 issues an `UPDATE` against
`public.vault_projects` naming `user_id`. The custody-acceptance RPC (plan 11,
section (h)) **calls `public.transfer_vault_project_custody()`** instead — a
nested definer call runs in the same transaction, so atomicity is preserved,
and the sanctioned function's double filter and its stale-custodian NULL-return
semantics come along for free. That keeps "one sanctioned write path" literally
true at zero cost. It is text-locked by `__tests__/migration-198.test.ts`
(`the 190/196 exemption is role-scoped — this file must not use it`), and that
assertion was verified failable this session by adding an offending `UPDATE`
and watching it go red.

**Migrations 190 and 196 are deliberately NOT edited.** Both are applied,
reviewed, and text-locked by their own suites. Churning two production
migrations to correct a forward-looking sentence is higher-risk than removing
the need for the sentence to be relied on.

**The option considered and rejected.** Tightening the guard with a
transaction-local marker: have `transfer_vault_project_custody()` execute
`SET LOCAL funun.custody_transfer = 'on'` and have both guards additionally
require `current_setting('funun.custody_transfer', true) = 'on'`. Rejected on
two grounds — it rests on a `SET LOCAL` revert behaviour (a `SET LOCAL` issued
inside a function that has its own `SET` clause reverting when that function
exits) that was **not verified** against the documentation or a live database,
and it would require editing both production migrations. If it is ever revisited
it must be confirmed on a preview branch first.

**When it can be acted on.** Not urgent and possibly never. If a future phase
does need a definer function that moves `user_id` outside the sanctioned path,
that is the moment to either tighten the guard or correct the two headers.

## 3. 38.0.1 Part A check A9 counted FIVE tables, not seven

**What was checked.** `38.0.1-VERIFICATION.md`'s Part A results table, row A9.

**The finding.** A9 is recorded as
`attachments / grants / members / permission_requests / roster_relationships`
→ `0 / 0 / 0 / 0 / 0`. That is five tables. It did **not** count
**`workspace_audit_log`** or **`workspace_invitations`**.

**Why it matters.** Two of this phase's requirements assume those two tables are
empty:

- **WSR-19** (redacted audit reads / no restricted PII in `changes`) assumes
  there is no pre-existing audit row already carrying an invitation email in a
  broadly readable `changes` JSON. If `workspace_audit_log` is non-empty, the
  PII fix needs a remediation pass over existing rows, not only a
  forward-looking write rule.
- **WSR-26** (revoke `service_role`'s UPDATE/DELETE/TRUNCATE on
  `workspace_audit_log`, plus plan 07's append-only triggers) becomes harder to
  reverse if rows already exist, because after it lands nothing can delete them.

The narrative around A9 says "every workspace table is still empty", which is a
broader claim than the check actually made.

**What plan 17 must do.** Its Part A probe must count **`workspace_audit_log`**
and **`workspace_invitations`** explicitly, and report them alongside the
original five, before this phase relies on emptiness anywhere. Migration 198's
"WHY NO BACKFILL EXISTS" header paragraph points at this note for exactly that
caveat.

Separately: plan 17's Part B harness must **keep** its existing guard that
refuses to run if `workspace_members` is non-empty. That guard is what stops a
seed-and-teardown harness from running against real member data, and it is
independent of this counting gap.

**When it can be acted on.** At plan 17, before the behavioural window opens.

## Research corrected in place

`38.0.2-RESEARCH.md` §6.3 recommended `AS RESTRICTIVE FOR ALL ... USING (false)`
on `workspace_audit_log`. **`FOR ALL` covers SELECT**, and a restrictive policy is
AND-ed with the permissive ones — so it would have made the table unreadable to
`authenticated`, destroying D-50's read and the redacted SELECT policy the same
migration recreates. It would also have passed testing, because the definer reader
runs as `postgres`. Plan 07 caught it before it shipped and implemented two
command-scoped policies instead; §6.3 now carries a boxed correction so plans
10/11/14 cannot copy the broken form.

# ⚠ HIGH — the invitation REVOKE path breaks when 197 applies (found by plan 14)

**Status: OPEN. Needs a follow-up task after plan 11 closes migration 198.**

`app/api/workspaces/[workspaceId]/invitations/route.ts` still performs two
route-side consequential writes, each in its own transaction:

- **line ~287** — `.update({ status: 'revoked' })` on `workspace_invitations`
- **line ~297** — `.update({ status: 'removed' })` on the paired `workspace_members` seat

Once migration 197 applies, `assert_workspace_change_is_audited` requires an audit
row with `created_at = now()` **in the same transaction**. A PostgREST update from
a route is its own transaction, so:

- the first write's audit row lands in a *different* transaction and cannot match;
- the second has **no audit row written for it at all**.

Both therefore abort at COMMIT. **Invitation revocation stops working.**

Plan 14 could not fix it: the fix is a `workspace_revoke_invitation` RPC in
migration 198, which plan 11 was closing concurrently. Correct scoping, not an
omission.

**Verified independently at merge review:** a repo-wide grep for route-side status
writes found `invitations/route.ts:287` and `:297` as the only remaining
consequential writers outside the RPCs. (`members/route.ts` already goes through
`p_new_status`; `accept/route.ts`'s two writes are removed by plan 14's own
repoint, which was not yet merged when the grep ran.) So closing this closes the
class — it is the last one.

**The follow-up must:**
1. Add `public.workspace_revoke_invitation(...)` to migration 198, stamped from the
   established skeleton — lock, revalidate, mutate **both rows**, audit **both**,
   one transaction. Note it mutates two tables, so LO-1's ranked order applies.
2. Repoint the revoke handler onto it.
3. **Plan 17's Part B does not currently cover the revoke path.** Add an assertion,
   or the next person to learn this is a beta user who cannot revoke an invitation.
