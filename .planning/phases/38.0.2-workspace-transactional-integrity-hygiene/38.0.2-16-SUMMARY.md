# Phase 38.0.2 Plan 16: The Custody Response Path Onto Its Transactional RPC — Summary

**WSR-09's route half is closed.** The PATCH handler ran three separate transactions — read the
transfer, CAS the diary to `accepted` with `.eq('state','offered')`, then call
`transfer_vault_project_custody`. A crash, a redeploy or a concurrent transfer landing between the
last two left the diary saying `accepted` while custody never moved: split-brain on the single field
that decides who holds a Member's record. That sequence is now one
`workspace_accept_custody_transfer` RPC call. WSR-09 had been deferred twice; it is not deferred
again.

## What changed

**Deleted from the PATCH handler, and only from there:** the diary
`.update({ state, responded_at }).eq('id').eq('state','offered')` call with its two-branch result
handling; the `service.rpc('transfer_vault_project_custody', ...)` call with its two-branch result
handling; both `logWorkspaceAction` calls on the accept and decline/withdraw paths; and the
now-orphaned `respondedAt` local.

**Kept verbatim, because they are the documented second enforcement point and not duplication:**
the `requireMemberApiAccount` gate, `RespondSchema`, the service-client read of the transfer row,
`assertMayRespond` including its F1 self-dealing refusal, `isLegalTransferTransition`, and the
derivation of `targetState` from the action. Tests prove each of these refuses *before* the RPC is
reached.

**Added:** a `CUSTODY_RESPONSE_OUTCOMES` map covering migration 198 §(h)'s full vocabulary — `ok`,
`not_found` → 404, `stale` → 409, `already_resolved` → 409, `forbidden` → 403, `stale_custodian` →
409 — plus an `UNRECOGNISED_OUTCOME` fallback that degrades an unknown code to a 400 with a sentence
rather than a 500 with a stack trace, and a `respondToPostgresError` helper mapping `40P01` and
`55P03` to a retry-safe 409.

**Unchanged:** POST and GET, byte for byte apart from one added comment on POST stating why the offer
is not moved to an RPC (it is a single insert guarded by migration 187's BEFORE INSERT trigger and
the partial unique index, so there is no multi-statement race to close).

## The three things from migration 198 that this route does not contradict

1. **No `UPDATE` on `vault_projects` anywhere.** The route does not write that table and never did;
   it now does not even call `transfer_vault_project_custody`. §(h) calls it, and §(h) issues no raw
   UPDATE either — deliberately, because migrations 190 and 196 exempt `current_user IN ('postgres')`
   which is true inside any postgres-owned definer function, so a raw UPDATE would have worked and
   that is precisely the problem. Nothing here reopens that.
2. **The custody move happens before the diary UPDATE, inside the function.** The route does not
   reorder, second-guess or replicate that ordering. It passes `p_action` and reads one outcome code.
3. **The nullable `workspace_id`.** The route's audit condition on the response path is gone entirely
   — the audit row is now written by §(h) whenever `workspace_id IS NOT NULL`, which is exactly the
   condition the route used to apply. The POST path's surviving `if (workspaceId)` guard is
   unchanged and still aligned with the same rule. Nothing in this change makes an audit row
   mandatory for a transfer with no workspace.

## What the tests prove, and what they emphatically do not

`app/api/vault/custody-transfers/route.test.ts` — 19 cases — proves the route's branching, the
precedence of its predicates over the RPC, the outcome-to-HTTP mapping, and that the response path
issues exactly one `.rpc()` call and zero `.update()` calls. The stub client refuses a route-side
update on `workspace_custody_transfers` by throwing, so reintroducing the defect fails loudly.

**It cannot prove the RPC works, and nothing in this plan should be read as claiming it does.**
Migration 198 is authored and unapplied; no test here opens a database connection. The precedent is
exact: migration 190's suite was green, its `transfer_vault_project_custody` function existed, and
this very route called it correctly — and custody transfer was still broken in production for a full
day, raising 42501, because `guard_owner_immutable` (migration 139) fired first under a different
name and refused the write. It took migration 196. The nested UPDATE inside
`transfer_vault_project_custody` fires **both** `vault_projects` guards and **both must admit it**.
Only a real custody accept against a live database proves that. **Plan 17 owns it.** The suite's
header states this in full so a future reader of a green run is not misled.

## Deviations from Plan

### 1. `[Rule 3 - Blocking]` `logWorkspaceAction` import kept — the acceptance criterion is mis-specified

**Found during:** Task 1.

**Issue.** The criterion *"The file contains no `logWorkspaceAction` call"* contradicts two other
instructions in the same plan: the action block says to delete *"both `logWorkspaceAction` calls **on
the accept and decline/withdraw paths**"* and to *"Delete the `logWorkspaceAction` import **if
nothing else in the file uses it**"*, and the plan also says *"Leave POST and GET untouched."* The
POST offer path has its own `logWorkspaceAction` call, guarded by `if (workspaceId)`, which is not on
a response path and which migration 198 §(h) does not absorb — §(h) resolves offers, it does not
create them.

**Resolution.** Both response-path calls deleted; the POST offer call and the import kept. Removing
the POST call would have silently dropped `custody.transfer.offered` from the audit trail and
violated "leave POST untouched". Flagged rather than contorted, per the plan's own sanity rule.

**Files modified:** `app/api/vault/custody-transfers/route.ts`. **Commit:** `d17ab34`.

### 2. `describeTransferEffect` was never imported by this route, and still is not

**Found during:** Task 1.

**Issue.** The criterion says all four helpers are *"still imported and used"*. `describeTransferEffect`
has never been imported by this route — a repo-wide grep finds it only in
`lib/workspaces/custody-transfer.ts` and its own unit test. It is UI copy, not a route predicate.

**Resolution.** Not added. The only non-contorted way to use it here would be to put its sentence in
the PATCH response body, which directly violates the plan's own must-have that *"The success response
body keeps its existing shape, so no client change is needed."* The related must-have —
*"`describeTransferEffect`'s sentence is still what both parties are shown, unchanged"* — is satisfied:
`lib/workspaces/custody-transfer.ts` was not touched and its own suite still passes.

### 3. The two pinned messages are test-local literals, not imports from the route

**Found during:** Task 2.

**Issue.** Task 2 asks for *"a case asserting the stale-custodian response message is identical to
the constant the route returns."* A Next.js App Router `route.ts` module may only export its HTTP
handlers and the route-segment config fields; a repo-wide check found no precedent for exporting an
arbitrary constant from a `route.ts`, and `npm run build`'s route type-check is not runnable here to
prove it safe.

**Resolution.** Both sentences are declared as literals at the top of the test with a comment
explaining why they are not imported. The protective property the criterion wants is fully preserved:
if a future edit rewords either constant in the route, the test goes red. Noted so a later reader does
not read this as a shortcut.

## Cross-plan notes

1. **Deployment ordering is now load-bearing.** `PATCH /api/vault/custody-transfers` calls a function
   that does not exist in production yet. Between merging this and applying migration 198, every
   accept, decline and withdraw returns a 500 from the undefined-function error. This is the same
   coupling plans 12 and 14 created for their own routes; it needs migration 198 to land in the same
   deploy, at plan 17's window.

2. **`transfer_vault_project_custody` now has exactly one caller.** A grep for it across the
   codebase returns only migration files and comments. Any future direct caller is a regression;
   T-38.0.2-16-04 is now enforced at this route by a named test, but nothing enforces it repo-wide.
   A file-wide assertion in a later plan would close that.

3. **The `'stale'` outcome has a new user-facing sentence** — "This transfer changed while you were
   responding. Reload it and try again." It has no predecessor in the old route (there was no CAS
   token before), so nothing was reworded, but it is new copy a UI may want to render.

4. **The `'forbidden'` outcome sentence is deliberately generic** — "You are not permitted to respond
   to this custody transfer." In practice it is unreachable: `assertMayRespond` refuses every case
   §(h)'s authority predicate refuses, before the RPC is called. It exists because §(h) audits its
   forbidden branch and a reachable path must not 500. If plan 17's harness ever observes a
   `forbidden` outcome arriving at the route, the two predicates have drifted and that is a finding.

5. **Confirming plan 11's request:** this plan does not contradict the nullable-`workspace_id` choice.
   The route's response-path audit condition was deleted rather than changed, and §(h)'s
   `workspace_id IS NOT NULL` condition reproduces it exactly.
