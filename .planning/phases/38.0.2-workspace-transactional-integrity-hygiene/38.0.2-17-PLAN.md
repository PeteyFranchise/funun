<objective>
Build the phase's two verification artefacts, map every requirement to the evidence that actually
proves it, and hold the joint push.

**Why behavioural verification is mandatory here, not optional.** This repo has no live-Postgres
test harness. Every claim the text-lock suites make is a reading of SQL text, not an observation of
a running database. That gap is not theoretical: migration 190's suite was green, its function
existed, and the route called it correctly — and custody transfer was still broken in production for
a day, because migration 139's differently-named `guard_owner_immutable` also fires on
`vault_projects` and refused the sanctioned RPC. Only Part B, executing the real RPC, surfaced it.
**A plan whose entire verification is `npm test -- migration-197` proves nothing about this phase.**

**Why a single-shot production window rather than a preview branch.** Supabase branching needs a paid
plan and the org is on Free. 38.0.1 Part B established the pattern: seed, enable the kill switch,
assert, tear down and restore, all inside one atomic `DO` block, with per-assertion subtransactions
so one failure costs one row rather than the whole result set. It ran cleanly, and it found a
production bug nothing static could reach. **Extend that file rather than writing a new one** — it
already seeds six identities, already guards against running into live data, and its teardown is
already correct for the tables 38.0.1 touched.

**The one assertion that flips.** 38.0.1's Part B check B3 asserted a guest reaching an attached
project was correct behaviour, and recorded that the contrary expectation was a defect in the test.
R-20 changed the answer: the guest must now be refused. The same run must also prove the floor is
not over-applied, so an active non-guest non-owner (the seeded admin) must still reach the project.

Output: a structural probe, an extended behavioural harness, a requirement→evidence map, and the
blocking checkpoint at which the owner pushes both migrations, deploys the code, runs both parts, and
decides whether the D-56 argument now holds.

**Non-negotiable constraints for this plan:**
- **Do NOT open a database connection. Do NOT run `supabase db push`, `db reset`, `migration up`, or
  `db query`.** This plan AUTHORS the SQL the owner runs; it never runs it.
- **Do NOT flip the D-56 kill switch.** The harness flips it inside its own atomic block, run by the
  owner, and restores it in the same transaction. Nothing else in this phase may touch it.
- Do NOT touch anything under `lib/playbook/`, `components/playbook/`, or `app/**/playbook/`.
- Stage by explicit path only. **Never `git add -A`** — expect unrelated modified and untracked files
  in this working tree.
- Use `npx tsc --noEmit`, never `npm run build`.
</objective>
