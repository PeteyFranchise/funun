# Phase 38.0.2 Plan 15: Roster Routes and the Audit Writer Summary

**Both roster surfaces now write through one compare-and-set RPC and the workspace reads through the collapsing definer function, so a concurrent PATCH can no longer overwrite a terminal state, a crash can no longer separate a block from its block row, and a workspace can no longer learn it was blocked — while the owner still sees the `proposed` rows migration 197 took away from the raw table.**

## What was built

### Task 1 — `app/api/roster/relationships/route.ts` (the Member surface)

The four PATCH branches collapsed into a single flow: resolve the target
state for the friendly pre-refusal, run `assertCanTransition` (or
`assertMemberMayEnd` for `end`), then one
`service.rpc('workspace_transition_roster_relationship', ...)` carrying
`p_expected_state` from the loaded row and `p_actor_side: 'member'`.

Deleted: all four `.update(...)` calls, all four `logWorkspaceAction` calls,
the `workspace_roster_blocks` upsert, the `logWorkspaceAction` import, and
the now-unused `nowIso`.

Kept and commented: the identity check (`row.member_user_id !== gate.user.id`
→ 403), both assertion helpers, and the D-56 asymmetry — restated at the RPC
call site so a reader cannot conclude one of the two layers is redundant.
Both gate `accept` only; D-18 makes revocation unconditional.

The GET is byte-for-byte unchanged apart from a new comment naming R-23: this
surface deliberately reads the raw table and keeps the true `blocked` state,
because the collapse is a workspace-facing concern and pointing this reader at
`workspace_roster_page` would hide a Member's own block from them.

### Task 2 — `app/api/workspaces/[workspaceId]/roster/route.ts` (the workspace surface)

**The repoint.** GET now calls `public.workspace_roster_page` on the
**session** client (the function's own `p_uid = (SELECT auth.uid())` clause
means a service-role call returns zero rows), with limit and offset clamped to
the same 1..200 / default-50 window the SQL clamps to. `loadRelationshipTier`
mapping is unchanged.

**The `end` write.** `assertWorkspaceMayEnd` stays as the friendly
pre-refusal; the `.update(...)` and the `logWorkspaceAction` call are replaced
by one RPC call with `p_actor_side: 'workspace'` and the loaded state as the
CAS token, then a re-read through `ROSTER_COLUMNS`.

**The D-05 refusal.** Any `action` other than `end` is now refused at the
route with a 403 naming the rule — accepting, refusing and blocking are the
named Member's decisions alone — before the RPC, and again inside it.

**POST and the amend path are untouched**, `logWorkspaceAction` included, and
both now carry a comment saying why that is deliberate rather than an
oversight.

### Task 3 — `lib/workspaces/audit.ts`

The superseded "ONE write-through call every workspace-context write invokes"
sentence is gone. In its place: migration 198's RPCs write the audit row for
every consequential change inside their own transaction, migration 197's
deferred triggers make that non-bypassable, and `logWorkspaceAction` survives
for the four non-consequential uses — invitation issuance, evidence upload,
kill-switch flips, workspace configuration — plus a paragraph on the three
new constraints (append-only, restricted-PII, deferred assertion) and one on
why the never-throws contract is retained. No behaviour change; the six
pre-existing tests pass untouched.

## The two items called out in the brief

### 1. Two `end` action strings — confirmed, nothing to do

Migration 198 section (g) resolves the audit action name with
`WHEN p_actor_side = 'workspace' THEN 'workspace.roster.ended' ELSE
'roster.ended'`. Both strings exist and match what each route already
emitted, so the trail stays continuous. My routes now write **neither** — the
RPC owns both. No route-side change was needed or made.

**`target_id` check.** Every audit row this plan leaves behind carries the
mutated row's own id, so plan 07's deferred constraint triggers will not abort
at COMMIT:

- Member route: **zero** `logWorkspaceAction` calls remain. The RPC writes
  `target_id = v_relationship.id`.
- Workspace route POST: `targetId: inserted.id` — the inserted relationship
  row. ✓
- Workspace route amend path: `targetId: target.id` — the amended row. ✓
- Workspace route `end`: the call is gone; the RPC writes it. ✓

### 2. The restricted-PII strip does NOT belong in `lib/workspaces/audit.ts`

**Conclusion: plan 14's route is the right place; `audit.ts` is not.** Four
reasons, and the header now records them as a standing prohibition rather
than a silent omission:

1. **Migration 197 section (f)'s own `COMMENT` says so.** It names the
   invitation-issuance route as "the one offender that exists today" and says
   "plan 14 removes it". The guard was designed with that call site in mind.
2. **A silent strip converts a loud, correct refusal into quiet data loss.**
   The trigger REFUSES the INSERT; a stripper here would let the write
   succeed with a hole in it, and nobody would ever learn a route tried to
   log PII. That is precisely `.claude/CLAUDE.md`'s "Silent Failures in
   Readiness Calculation" anti-pattern.
3. **`logWorkspaceAction` never throws.** A strip here would be invisible on
   both ends — no exception, no `{ ok: false }`, no signal at all.
4. **It would defeat the backstop.** The two-layer doctrine is "the caller
   does not write PII" (primary) plus "the trigger refuses it" (backstop). A
   third silent layer between them removes the backstop's only diagnostic
   value.

The header states this explicitly: *"THIS FUNCTION DELIBERATELY DOES NOT STRIP
THEM AND MUST NOT BE MADE TO."* If plan 14 concludes otherwise it will find
that sentence and a test-pinned reason before it changes anything.

## Deviations from plan

### [Rule 3 — Blocking] One pre-existing test re-expressed rather than left alone

**Found during:** Task 2.
**Issue:** Task 3's action says *"Do not modify or delete an existing test in
the workspace roster suite."* But the existing case *"leaves the end action
untouched — it writes no date bound of its own"* asserts
`service.calls.updates[0]` matches `{ state: 'ended' }` — an assertion against
the exact `.update(...)` Task 2 is required to delete. The two instructions
cannot both be satisfied.
**Fix:** Re-expressed the case against the RPC arguments, keeping its title
and strengthening its original claim (the route now issues *no* update at
all, so it certainly writes no date bound). A comment above it records that
the amendment is not a weakening. No other existing case was touched; all 15
pre-existing tests still pass.
**Files modified:** `app/api/workspaces/[workspaceId]/roster/route.test.ts`
**Commit:** `c8c6d3dc`

### [Rule 2 — Missing critical functionality] `PatchRosterSchema.action` widened so the D-05 refusal is explicit

**Found during:** Task 2.
**Issue:** The schema had `action: z.literal('end').optional()`, so
`action: 'accept'` was already refused — but with a generic Zod message
("Invalid literal value, expected \"end\""). The plan's action text requires
*"an explicit refusal for any action other than `end` ... with a comment
stating that a workspace may never accept, refuse or block on a Member's
behalf"*, which an implicit literal cannot provide, and which a test cannot
distinguish from any other malformed body.
**Fix:** Widened to `z.string().trim().max(50).optional()` and added an
explicit 403 branch naming the rule, ahead of the target load and the RPC.
The bound (`max(50)`) keeps the field from becoming an unbounded string.
**Files modified:** `app/api/workspaces/[workspaceId]/roster/route.ts`
**Commit:** `da3ab2df`

### [Judgment call] Page clamp constants declared locally, not imported

**Found during:** Task 2. The plan points at `lib/workspaces/catalogue.ts`
"for the pagination-parameter idiom". I followed the **idiom** (a
`clampLimit`/`clampOffset` pair mirroring the SQL's own
`LEAST(GREATEST(COALESCE(...)))`) but declared `ROSTER_PAGE_MAX = 200` /
`ROSTER_PAGE_DEFAULT = 50` locally rather than importing
`WORKSPACE_CATALOGUE_PAGE_MAX`/`_DEFAULT`. Those constants carry a doc comment
binding them to **migration 194's** clamp; this route's clamp must track
**migration 197's**. They agree today, and importing would mean a future
change to 194 silently moved the roster page too. The reason is written above
the constants.
