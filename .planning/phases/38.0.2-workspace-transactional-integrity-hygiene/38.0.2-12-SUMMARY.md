# Phase 38.0.2 Plan 12: Members Route Repointed, Ownership Route Added — Summary

The members route now has **one writer** — `workspace_change_member_role_or_status` — and no
coupling to an English error sentence; a new two-sided ownership route lives inside
`/api/workspaces/**` with four enforcement points and no route-side writer of any kind.

## What was built

### Task 1 — `app/api/workspaces/[workspaceId]/members/route.ts` (commit `0b27c029`)

**Deleted**, per RESEARCH §11.3 (keep every predicate, delete every mutation sequence):

- The cross-transaction owner-floor `count` query and the helper wrapping it. That count was
  finding F15: two concurrent demotions of two *different* owners each counted one remaining
  owner, each concluded the floor held, and both proceeded — correct today only because the
  trigger caught the second at write time.
- The string-sniffing helper that tested whether a Postgres error message contained a substring
  of the owner-floor sentence. Three files were coupled to one English sentence; rewording
  migration 182's `RAISE` would have silently turned every owner-floor refusal into a 500.
- Both `.update(...).eq('id', target.id)` sequences and both paired audit-helper calls. The
  audit-helper import is gone from this file entirely — the RPC writes its own audit row in the
  same transaction as the mutation.

**Kept**, unchanged: `requireWorkspaceAccess`, `requireWorkspaceRole`, `loadTargetMember` (a read
producing the friendly pre-refusals and supplying the CAS tokens), both Zod schemas,
`isLegalMembershipTransition`, `WORKSPACE_OWNER_FLOOR_MESSAGE`, and the GET handler's behaviour.

**Added:**

- A module-scope `MEMBER_CHANGE_OUTCOMES` map covering migration 198 section (c)'s full
  vocabulary — `not_found` 404, `forbidden` 403, `forbidden_owner_row` 403,
  `promotion_requires_transfer` 409 (with a sentence naming
  `POST /api/workspaces/{workspaceId}/ownership`), `no_self_role_change` 403, `stale` 409,
  `illegal_transition` 400, `floor` 409 — plus a fallback so an unrecognised code degrades to a
  400, never a 500. `floor` uses `WORKSPACE_OWNER_FLOOR_MESSAGE` verbatim from the imported
  constant.
- `respondToPostgresError`: `40P01` and `55P03` → 409 with a retry-safe sentence; anything else
  → 500. Commented that migration 198's `SET LOCAL lock_timeout = '3s'` is what turns a blocked
  row lock into a bounded, retryable code rather than a hung request.
- A `canManageOwners` gate on both owner-touching paths, **beside** `canManageWorkspaceMembers`
  and never instead of it (orchestrator carry-forward, wave 1 item 5). PATCH gates when the
  target's role is `owner` **or** the requested role is `owner`; DELETE gates when the target is
  an owner.

**R-21 Option A**, stated in the header and at the call site: the route passes `p_actor_id` —
the identity `requireWorkspaceAccess` already proved — and nothing else about the caller. There
is no `p_actor_role` argument. The header records explicitly that R-05's "enforced in the
database, never route logic" is therefore only *partially* satisfied: the authority half is in
the database, the identity half is here.

### Task 2 — `app/api/workspaces/[workspaceId]/ownership/route.ts` (commit `cb1d4906`)

`POST` (nominate), `GET` (list), `PATCH` (accept / decline / withdraw).

- **Why inside `/api/workspaces/**`.** The header states the deliberate asymmetry with
  `app/api/vault/custody-transfers/route.ts`, which lives *outside* because custody is a Member
  act carrying no workspace authority (after F1 it has no workspace lookup to prove authority
  through, and the kill switch has nothing to gate there). Workspace ownership is the opposite —
  entirely a workspace act, the broadest authority the model grants — so it belongs behind the
  path-segment gate and the kill switch (D-31).
- **Four enforcement points**, listed in the header in the custody route's FIRST/SECOND/THIRD
  style, extended to four: the route gates, the pure predicates, the RPC's post-lock checks, and
  migration 197's CHECKs / triggers / one-live-offer index.
- **`POST`** gates with `requireWorkspaceRole(access, canManageOwners, ...)`, parses a `.strict()`
  Zod body behind a `pickFields` allowlist, reads the successor's seat (treating an expired
  `expires_at` as not live), calls `assertMayNominate` for the friendly pre-refusal, then makes
  **one** `service.rpc('workspace_nominate_owner', ...)` call. On `ok` it returns 201 with the
  transfer row and `describeOwnershipTransferEffect`'s sentence, so both parties see the same
  account of what changes and what does not.
- **`GET`** reads `workspace_ownership_transfers` through the **RLS-scoped session client**, not
  the service client, with a comment matching the reasoning in the custody route's GET: migration
  197's `workspace_ownership_transfers_select` policy is the filter, so visibility is decided by
  one reviewed policy. The `.eq('workspace_id', ...)` scopes the list to the path segment; it does
  not decide who may see a row.
- **`PATCH`** gates on `requireWorkspaceAccess` **only**, with an explicit comment saying why —
  the successor accepting is by definition not yet an owner, so an owner-only gate here would make
  the two-sided act impossible to complete and leave `accept` reachable by nobody. Authority to
  respond comes from the nomination (`assertMayRespond`), not from a workspace role.
- **No audit-helper call appears anywhere in this file.** Both RPCs write their own audit rows,
  including for every authority refusal (R-26).

## Deviations from Plan

### 1. [Rule 3 — Blocking] `canRemoveMember` is no longer imported by the members route

- **Found during:** Task 1.
- **Issue:** The plan's action says to **keep** `canRemoveMember` and `assertOwnerFloorHolds`
  alongside the other predicates. `canRemoveMember`'s only call site in this file was *inside*
  `refuseIfOwnerFloorBreaks`, and its `remainingActiveOwnersAfterRemoval` argument can only be
  produced by the cross-transaction `count` query the same plan deletes (F15). Keeping the import
  with no call site is an unused import, which is a lint error under `next build` even though
  `tsc` passes — a failure mode the plan's own constraints call out explicitly.
  `assertOwnerFloorHolds` was never imported by this route.
- **Fix:** Read "keep" as RESEARCH §11.2 means it — the *predicate survives in the codebase*, not
  "this route must call it". Both remain exported, unchanged and independently tested in
  `lib/workspaces/membership.ts`, which is untouched by this plan. The owner floor now reaches
  this route as the outcome code `'floor'` and is expressed with the same shared constant.
- **Files modified:** `app/api/workspaces/[workspaceId]/members/route.ts` (import list only).
- **Commit:** `0b27c029`.

### 2. [Rule 3 — Blocking] Three identifier names removed from comments to satisfy literal greps

- **Found during:** Task 1, at the acceptance-criteria check.
- **Issue:** The plan's action text asks the outcome-map comment to explain *that* the `'floor'`
  entry replaces a string match on a Postgres error message and *that* three files were coupled
  to one English sentence. My first draft did so by naming the deleted helpers and quoting the
  sentence — which made the file contain `isOwnerFloorTriggerError`, `refuseIfOwnerFloorBreaks`
  and the literal `at least one active owner`, tripping three acceptance criteria that are worded
  as literal absence.
- **Fix:** Rewrote the three comment passages to describe the deleted mechanism without naming it
  or quoting the sentence ("a route-local sniffer that tested whether the database error message
  contained a substring of that sentence"). The explanation is intact; the greps are clean. The
  same reasoning removed the audit-helper's identifier from a prose mention in the header, so the
  T-38.0.2-12-06 check ("no such call remains") cannot be confused by a comment.
- **Files modified:** `app/api/workspaces/[workspaceId]/members/route.ts` (comments only).
- **Commit:** `0b27c029`.

### 3. [Design reading] No `expectedRole` / `expectedStatus` accepted from the members request body

- **Found during:** Task 1.
- **Issue:** Task 1's `<behavior>` says "PATCH with a stale `expectedRole`/`expectedStatus`
  returns 409", while its `<action>` says to pass "the target's currently-loaded role and status
  as the CAS tokens".
- **Fix:** Followed the action. The CAS tokens come from the route's own `loadTargetMember` read,
  so `'stale'` means the row moved between that read and the RPC's lock — the actual race the CAS
  exists to catch. Nothing role-shaped is accepted from the body beyond the requested `role`
  itself, which keeps T-38.0.2-12-03's assertion clean. The ownership route *does* accept
  `expectedState` from the body, as its own action text specifies; that is a transfer state, not
  a role. Behaviour is covered either way: a `'stale'` outcome maps to 409.
