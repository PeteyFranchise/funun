# Phase 38.0.2 — Requirement → Evidence Map

## Four kinds of evidence, and they are not interchangeable

This repo produces four kinds of evidence about a requirement. They answer different
questions and they cost different amounts to fake:

| Kind | Answers | Where it lives |
|---|---|---|
| **text-lock** | *What does the SQL say?* | `__tests__/migration-19X.test.ts` — asserts the authored SQL string contains what it was reviewed as containing |
| **unit** | *What does a pure function decide?* | `lib/workspaces/*.test.ts` — a decision table, an authority predicate, a legal-edge set |
| **route unit** | *What does a handler do with an answer?* | `app/api/**/route.test.ts` — outcome codes to HTTP statuses, arguments handed to `.rpc()`, writes recorded by a stub client |
| **structural probe** | *What does the DEPLOYED DATABASE contain?* | `38.0.2-VERIFY-A-STRUCTURAL.sql`, run read-only against production |
| **behavioural assertion** | *What does the RUNNING SYSTEM do?* | `38.0.2-VERIFY-B-PRODUCTION-SINGLE.sql`, one atomic window against production |

### The incident that makes the distinction load-bearing

Migration 190 shipped a `BEFORE UPDATE` trigger making `vault_projects.user_id` immutable
outside one sanctioned function. Its **text-lock suite was green**. Its **function existed** —
a structural probe would have said PASS. **The route called it correctly** — the route unit
suite was green. And **custody transfer was broken in production for a day**, because
migration 139's differently-*named* `guard_owner_immutable` also fires on `vault_projects` and
refused the sanctioned RPC. Three kinds of evidence were all green and none of them could see
it. Only 38.0.1's Part B, executing the real RPC, surfaced it — and migration 196 fixed it.

**Therefore: a requirement whose only evidence is text-lock is NOT verified in production, and
must not be marked so in `.planning/REQUIREMENTS.md`.** The same goes for a structural probe:
a green Part A is a reading of the catalogue, not an observation of behaviour. Both files say
so in their own headers.

**And a behavioural PASS is not a blanket warrant either.** Part B asserts the specific
propositions listed below and nothing wider. Where it does not reach a requirement, the row
says so instead of borrowing credit from a database check that happens to be green.

### The one requirement with no database evidence at all

**WSR-21 is application-layer and cannot be reached by SQL.** `lib/workspaces/appears-on.ts`
composes two Supabase queries and decides, in TypeScript, which relationship admits a project
to the "appears on" shelf. There is no function, no policy and no trigger to probe, so Part A
has nothing to read and Part B has nothing to call. Its evidence is 22 unit tests against a
stubbed client, and that is the whole of it.

That is not a defect in this phase's verification — it is the honest classification. But it
means WSR-21 must be recorded in `.planning/REQUIREMENTS.md` as **verified by unit test**,
never as "verified in production", and a future phase that changes the shelf's admission rule
gets no warning from either SQL file.

One residue on the same module, filed by plan 04 and still open: `appears-on` filters
relationships on `state = 'accepted'` only, not the `effective_from` / `terminates_on` window
that `workspace_roster_relationship_is_live` also checks. No live exposure — a project
reachable through workspace A and also attached to B could carry B's stale role label.
