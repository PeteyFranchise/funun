# Phase 38.0.2 Plan 04: Appears-on requires a relationship naming the caller — Summary

**Delegated workspace access no longer buys a contribution credit: an Appears-on row now requires an accepted roster relationship naming the caller, and a project attached to two workspaces stops losing one of them silently.**

## Performance

- **Duration:** ~18 min
- **Started:** 2026-09-07T23:55Z (approx)
- **Completed:** 2026-09-08T00:13Z (approx)
- **Tasks:** 2 of 2
- **Files modified:** 2

## Accomplishments

- **Defect 1 fixed (the one that matters).** `resolveAppearsOnRows` used to return whatever the RLS client handed back, looking up `contributionRole` afterwards and letting a `null` through. A workspace admin who contributed nothing therefore saw the record on their own "Appears on" shelf. The row filter is now "an accepted `workspace_roster_relationships` row names the caller on a workspace whose live attachment reaches this project" — no relationship, no row. This is D-43 one layer down: access and credit are different questions and the module used to answer the second with the first.
- **Defect 2 fixed.** `new Map(attachmentRows.map(a => [a.project_id, a.workspace_id]))` kept only the last attachment per project. It is now a `Map<string, string[]>` built by accumulation, intersected with the relationships the caller actually holds — so the caller's own workspace can no longer be overwritten by an unrelated one that happened to come back later.
- **Determinism written down, not assumed.** When two of the caller's accepted relationships reach the same project, `compareCallerRelationships` picks earliest `accepted_at`, sorts a null `accepted_at` last, and breaks a remaining tie on `workspace_id` ascending. The rule sits in a comment above the comparator explaining *why* determinism matters (the choice decides which role a human reads, so an order-dependent answer makes the shelf appear to change for no reason), and is locked by a test that invokes `resolveAppearsOnRows` twice with the attachment rows reversed.
- **Fail-closed on admission queries.** An error from the attachment or relationship query now returns `[]` rather than treating an unknown set as an empty one — guessing in the caller's favour is exactly the credit inflation R-09 forbids.
- **Every pre-existing guarantee survives:** read-only, no service-role import, no exported name beginning `create`/`update`/`delete`/`save`, own custodianship excluded, `excludeProjectIds` honoured on the JS side, `partitionVaultLanes` byte-for-byte untouched.

## Existing tests whose behaviour changed — named, as required

Two existing expectations encoded defect 1 and were rewritten in place (no test was deleted). Both now carry an in-body comment saying so, in the style `38.0.1-VERIFICATION.md` used when it recorded that Part B check B3 was a defect in the test rather than in the code.

1. **`degrades to a null holder name and null contribution role when no attachment/profile row resolves`** → renamed to **`keeps a row whose accepted relationship names no professional role, and degrades the holder name to null`**. The old case passed *no attachment and no relationship at all* and asserted a row came back with `contributionRole: null`. That is a one-sentence statement of the defect: delegated access alone returning a row. The genuine degradation property is narrower and survives — an accepted relationship naming no `professional_role` still admits the row, and a missing profile row still degrades `holderName` to `null`.
2. **`every returned row is marked read-only`** — kept its title and its assertion, but the fixtures previously passed no attachments and no relationships while expecting two rows. The property under test is `readOnly`, not admission, so both rows were given a genuine accepted relationship and the assertion keeps its original meaning.

Both rewrites are deliberate corrections to a module that already shipped, not incidental churn.

## Decisions Made

- **The relationship admits; the role only labels.** `contributionRole: null` no longer means "nothing found" — it means the admitting relationship names no professional role. An unlabelled contributor is still a contributor. The `AppearsOnRow` doc comment now says this explicitly, because the field's meaning changed even though its type did not.
- **Fail-closed scope is the two admission queries only.** The plan's behaviour bullet says "an error from any query yields an empty array". I read that as scoped to the queries that decide admission (`workspace_attachments`, `workspace_roster_relationships`) and deliberately did NOT extend it to `user_profiles`: that lookup decides nothing about who appears, and emptying a contributor's whole shelf because a display-name fetch blipped would contradict the module's own documented degradation guarantee. A test (`still returns an admitted row with a null holder name when only the profile lookup fails`) pins the distinction so it is a decision on the record rather than an omission. **Flagging this as the one place my reading is narrower than the plan's literal wording.**
- **No RPC.** Per the plan and RESEARCH §8.

## Optional follow-up (recorded, not built)

- **A set-based RPC in migration 194's shape remains the long-term answer** for this reader — one round trip, the admission join done in SQL where `workspace_project_permission` already lives, and no chance of the TypeScript and the policy drifting. WSR-21 does not require it and the corrected TypeScript is far cheaper, so it is deliberately out of scope here. RESEARCH §8 records the same recommendation.
- **The relationship date window is not consulted.** `workspace_roster_relationship_is_live` (migration 183) checks `effective_from` / `terminates_on` in addition to `state = 'accepted'`; this reader checks `state` only, exactly as the plan specifies. In practice a project whose only path is an expired relationship is not returned by the RLS client at all, so there is no live exposure. The residual case is narrow: a project reachable through workspace **A** (live) that is also attached to workspace **B**, where the caller's **B** relationship has terminated — the comparator could then label the row with **B**'s stale role. Credit accuracy, not access. Worth a one-line widening (`select effective_from, terminates_on` and reuse `isWorkspaceAccessLive`) in a later plan; **not** done here because `lib/workspaces/roster.ts` is outside this plan's declared files and neighbouring plans are in flight.
