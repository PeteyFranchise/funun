Four changes, each closing a verified finding:

**WSR-18 / R-12 — every active seat currently sees every `proposed` relationship.** Migration 183's
policy admits `member_user_id = auth.uid() OR workspace_member_role(...) IS NOT NULL`, so a guest
or contractor sees a claim about a Member who has not accepted it. D-05 says the workspace sees
nothing until acceptance; the current policy contradicts it.

**R-23 — and the `blocked` state leaks further than the policy.** Migration 183 deliberately keeps
`workspace_roster_blocks` Member-private *so a workspace must never be able to enumerate who blocked
it (T-38-04-05)* — but the relationship row itself carries `state = 'blocked'`, which says exactly
the same thing. R-23 settles it: `blocked` collapses to `refused` in every workspace-facing read.

**WSR-29 / R-20 — role gates nothing about project access.** 38.0.1 Part B confirmed
behaviourally that a **guest** reaches a Member's attached project exactly as the **owner** does,
because grants are per-relationship and hop 2 filters only on `status` and `expires_at`. The owner
decided on 2026-09-07 to add a role floor excluding `guest`.

**WSR-23 / R-15 — `workspaces_select_member` has a `created_by = auth.uid()` fallback**, so a
creator removed from their own workspace still sees it forever.

together, so the API gate stays at one service-role round trip.
