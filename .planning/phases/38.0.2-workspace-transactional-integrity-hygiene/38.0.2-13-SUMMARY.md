# Phase 38.0.2 Plan 13: Workspace Creation, Cohort Gate and Role Floor — Summary

The workspace access gate now resolves the D-56 kill switch and the D-55 pilot cohort in
one service-role round trip and distinguishes 503 from 404; workspace creation is a single
`workspace_create` RPC call with the compensating DELETE deleted; and the R-20 guest floor
is applied at exactly the two project-data routes and provably nowhere else.

## What Was Built

**Task 1 — `lib/workspaces/access.ts` (WSR-16 / R-07 / R-25 / WSR-29).**
`requireWorkspaceAccess` replaced its `isWorkspaceAccessEnabled(createServiceClient())` call
with `resolveWorkspaceAccessDecision(createServiceClient(), <caller id>, process.env)`. The
result union gained a `404` arm and an exported `WORKSPACE_NOT_FOUND` constant. A separate
exported `requireWorkspaceProjectAccess` composes `canReachWorkspaceProjects` through the
existing `requireWorkspaceRole` — it is deliberately NOT a branch inside the gate.

**Task 2 — `app/api/workspaces/route.ts` (WSR-23 / R-15).** POST now performs exactly one
`rpc('workspace_create', …)` call. The two inserts, the compensating `.delete()` and the
route-side `logWorkspaceAction` call are gone; the `logWorkspaceAction` import went with
them. An outcome map (`disabled` → 503, unrecognised → 400) and a Postgres-code map
(`40P01`/`55P03`/`23505` → 409, `22023` → 400) were added in plan 12's shape. GET is
byte-for-byte unchanged and still ungated.

**Task 3 — the two project-data routes (R-20 / WSR-29).** `requireWorkspaceProjectAccess`
composes immediately after `requireWorkspaceAccess` at the attachments GET (the
`loadWorkspaceCatalogue` read), POST and DELETE, and at the workspace-projects POST.

## The R-20 Subtlety, Resolved as Specified

R-20 pulls in two directions: the API gate must carry the SQL's floor, and guests must keep
everything that is not project data. A blanket floor inside `requireWorkspaceAccess` would
satisfy the first and violate the second, because that gate also covers chrome routes.

The floor is therefore a separate composition applied at four named handlers. Three
independent tests hold the line:

- `requireWorkspaceAccess — the R-20 role floor is deliberately NOT applied here ›
  admits a guest through the plain gate`;
- `R-20 — a guest still reaches a workspace CHROME route › admits a guest to the members
  list (GET /members)`, which runs the REAL members handler, not a stub;
- `attachments — contractor … is still refused an attach by the EXISTING owner/admin gate,
  not by the floor`, which proves the floor did not replace the gate it sits beside.

Mutation cycle 3 below is the direct evidence: adding a floor branch inside the gate turns
the chrome-route test red.

## Gate Ordering — One Deliberate Refinement

The plan's `key_links` states the order as *kill switch → cohort → null user → staff →
membership*, while the plan's `<action>` states that a null user must be resolved for the
platform half and *"only then return 401"*. Those two cannot both be read literally: the nil
sentinel id handed to the resolver for an unauthenticated caller can never match a cohort
row, so mapping the cohort half before the 401 would answer every signed-out request 404
and break the pre-existing `rejects an unauthenticated request with 401` test.

Implemented per the `<action>` text: **both halves are resolved first, in one round trip**
(the F7 ordering, preserved literally — the switch is consulted before any identity work),
then 503, then 401, then 404, then staff, then membership. A comment at the branch and a
paragraph in the module header record why. Two tests pin it: `still returns 401 — not 404 —
for a null user while the platform half is consulted (F7 ordering)` asserts both the status
and that the round trip happened.

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's "unknown body key → 400" behaviour bullet is not what the
route does, and never was**
- **Found during:** Task 2
- **Issue:** The plan's `<behavior>` says POST "still rejects an unknown body key via
  `pickCreateFields` + Zod `.strict()`, before any RPC call". It does not. `pickCreateFields`
  runs BEFORE Zod and *drops* keys outside `WORKSPACE_CREATE_FIELDS`, so an unknown key never
  reaches `.strict()` and produces a 201, not a 400. This is pre-existing, unchanged, and
  correct — the allowlist's guarantee is "a server-owned value never travels from a request
  body into the write", not "an unknown key is rejected". Six tests written to the plan's
  wording failed against the real behaviour.
- **Fix:** Rewrote that describe block to assert the true guarantee: each of the six
  server-owned fields is dropped and provably absent from the recorded RPC arguments;
  `p_actor_id` is the PROVED actor, never a body-supplied `created_by`; and a genuinely
  invalid payload still 400s before any RPC call. Corrected the stale route comment that
  still read "let alone the insert below" and added the drop-not-reject distinction there.
- **Files modified:** `app/api/workspaces/route.ts`, `app/api/workspaces/route.test.ts`
- **Commit:** e11d0607

## Cross-Plan Notes — SIX NEIGHBOURING SUITES NEED A ONE-LINE STUB CHANGE

**This is the one thing a reviewer must act on.** Moving the gate's switch read from
`.from('workspace_access_config')` to `.rpc('workspace_access_permitted')` — which the plan
mandates and which the phase's own design requires — breaks every route suite whose
`createServiceClient` stub cannot answer that RPC. The resolver catches the resulting
`TypeError`, fails closed by design, and the handler returns 503. **99 of the 105 failures
report `Received: 503`**, which is the signature.

I did not touch these files: plan 14 owns invitations, plan 15 owns roster, plan 12 owns
members, and the phase brief forbids reaching across.

Baseline before this plan: 9 suites / 187 tests, all green. After: 3 suites green,
6 suites / 105 tests failing.

| `app/api/workspaces/[workspaceId]/roster/route.test.ts` | 13 / 13 | plan 15 | add `rpc` (A) |
| `app/api/workspaces/[workspaceId]/roster/evidence/route.test.ts` | 12 / 12 | plan 15 | add `rpc` (A) |
| `app/api/workspaces/[workspaceId]/permission-requests/route.test.ts` | 17 / 23 | — | add `rpc` (A) |

| `app/api/workspaces/[workspaceId]/ownership/route.test.ts` | 33 / 33 | — | branch on `fn` (B) |

**Remedy A** — the stub has no `rpc` at all. Add one method to the service-client stub:

```ts
rpc: () => Promise.resolve({ data: [{ access_enabled: true, cohort_ok: true }], error: null }),
```

**Remedy B** — the stub HAS an `rpc`, but it returns its own RPC's outcome shape for *every*
`fn`, so `access_enabled` is `undefined` → `false` → 503. It must branch:

```ts
rpc: jest.fn((fn: string, args: Record<string, unknown>) => {
  if (fn === 'workspace_access_permitted') {
    return thenable(() => ({ data: [{ access_enabled: true, cohort_ok: true }], error: null }))
  }
  rpcCalls.push({ fn, args })   // ← keep the existing body below this branch
  …
})
```

**Note for plans 12 and 16 specifically:** the members suite asserts *"every mutating request
produces exactly ONE `.rpc()` call"*. That is now two calls per request — the gate's decision
and the route's write. The assertion should filter `rpcCalls` by `fn`, or (better) the
decision call should be excluded at the branch above before `rpcCalls.push`, which keeps the
existing "exactly one" assertion true and meaningful. The snippet above does exactly that.

Two suites that stub `workspace_access_config` are unaffected and stay green
(`app/api/settings/permissions/route.test.ts`, `app/api/roster/relationships/**`) — they
reach the config table through a path other than this gate.

**Also for plan 14:** `lib/workspaces/access.ts`'s header now enumerates all three
