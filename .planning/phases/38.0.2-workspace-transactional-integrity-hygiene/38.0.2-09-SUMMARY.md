# Phase 38.0.2 Plan 09: Close Migration 197 Summary

Migration 197 is complete at twelve sections and 1787 lines — the roster proposal
narrowing, the R-23 `blocked` collapse, the WSR-29 role floor at
`workspace_project_permission`'s hop 2, the removal of the `created_by`
visibility fallback, and the one-round-trip cohort gate — text-locked by 159
tests and **unapplied**.

**No database connection of any kind was opened, and no migration was applied.**

## What Was Built

### Section (i) — the roster proposal narrowing and the `blocked` collapse

`workspace_roster_relationships_select` is dropped and recreated with four
branches: the named Member (including while `proposed`, which is D-05's other
half), the owner, the `admin` proposal-management surface, and
`state IN ('accepted', 'ended')` for every other active seat. Migration 183's
bare `workspace_member_role(...) IS NOT NULL` branch — the one that let a guest
or contractor see every proposal — is gone.

`public.workspace_roster_page(p_workspace_id, p_uid, p_limit, p_offset)` is the
workspace-facing read, declaring all fifteen `ROSTER_COLUMNS` names as its
security contract with `state` collapsed:
`CASE WHEN r.state = 'blocked' THEN 'refused' ELSE r.state END`.

One thing worth naming because it was checked rather than assumed: **`refused_at`
is already populated on a block.** The Member's PATCH handler writes
`{ state: 'blocked', refused_at: nowIso }` in the same UPDATE the refuse branch
uses. So passing `refused_at` straight through avoids the tell-tale a collapse
would otherwise create — a `refused` row with no refusal timestamp, from which a
reader could infer the collapse and therefore infer the block. The collapse
leaves no fingerprint, and a mutation nulling that column is caught (M07).

The reader repeats the policy's four visibility branches verbatim. A SECURITY
DEFINER function bypasses RLS, so a WHERE clause any broader than the policy
would *be* the way around the policy.

### Section (j) — `workspaces_select_member` without the creator fallback

Recreated with the membership branch alone. The header records why the fallback
existed (two-transaction creation with a compensating DELETE that does not run if
the process dies between the inserts, leaving a workspace with no owner seat and
therefore no member to see it) and why removing it is safe only once migration
198's `workspace_create` makes creation atomic — **the second reason 197 and 198
push together.**

### Section (k) — the WSR-29 role floor

`workspace_project_permission` v3 reproduces migration 192's body verbatim, all
six hops, plus exactly one conjunct on hop 2's `workspace_members` join,
immediately after the `expires_at` clause:

    AND m.role IN ('owner', 'admin', 'member', 'contractor')

This is proved to be the *only* change: the suite reads migration 192 from disk,
slices both function bodies, and asserts the line-by-line diff is exactly one
added line and zero removed. Hop 2 is the single chokepoint, so the floor reaches
all four `workspace_read_*` functions and all ten calling policies without any of
them being touched.

The suite imports `WORKSPACE_PROJECT_ACCESS_ROLES` from
`@/lib/workspaces/membership` and asserts the conjunct's literals equal it
exactly — so the SQL half and plan 03's `canReachWorkspaceProjects` cannot drift.
That is the WSR-17 failure class this phase exists partly to close.

### Section (l) — `workspace_access_permitted`

`(p_uid UUID, p_require_cohort BOOLEAN) RETURNS TABLE (access_enabled BOOLEAN,
cohort_ok BOOLEAN)` — the exact signature and result shape
`lib/workspaces/cohort.ts` already calls. Two booleans, not one, so the gate can
distinguish **503** (D-56 is off for everybody) from **404** (R-25: this Member
is outside the pilot cohort). Granted to `service_role` only, deliberately unlike
the two client readers in the same file, with the difference documented in both
directions so nobody harmonises them later.

### The header is closed

The "DELIBERATELY INCOMPLETE UNTIL PLAN 09" language is replaced by a twelve-
section inventory attributing each section to its plan, and by the sentence that
matters most at this point: **complete is not the same as pushed.**

## Deviations from Plan

### 1. [Rule 2 — required by the closure task] The plan-05 "INCOMPLETE" test was rewritten

- **Found during:** Task 3 / the header closure.
- **Issue:** Plan 05 wrote `expect(prose).toMatch(/DELIBERATELY INCOMPLETE UNTIL
  PLAN 09/)`, text-locking a header sentence whose entire purpose was to expire
  when plan 09 closed the file. Task 3's instruction not to modify a plan-05 or
  plan-07 test collides directly with this plan's mandate to close the header.
  Keeping the old form would have required the finished migration to keep telling
  reviewers it was unfinished — the assertion would have been enforcing a lie.
- **Fix:** Replaced, not deleted, and strictly stronger. It now locks the closure
  claim, the three-plan authorship line, the twelve-section inventory, that
  *complete is not the same as pushed*, and that the old sentence is **gone**
  (`not.toMatch(/DELIBERATELY INCOMPLETE/)`). Proved failable by M33.
- **Every other plan-05 and plan-07 test is untouched.** 113 → 159 with zero
  deletions and one rewrite.

### 2. [Mis-specified acceptance criterion] "no reference to `workspace_read_`" needed the right scope

- **Found during:** Task 3.
- **Issue:** My own new assertion `expect(sql).not.toMatch(/workspace_read_/)`
  failed, because section (k)'s `COMMENT ON FUNCTION` *names* the four
  `workspace_read_*` functions to explain why they need no edit. `sql` retains
  `COMMENT ON` bodies; `executable` does not.
- **Fix:** Scoped to `executable`. Naming the four readers is the opposite of
  touching them; what must not appear is a definition. Proved failable by M36
  (adding a `workspace_read_tracks()` definition). This is the third consecutive
  plan on these two files to hit a scope mismatch of this shape — plans 05, 07
  and 08 each flagged one.

### 3. [Rule 2] `COALESCE(p_require_cohort, TRUE)` added beyond the plan text

- **Found during:** Task 2.
- **Issue:** The plan specifies `cohort_ok` as `NOT p_require_cohort OR EXISTS
  (...)`. A NULL argument makes `NOT p_require_cohort` evaluate to NULL, so
  `cohort_ok` returns neither true nor false and the gate has to guess. Plan 07
  hit the identical shape on the audit reader's `full_view` flag.
- **Fix:** `NOT COALESCE(p_require_cohort, TRUE)` — an absent or malformed
  argument reads as "cohort membership IS required", never "waive the bound".
  Same posture as `workspace_access_enabled()`'s own `COALESCE(..., FALSE)`
  (migration 186) and as `lib/workspaces/cohort.ts`'s closed default. Proved
  failable by M27.

### 4. One `COMMENT ON` semicolon changed to a dash

Section (k)'s comment initially used a semicolon inside the enumeration of hops,
which migration 192's comment never does — and `__tests__/migration-192.test.ts`
extracts that comment with `[^;]*;`. Aligned to migration 192's punctuation so
the two comments stay diffable side by side. Cosmetic, recorded for completeness.

## The One Residual — raised, not decided

**R-23 is implemented at the read function, which is what the plan specifies.**
The policy still admits owners and admins to the raw
`workspace_roster_relationships` row, and RLS is row-level — Postgres cannot
redact a column through a policy. So **an owner or admin querying the table
directly through PostgREST with their own session JWT still sees
`state = 'blocked'`.** Plan 15 repoints the workspace roster GET at
`workspace_roster_page`, so the application surface is collapsed either way; the
raw path is the gap.

Closing it entirely means excluding `blocked` from policy branches 2 and 3, which
makes the row **vanish** from the workspace's raw view rather than reading as
`refused` — strictly stronger, and a different mechanism from the one R-23
describes. It is written into the migration comment and raised as **owner review
question 5**, because this plan is the last owner of the file and the checkpoint
is the right place to settle it.

   client, not the service client. **Do not repoint

   must keep the true state.

   from a session client returns a permission error, which
   `resolveWorkspaceAccessDecision` will read as a closed decision — a silent
   "nobody gets in" rather than a loud failure. It must be invoked with the
   service-role client.
