# Phase 38.0.2 Plan 11: Close WSR-09 and complete migration 198 — Summary

Custody acceptance is now one transaction that calls the one sanctioned write path
instead of joining the role-scoped exemption set, the custody diary finally has a
terminal-state guard, and migration 198 is complete and unapplied.

**No database connection of any kind was opened and no migration was applied.**

## What was built

### Section (h) — `public.workspace_accept_custody_transfer(UUID, UUID, TEXT, TEXT)`

One RPC serving `accept`, `decline` and `withdraw`, so the diary write is atomic on
every path rather than only on the one that also moves custody.

| Step | What it does |
|---|---|
| 0 | `SET LOCAL lock_timeout = '3s'` (LO-4) |
| — | `p_action` validation → `RAISE invalid_parameter_value` (not audited, R-26) |
| 1 | **No D-56 consultation**, deliberately — commented at length |
| 2 | Rank 7 `workspace_custody_transfers`, then rank 8 `vault_projects`, both `FOR NO KEY UPDATE` |
| 3 | CAS on `p_expected_state`; terminal-state check; authority; stale-custodian pre-check |
| 4 | `transfer_vault_project_custody(...)` **then** the diary `UPDATE` |
| 5 | The audit row, in the same transaction, when the transfer has a workspace |

Outcome vocabulary plan 16 must map: `ok`, `not_found`, `stale`, `already_resolved`,
`forbidden`, `stale_custodian`.

### Section (i) — `public.guard_custody_transfer_transition()`

`BEFORE UPDATE FOR EACH ROW` on `workspace_custody_transfers`. Refuses any `OLD.state`
other than `offered`, any `NEW.state` outside the three legal exits, and any change to
the five identity columns (`project_id`, `from_user_id`, `to_user_id`, `offered_by`,
`workspace_id`) — the last compared with `IS DISTINCT FROM`, because `workspace_id` is
nullable and `NULL <> NULL` is `NULL`. Until this trigger, the *only* thing preventing
a double-resolve of a custody offer anywhere in the system was the route's
`.eq('state', 'offered')` filter, in a flow spanning three transactions.

## The three carry-forwards this plan owned

**1. The RPC CALLS `transfer_vault_project_custody()`.** It issues no `UPDATE` against
`public.vault_projects` anywhere. Plan 06's file-wide assertion is untouched and still
passes; a second, section-local assertion was added whose failure message spells out
*why* — that migrations 190 and 196 exempt `current_user IN ('postgres')`, which is true
inside any postgres-owned definer function including this one, so a raw UPDATE would
have worked, and succeeding is precisely why it must not be written. Proved failable
(M1): the mutation turns four tests red.

**2. Both `raisingRefusalViolation` and `auditedRefusalViolation` are called**, for both
audited refusal codes (`forbidden`, `stale_custodian`). Proved failable (M3): a `RAISE`
inserted between the `forbidden` audit INSERT and its RETURN turns the test red — the
exact mutation that survived plan 08's helper alone.

**3. Every audit row's `target_id` is `v_transfer.id`.** Asserted twice: the existing
target-type loop, plus a new by-name parser that reads the `target_id` column out of
every audit INSERT in every function in the file and refuses a literal `NULL` (M5).

Also honoured: `FOR NO KEY UPDATE` at both lock sites (M8, M15 both caught, so the
LO-2 justification window is not pre-authorised at either); LO-1's ascending 7 → 8
order (M6); and the phrase `key column` appears nowhere in the ten comment lines above
either lock.

## Deviations from Plan

### 1. [Rule 2 — missing critical functionality] The nullable `workspace_id` contradiction, and how it was resolved

**Found during:** Task 1, at the step the plan itself flagged as "the one place in the
phase where the audit-assertion trigger and a nullable column can contradict each other".

**The issue, stated as three facts that cannot all hold:**

- `workspace_audit_log.workspace_id` is `NOT NULL` and references `public.workspaces`
  (migration 182).
- `workspace_custody_transfers.workspace_id` is **nullable**, deliberately — a transfer
  may be offered outside any workspace context (migration 185).
- Migration 197's `assert_workspace_custody_transfer_change_audited` is an
  `AFTER UPDATE OF state` deferred constraint trigger that fires **unconditionally** and
  demands an audit row at COMMIT.

For a transfer with no workspace, **no audit row can be written at all** — so the
unconditional trigger aborts the transaction at COMMIT and every direct
Member-to-Member custody accept, decline and withdraw becomes impossible. **That is true
of the current route too, not only of the RPC that replaces it**: the trigger fires on
the state UPDATE regardless of who issues it. Migration 197 would have broken custody
transfer in production the moment it applied.

**The fix:** the audit row is written whenever `workspace_id IS NOT NULL` (matching the
route's existing `if (row.workspace_id)` condition, so the trail stays continuous), and
migration 198 **re-creates** migration 197's constraint trigger, under its own name, with
`WHEN (NEW.workspace_id IS NOT NULL)`. Nothing else about it changes: same function,
same column scope, same `AFTER UPDATE OF state`, same `DEFERRABLE INITIALLY DEFERRED`,
same table, same name. 198 applies after 197 in the same window, so the re-creation wins.

**Migration 197 is NOT edited.** This is the same later-migration-adjusts-an-earlier-object
pattern migration 196 used on migration 139's guard, and for the same reason.

**Why this is not a weakening.** It is 197's own stated discipline carried one step
further — it column-scoped this family of triggers because "a constraint that fires on
writes nobody considers consequential is one that gets disabled, not one that gets
satisfied". A constraint that demands a row the schema makes impossible to write is not
strict, it is unsatisfiable. WSR-13's custody guarantee now reads: *every custody
resolution that can be audited must be.* The other three assertion triggers are
untouched and stay unconditional (asserted by test).

**Alternatives rejected, recorded so the owner can overrule:** making
`workspace_audit_log.workspace_id` nullable (a far larger change reaching every policy,
index and reader of that table, including D-50's both-sides read and 197's redacted
audit page); refusing to resolve a NULL-workspace transfer (deletes the flow the column
was made nullable to support).

**This is review item 1 at the checkpoint.**

### 2. [Rule 1 — bug] The custody move is issued BEFORE the diary UPDATE

**Found during:** Task 1, writing step (4).

**The issue:** the plan specifies the diary UPDATE first, then the nested custody call,
then `return 'stale_custodian'` if the call returns NULL. But **a RETURN commits.** With
that ordering, the NULL branch would commit a transfer row reading `accepted` with
custody unmoved — F9's split-brain, rebuilt inside the function written to close it.

**The fix:** the custody move runs first. Its NULL branch has then mutated nothing and
can report its outcome code honestly. Both writes are still in one transaction, so F9 is
closed either way; the ordering is what makes the outcome-code discipline safe.

**LO-1 is unaffected** — it governs lock *acquisition*, and both row locks are held
before either write, so neither write acquires anything new. Only the write order is
8 → 7 → 9, and it is documented at the point of deviation as the template requires.
Text-locked by a test (M2 caught).

### 3. [Rule 3 — blocking] The plan-06 incompleteness notice and its twin test

The header carried `**THIS FILE IS INCOMPLETE AS OF PLAN 06.** ... Do not review this
file as a finished artifact before plan 11`, asserted by a plan-06 test. Plan 11's
checkpoint asks the owner to review it as a finished artifact, so leaving that sentence
in place would actively mislead. The header now declares completion (and, separately,
that complete and unapplied are different things), and the one plan-06 test was rewritten
in step with it.

**This is the plan's one "do not modify a test written by plan 06" criterion, and it
could not be honoured as written** — the header change was directed explicitly and the
test asserted its exact opposite. The replacement is **stronger**, not weaker: it
additionally requires the stale sentence to be *gone* rather than merely contradicted
further down. Proved failable (M13). No other plan-06, 08 or 10 test was modified,
deleted or weakened.

### 4. [Rule 3 — blocking] Precision fix: the drop-no-trigger assertion could not see `CREATE CONSTRAINT TRIGGER`

`it('drops no trigger it does not itself create')` matched only `CREATE TRIGGER <name>`,
so section (i)'s legitimate same-name re-creation of a *constraint* trigger read as
removing a guard. Extended to `CREATE (?:CONSTRAINT )?TRIGGER`. This is the fourth
instance of the class of false positive plans 06, 08 and 10 each corrected, and is
corrected the same way: it removes no protection, and M12 (a DROP naming migration 187's
`guard_custody_transfer_offered_by_holder`, which this file does not create) is still
caught.
