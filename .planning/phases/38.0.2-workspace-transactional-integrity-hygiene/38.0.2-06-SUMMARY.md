# Phase 38.0.2 Plan 06: Open Migration 198 and Write the Transactional-RPC Doctrine Summary

**One-liner:** Migration 198 is open with the LO-1 lock order, LO-2 `FOR NO KEY UPDATE`,
LO-3, LO-4, R-26 and R-21 each stated as a named rule with its reason, the canonical RPC
template as a reference block, and `public.workspace_create` writing workspace, owner seat
and audit row in one transaction — all of it machine-checked by a 48-test harness whose
lock-order, lock-mode, bounded-wait and grant-posture assertions cover functions plans 08,
10 and 11 have not written yet.

## No database connection was opened

**No database command was run at any point in this plan.** No `supabase db push`, no
`supabase db reset`, no `supabase migration up`, no `supabase db query`, no scratch
database, no connection of any kind. Migration 198 is authored and text-tested only. The
D-56 kill switch was not read, written or flipped; `lib/workspaces/access-kill-switch.ts`
and `app/api/admin/workspaces/access/` show a zero-line diff across all three commits.

### Task 2 — `__tests__/migration-198.test.ts` (668 lines, 48 tests)

Header states the text-lock limitation first and names the 139 → 196 outage as why that
distinction is taken seriously, points at plan 17's behavioural harness, and tells plans
08, 10 and 11 that they **add describe blocks and fixture entries, never rewrite the
harness**.

**Module-scope harness:** `migration`, `sql`, `prose`, `executable`, `masked` (a
line-preserving comment mask, so lock sites report real line numbers),
`normalizeWhitespace`, `flatSql`, `functionNames()`, `functionBlock()`,
`rpcFunctionNames()`, `LO1_RANKS` (14 entries — nine primary plus four auxiliaries at
+0.5, with `workspace_ownership_transfers` sharing rank 7), `lockedTablesInOrder()`,
`lockSites()`.

**Assertions that extend themselves to functions that do not exist yet** — all iterate
`functionNames()` or `rpcFunctionNames()`, never a hard-coded list:

- **LO-1** — every locked table resolves to a known rank (an unranked table is itself a
  failure), and no adjacent pair decreases. The failure message names the function and
  both table names with both ranks, e.g.
  `public.workspace_mutation_probe: LO-1 violation — locks public.vault_projects (rank 8) then public.workspace_members (rank 2); ranks must never decrease`.
- **LO-2** — every locking clause is `FOR NO KEY UPDATE`; a stronger mode is a failure
  unless a `--` comment in the ten preceding raw lines names a DELETE or a key-column
  change; no `SKIP LOCKED`, no `NOWAIT`.
- **LO-4** — every RPC body sets `lock_timeout`.
- **R-21 grant posture** — a `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` and a
  `GRANT EXECUTE ... TO service_role` per RPC, and nothing in the file granted to
  `authenticated` or `anon`. Commented as migration 123's posture and explicitly not 046's.
- **Declaration posture** — `SECURITY DEFINER` on every RPC, `SET search_path = ''` on
  every function, and every table reference and `%ROWTYPE` declaration inside every body
  schema-qualified.
- **The role-scoped exemption guard** — no `UPDATE public.vault_projects` whose SET list
  names `user_id`, anywhere in `executable`.

Plus header-discipline tests against `prose`, `workspace_create`-specific tests, negative
structural guarantees, and the file-shape test.

## Two assertions that are currently vacuous, stated honestly

1. **LO-2's "every locking clause is `FOR NO KEY UPDATE`" has zero clauses to check
   today.** `workspace_create` is INSERTs only and locks nothing — RESEARCH §3.4 predicts
   exactly this ("Inserts only; no pre-existing rows to lock"). The assertion is written
   and proved failable (mutation 2 above), and it becomes load-bearing the moment plan 08
   appends the first `SELECT … FOR NO KEY UPDATE`.
2. **LO-1's ordering assertion likewise has a single-element sequence to walk.** Same
   situation, same proof, same activation point.

Both are deliberate: the machinery had to be built here so plans 08, 10 and 11 inherit it
for free, and the plan says so.

**1. [Rule 3 — Blocking] The orchestrator-notes file already existed with content.**
- **Found during:** Task 3.
- **Issue:** The plan says "Create" the file and that it should contain "exactly three
  numbered items". The file already existed with 61 lines of planning-session content,
  including three bold-numbered accepted decisions and a "Backlog, not this phase" section
  that already carried short versions of items 1 and 2. The explicit execution instruction

- **Fix:** Appended a clearly delimited
  `# Findings recorded during execution — plan 06 (2026-09-07)` section containing exactly
  three numbered items, and stated in its preamble that items 1 and 2 expand the two
  existing backlog bullets with evidence rather than duplicating them as new findings.
- **Consequence for the acceptance criterion:** the file now contains six numbered items
  overall — three from the planning session, three from this plan. Per the
  at-least-1 sanity rule, the criterion is satisfied idiomatically rather than by deleting
  the planner's work.
- **Commit:** `1691c6a6`

**2. [Rule 2 — Missing critical functionality] The test harness had to distinguish RPCs
from trigger functions, or it would have broken plan 11.**
- **Found during:** Task 2, while reading plan 11's acceptance criteria.
- **Issue:** The plan says the grant-posture, `lock_timeout` and `SECURITY DEFINER`
  assertions should loop over `functionNames()`. Plan 11 appends
  `public.guard_custody_transfer_transition`, a **trigger** function. A trigger function
  takes no EXECUTE grant, is not `SECURITY DEFINER` in this repo's idiom (migration 196's
  guard tests `current_user` itself, so elevating it would be wrong), and needs no
  `lock_timeout` because it runs inside its caller's transaction. A literal loop over all
  functions would have forced plan 11 to either misdeclare its guard or rewrite the
  harness — the exact thing this plan exists to prevent.
- **Fix:** Added `rpcFunctionNames()` = `functionNames()` minus anything declaring
  `RETURNS TRIGGER`, documented at the definition. RPC-only assertions iterate it; LO-1
  and `SET search_path = ''` still iterate every function.
- **Commit:** `7e06ab6c`

**3. [Rule 2 — Missing critical functionality] The "no `DROP TRIGGER`" negative was
written as an allowlist rather than a blanket ban.**
- **Found during:** Task 2, same review.
- **Issue:** A blanket `DROP TRIGGER` ban would break plan 11 if it follows this repo's
  house idempotency idiom (`DROP TRIGGER IF EXISTS <name> ON <table>;` immediately before
  `CREATE TRIGGER <name>`, as migration 182 does five times).
- **Fix:** The assertion is now "drops no trigger it does not itself create", which still
  catches the dangerous case — dropping a pre-existing guard — while permitting the
  idempotency idiom. Verified failable by dropping
  `guard_workspace_never_zero_owners` (mutation 6 above).
- **Commit:** `7e06ab6c`
