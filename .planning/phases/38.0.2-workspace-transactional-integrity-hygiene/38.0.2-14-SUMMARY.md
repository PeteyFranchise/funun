# Phase 38.0.2 Plan 14: Invitation Routes Summary

Invitation redemption now runs as one `workspace_redeem_invitation` call behind a
read-only predicate layer, the acceptor is cohort-gated at the third and last
kill-switch call site, and no invited email address reaches the broadly-readable
audit `changes` column.

## What was built

### Task 1 — `app/api/workspaces/invitations/accept/route.ts`

The four-transaction sequence is gone in full: the invitation status CAS whose
result was never checked, the self-heal write, the seat lookup, both seat write
branches, and the route-side `logWorkspaceAction` call with
`targetId: pendingSeat?.id ?? null`. The file now contains no `.update(` and no
`.insert(` anywhere, and computes no audit target — so the null-target shape that
migration 197's deferred constraint trigger refuses at COMMIT cannot originate
here.

`isWorkspaceAccessEnabled` was replaced by `resolveWorkspaceAccessDecision` +
`isWorkspaceAccessPermitted` — the shared reading all three call sites use, so
this one cannot drift from the other two. `accessEnabled === false` → 503 with the
existing message; `cohortEligible === false` → 404 (R-25), with a body **identical
to the unknown-token 404** so the pair cannot be used to probe whether an
invitation exists.

`canAcceptWorkspaceInvitation` (plan 02) is deliberately **not** called: it
composes exactly these two calls but collapses them into one boolean, and R-25
requires the two answers to stay apart — 503 and 404 answer different questions.
The composition is otherwise identical, so no behaviour diverges from plan 02's
intent.

## Deviations from Plan

### Auto-fixed / judgement calls

**1. [Rule 2 — audit coverage] The route-side email comparison was removed, not kept.**
- **Found during:** Task 1.
- **Issue:** Keeping the route-side `sessionEmail !== invitation.email` branch
  would refuse every mismatch before the RPC, so the RPC's
  `workspace.invitation.redemption_refused` audit INSERT could never execute.
  T-38.0.2-14-02's stated mitigation ("the refusal is audited") would have been
  false, and a security-critical audit path would have been dead code.
- **Fix:** The RPC decides `email_mismatch` and returns 403 with the **existing
  sentence**. The route still refuses 403 when `normalizeInvitedEmail(user.email)`
  returns null, because the RPC treats a null `p_actor_email` as a validation
  error and raises — that would surface as a 500 instead of the sentence.
- **Effect on the plan's behaviour bullet:** unchanged — "a session email that
  does not match returns 403 with the existing message" holds on both paths.
- **Commit:** `9777ee24`

**2. [Rule 1 — behaviour regression] An expired-but-still-pending invitation is sent to the RPC.**
- **Found during:** Task 1.
- **Issue:** If `isInvitationRedeemable` refused every non-redeemable invitation
  route-side, the RPC's self-heal (`pending` → `expired`, with its audit row)
  would be permanently unreachable and expired invitations would never be swept
  — a silent regression from the old route, which self-healed in exactly this
  case.
- **Fix:** The predicate layer refuses only **terminal** statuses (accepted,
  refused, revoked, already-swept expired), where there is nothing to heal. A
  still-`pending` row whose expiry has passed goes to the RPC, which sweeps and
  audits it under the lock and returns `'expired'` → 410. The route still writes
  nothing on that path, which the suite asserts.
- **Commit:** `9777ee24`

**3. [Rule 2 — layers must agree] `42501` maps to 503, not 500.**
- The RPC RAISEs `insufficient_privilege` when the D-56 control is off. The route
  gate already answers that with 503, but the switch can flip between the gate and
  the RPC. Mapping 42501 to 503 makes the second layer give the same answer as the
  first instead of a 500. Added beside the `40P01`/`55P03` → 409 helper.

### Mis-specified acceptance criterion (flagged, not contorted)

Task 1 requires "no `targetId` expression". The file contains the string
`targetId` **once, inside a header comment**, in the paragraph naming
`targetId: pendingSeat?.id ?? null` as the shape that was removed and must not
return. That is a comment, not an expression — and it mirrors migration 197's and
198's own "named so nobody reintroduces it" prose. A grep-count reading of the
criterion would flag it; the criterion's intent is satisfied. No `targetId` is
computed or passed anywhere.

Similarly, Task 1's "exactly ONE `.rpc()` call" is satisfied as **one redemption
RPC call**. The route makes a second `.rpc()` on the same service client for
`workspace_access_permitted`, which is the cohort gate the same task requires; the
tests assert `workspace_redeem_invitation` is called exactly once on success and
zero times whenever a route-side predicate refuses first.

## Carry-forward decisions this plan was asked to settle

### 1. The dangling NULL-`user_id` pending seat — ACCEPTED by this phase

**The situation.** When the invitee had no account at issuance time, the issuance
route writes a `workspace_members` row with `user_id = NULL`. That row does not
match `idx_workspace_members_unique_user` (partial, `WHERE user_id IS NOT NULL`),
so migration 198's one-statement upsert cannot adopt it — it inserts a fresh
seat for the actor and the NULL row lingers. This is the **common new-invitee
path**, not an edge case.

**It is inert, verified rather than assumed.** `workspace_members.invited_email`
has exactly one non-test reader in the whole repo — the revoke handler at
`app/api/workspaces/[workspaceId]/invitations/route.ts:325`. No RLS policy and no
access helper in `supabase/migrations/18*.sql` or `19*.sql` keys on it; every one
keys on `user_id`. A NULL-`user_id` pending row therefore grants nothing and is
counted by nothing.

**Retiring it from a route is IMPOSSIBLE once 197 applies — this is a proof, not
a preference.** `assert_workspace_member_change_audited` fires
`AFTER UPDATE OF role, status` and requires an audit row with
`target_id = NEW.id AND l.created_at = now()`, where `now()` is
`transaction_timestamp()`. A PostgREST `.update()` from a route is its own
transaction and the paired audit `.insert()` is a different one with a different
`now()`, so the check can never be satisfied from route code. Retiring the seat
also requires a second `UPDATE OF status` on `workspace_members`, which the redeem
RPC's own acceptance criteria forbid, and D-14 forbids deleting it.

**Decision: the phase accepts the row.** The correct home for retiring it is
inside a future RPC (either a widened `workspace_redeem_invitation` that adopts or
retires the paired NULL row in the same transaction, or a sweep RPC), not in route
code. Recorded here so it is decided rather than left undecided.

### 2. Two outcome codes beyond the plan's vocabulary — MAPPED

`owner_invitation_forbidden` and `owner_seat_conflict` were read out of migration
198 section (f) and both map to 409 with their own sentences. Neither falls
through to the fallback and neither can produce a 500. The full vocabulary was
taken from the migration, not the plan text.

### 3. R-24 — DONE, and it is the third of three

The accept route no longer calls `isWorkspaceAccessEnabled` directly. The file
header names this as the third and last kill-switch call site and lists the other
two (`app/api/workspaces/route.ts` and `lib/workspaces/access.ts`), matching what
plan 13 was asked to write in `lib/workspaces/access.ts`. R-25's 404 is asserted
by a test titled for R-24, and mutation M1 proves the assertion fails if it becomes
a 403.

## Cross-plan notes

### ⚠ HIGH — the invitation REVOKE handler will fail outright once migration 197 applies

Not in this plan's scope to fix (it needs an RPC that does not exist, in a
migration plan 11 closes concurrently), but it is a push-window blocker and the
offending lines are in a file this plan touched, so it is reported precisely.

`app/api/workspaces/[workspaceId]/invitations/route.ts` `DELETE` performs two
route-side consequential writes, each in its own PostgREST transaction:

- **line 313** — `workspace_invitations.update({ status: 'revoked' })`, covered by
  `assert_workspace_invitation_change_audited` (`AFTER UPDATE OF status`). The
  audit row is written afterwards, in a different transaction, so
  `l.created_at = now()` cannot match and the UPDATE aborts at COMMIT.
- **line 323** — `workspace_members.update({ status: 'removed' })` on the paired
  pending seat, covered by `assert_workspace_member_change_audited`. This one has
  **no audit row written for it at all**, at any time.

A repo-wide grep confirms these are the **only** remaining route-side
`UPDATE OF status/role` writers against `workspace_invitations` or
`workspace_members` outside the RPCs — every other consequential writer has
already been moved. So closing this closes the class. Suggested home: a
`workspace_revoke_invitation` RPC (invitation status + paired seat + two audit
rows in one transaction), or plan 17 confirming the behaviour and deferring it
with the switch still off.

Plan 17's Part B harness should also assert the revoke path, which its current
checks do not cover.

### For plan 15 — nothing crossed into `lib/workspaces/audit.ts`

The email removal belonged in the route's call site, not in `logWorkspaceAction`,
so `lib/workspaces/audit.ts` was **not** touched. One observation for plan 15 if
it is hardening that module: `logWorkspaceAction` takes `changes` as an
unconstrained `Record<string, unknown>` and never inspects it, so the only
compile-time protection against a restricted key is per-call-site review. A typed
`RestrictedKey`-excluding parameter there would make WSR-19 structural rather than
reviewed — offered as a note, not a request.

### For plan 13 — the kill-switch call-site note

This route's header names the three call sites and their files. If plan 13 words
the note in `lib/workspaces/access.ts` differently, the two should be reconciled
at merge; the facts (three sites, this being the third, F7's shape) are identical.
