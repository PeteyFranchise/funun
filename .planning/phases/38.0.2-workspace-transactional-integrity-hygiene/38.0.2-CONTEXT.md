# Phase 38.0.2 — Workspace Transactional Integrity & Hygiene

## Goal

The 13 findings deferred from 38.0.1 on context-cost grounds, not difficulty.
The core is **transactional SECURITY DEFINER RPCs for every consequential state
change** — each doing `SELECT ... FOR UPDATE`, revalidating preconditions,
mutating, and writing its audit row **in one transaction**. Plus the ownership
hierarchy and two-sided ownership transfer, the D-55 cohort gate, audit
redaction, and remaining hygiene.

## ⚠ BINDING CONDITION — inherited from 38.0.1

**The D-56 kill switch must stay OFF in production until this phase ships.**
Verified OFF on 2026-09-07 (Part A check A8).

This is not caution, it is containment. **WSR-07/08 need no grants to exploit** —
an admin can promote themselves to owner and remove the real owner. The switch is
the only thing standing in the way. Nothing in this phase may flip it, and the
phase is not done until someone can argue it is safe to turn on.

## Locked decisions (from `38.0.1-CONTEXT.md`; no discussion needed)

- **R-05 (F5):** Only owners may promote to owner; admins may not edit or remove
  owner rows; no self-promotion. **Ownership transfer becomes two-sided** — the
  owner nominates, the successor accepts — mirroring D-29 custody transfer.
  Enforced in the database/RPC, never in route logic.

- **R-06 (F9/F11/F15/F16/F14):** **Transactional SECURITY DEFINER RPCs for every
  consequential state change** — custody acceptance, invitation redemption,
  ownership and owner-floor changes, roster transitions. Each does
  `SELECT ... FOR UPDATE`, revalidates, mutates, and writes the audit row in the
  same transaction. Closes all four races and F14's best-effort audit together:
  a consequential mutation can no longer succeed without its audit record.

- **R-07 (F17):** **The D-55 cohort gate is a release requirement.** Server-side
  cohort eligibility in workspace creation and `requireWorkspaceAccess`,
  following the Song Passport pilot pattern. Without it, re-enabling the kill
  switch goes from "off" straight to "every Member".

- **R-09 (F20):** "Appears on" requires an explicit contributor or roster
  relationship **naming the caller**. Delegated workspace access is not
  contribution credit. Also fix `workspaceIdByProjectId` silently overwriting
  multi-workspace attachments.

- **R-12 (F13):** A `proposed` relationship is visible **only to the named Member
  and the owner/admin proposal-management surface** — not to ordinary members,
  contractors or guests. D-05 says the workspace sees nothing until acceptance;
  the current policy contradicts it.

- **R-13 (F14):** No restricted PII in the broadly readable `changes` JSON —
  invitation emails are currently exposed to every workspace member. Introduce
  viewer-class-redacted audit reads.

- **R-15 (F21):** Remove the `created_by = auth.uid()` fallback in
  `workspaces_select_member`, or condition it on live membership. Make workspace
  creation atomic so the fallback is unnecessary.

- **S1:** Explicitly revoke `service_role`'s UPDATE/DELETE/TRUNCATE on
  `workspace_audit_log` and add a rejecting policy.

  **The "verify at runtime" half is DONE.** Part A check A10 confirmed on
  production 2026-09-07 that `service_role` holds **TRUNCATE, DELETE and UPDATE**
  on that table — `REVOKE ... FROM PUBLIC` did not touch them, exactly as
  suspected. The audit log is not append-only today. Only the revoke remains.

## Watch-outs

- ~~**No `SELECT ... FOR UPDATE` plpgsql RPC exists anywhere in this repo.**~~
  **WRONG — corrected 2026-09-07 by research.** I copied this from the roadmap's
  watch-out without checking it. **Twenty-seven `SECURITY DEFINER` functions in
  this repo use `FOR UPDATE`**, several of them close analogs:
  - `123_job_claim_leases.sql` — `FOR UPDATE SKIP LOCKED` inside a
    `SECURITY DEFINER SET search_path = ''` RPC with correct REVOKE/GRANT.
    **Use this as the security template.**
  - `046_atomic_opportunity_apply.sql` — locks two rows and returns an
    outcome-code discriminator the route maps to an HTTP status. **Best
    behavioural template, worst security template** — it has no `REVOKE` at all,
    so `PUBLIC` and `anon` hold `EXECUTE` on a definer function. Pre-existing;
    do not copy that half, and log it as backlog rather than fixing it here.
  - `127` — already documents "The RPC itself is one database transaction."

  This is **build-from-analog after all.** Planning should follow the existing
  idiom rather than inventing one.

- **The 190/196 trigger exemption is ROLE-scoped, not FUNCTION-scoped** — and
  their headers claim otherwise. Both guards test `current_user IN ('postgres')`,
  which is true inside **any** postgres-owned `SECURITY DEFINER` function, not
  just `transfer_vault_project_custody()`. Migration 190's header says the rule
  is "only this one function's execution context is permitted"; the code does not
  enforce that. Nothing exploits it today — no existing definer function writes
  `vault_projects.user_id` — but **every new RPC this phase adds silently joins
  the exemption set.**

  **Constraint for this phase:** the custody-acceptance RPC must *call*
  `public.transfer_vault_project_custody()` rather than issue its own `UPDATE`
  on `vault_projects.user_id`. That keeps one sanctioned write path and costs
  nothing. Do not widen the guards, and do not edit 190's or 196's text-locked
  headers — record the discrepancy, do not churn reviewed migrations.

- **`service_role` carries `BYPASSRLS`, so S1's "rejecting policy" is inert
  against it.** The revoke works; a policy does not. Only table privileges and
  **triggers** bind `service_role`, and `TRUNCATE` needs its own
  `FOR EACH STATEMENT` trigger. Root cause of S1 confirmed: Supabase's
  `ALTER DEFAULT PRIVILEGES ... GRANT ALL ON TABLES TO service_role` is a direct
  grant, which `REVOKE ... FROM PUBLIC` never touched.
- **Locking order matters.** Concurrent custody and roster operations must not
  deadlock. Pick one order, document it, and make every RPC follow it.
- Migration numbers are **197–198**. Check the LIVE LEDGER in `.planning/ROADMAP.md`
  before claiming one — this project has had six stale-migration-number incidents,
  and 195 and 196 were both claimed after 38.0.2's range was first reserved.

## R-20 — role floor on project access (owner decision, 2026-09-07)

**Decided. This replaces the open question below.**

`workspace_members.role` currently gates nothing about project access. Part B
confirmed behaviourally that a **guest** reaches a Member's attached project
exactly as the **owner** does: grants are per-relationship, not per-member, and
`workspace_project_permission` hop 2 filters on `status` and `expires_at` with no
role condition at all.

**Decision: add a role floor excluding `guest`.** Owner, admin, member and
contractor keep access. A guest gets workspace chrome and never reaches a
Member's project data.

Implementation notes for the planner:

- The floor belongs in **`workspace_project_permission`'s hop 2**, as one extra
  conjunct on the `workspace_members` join. That is the single chokepoint: the
  four `workspace_read_*` functions all call it, so the floor propagates to
  every child-table read without touching those four functions at all.
- `requireWorkspaceAccess` (the API gate) must be given the **same** floor. This
  repo's doctrine is two independent layers agreeing — migrations 078, 136, 187,
  190, 196 — not deduplication. WSR-17 exists precisely because those two layers
  once disagreed about `expires_at`; do not reintroduce that class of drift.
- This lands in one of this phase's migrations (197 or 198) alongside the R-05
  role-hierarchy work, since both rewrite role semantics and should ship together.
- **Guests keep everything that is not project data**: workspace membership,
  chrome, and whatever R-12's proposal-visibility rules already allow them.
- Verify behaviourally, not just structurally. The Part B harness already seeds a
  guest identity (`ffff0000-…-005`) and asserts against it — that assertion flips
  from "PASS — matches the per-relationship model" to "PASS — guest refused".

Adds requirement **WSR-29**.

# Decisions from the research open questions (2026-09-07)

Research raised 11. Q9 was already settled as **R-20** (role floor). Four went to
the owner; six were routine and are decided here with the reasoning stated so
they can be overridden.

## Owner decisions

- **R-21 — Actor binding: Option A, service-role RPC with route-asserted
  identity.** The route passes the actor id it already proved via
  `requireWorkspaceAccess`; the RPC re-derives that actor's **authority** (role,
  active status, `expires_at`) from the database and **never accepts a role
  parameter**.

  **Write the limitation into every migration header, do not gloss it:** R-05
  says "enforced in the database/RPC, never route logic." Under Option A the
  *authority* is in the database but the *identity* still comes from the route.
  That is a partial satisfaction of R-05, accepted deliberately, because Option B
  would require the staff-identity refusal in SQL (`getStaffRoles` reads
  `app_metadata`, which has no equivalent in this repo) and would widen the
  client-reachable write surface migration 182 §(e) deliberately closed.

- **R-22 — Ownership transfer TRANSFERS.** Promote the successor, then demote the
  nominator to `admin`, **in that statement order** — `guard_workspace_never_zero_owners`
  sees uncommitted writes from earlier statements in the same transaction, so the
  reverse order raises `42501`. A separate add-a-second-owner RPC is a later
  phase's problem; do not build it here.

- **R-23 — `blocked` collapses to `refused` in every workspace-facing read.** The
  workspace must not be able to distinguish a decline from a block. The Member's
  own view keeps the true state and the block keeps working. This fixes a live
  contradiction with T-38-04-05, which says the workspace must never enumerate
  who blocked it.

- **R-24 — The cohort gate applies to the ACCEPTOR of an invitation, not only to
  workspace creation.** Otherwise one cohort owner can pull in unlimited
  non-cohort Members and the pilot bound stops meaning anything.

## Routine decisions (mine — override if you disagree)

- **R-25 — A non-cohort Member gets 404, not 403,** from `requireWorkspaceAccess`.
  During a bounded pilot, someone outside the cohort should not learn the feature
  exists. 403 is more honest but leaks the existence of a capability they cannot
  reach; 404 matches how the rest of this repo hides unreachable resources.

- **R-26 — Audit AUTHORITY refusals; do not audit validation errors.** "An admin
  attempted self-promotion" belongs on the record; "a date failed to parse" does
  not. This forces those specific refusals to be **outcome codes, not `RAISE`** —
  a `RAISE` rolls back the audit row written moments earlier in the same
  transaction (§2.3). Validation errors may keep raising.

- **R-27 — Confirmed: narrowing `workspace_audit_log_select` is acceptable.**
  The workspace still sees its own trail; ordinary members reach it through a
  redacted RPC instead of the raw table. D-50's intent — a workspace can audit
  itself — is preserved; only the mechanism changes.

- **R-28 — Fix the owner-floor `expires_at` gap in this phase.** The floor
  currently counts an owner whose seat has expired, so a workspace can satisfy
  "at least one active owner" with an owner who has no live access. Not a defect
  against any WSR, but R-05 rewrites this exact trigger and fixing it separately
  later would mean touching it twice.

- **R-29 — No cohort admin surface this phase. SQL seeding is acceptable for
  beta.** WSR-16 needs the gate to *work*, not a UI to manage it. Building an
  admin surface widens the phase for a population the owner can currently seed by
  hand in one statement.

- **R-30 — Behavioural verification uses the single-shot production window**, the
  pattern proven in 38.0.1 Part B: seed, enable the kill switch, assert, tear
  down and restore, all inside one atomic `DO` block, with per-assertion
  subtransactions so one failure costs one row. Supabase branching needs a paid
  plan and the org is on Free. That harness already seeds six identities and is
  the natural place to extend — its guest assertion flips under R-20, and it must
  gain checks for R-22, R-23 and R-24.

  **Note for the planner:** Part A's population check (A9) counted five workspace
  tables but NOT `workspace_audit_log` or `workspace_invitations`. WSR-19 and
  WSR-26 both assume those are empty. Re-check before relying on it.
