# Phase 38.0.2 — Workspace Transactional Integrity & Hygiene

## Goal

The 13 findings deferred from 38.0.1 on context-cost grounds, not difficulty.
The core is **transactional SECURITY DEFINER RPCs for every consequential state
change** — each doing `SELECT ... FOR UPDATE`, revalidating preconditions,
mutating, and writing its audit row **in one transaction**. Plus the ownership
hierarchy and two-sided ownership transfer, the D-55 cohort gate, audit
redaction, and remaining hygiene.

## ⚠ BINDING CONDITION — inherited from 38.0.1

**The D-56 kill switch must stay OFF in production until this phase ships.**
Verified OFF on 2026-09-07 (Part A check A8).

This is not caution, it is containment. **WSR-07/08 need no grants to exploit** —
an admin can promote themselves to owner and remove the real owner. The switch is
the only thing standing in the way. Nothing in this phase may flip it, and the
phase is not done until someone can argue it is safe to turn on.

## Locked decisions (from `38.0.1-CONTEXT.md`; no discussion needed)

- **R-05 (F5):** Only owners may promote to owner; admins may not edit or remove
  owner rows; no self-promotion. **Ownership transfer becomes two-sided** — the
  owner nominates, the successor accepts — mirroring D-29 custody transfer.
  Enforced in the database/RPC, never in route logic.

- **R-06 (F9/F11/F15/F16/F14):** **Transactional SECURITY DEFINER RPCs for every
  consequential state change** — custody acceptance, invitation redemption,
  ownership and owner-floor changes, roster transitions. Each does
  `SELECT ... FOR UPDATE`, revalidates, mutates, and writes the audit row in the
  same transaction. Closes all four races and F14's best-effort audit together:
  a consequential mutation can no longer succeed without its audit record.

- **R-07 (F17):** **The D-55 cohort gate is a release requirement.** Server-side
  cohort eligibility in workspace creation and `requireWorkspaceAccess`,
  following the Song Passport pilot pattern. Without it, re-enabling the kill
  switch goes from "off" straight to "every Member".

- **R-09 (F20):** "Appears on" requires an explicit contributor or roster
  relationship **naming the caller**. Delegated workspace access is not
  contribution credit. Also fix `workspaceIdByProjectId` silently overwriting
  multi-workspace attachments.

- **R-12 (F13):** A `proposed` relationship is visible **only to the named Member
  and the owner/admin proposal-management surface** — not to ordinary members,
  contractors or guests. D-05 says the workspace sees nothing until acceptance;
  the current policy contradicts it.

- **R-13 (F14):** No restricted PII in the broadly readable `changes` JSON —
  invitation emails are currently exposed to every workspace member. Introduce
  viewer-class-redacted audit reads.

- **R-15 (F21):** Remove the `created_by = auth.uid()` fallback in
  `workspaces_select_member`, or condition it on live membership. Make workspace
  creation atomic so the fallback is unnecessary.

- **S1:** Explicitly revoke `service_role`'s UPDATE/DELETE/TRUNCATE on
  `workspace_audit_log` and add a rejecting policy.

  **The "verify at runtime" half is DONE.** Part A check A10 confirmed on
  production 2026-09-07 that `service_role` holds **TRUNCATE, DELETE and UPDATE**
  on that table — `REVOKE ... FROM PUBLIC` did not touch them, exactly as
  suspected. The audit log is not append-only today. Only the revoke remains.

## Watch-outs

- **No `SELECT ... FOR UPDATE` plpgsql RPC exists anywhere in this repo.** The
  transactional core is build-from-research, not build-from-analog. This is the
  single biggest risk in the phase and the reason research runs before planning.
- **Locking order matters.** Concurrent custody and roster operations must not
  deadlock. Pick one order, document it, and make every RPC follow it.
- Migration numbers are **197–198**. Check the LIVE LEDGER in `.planning/ROADMAP.md`
  before claiming one — this project has had six stale-migration-number incidents,
  and 195 and 196 were both claimed after 38.0.2's range was first reserved.

## What 38.0.1 established that this phase can rely on

Verified in production 2026-09-07 (Part A 35/35 structural, Part B 12/12
behavioural — see `38.0.1-VERIFICATION.md`):

- `workspace_project_permission` binds access to current custody and
  re-validates the delegation lineage on every call. Both proven behaviourally.
- Both membership helpers check `expires_at`; RLS and the API gate agree.
- The four child tables carry no workspace policy branch — `vault_projects` is
  the only table whose policies name a workspace helper.
- The four `workspace_read_*` functions bind `p_uid` to `auth.uid()`; read
  impersonation is refused behaviourally.
- Custody is immutable to a direct UPDATE as `authenticated`, and the sanctioned
  two-sided RPC works (migration 196 — a bug Part B found).
- All five workspace tables held **zero rows** as of 2026-09-07, so this phase
  starts with no data migration anywhere.

## Open question carried in (not blocking)

`workspace_members.role` does not gate project access at all — a guest reaches an
attached project exactly as an owner does, because grants are per-relationship,
not per-member. Not a defect against any WSR as written. **R-05 touches the role
hierarchy**, so this phase is the natural place to decide whether role should
also gate project reads, or whether the tier should be renamed/documented.
Surface it to the owner; do not decide it silently.
