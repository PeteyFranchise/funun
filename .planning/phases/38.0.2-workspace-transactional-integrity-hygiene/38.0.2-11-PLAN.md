<objective>
Close WSR-09 — the transactional custody acceptance — and complete migration 198.

**WSR-09 has been deferred twice.** The P0 hotfix shipped its cheap half (the stale-custodian guard
and the single-row check), which closed the dangerous overwrite. The residual window is still open:
`app/api/vault/custody-transfers/route.ts` PATCH runs **three separate transactions** — read the
transfer, CAS-update the transfer to `accepted`, then call `transfer_vault_project_custody`. A crash
or a concurrent transfer between steps 2 and 3 leaves the diary saying `accepted` while custody
never moved. Split-brain, on the one record whose custodian decides who can reach it.

**The single most important design constraint in this plan.** Migrations 190 and 196 both exempt
`current_user IN ('postgres')`, which is true inside **any** postgres-owned SECURITY DEFINER
function — not only `transfer_vault_project_custody()`. Their headers say otherwise; the code does
not enforce what the headers describe. Every RPC this phase adds therefore silently joins that
exemption set, and this RPC is the only one that has any reason to touch `vault_projects.user_id`.

**So it must not.** It calls `public.transfer_vault_project_custody(p_project_id, p_from_user_id,
p_to_user_id)`. Nested definer calls run in the same transaction, so atomicity is preserved; the
double filter and the NULL-return stale-custodian semantics come along for free; and "one sanctioned
path" stays literally true. The cost is nothing. **Do not widen migration 190's or 196's guards, and
do not edit their text-locked headers.**
