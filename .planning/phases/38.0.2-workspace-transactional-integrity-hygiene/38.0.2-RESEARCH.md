## Summary

**The CONTEXT.md watch-out is wrong on its central premise, and that is the most important finding in this document.** CONTEXT.md says "No `SELECT ... FOR UPDATE` plpgsql RPC exists anywhere in this repo" and calls the transactional core "build-from-research, not build-from-analog." **Four in-repo analogs exist**, all applied and in production:

| Migration | Mechanism | Quality as a template |
|---|---|---|
| `123_job_claim_leases.sql` | `SELECT ... FOR UPDATE SKIP LOCKED` inside a `plpgsql SECURITY DEFINER SET search_path = ''` RPC, with `REVOKE ... FROM PUBLIC, anon, authenticated` + `GRANT ... TO service_role` | **Best template in the repo.** Copy this shape. |
| `046_atomic_opportunity_apply.sql` | `SELECT ... FOR UPDATE` on two rows inside a `plpgsql SECURITY DEFINER` RPC, returning an **outcome-code discriminator** the route maps to HTTP status | Best *behavioural* template (outcome codes). **Do NOT copy its security posture** — see Pitfall 8. |
| `126_selects_reaction_cap_lock.sql` | `pg_advisory_xact_lock(hashtextextended(...))` inside a trigger, to serialise a count-then-insert | Right tool when there is no row to lock. |
| `127_atomic_checklist_reorder.sql` | `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE` + `GET DIAGNOSTICS ROW_COUNT` + `RAISE ... USING ERRCODE='serialization_failure'` | Right tool for whole-set invariants. Its comment states plainly: *"The RPC itself is one database transaction."* |

So the phase is build-from-analog after all. That materially lowers the risk CONTEXT.md called "the single biggest risk in the phase" — but it raises a different one: **046 is a security anti-pattern that must not be propagated** (no `REVOKE`, so `PUBLIC` — including `anon` — holds `EXECUTE`; and `SET search_path = public` with unqualified table names, contrary to the house `SET search_path = ''` convention used by 064/078/136/182/190/196).

The second-most important finding: **migrations 190 and 196 did not build a per-function exemption; they built a per-role one.** Both guards test `current_user IN ('postgres')`. `current_user` is `postgres` for the duration of **any** `SECURITY DEFINER` function owned by `postgres` — not only `transfer_vault_project_custody()`. Every new definer RPC this phase adds therefore silently joins the exemption set for `vault_projects.user_id`. The migration headers describe this as "only this one function's execution context is permitted"; that sentence is not what the code enforces. §4 gives three ways to handle it.

Third: **`service_role` carries the `BYPASSRLS` attribute** [CITED: supabase.com/docs/guides/database/postgres/roles]. CONTEXT.md's S1 remedy is "revoke ... and add a rejecting policy." The revoke works. **The rejecting policy does nothing at all against `service_role`** — no RLS policy, permissive or restrictive, constrains a `BYPASSRLS` role [CITED: postgresql.org/docs/current/ddl-rowsecurity.html]. Only table privileges and **triggers** bind it. §6 gives the three-layer design that actually holds.

**Primary recommendation:** build one canonical transactional-RPC template (from migration 123's shape + migration 046's outcome-code return), stamp six RPCs from it, adopt the single global locking order in §3, use `FOR NO KEY UPDATE` everywhere (§3.3), and make the audit non-bypassable with a *deferred constraint trigger* rather than trusting each function author to remember the insert (§6.4).

## §2 — The canonical transactional RPC (the answer to research question 1)

### 2.1 Why a single RPC is atomic here

PostgREST wraps every request — including `POST /rpc/<function>` — in **one SQL transaction at `READ COMMITTED`**; any database failure or `RAISE` inside the function rolls the whole transaction back, otherwise it `COMMIT`s. [CITED: docs.postgrest.org/en/v13/references/transactions.html — confidence MEDIUM, read via search summary; the page itself returned HTTP 429 and could not be fetched directly this session]

This is corroborated in-repo by migration 127's own comment: *"The RPC itself is one database transaction."* [VERIFIED: `supabase/migrations/127_atomic_checklist_reorder.sql:59`]

**Consequence the planner must internalise:** the four races (F9, F11, F15, F16) exist because each route issues 2–5 separate `supabase-js` calls, which are 2–5 separate transactions. Folding them into one RPC is not an optimisation; it is the entire fix.

### 2.2 The skeleton

This is the shape every RPC in the phase should be stamped from. It merges migration 123's security posture with migration 046's outcome-code return.

```sql
-- ─── Template: a consequential-state-change RPC ────────────────────────────
-- Copy this shape. Every deviation must be justified in the migration header.
CREATE OR REPLACE FUNCTION public.workspace_<verb>_<noun>(
  p_actor_id      UUID,          -- asserted by the route AFTER requireWorkspaceAccess (see §3.5)
  p_<target>_id   UUID,
  p_expected_state TEXT DEFAULT NULL   -- optional caller-side CAS token
)
RETURNS TABLE (
  outcome   TEXT,   -- 'ok' | 'not_found' | 'stale' | 'forbidden' | 'floor' | ...
  target_id UUID,
  audit_id  UUID
)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  v_row      public.workspace_<table>%ROWTYPE;
  v_actor_role TEXT;
  v_audit_id UUID;
BEGIN
  -- ── 0. Bound the wait. A row lock inside a Node request path must never
  --       hang indefinitely; PostgREST's own timeout is not a substitute.
  SET LOCAL lock_timeout = '3s';

  -- ── 1. GLOBAL GATE FIRST. Migration 192/194 precedent: the D-56 kill
  --       switch is consulted before ANY other work, and fails closed.
  IF NOT public.workspace_access_enabled() THEN
    RAISE EXCEPTION 'workspace access is disabled'
      USING ERRCODE = 'insufficient_privilege';
  END IF;

  -- ── 2. LOCK, IN THE GLOBAL ORDER (§3). Ascending rank only, never
  --       descending, never conditionally reordered.
  SELECT * INTO v_row
    FROM public.workspace_<table>
   WHERE id = p_<target>_id
     FOR NO KEY UPDATE;          -- §3.3: NO KEY, not FOR UPDATE

  IF NOT FOUND THEN
    RETURN QUERY SELECT 'not_found'::TEXT, NULL::UUID, NULL::UUID;
    RETURN;
  END IF;

  -- ── 3. REVALIDATE EVERY PRECONDITION *AFTER* THE LOCK.
  --       This is the point of the exercise. A precondition checked before
  --       the lock proves nothing. Re-derive the actor's AUTHORITY here —
  --       never accept a role passed in as a parameter.
  SELECT m.role INTO v_actor_role
    FROM public.workspace_members m
   WHERE m.workspace_id = v_row.workspace_id
     AND m.user_id      = p_actor_id
     AND m.status       = 'active'
     AND (m.expires_at IS NULL OR m.expires_at > now());

  IF v_actor_role IS NULL OR v_actor_role NOT IN ('owner') THEN
    RETURN QUERY SELECT 'forbidden'::TEXT, v_row.id, NULL::UUID;
    RETURN;
  END IF;

  IF p_expected_state IS NOT NULL AND v_row.state IS DISTINCT FROM p_expected_state THEN
    RETURN QUERY SELECT 'stale'::TEXT, v_row.id, NULL::UUID;
    RETURN;
  END IF;

  -- ── 4. MUTATE. One row per statement against workspace_members (§4.2).
  UPDATE public.workspace_<table>
     SET state = '<new>', <ts_column> = now()
   WHERE id = v_row.id;

  -- ── 5. AUDIT, IN THE SAME TRANSACTION. Never a second round trip.
  --       No restricted PII in `changes` (WSR-19, §10).
  INSERT INTO public.workspace_audit_log (
    workspace_id, actor_user_id, subject_member_id,
    action, permission_relied_on, target_type, target_id, changes
  ) VALUES (
    v_row.workspace_id, p_actor_id, v_row.member_user_id,
    'workspace.<noun>.<verb>', NULL, 'workspace_<table>', v_row.id,
    jsonb_build_object('state', jsonb_build_object('before', v_row.state, 'after', '<new>'))
  )
  RETURNING id INTO v_audit_id;

  RETURN QUERY SELECT 'ok'::TEXT, v_row.id, v_audit_id;
END;
$$;

-- ── Grants. Migration 123's posture, NOT migration 046's (which has none,
--    leaving PUBLIC — and therefore anon — holding EXECUTE).
REVOKE EXECUTE ON FUNCTION public.workspace_<verb>_<noun>(UUID, UUID, TEXT)
  FROM PUBLIC, anon, authenticated;
GRANT  EXECUTE ON FUNCTION public.workspace_<verb>_<noun>(UUID, UUID, TEXT)
  TO service_role;

COMMENT ON FUNCTION public.workspace_<verb>_<noun>(UUID, UUID, TEXT) IS
  '...one paragraph naming: the lock order it follows, every precondition it revalidates after the lock, which triggers fire on its mutations, and the fact that its audit row is written in the same transaction...';

NOTIFY pgrst, 'reload schema';
```

### 2.3 `RAISE` vs outcome code — the rule

This distinction is load-bearing and easy to get wrong.

| Situation | Mechanism | Why |
|---|---|---|
| Business outcome (stale CAS, already resolved, not found, owner floor would break) | **Return an outcome code** | A `RAISE` rolls back the transaction — **including any audit row already written**. A refusal you want on the record must not `RAISE`. |
| Authorization/invariant violation that should never happen from a correct caller | **`RAISE ... USING ERRCODE = '<sqlstate>'`** | Guarantees rollback; surfaces as a `PostgrestError` with a `code`. |
| A trigger refusing (owner floor, immutable `user_id`) | `RAISE` from the trigger, rolls back | Last line of defence; the RPC should have caught it first and returned a code. |

**The consequence nobody expects:** *you cannot audit a refusal in the same transaction as a `RAISE`.* If the phase wants "refused promotion attempts" on the audit trail, those paths must return outcome codes, not raise. **Surface this to the owner** — it is a product decision, not a technical one.

Route-side mapping follows the existing precedent in `app/api/antenna/opportunities/[opportunityId]/apply/route.ts:47-58` (a `Record<string, {error, status}>` lookup keyed on the outcome discriminator, with a fallback). Reuse it verbatim in shape.

### 2.4 What to stop doing

`app/api/workspaces/[workspaceId]/members/route.ts:97-99` defines `isOwnerFloorTriggerError(message)` — it string-matches `'at least one active owner'` against a Postgres error message. Three files are now coupled to one English sentence (migration 182's `RAISE`, `WORKSPACE_OWNER_FLOOR_MESSAGE` in `lib/workspaces/membership.ts`, and this sniffer). ## §3 — Locking order (the answer to research question 2)

### 3.1 The rule, stated as a rule

> **FUNŪN WORKSPACE LOCK ORDER (LO-1).**
> Any transaction that locks more than one row must acquire those locks in **strictly ascending rank order**, and must never re-acquire a lower rank after acquiring a higher one. Within a single table, lock multiple rows in ascending `id` order (`ORDER BY id`).
>
> | Rank | Table | Note |
> |---|---|---|
> | 1 | `public.workspaces` | the container |
> | 2 | `public.workspace_members` | the seat |
> | 3 | `public.workspace_roster_relationships` | the consent root |
> | 4 | `public.workspace_invitations` | pending seat |
> | 5 | `public.workspace_attachments` | the link to a project |
> | 6 | `public.workspace_grants` | the permission on that link |
> | 7 | `public.workspace_custody_transfers` / `workspace_ownership_transfers` | two-sided offers |
> | 8 | `public.vault_projects` | the shared resource |
> | 9 | `public.workspace_audit_log` | **INSERT only — never locked.** Always last. |
>
> Auxiliary tables not in this list (`workspace_roster_blocks`, `workspace_agreement_evidence`, `workspace_permission_requests`, `workspace_permission_bundles`) inherit the rank of their parent + 0.5 and are touched **after** it.

### 3.2 Why this order and not another

1. **It follows the foreign-key direction, parent before child.** Every workspace FK points "upward" toward `workspaces`. Postgres itself takes a `FOR KEY SHARE` lock on the *parent* row when a child row is inserted [CITED: postgresql.org/docs/current/explicit-locking.html §13.3.2, corroborated by the PG 9.3 FK-lock design]. Locking parents first therefore agrees with the order the database already acquires locks implicitly, rather than fighting it — which is precisely the lock-order *inversion* that produces deadlocks.

2. **`vault_projects` is last because it is the single most contended row, and it is the join point of the two flows most likely to collide.** Custody acceptance (rank 7 → 8) and roster/attachment work (ranks 1–6 → 8) both terminate at the same `vault_projects` row. Placing it last means every transaction holds it for the shortest possible interval, and both flows arrive at it in the same direction. If `vault_projects` were ranked first, a custody accept and a catalogue attach would each hold a workspace-side row while waiting for the other — the textbook deadlock.

3. **`workspace_audit_log` is rank 9 and takes no row lock.** An `INSERT` acquires only a `ROW EXCLUSIVE` table lock, which does not conflict with other inserts. Placed last, its position cannot influence deadlock at all — and placing it last is also what makes "the mutation and its audit row are one transaction" trivially true.

4. **The order is mechanically checkable.** A text-lock test can extract every `FROM public.<table>` that is followed by a locking clause in each new function body and assert the rank sequence is non-decreasing. **Recommend the planner add exactly that assertion to `__tests__/migration-197.test.ts`** — it is the only way this rule survives a future edit, given there is no live-Postgres harness (see Pitfall 1).

5. **Postgres's own guidance backs the approach:** *"The best defense against deadlocks is generally to avoid them by being certain that all applications using a database acquire locks on multiple objects in a consistent order... One should also ensure that the first lock acquired on an object in a transaction is the most restrictive mode that will be needed for that object."* [CITED: postgresql.org/docs/current/explicit-locking.html §13.4]

   The second half matters: **do not lock a row `FOR NO KEY UPDATE` and later re-lock it `FOR UPDATE`** — that is a lock upgrade and a deadlock source. If any row in a transaction will ever need `FOR UPDATE`, take `FOR UPDATE` on the first touch.

### 3.3 `FOR UPDATE` vs `FOR NO KEY UPDATE` (the answer to research question 3)

> **RULE LO-2: use `FOR NO KEY UPDATE` throughout this phase. `FOR UPDATE` is required only for a row that will be `DELETE`d, or whose primary key / FK-referenced unique key will change. Neither happens in this phase.**

**The mechanism.** Postgres's row-lock conflict matrix (Table 13.3) [CITED: postgresql.org/docs/current/explicit-locking.html]:

| Requested \ Held | `FOR KEY SHARE` | `FOR SHARE` | `FOR NO KEY UPDATE` | `FOR UPDATE` |
|---|---|---|---|---|
| `FOR KEY SHARE` | — | — | — | **X** |
| `FOR SHARE` | — | — | **X** | **X** |
| `FOR NO KEY UPDATE` | — | **X** | **X** | **X** |
| `FOR UPDATE` | **X** | **X** | **X** | **X** |

The decisive cell: **`FOR UPDATE` conflicts with `FOR KEY SHARE`; `FOR NO KEY UPDATE` does not.**

**Why that matters given these tables have foreign keys pointing at them.** All seven tables in LO-1 are FK *parents*:

- `workspaces` ← `workspace_members`, `workspace_invitations`, `workspace_roster_relationships`, `workspace_grants`, `workspace_attachments`, `workspace_audit_log`, `workspace_custody_transfers`
- `workspace_roster_relationships` ← `workspace_attachments`, `workspace_grants`, `workspace_agreement_evidence`, `workspace_permission_requests`
- `vault_projects` ← `tracks`, `vault_assets`, `vault_documents`, `tool_outputs`, `workspace_attachments`, `workspace_grants`, `workspace_custody_transfers`

When a concurrent transaction inserts *any* child row, Postgres takes `FOR KEY SHARE` on the parent to guarantee the key still exists at commit [CITED: PG 9.3 FK-lock behaviour, corroborated across postgresql.org message-id archives and cybertec-postgresql.com]. Therefore:

- Locking a `workspaces` row **`FOR UPDATE`** would block *every* concurrent membership insert, invitation, grant, attachment **and audit-log insert** in that workspace for the whole transaction. That is both a self-inflicted throughput cliff and a much larger deadlock surface — the very thing LO-1 exists to prevent.
- Locking it **`FOR NO KEY UPDATE`** blocks only other writers of the same row. Concurrent child inserts proceed.

**None of this phase's mutations touch a key column:**

| Mutation | Column(s) changed | Key? |
|---|---|---|
| Roster transition | `state`, `accepted_at`, `refused_at`, `ended_at`, `ended_by` | no |
| Membership re-role / status | `role`, `status`, `updated_at` | no |
| Invitation redemption | `status`, `accepted_at`, `accepted_by`; plus `workspace_members.user_id`, `status` | see caveat |
| Custody accept | `workspace_custody_transfers.state`; `vault_projects.user_id` | no — children reference `vault_projects.id`, not `user_id` |
| Ownership accept | `workspace_members.role` ×2 | no |
| Grant revoke | `revoked_at`, `revoked_by` | no |
| Attachment detach | `detached_at`, `detached_by` | no |

Nothing is deleted anywhere — D-14, D-17 and D-25 all forbid it, and every existing route already does status-updates instead of deletes. So `FOR UPDATE` is not needed anywhere in this phase.

**One caveat, stated honestly.** An `UPDATE` that modifies a column covered by *a unique index usable in a foreign key* implicitly takes `FOR UPDATE` rather than `FOR NO KEY UPDATE`. `workspace_members` has `idx_workspace_members_unique_user (workspace_id, user_id) WHERE user_id IS NOT NULL` — a **partial** unique index, which cannot back a foreign key — and invitation redemption sets `user_id`. I expect Postgres to treat this as a no-key update, but **I could not verify Postgres's exact test without a live database, and this research made no database connection.** The failure mode is benign: if Postgres takes the stronger lock anyway, the statement is *more* serialised than intended, never less. It is never a correctness problem. **Flagging it as unverified rather than asserting it.**

**Additional recommendations:**

- `SET LOCAL lock_timeout = '3s'` at the top of every RPC. A blocked row lock in a Node request path is a hung HTTP request; a bounded wait converts it into a `55P03 lock_not_available` the route can map to 409/503.
- Do **not** use `NOWAIT` — it turns ordinary contention into user-visible errors. Do **not** use `SKIP LOCKED` — that is correct for a work queue (migration 123) and wrong for an authorization decision, where skipping a row means silently reading stale state.
- Deadlocks that do occur surface as SQLSTATE `40P01`. The route should map `40P01` and `55P03` to **409 with a retry-safe message**, not 500.

### 3.5 The actor-binding fork — decide this before writing any RPC

Migration 194 binds the caller with `AND p_uid = (SELECT auth.uid())` inside the function body — the pattern that makes read impersonation impossible (verified behaviourally as Part B check B9). **That pattern is not available to these write RPCs as currently designed**, because migration 182 section (e) REVOKEs all writes from `authenticated` and the house doctrine is *"every write goes through a service-role API route that has already proved caller authority."* Under a service-role client, `auth.uid()` is NULL.

Two options, and the planner must pick one explicitly:

**Option A — service-role RPC, actor asserted by the route (RECOMMENDED).**
`GRANT EXECUTE ... TO service_role` only (migration 123's posture). `p_actor_id` is supplied by the route from `requireWorkspaceAccess`'s already-proved `access.userId`. The RPC re-derives the actor's *authority* (role, active status, `expires_at`) from the database — it never accepts a role parameter.
- Preserves existing doctrine and every existing gate.
- **Honest limitation:** R-05 says "enforced in the database/RPC, never in route logic." Under Option A the *authority* is in the database but the *identity* still comes from the route. That is a partial satisfaction of R-05 and should be written down, not glossed.

**Option B — session-client RPC, actor bound to `auth.uid()`.**
`GRANT EXECUTE ... TO authenticated`, `p_actor_id` unused or asserted `= auth.uid()`, called with `createApiClient()`. R-05 is then satisfied literally.
- Every authority check must be complete inside the RPC, because any authenticated user can call it directly — including the D-56 kill switch (available: `workspace_access_enabled()`), the staff-identity refusal (**not** available in SQL — `getStaffRoles(user)` reads `app_metadata`; `auth.jwt()` can reach it but that is a new pattern in this repo), and the cohort gate.
- Departs from 182's stated write posture and widens the client-reachable surface.

**Recommendation: Option A**, with the route-side gate order unchanged and the RPC re-deriving authority. Record the R-05 limitation in the migration header. **Surface the choice to the owner** — it is the difference between "the database enforces who may promote" and "the database enforces what a promotion must look like."

## §4 — Trigger interaction (the answer to research question 4)

### 4.1 The correction, stated first

**`SECURITY DEFINER` changes the effective user for permission checks (and therefore what `current_user` reports). It does NOT bypass triggers.** A `BEFORE UPDATE FOR EACH ROW` trigger fires on an `UPDATE` issued inside a `SECURITY DEFINER` function exactly as it does anywhere else.

This is not speculation — it is written into migration 196's own header as the diagnosed root cause of a bug that reached production: migration 139 stated a future transfer would run through *"a SECURITY DEFINER function owned by the table owner, which this trigger does not fire against."* That parenthetical was wrong, custody transfer never worked, and only Part B — executing the real RPC — surfaced it. [VERIFIED: `supabase/migrations/196_owner_immutable_guard_custody_exemption.sql` header]

**Every RPC in this phase must therefore be designed with an explicit answer to: "which triggers fire, on which statement, in which order, and what do they see?"**

### 4.3 `guard_workspace_never_zero_owners` — the trigger that decides your write order

This is the single most consequential trigger interaction in the phase. Read `supabase/migrations/182_workspaces_foundation.sql:345-383` carefully; the facts that matter:

```sql
IF (TG_OP = 'DELETE' AND OLD.role = 'owner' AND OLD.status = 'active')
   OR (TG_OP = 'UPDATE' AND OLD.role = 'owner' AND OLD.status = 'active'
       AND (NEW.role <> 'owner' OR NEW.status <> 'active')) THEN
  SELECT COUNT(*) INTO v_remaining_owners
  FROM public.workspace_members
  WHERE workspace_id = OLD.workspace_id
    AND role = 'owner' AND status = 'active' AND id <> OLD.id;
  IF v_remaining_owners = 0 THEN RAISE EXCEPTION ...; END IF;
END IF;
```

**Four consequences:**

1. **It runs inside your transaction and sees your own uncommitted writes from *previous statements*.** Therefore, for a two-sided ownership transfer:
   > **RULE: promote the successor in statement 1, demote the incumbent in statement 2.** In that order, the trigger firing on the demotion counts the freshly-promoted successor and passes. In the reverse order, it counts zero and raises `42501`.

   This is not a subtlety the planner can leave to the implementer. Write it into the plan's action text.

2. **It does not fire on the promotion.** The guard's `TG_OP = 'UPDATE'` branch requires `OLD.role = 'owner'`. Promoting a member to owner has `OLD.role = 'admin'` and the branch is skipped entirely. **So the owner-floor trigger provides zero protection against unauthorized promotion** — that is exactly finding F5/WSR-07, and it needs a *new* trigger (§7.3).

3. **It does not consider `expires_at`.** An owner seat whose `expires_at` has passed still counts toward the floor, while post-192 `workspace_member_role()` treats that same seat as no membership at all. **A workspace can therefore satisfy the never-zero-owners floor with an owner who has no live access.** This is not a defect against any WSR as written. **Surface it to the owner alongside the carried-in `role`-does-not-gate-project-access question — they are the same class of issue.**

4. **Multi-row `UPDATE` statements are dangerous here.** A `BEFORE ROW` trigger's own `SELECT` uses the current command's snapshot, which in `READ COMMITTED` does **not** include rows updated by that same command. A single statement demoting two owners would fire the trigger twice, each invocation blind to the other's pending change.
   > **RULE: never issue a multi-row `UPDATE` against `workspace_members` inside these RPCs. One row per statement, always.**

### 4.4 The `vault_projects` exemption is broader than its own documentation claims

Both guards test the same predicate:

- migration 190: `IF NEW.user_id IS DISTINCT FROM OLD.user_id AND current_user NOT IN ('postgres') THEN RAISE`
- migration 196: `IF NEW.user_id IS DISTINCT FROM OLD.user_id AND NOT (TG_TABLE_NAME = 'vault_projects' AND current_user IN ('postgres')) THEN RAISE`

`current_user` is `postgres` for the duration of **any** `SECURITY DEFINER` function owned by `postgres` — not only `transfer_vault_project_custody()`. Migration 190's header says the exemption is *"available ONLY to code that calls that specific function"* and migration 196's says *"only this one function's execution context... is permitted."* **Those sentences describe an intent the code does not enforce.** [VERIFIED: reading both function bodies]

**Every new `SECURITY DEFINER` function this phase adds silently joins the exemption set.** Three ways to handle it, in order of preference:

**(a) RECOMMENDED — don't touch `user_id` directly.** The custody-accept RPC calls `public.transfer_vault_project_custody(p_project_id, p_from_user_id, p_to_user_id)` rather than issuing its own `UPDATE`. Nested `SECURITY DEFINER` calls run in the same transaction, so atomicity is preserved; the double-filter `WHERE id = ... AND user_id = ...` and its NULL-return stale-custodian semantics come along for free; and the "one sanctioned path" doctrine stays literally true. Cost: nothing. **This is the answer.**

**(b) Accept and document.** Add to migrations 197/198's headers an explicit statement that the exemption is role-scoped, list every postgres-owned definer function that can now move `user_id`, and add a text-lock test asserting that no *new* function in this phase contains an `UPDATE public.vault_projects ... SET user_id`.

**(c) Tighten the guard with a transaction-local marker.** Have `transfer_vault_project_custody()` execute `SET LOCAL funun.custody_transfer = 'on'` and have both guards additionally require `current_setting('funun.custody_transfer', true) = 'on'`. PostgreSQL reverts a `SET LOCAL` issued inside a function that has its own `SET` clause when that function exits, which gives exactly function-scoped semantics. **[ASSUMED — I did not verify this revert behaviour against the docs this session, and it is subtle enough that it must be confirmed on a preview branch before it is relied on.]** Also: this edits two applied, text-locked, production migrations (190 and 196) — a materially higher-risk change than (a).

### 4.5 Trigger-related rules for the plans

- `update_updated_at()` fires on every UPDATE. Do not set `updated_at` manually in these RPCs; it will be overwritten. (`app/api/workspaces/[workspaceId]/members/route.ts` already correctly omits it.)
- Nothing in this phase should `DISABLE TRIGGER` or set `session_replication_role`. If any migration does, that is a review-blocking finding.
- `workspace_custody_transfers` has **no** UPDATE guard. The only thing stopping a double-resolve today is the route's `.eq('state', 'offered')` CAS. When that CAS moves into an RPC, consider adding a terminal-state trigger mirroring migration 195's `workspace_permission_request_transition_guard()` — that is the shape this repo already uses for "these states are terminal", and it is the second independent layer §11 argues for.

## §6 — Making the audit genuinely non-bypassable (the answer to research question 5)

### 6.1 Why `REVOKE ... FROM PUBLIC` missed `service_role`

Supabase's bootstrap runs `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO postgres, anon, authenticated, service_role` [CITED: supabase.com/docs — corroborated across supabase/supabase docs and the Oct-2026 Data API grants changelog]. That is a **direct** grant to the role, not membership in `PUBLIC`. `REVOKE UPDATE, DELETE ON public.workspace_audit_log FROM PUBLIC` (migration 182 line 251) therefore removed nothing from `service_role`. Part A check A10 confirmed exactly that on production. [VERIFIED]

### 6.2 A "rejecting policy" does nothing against `service_role`

`service_role` carries the `BYPASSRLS` attribute [CITED: supabase.com/docs/guides/database/postgres/roles]. PostgreSQL: *"Superusers and roles with the BYPASSRLS attribute always bypass the row security system when accessing a table."* [CITED: postgresql.org/docs/current/ddl-rowsecurity.html]

**A `RESTRICTIVE` policy on `workspace_audit_log` will not stop a `service_role` UPDATE or DELETE.** CONTEXT.md's S1 wording ("revoke ... and add a rejecting policy") is half right; the policy half must not be counted as the enforcement. Keep it as defence-in-depth against a hypothetical future non-BYPASSRLS role that gets a grant, but say so in the header.

### 6.3 The three layers that do bind (recommended migration content)

```sql
-- ── Layer 1: privileges. The one that actually removes service_role's
--    ability. BYPASSRLS confers no table privileges, so this binds it.
REVOKE UPDATE, DELETE, TRUNCATE ON public.workspace_audit_log
  FROM PUBLIC, anon, authenticated, service_role;
-- INSERT and SELECT are deliberately retained for service_role (writes) and
-- authenticated (D-50 both-sides reads, via §10's redacted path).

-- ── Layer 2: triggers. Fire for EVERY role — including BYPASSRLS roles and
--    the table owner. This is what survives a future re-GRANT, whether by a
--    migration, an ALTER DEFAULT PRIVILEGES change, or a Supabase platform
--    default. Note TRUNCATE needs its own STATEMENT-level trigger: row-level
--    triggers do not fire for TRUNCATE.
CREATE OR REPLACE FUNCTION public.guard_workspace_audit_log_append_only()
RETURNS TRIGGER LANGUAGE plpgsql SET search_path = '' AS $$
BEGIN
  RAISE EXCEPTION
    'workspace_audit_log is append-only (D-50): rows cannot be updated, deleted or truncated by any role'
    USING ERRCODE = 'insufficient_privilege';
END; $$;

CREATE TRIGGER guard_workspace_audit_log_no_row_change
  BEFORE UPDATE OR DELETE ON public.workspace_audit_log
  FOR EACH ROW EXECUTE FUNCTION public.guard_workspace_audit_log_append_only();

CREATE TRIGGER guard_workspace_audit_log_no_truncate
  BEFORE TRUNCATE ON public.workspace_audit_log
  FOR EACH STATEMENT EXECUTE FUNCTION public.guard_workspace_audit_log_append_only();

-- ── Layer 3: a RESTRICTIVE policy. Honest scope: this constrains
--    authenticated/anon only, and both already lack the privilege. It is
--    forward-insurance, not the enforcement. Documented as such.
CREATE POLICY "workspace_audit_log_no_mutation" ON public.workspace_audit_log
  AS RESTRICTIVE FOR ALL TO authenticated, anon USING (false) WITH CHECK (false);
```

**The honest limitation to write into the header:** none of this constrains the database owner. `postgres` can `DROP TRIGGER`, `ALTER TABLE ... DISABLE TRIGGER`, or set `session_replication_role = 'replica'` (which disables triggers wholesale) and then mutate freely. The defensible claim is **"append-only to every application role"**, not "immutable." Do not overstate it in the header or the audit-trail UI copy.

### 6.4 The part CONTEXT.md's R-06 does not actually guarantee — and the fix

R-06 says the audit row is written *in the same transaction*. Putting the `INSERT` inside the RPC body achieves that. **But it does not make the audit non-bypassable — it makes it non-*partial*.** If a future RPC author simply omits the `INSERT`, nothing catches it. That is the same class of failure as F14, one layer up.

**Recommended mechanism — a deferred constraint trigger asserting the audit row exists at commit time:**

```sql
CREATE OR REPLACE FUNCTION public.assert_workspace_change_is_audited()
RETURNS TRIGGER LANGUAGE plpgsql SET search_path = '' AS $$
BEGIN
  -- workspace_audit_log.created_at DEFAULTs to NOW(), which is
  -- transaction_timestamp() -- identical for every row written by this
  -- transaction, and (with target_id) an effectively exact test.
  IF NOT EXISTS (
    SELECT 1 FROM public.workspace_audit_log l
     WHERE l.target_id  = NEW.id
       AND l.created_at = now()
  ) THEN
    RAISE EXCEPTION
      'a consequential change to %.% was committed without an audit row (WSR-13)',
      TG_TABLE_NAME, NEW.id
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;
  RETURN NULL;
END; $$;

CREATE CONSTRAINT TRIGGER assert_workspace_member_change_audited
  AFTER UPDATE OF role, status ON public.workspace_members
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION public.assert_workspace_change_is_audited();
-- ...and equivalents scoped to the consequential columns on
-- workspace_roster_relationships (state), workspace_invitations (status),
-- workspace_custody_transfers (state).
```

**Why deferred:** the check must run at `COMMIT`, after the RPC has written both the mutation and the audit row, regardless of the order they appear in the function body.

**Why column-scoped (`AFTER UPDATE OF role, status`):** an unscoped trigger would demand an audit row for every incidental save, including `updated_at`-only writes. Scoping to the columns that define a *consequential* state change matches R-06's own wording and keeps the constraint enforceable.

**Confidence:** MEDIUM. The mechanism (deferred constraint triggers, `now()` = `transaction_timestamp()`) is standard PostgreSQL, but the exact behaviour under this schema — particularly whether `target_id` is always set to the mutated row's `id` by every writer — **must be confirmed on a Supabase preview branch before this ships.** Today, `logWorkspaceAction` call sites do generally set `targetId` to the mutated row's id, but `app/api/workspaces/invitations/accept/route.ts:169` sets `targetId: pendingSeat?.id ?? null` — **null when no pending seat existed**, which would fail this assertion. That call site must be fixed as part of WSR-10.

**Cheaper alternative if the constraint trigger proves too invasive:** make `logWorkspaceAction` throw instead of returning `{ok:false}`, and make every call site await it before returning success. That closes F14's *observable* half (a silent failure becomes a 500) but leaves "an RPC that never calls it" open. Only the constraint trigger closes that. **Recommend the constraint trigger; note the fallback.**

## §7 — Ownership hierarchy and two-sided transfer (WSR-07 / WSR-08)

### 7.1 What exists to mirror

`workspace_custody_transfers` (migration 185) + its `BEFORE INSERT` guard (migration 187) + `lib/workspaces/custody-transfer.ts` + `app/api/vault/custody-transfers/route.ts` is a complete, reviewed, in-production two-sided flow. Reuse its parts:

| Custody part | Ownership analogue |
|---|---|
| `workspace_custody_transfers` table, `state IN ('offered','accepted','declined','withdrawn')`, all three exits terminal | `workspace_ownership_transfers`, same state set |
| Partial unique index `WHERE state = 'offered'` (one live offer per project) | one live nomination per **workspace** |
| `CHECK (from_user_id <> to_user_id)` | same |
| `guard_custody_transfer_offered_by_holder` BEFORE INSERT (migration 187) — the offerer must be the current holder | BEFORE INSERT: the nominator must be an **active owner** of the workspace and must be `from_user_id` |
| `TRANSFER_LEGAL_EDGES` + `isLegalTransferTransition` (pure, zero-I/O) | `OWNERSHIP_LEGAL_EDGES` + `isLegalOwnershipTransition` — copy the module shape verbatim |
| `assertMayRespond` — only `to_user_id` accepts/declines; only `offered_by`/`from_user_id` withdraws; **and the offerer can never also accept** | identical predicate |
| `describeTransferEffect()` — the sentence shown to both parties naming what changes and what does not | **needed here too.** Ownership of a *workspace* is not ownership of any Member's record, catalogue, or rights. Write the sentence. |

`lib/workspaces/custody-transfer.ts`'s header is a model for what the new module's header should say, including its account of the F1 hotfix (a workspace admin could once both offer and accept). **That exact attack shape is what R-05 is preventing at the workspace-ownership layer.**

### 7.2 The design question CONTEXT.md does not settle

Does accepting a nomination **transfer** ownership (incumbent demoted to `admin`) or **add** an owner?

- "Ownership transfer" implies the former.
- But `workspace_members` supports multiple `owner` rows, and D-13 is a *floor*, not a ceiling.

**Recommend: transfer** — promote the successor, then demote the nominator to `admin`, in that statement order (§4.3 rule 1). **But surface it; do not decide it silently.** A workspace with two founders will want "add an owner", and that is a different RPC (`workspace_grant_ownership`) with a different authority rule.

### 7.3 The new trigger WSR-07 needs

`guard_workspace_never_zero_owners` does **not** fire on promotion (§4.3 point 2), so there is currently no database-layer obstacle to an admin promoting themselves. Adding one requires the structural-exemption idiom migrations 190/196 established, because a trigger cannot see the human actor (`auth.uid()` is NULL under `service_role`; `current_user` is `service_role`):

```sql
CREATE OR REPLACE FUNCTION public.guard_workspace_owner_role_change()
RETURNS TRIGGER LANGUAGE plpgsql SET search_path = '' AS $$
BEGIN
  -- Two structural rules, neither actor-relative:
  --   * a row may not BECOME owner, and
  --   * an existing owner row may not be changed at all,
  -- except inside a postgres-owned SECURITY DEFINER function -- i.e. inside
  -- the sanctioned ownership RPCs, where the ACTOR-relative rules (owner
  -- only, no self-promotion, admins may not touch owner rows) are checked
  -- against a p_actor_id the route bound after requireWorkspaceAccess.
  IF current_user IN ('postgres') THEN RETURN NEW; END IF;

  IF TG_OP = 'UPDATE' AND OLD.role <> 'owner' AND NEW.role = 'owner' THEN
    RAISE EXCEPTION 'promotion to owner moves only through the two-sided ownership transfer (R-05/WSR-08)'
      USING ERRCODE = 'insufficient_privilege';
  END IF;

  IF TG_OP = 'UPDATE' AND OLD.role = 'owner' AND (NEW.role, NEW.status) IS DISTINCT FROM (OLD.role, OLD.status) THEN
    RAISE EXCEPTION 'an owner row changes only through the sanctioned ownership RPCs (R-05/WSR-07)'
      USING ERRCODE = 'insufficient_privilege';
  END IF;

  RETURN NEW;
END; $$;
```

**Two things to note.** First, this trigger is `BEFORE UPDATE` on `workspace_members` and will fire *alongside* `guard_workspace_never_zero_owners` and `workspace_members_updated_at` — name it so its alphabetical position is deliberate. Second, an `INSERT` branch is also needed: `POST /api/workspaces` inserts an `owner` row at creation, so the trigger must admit `TG_OP = 'INSERT'` from the (postgres-owned) `workspace_create` RPC — which is another reason WSR-23's atomic-create RPC is a prerequisite for WSR-07, not an independent item.

### 7.4 Where the actor-relative rules live

Inside the RPCs, checked against `p_actor_id`, with the actor's authority re-derived from the database:

| Rule (R-05) | Check |
|---|---|
| Only owners may promote to owner | `v_actor_role = 'owner'` after the lock |
| No self-promotion | `p_actor_id <> v_target_user_id` on the promote path, and the nominator can never be the acceptor (copy `assertMayRespond`'s self-dealing check) |
| Admins may not edit or remove owner rows | `IF v_target.role = 'owner' AND v_actor_role <> 'owner' THEN return 'forbidden'` |

## §9 — The D-55 cohort gate (WSR-16 / R-07) — the Song Passport pilot pattern

### 9.1 The pattern, as built

`lib/song-passport/feature.ts` + `supabase/migrations/156_song_passport_pilot_operations.sql`. [VERIFIED: read both]

**Shape of the gate function** (`isSongPassportAvailableForWork`), in evaluation order:

1. `SONG_PASSPORT_KILL_SWITCH === 'true'` → **false**. *"The emergency stop always wins."* Checked before everything, including the global enable.
2. `SONG_PASSPORT_ENABLED === 'true'` → **true** (general availability; no cohort lookup).

5. Any query error → **false** (fails closed).

**Shape of the cohort table** (`song_passport_cohorts`):
- Two nullable subject axes (`account_user_id`, `work_id`) with `CHECK (account_user_id IS NOT NULL OR work_id IS NOT NULL)`.
- `stage TEXT CHECK (stage IN ('internal','pilot','general'))`, `enabled BOOLEAN NOT NULL DEFAULT TRUE`, `flags JSONB`, `starts_at`/`ends_at` with `CHECK (ends_at IS NULL OR ends_at > starts_at)`.
- **Partial unique index per axis** (`(account_user_id, stage) WHERE account_user_id IS NOT NULL`).
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + `REVOKE ALL ... FROM authenticated, anon` — service-role reads only.
- `created_by UUID NOT NULL REFERENCES auth.users` — the cohort is an auditable act.
- `updated_at` trigger.

**Explicit doctrine in the source:** *"Server-only rollout boundary. Do not expose this as `NEXT_PUBLIC_*`: Slice 1 has no artist-facing UI or client writes, and the default must remain off."*

### 9.2 The workspace analogue

New table `workspace_cohorts` (migration 197 or 198), one axis (`account_user_id`) — a `workspace_id` axis is meaningless for the *creation* gate, since there is no workspace yet. Same columns, same indexes, same lockdown.

1. **D-56 kill switch** (`isWorkspaceAccessEnabled`) → 503. Already first; the F7 hotfix header explains why it must stay first.
2. **Cohort gate** → 403 (or 404 if the phase decides non-cohort Members should not learn the feature exists — **surface this; both are defensible and it is a product decision**).
3. `!user` → 401.
4. Staff role → 403.
5. Membership lookup → 403.

## §10 — Viewer-class-redacted audit reads (WSR-19 / R-13)

### 10.1 Two independent fixes, both required

**Fix 1 — stop writing restricted PII into `changes`.** The invited address already lives on `workspace_invitations.email`, whose SELECT policy is owner/admin-only (migration 182:324). The audit row's `target_id` already points at that invitation. So `changes` should carry `{ role }` and nothing else. Zero rows exist, so nothing to migrate.

Add a **write-time guard** as the second layer — a `BEFORE INSERT` trigger on `workspace_audit_log` rejecting any `changes` object containing a key in a restricted set:

```sql
IF NEW.changes ?| ARRAY['email','phone','contact_email','contact_phone','address','tax_id','token','token_hash','ipi','isni'] THEN
  RAISE EXCEPTION 'workspace_audit_log.changes may not carry restricted PII (WSR-19)'
    USING ERRCODE = 'check_violation';
END IF;
```
Note `?|` only inspects **top-level** keys. Nested objects (`{"before": {"email": ...}}`) slip through. Either recurse with `jsonb_path_exists(NEW.changes, '$.**.email')`, or state the top-level-only limitation in the header. **Recommend `jsonb_path_exists` with `$.**.<key>` and note it as MEDIUM confidence pending a preview-branch check.**

**Fix 2 — redacted reads.** Follow migration 193/194's precedent exactly: a `SECURITY DEFINER` RPC with an **explicit declared return column list as the security contract**, redacting in SQL with `CASE` so a withheld value never leaves the database.

```sql
CREATE OR REPLACE FUNCTION public.workspace_audit_page(
  p_workspace_id UUID, p_uid UUID, p_limit INT, p_offset INT
)
RETURNS TABLE (
  id UUID, actor_user_id UUID, subject_member_id UUID,
  action TEXT, permission_relied_on TEXT,
  target_type TEXT, target_id UUID,
  changes JSONB, changes_redacted BOOLEAN, created_at TIMESTAMPTZ
)
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = '' AS $$
  SELECT l.id, l.actor_user_id, l.subject_member_id, l.action, l.permission_relied_on,
         l.target_type, l.target_id,
         CASE WHEN v.full_view THEN l.changes ELSE '{}'::JSONB END,
         NOT v.full_view,
         l.created_at
    FROM public.workspace_audit_log l
    CROSS JOIN LATERAL (SELECT
      l.actor_user_id = p_uid
      OR l.subject_member_id = p_uid
      OR public.workspace_member_role(l.workspace_id, p_uid) IN ('owner','admin')
      AS full_view) v
   WHERE l.workspace_id = p_workspace_id
     AND p_uid = (SELECT auth.uid())            -- migration 194's caller bind
     AND public.workspace_access_enabled()
     AND public.workspace_member_role(l.workspace_id, p_uid) IS NOT NULL
   ORDER BY l.created_at DESC, l.id DESC
   LIMIT LEAST(GREATEST(COALESCE(p_limit, 50), 1), 200)
  OFFSET GREATEST(COALESCE(p_offset, 0), 0)
$$;
```

**Three properties to preserve from the 193/194 precedent:**
- `p_uid = (SELECT auth.uid())` — the parameter is explicit but can only ever name the caller. This is the fix Part B check B9 proved works; do not omit it.
- `LIMIT LEAST(GREATEST(..., 1), 200)` — an unbounded page on a definer function is a DoS surface (migration 194's own words).
- A **boolean** (`changes_redacted`) so the reader can distinguish "withheld" from "genuinely empty" without a second query.

**Redaction should be allowlist-based, not denylist.** `'{}'::JSONB` above is the strictest form. If the phase wants partial visibility, build the visible object with `jsonb_build_object` from a fixed set of safe keys — never `l.changes - ARRAY[...]`, which leaks anything a future writer adds.

### 10.2 The policy change this implies, and its D-50 tension

To make the redacted RPC the *only* path for ordinary members, `workspace_audit_log_select` (migration 186:451) must lose its broad `workspace_member_role(...) IS NOT NULL` branch, becoming actor-or-subject-or-owner/admin. **This narrows what D-50 literally says** ("visible to BOTH the workspace and the affected Member") — the workspace still sees its own trail, but ordinary members reach it through the redacted RPC rather than a direct table read.

**No app surface reads `workspace_audit_log` today** (grep found only `logWorkspaceAction` writing to it and test fixtures) — so this can be done cleanly with no UI breakage. But it is a change to a locked decision's surface. **Surface it to the owner; do not decide it silently.**

## §11 — Delete or keep the route-layer logic? (the answer to research question 6)

### 11.1 The doctrine, restated precisely

This repo's doctrine (migrations 078, 136, 187, 190, 196; `lib/workspaces/custody-transfer.ts`'s header; `app/api/vault/custody-transfers/route.ts`'s "FIRST/SECOND/THIRD enforcement point" comment) is **two independent layers agreeing on the same rule** — not deduplication.

The word doing the work is **independent**. Two layers are independent when they fail for different reasons: an application predicate and a database trigger; an RLS policy and a route gate; a unique index and a service-layer check. Two layers are **not** independent when one is a hand-copy of the other's logic against the same data in the same request — that is one layer plus a stale copy, and the stale copy is where drift lives.

### 11.2 The classification

**KEEP — genuine second enforcement points.** All are pure functions or gates that produce the user-facing sentence *before* the RPC runs, and all fail for different reasons than the database would:

## §13 — Common Pitfalls

### Pitfall 1 — There is no live-Postgres test harness, and text-lock tests cannot catch this class of bug
Migration 190's suite was green, its function existed, and the route called it correctly — yet custody transfer was broken in production for a day, because a *differently-named* second trigger also fired. Only Part B, executing the real RPC, surfaced it. **Every claim in this document about what a trigger does at runtime is a reading of SQL text, not an observation of a running database.**
**Avoid:** every plan in this phase must carry an owner-run behavioural check, not only a text-lock test. Concretely: a real ownership nomination + accept, a real invitation redemption, a real roster block, a real custody accept, and an attempted `service_role` `UPDATE` against `workspace_audit_log` (expect refusal).
**Warning sign:** a plan whose entire verification is `npm test -- migration-197`.

### Pitfall 2 — `SECURITY DEFINER` does not bypass triggers
Cost one production outage already (migration 139 → 196). **Avoid:** write the trigger inventory (§4.2) into every migration header that mutates one of these tables.

### Pitfall 3 — The `current_user IN ('postgres')` exemption is role-scoped, not function-scoped
§4.4. Every new definer function joins the exemption set for `vault_projects.user_id`.
**Avoid:** call `transfer_vault_project_custody()` rather than issuing your own `UPDATE`. Add a text-lock assertion that no new function in 197/198 contains `UPDATE public.vault_projects` with `user_id` in its SET list.

### Pitfall 4 — Owner-floor write order
Demote-then-promote raises `42501`; promote-then-demote passes. §4.3.
**Warning sign:** a plan action that says "update both member rows" without specifying order.

### Pitfall 5 — A `RAISE` rolls back the audit row you just wrote
§2.3. Refusals you want on the record must be outcome codes.
**Warning sign:** a plan that says "log the refusal and raise."

### Pitfall 6 — `FOR UPDATE` on an FK parent blocks all concurrent child inserts
§3.3. Use `FOR NO KEY UPDATE`.
**Warning sign:** any `FOR UPDATE` in a 197/198 migration without a written justification naming a DELETE or a key change.

### Pitfall 7 — Lock upgrades are a deadlock source
Locking a row `FOR NO KEY UPDATE` and later re-locking it `FOR UPDATE` in the same transaction is an upgrade. Postgres's own guidance: take the most restrictive mode you will need on the first touch.
**Avoid:** one locking clause per row per transaction.

### Pitfall 8 — Do not copy migration 046's security posture
`046_atomic_opportunity_apply.sql` is the best *behavioural* template in the repo and the worst *security* template: it has **no `REVOKE`/`GRANT` at all** (so `PUBLIC` — including `anon` — holds `EXECUTE` on a `SECURITY DEFINER` function), uses `SET search_path = public` instead of `''`, and references tables unqualified. Copy its outcome-code return shape only. Everything else comes from migration 123.
**(Note: `apply_to_opportunity_atomic`'s open `EXECUTE` grant is a pre-existing issue outside this phase's scope. Worth capturing as a backlog item, not fixing here.)**

### Pitfall 9 — Multi-row `UPDATE` against `workspace_members`
§4.3 point 4. A `BEFORE ROW` trigger's own `SELECT` does not see rows changed by the same command.
**Avoid:** one row per statement.

### Pitfall 10 — Migration numbers
The LIVE LEDGER in `.planning/ROADMAP.md` is authoritative: **197–198**. Six stale-numbering incidents have already occurred; the headers of 190, 191, 192 and 193 all carry ranges that are now off by two and are deliberately not being edited.
**Avoid:** never read a migration file header for a number.

### Pitfall 11 — The audit `changes` PII guard only sees top-level keys
`jsonb ?| ARRAY[...]` does not recurse. `{"before": {"email": "..."}}` passes. §10.1.
**Avoid:** use `jsonb_path_exists(changes, '$.**.email')`, and verify it on a preview branch.

### Pitfall 12 — Three kill-switch call sites, not one
`requireWorkspaceAccess`, `POST /api/workspaces`, and `POST /api/workspaces/invitations/accept` each call `isWorkspaceAccessEnabled` independently. The cohort gate must reach all three, or WSR-16 reproduces hotfix F7's shape.

### Pitfall 13 — `git add -A` and stale state
Per standing project memory: parallel sessions make filesystem and DB state stale. Re-verify immediately before acting; never `git add -A`.

## §17 — What I could NOT determine (stated rather than guessed)

1. **Whether `UPDATE workspace_members SET user_id = ...` takes `FOR NO KEY UPDATE` or is upgraded to `FOR UPDATE`** because of the *partial* unique index `idx_workspace_members_unique_user`. A partial index cannot back a foreign key, so I expect no upgrade — but I could not confirm Postgres's exact test without a database. **Benign either way** (a stronger lock is safe, just less concurrent). §3.3.

2. **Whether `SET LOCAL` inside a function that has its own `SET` clause reverts at function exit** — the mechanism §4.4 option (c) depends on. Marked `[ASSUMED]`. Option (a) avoids needing it at all; recommend (a).

3. **Whether `postgres` on this Supabase project is a true superuser.** `38.0.1-PREFLIGHT.md` P1 calls it "this project's confirmed superuser role," but on hosted Supabase `postgres` is typically *not* `rolsuper`. This matters only for the honesty of §6.3's limitation paragraph (whether `session_replication_role = 'replica'` is reachable). It does not change any recommendation. **Verifiable with `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname IN ('postgres','service_role')` — add it to the phase's Part A probe.**

4. **Whether `workspace_audit_log` and `workspace_invitations` are empty in production.** Part A check A9 counted five tables and did not include these two. WSR-19's PII fix and WSR-26's revoke both assume emptiness. **Add both counts to the pre-flight probe.**

7. **Trigger firing order for two same-event `BEFORE ROW` triggers** — I state alphabetical-by-trigger-name from training knowledge and it is consistent with the observed 139-before-190 behaviour, but I did not re-fetch the documentation this session. `[ASSUMED]`, though the 196 incident is strong indirect evidence.
