<objective>
Fix the two verified defects in `lib/workspaces/appears-on.ts` (R-09 / WSR-21).

**Defect 1 — a row appears with no relationship naming the caller.** `resolveAppearsOnRows` selects
from `vault_projects` through the RLS client, so a row appears purely because
`workspace_project_permission(..., 'view_summaries')` admitted it — that is, because of delegated
workspace access. `contributionRole` is looked up afterwards and may be `null`, but a null does not
exclude the row. So a workspace admin with no contribution to a record sees it on their personal
"Appears on" shelf, which is a contribution claim they never earned.

**Defect 2 — multi-workspace attachments are silently overwritten.**
`new Map(attachmentRows.map(a => [a.project_id, a.workspace_id]))` keeps only the LAST attachment
per project. A project attached to two workspaces loses one — possibly the caller's own, in which
case `contributionRole` comes back `null` for a genuine contributor.

Purpose: make "Appears on" mean what it says. Appearing on a record is a contribution fact
(D-27, D-35); it must require an explicit relationship naming the caller, and it must not be
inferable from delegated access.

Output: a corrected pure-ish reader and its extended suite. No migration, no route change. Research
notes that a set-based RPC would be the long-term answer; WSR-21 does not require one and a
corrected TypeScript implementation is far cheaper — record the RPC as an optional follow-up in the
SUMMARY, do not build it here.

**Non-negotiable constraints for this plan (phase-wide):**

- Do NOT flip the D-56 kill switch.
- Do NOT touch anything under `lib/playbook/`, `components/playbook/`, or `app/**/playbook/`.
- Stage by explicit path only. **Never `git add -A`.**
- Use `npx tsc --noEmit`, never `npm run build`.
- Jest reads its positional argument as a regex — use literal paths.
</objective>

  <action>
    Edit `lib/workspaces/appears-on.ts`.

    **Change 1 — the attachment map.** Replace the `workspaceIdByProjectId` construction with a
    `Map<string, string[]>` built by accumulation, so every live attachment for a project is kept.
    Comment the line with the defect it fixes: the previous `new Map(rows.map(...))` form kept only
    the last attachment per project, so a project attached to two workspaces silently lost one —
    possibly the caller's own.

    **Change 2 — select the relationships the caller actually holds.** Widen the
    `workspace_roster_relationships` select to include `accepted_at` alongside `workspace_id` and
    `professional_role`, keeping the existing `member_user_id = caller` and `state = 'accepted'`
    filters and the `.in('workspace_id', workspaceIds)` narrowing (now built from the flattened
    union of all attachment workspace ids).

    **Change 3 — resolve one relationship per project, deterministically.** For each candidate
    project, intersect its attachment workspace ids with the workspaces the caller holds an accepted
    relationship on. If the intersection is empty, DROP the row. If it has one element, use it. If
    it has more than one, choose the relationship with the earliest `accepted_at`, treating a null
    `accepted_at` as later than any non-null value, and break a remaining tie on `workspace_id`
    ascending. Write that rule as a comment above the comparator, stating that determinism matters
    because the chosen workspace decides which contribution role a human sees, and an
    order-dependent answer would make the shelf appear to change for no reason.

    **Change 4 — the row filter.** Build the returned array by mapping only the projects that
    survived Change 3, rather than mapping all rows and letting `contributionRole` fall to null.
    State in a comment that this is R-09/WSR-21's actual requirement: delegated workspace access is
    not contribution credit, so the relationship is the admission ticket and the role is only a
    label on it.

    Update the module header and `AppearsOnRow.contributionRole`'s doc comment so neither still
    describes the old behaviour. Add a short paragraph to the header naming R-09/WSR-21 and both
    defects, in the style the rest of this repo's headers use for post-mortem notes.

    Keep every existing guarantee: no service-role client, no write helper, `partitionVaultLanes`
    untouched, the caller's own custodianship and `excludeProjectIds` both still excluded on the JS
    side rather than trusting the query, and an error on any query still yielding an empty array.

    Do not add a Supabase RPC. Record in the SUMMARY that a set-based RPC in migration 194's shape
    remains the long-term answer and is deliberately out of scope for WSR-21.

| multi-workspace attachment → single-workspace assumption | Collapsing many attachments to one silently changes which relationship is consulted. |
