# Phase 38.0.2 Plan 10: Invitation Redemption and Roster Transition RPCs Summary

Migration 198 gains sections (f) and (g): invitation redemption becomes one
transaction with one seat statement and two audit rows, and every roster
transition becomes a compare-and-set inside a row lock whose block side effect
can no longer be separated from the state change by a crash.

**No database connection was opened and no migration was applied.** Every
verification in this plan is a text-lock test.

## What Shipped

### Section (f) — `public.workspace_redeem_invitation` (WSR-10 / WSR-16 / F11)

`(p_actor_id UUID, p_token_hash TEXT, p_actor_email TEXT, p_require_cohort BOOLEAN)`
→ `(outcome, workspace_id, member_id, member_role, invitation_audit_id, member_audit_id)`

- Locks **1 → 2 → 4** — `workspaces`, the candidate seat, then the invitation
  keyed on its `UNIQUE token_hash` — all `FOR NO KEY UPDATE`. The invitation's
  `workspace_id` is read unlocked first, because rank 1 cannot be locked before
  it is known; that read is treated as proving nothing.
- **The CAS is now structural.** The route's `.eq('status','pending')` — whose
  row count was never checked — is gone, because the row is locked and its
  status revalidated under that lock.
- **The seat is ONE statement:** `INSERT ... ON CONFLICT (workspace_id, user_id)
  WHERE user_id IS NOT NULL DO UPDATE`, inferring migration 182's partial unique
  index. The lookup-then-update-or-insert fork that let two concurrent
  redemptions both take the INSERT branch is gone entirely.
- **R-24:** `public.workspace_access_permitted(p_actor_id, p_require_cohort)` is
  consulted **before the invitation is read at all**, so an ineligible caller
  learns nothing. Kill switch off → `RAISE` (a platform fact, nothing to audit);
  cohort miss → outcome `not_in_cohort`, which plan 14 maps to **404** per R-25.
- **The self-heal is folded in** as an audited outcome, never a `RAISE` — that
  branch mutates, and a `RAISE` would roll its audit row back and then fail
  migration 197's deferred assertion on `workspace_invitations`.
- **Two audit rows, one per mutated table**, each with `target_id` set to the
  mutated row's own id. `changes` carries the role and nothing else.

Outcome vocabulary: `ok`, `not_found`, `not_in_cohort`, `expired`,
`not_pending`, `email_mismatch`, `owner_invitation_forbidden`,
`owner_seat_conflict`, `illegal_transition`.

### Section (g) — `public.workspace_transition_roster_relationship` (WSR-12 / F16)

`(p_actor_id UUID, p_relationship_id UUID, p_action TEXT, p_expected_state TEXT, p_actor_side TEXT)`
→ `(outcome, relationship_id, new_state, audit_id)`

- Locks **1 → 3 → 3.5**, the block table only for the `block` action, LO-1's
  auxiliary rule.
- **The compare-and-set** against the locked row. No `.eq('state', ...)` existed
  anywhere in either route.
- **The `workspace_roster_blocks` upsert is in the same transaction** as the
  state change. Today a crash between them leaves a `blocked` relationship with
  no block row — and `assertCanPropose` reads the *block table*, not the state,
  so the workspace would then be permitted to re-propose.
- **The kill switch is consulted only on `accept`**, inside the action branch,
  preserving the deliberate asymmetry: refuse, block and end are the Member's own
  protective actions and D-18 makes revocation unconditional.
- `p_actor_side` selects which authority rule runs; **authority is re-derived
  from the database on both sides** and no role parameter is accepted.
- `blocked` is **not** collapsed to `refused` at the write — R-23 collapses it
  only in the workspace-facing read (migration 197's `workspace_roster_page`).

Outcome vocabulary: `ok`, `not_found`, `stale`, `forbidden`,
`illegal_transition`.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 — missing critical protection] An owner seat could be silently demoted by redemption**

- **Found during:** Task 1, reading `guard_workspace_owner_role_change`.
- **Issue:** The plan's `DO UPDATE SET role = EXCLUDED.role` would demote a
  caller who already holds an **owner** seat if they redeemed a lower-role
  invitation to the same workspace — outside the two-sided transfer, and past
  migration 197's guard, whose first statement is
  `IF current_user IN ('postgres') THEN RETURN NEW` and which therefore *admits*
  the statement inside this definer function. `guard_workspace_never_zero_owners`
  would catch it only when that owner is the last one, and then as a raised
  42501 the route reports as a 500.
- **Fix:** audited refusal, outcome `owner_seat_conflict`.

**2. [Rule 2 — D-14 violation] `DO UPDATE SET status = 'active'` would revive a removed seat**

- **Found during:** Task 1.
- **Issue:** `removed` is terminal in migration 182's status set and D-14 says
  nothing is ever revived. A person removed from a workspace while an invitation
  to it was still pending could have let themselves back in.
- **Fix:** an allowlist of migration 182's inbound edges to `active`
  (`pending`, `active`, `suspended`, `expired`); anything else returns
  `illegal_transition`. Not audited, matching section (c)'s treatment of the
  same code.

**3. [Rule 2 — D-11 time-boxing defeated] A contractor invitation could produce an unbounded seat**

- **Found during:** Task 1.
- **Issue:** the issuance route sets `expires_at` on the *pending* seat for a
  time-boxed role. When the invitee had no account at issuance, that pending row
  carries `user_id = NULL`, so it is **not** the row the single statement
  conflicts with — a plain INSERT would create a contractor seat with no expiry
  at all.
- **Fix:** `expires_at` is carried across from the paired `NULL`-user_id pending
  seat by a **scalar subquery inside the same INSERT**. It is a read, not a
  branch: there is still exactly one INSERT and no conditional UPDATE. On the
  conflict path `expires_at` is untouched, so an existing seat keeps its window.

**4. [Rule 3 — blocking] `DO UPDATE SET` tripped plan 06's schema-qualification scan**

- **Found during:** Task 1, first suite run.
- **Issue:** the scan's regex reads `UPDATE\s+(relation)`, so
  `DO UPDATE SET status = 'active'` was reported as an unqualified relation
  named `SET`.
- **Fix:** a `DO_UPDATE` strip, written in the same "PRECISION FIX, NOT A
  WEAKENING" shape and with the same reasoning plan 06 used for `LOCK_CLAUSE`
  ("FOR NO KEY UPDATE" contains UPDATE) and plan 08 used for `DISTINCT_FROM`
  ("IS DISTINCT FROM" contains FROM). Proved by mutation that a genuine
  unqualified relation is still caught after the strip.

**5. [Interpretation] `end` audits under two action strings, not one**

- The plan said the audit actions must "match the strings the routes already
  emit". The Member route emits `roster.ended`; the workspace route emits
  `workspace.roster.ended`. One RPC now serves both, so the `end` action string
  is side-conditional. Collapsing them would rewrite the meaning of every
  historical row of one of the two. **Plan 12 must expect both.**

**6. [Harness] Refusal branches capture into `v_audit_id`**

- Plan 08's shared `auditedRefusalViolation` hard-codes
  `RETURNING id INTO v_audit_id`. Section (f) returns two distinct audit ids, so
  it declares a dedicated `v_audit_id` used by the refusal branches only — the
  shared assertion then applies to this function unchanged rather than being
  narrowed for it.

## Carry-forwards

### 1. PLAN 14 — a dangling pending seat is now possible, and it is deliberate

The single `INSERT ... ON CONFLICT (workspace_id, user_id)` statement the plan
mandates **cannot adopt a pending seat whose `user_id` is NULL** — that row does
not match the partial index, so redemption by an invitee who registered *after*
the invitation was issued creates a new active seat and leaves the pending
`NULL`-user_id row behind as `pending` forever.

This is **inert** — every membership helper keys on `user_id`, so a
`NULL`-user_id row grants nothing — and D-14 forbids deleting it. But it is a
hygiene defect the current route does not have, and it is the **common** path
for a brand-new invitee, not an edge case.

It was not fixed here because retiring that row is a second consequential
`UPDATE OF status` on `workspace_members`, which needs its own audit row under
migration 197's deferred trigger, and the plan's acceptance criteria explicitly
forbid a second UPDATE against that table in this function. **Plan 14 should
either retire the dangling seat from the route after a successful redemption, or
the phase should accept it and say so.** The `expires_at` carry-over above is the
only part of it this plan closed.

### 2. PLAN 11 — call `raisingRefusalViolation` as well as `auditedRefusalViolation`

The shared helper does not verify the half its call-site test names claim. The
new helper is in the file and takes the same `(fn, code)` arguments.

### 3. PLAN 11 — you inherit two new loops with no edit

`every mutating function writes an audit row in the same transaction` iterates
`functionNames()`. Section (h) mutates `workspace_custody_transfers`, which is in
the `AUDITED_TABLES` list, so it will be required to audit and required not to
target a workspace id the moment it is appended.

### 4. PLAN 11 — the `DO_UPDATE` strip is now in the harness

If section (h) uses an upsert, the schema-qualification scan already tolerates
`DO UPDATE SET`. Do not remove the strip.

### 5. PLAN 12 / 14 — the outcome codes beyond the plan's vocabulary

- Redemption adds `owner_invitation_forbidden`, `owner_seat_conflict` and
  `illegal_transition` (deviations 1–3). All three are 409-class refusals.
- `not_in_cohort` → **404**, `disabled` → **503** (raised as
  `insufficient_privilege`), and `55P03` / `40P01` → **409 retry-safe**, per the
  file header.
