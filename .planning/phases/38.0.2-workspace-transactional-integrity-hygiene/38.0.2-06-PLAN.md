      7 `workspace_custody_transfers` / `workspace_ownership_transfers`, 8 `vault_projects`,

      table locks multiple rows in ascending `id` order.

      is last because it is the most contended row and the join point of the two flows most likely
      to collide; the audit log takes no row lock so its position cannot influence deadlock; and
      Postgres's own guidance is to acquire locks on multiple objects in a consistent order and to
      take the most restrictive mode you will need on the first touch.
    - **RULE LO-2 — `FOR NO KEY UPDATE`, NOT `FOR UPDATE`.** Give the reason, not just the rule: all
      seven tables are foreign-key parents, and `FOR UPDATE` conflicts with `FOR KEY SHARE` while
      `FOR NO KEY UPDATE` does not — so locking a `workspaces` row `FOR UPDATE` would block every
      concurrent membership, invitation, grant, attachment and audit-log insert in that workspace
      for the whole transaction. Nothing in this phase deletes a row or changes a key column
      (D-14/D-17/D-25 forbid deletes and every route already does status updates instead), so the
      stronger mode is never needed. State the one honest unknown: an UPDATE touching a column
      covered by a unique index usable in a foreign key is implicitly upgraded, and
      `workspace_members` carries a **partial** unique index on `(workspace_id, user_id)` which
      cannot back a foreign key — so no upgrade is expected, but this was not verified against a
      live database and the failure mode is benign (a stronger lock, never a weaker one).
    - **RULE LO-3 — NO LOCK UPGRADES.** One locking clause per row per transaction. Do not lock a
      row `FOR NO KEY UPDATE` and later re-lock it more strongly.
    - **RULE LO-4 — BOUNDED WAIT.** `SET LOCAL lock_timeout = '3s'` at the top of every RPC. A
      blocked row lock in a Node request path is a hung HTTP request; a bounded wait becomes a
      `55P03` the route maps to 409. Do not use `NOWAIT`; do not use `SKIP LOCKED` — skipping a row
      in an authorization decision means silently reading stale state. Deadlocks surface as `40P01`;
      both `40P01` and `55P03` map to 409 with a retry-safe message, never 500.
    - **RULE R-26 — RAISE VERSUS OUTCOME CODE.** A business outcome (stale CAS, already resolved,
      not found, the owner floor would break, an authority refusal the phase wants on the record)
      returns an outcome code. An authorization or invariant violation that a correct caller could
      never produce raises with an explicit `ERRCODE`. The reason is mechanical and easy to get
      wrong: **a RAISE rolls back the transaction, including any audit row already written in it.**
      R-26 requires authority refusals to be audited, so those specific paths must not raise.
