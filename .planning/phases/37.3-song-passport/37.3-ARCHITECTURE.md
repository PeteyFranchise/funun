# Phase 37.3 — Song Passport Architecture

## Current-system audit

| Domain | Existing source | Reusable foundation | Gap Phase 37.3 must close |
|---|---|---|---|
| Underlying work | `works` | One composition entity; release link seam | No canonical Passport status/schema version |
| Recording versions | `work_versions` | Distinct audio rows, creator, performers, lineage-ready identity | No master designation lifecycle, hashes or Passport field state |
| Creative record | `lyric_blocks`, `ai_entries`, `work_diary_events` | Attributed blocks, AI disclosure, append-only diary | No Passport provenance projection or approval boundary |
| Collaboration | `work_members` plus presence/locks/snapshots/comments | Owner/member access and safe live creative editing | Tiers are too broad for legal/metadata/delivery actions |
| Contributor identity | `collaborators`, `user_profiles` | Reusable identity and claimed-member links | No per-song consent, provenance head or outdated-state handling |
| Composition ownership | `split_sheets`, `split_sheet_parties` | Explicit lock/signature lifecycle; linked `work_id` | No field-level projection into the Passport or conflict state |
| Contracts | `vault_documents` and e-sign lifecycle | Stored evidence and execution status | Work-level authority links and chain-of-title events need normalization |
| Release record | `vault_projects`, `tracks` | Release facts, track metadata, readiness and distribution fields | Graduation mapping and immutable approved snapshots are missing |
| Metadata | `tracks.metadata` plus Metadata Studio | Broad composition/recording/release schema | JSONB can drift from profiles/splits; no per-field provenance/state |
| Audio custody | private storage, `work_versions`, `tracks` | Separate original objects and controlled routes | Unified source/derivative lineage across work and release is incomplete |
| Delivery evidence | `metadata_delivery_exports` | Source/output hashes, metadata snapshot, manifest and receipt | Release-track-only shape; no canonical Passport snapshot FK |
| Internal doctrine | Playbook Company-wide room | Published SOP entries and role grants | Song Passport entry must be seeded and versioned |

## Architecture decision

Use a **normalized provenance ledger plus immutable JSON snapshots**:

- normalized records enforce identity, scope, state, authority and referential integrity;
- JSONB stores typed field values and immutable snapshot payloads without one migration per
  metadata vocabulary addition;
- current heads point to append-only revisions rather than overwriting historical values;
- exports and approvals bind to snapshot IDs, never to the mutable current view.

Do not make `tracks.metadata` or one large `works.passport JSONB` the sole source of truth.
Those shapes cannot safely express per-field source, privacy, confirmation, conflict and
supersession without hidden application conventions.

## Target logical model

### `song_passports`

One row per `works.id` with a unique work foreign key, schema version, lifecycle state and
timestamps. Work ownership remains authoritative in `works`; do not duplicate it as a
second editable owner field.

### `song_passport_values`

Append-only revisions for meaningful fields. Each revision contains:

- Passport and layer (`contributor`, `composition`, `recording_version`, `release`)
- exactly one typed target where required (`collaborator_id`, `work_version_id`,
  `vault_project_id`, `track_id`)
- stable `field_key`, typed `value_jsonb` and schema version
- source kind/table/record/revision and source actor
- trust state and visibility class
- confirmer/confirmation time, approver/approval time and lock reason
- `supersedes_value_id`, created actor/time and conflict group where applicable

Application writes create revisions. A database constraint or transactionally maintained
head relation guarantees one current revision per field and target.

### `song_passport_snapshots`

Append-only payloads for approval, release, export, registration, delivery, custody transfer
and audit. Store purpose, schema version, canonical JSON payload, SHA-256, creator/time and
optional predecessor/supersession link. No update/delete grant for browser roles.

### `song_passport_actions`

Append-only confirmations, approvals, rejections, disputes, resolutions and revocations.
Each action records actor, authority basis, scope, related value/snapshot, reason and time.
An approval cites the immutable snapshot actually reviewed.

### `song_passport_tasks`

Operational assignments linked to a field, conflict or approval requirement. Store assignee,
status, due date and rule source. Database/readiness logic must ignore task completion unless
the underlying fact independently reaches the required state.

### `song_passport_custody_events`

Chain-of-title and custody changes with previous/new controller, effective scope/date,
territory/term, governing Contract Locker document, affected versions and immutable before/
after snapshots. This table records evidence and declarations; it does not adjudicate title.

### `song_passport_release_links`

Explicit work/version-to-release/track mapping, selected-master status and predecessor link.
Preserve `works.graduated_project_id` during migration as the existing compatibility seam;
the normalized link becomes authoritative only after shadow-read comparison passes.

### Export evidence

Additive future migrations should link `metadata_delivery_exports` to a Passport snapshot or
create a provider-neutral export ledger if work-level exports cannot fit its non-null release
project/track constraints. Never weaken its append-only server-only posture.

## Source authority and conflict rules

| Fact | Default source authority | Conflict behavior |
|---|---|---|
| Contributor identity | Confirmed `user_profiles`/claimed collaborator | Mark outdated; identity subject reviews |
| Writer shares | Executed `split_sheets` snapshot | Block affected approval; never average or overwrite |
| Contract authority | Executed `vault_documents`/e-sign evidence | Require authorized legal/operations review |
| Lyrics/authorship evidence | `lyric_blocks` plus diary/snapshots | Preserve proposals and history; no ownership inference |
| Version performers/producers | Confirmed `work_versions` Passport layer | Version-specific review; does not alter composition |
| Release identifiers/facts | Approved Release Report snapshot | New release revision; no back-propagation to demos |
| Delivery outcome | Export/delivery receipt and real partner acknowledgment | Preserve raw state; never infer acceptance from dispatch |

## Authorization matrix

Legend: V view, D draft/propose, C confirm own authority, A approve/freeze, X no access by default.

| Action | Owner | Admin member | Contributor | Identity subject | Release controller | Recipient | Staff |
|---|---:|---:|---:|---:|---:|---:|---:|
| View creative/public Passport | V | V | V | scoped V | V | scoped V | purpose-scoped V |
| View private identity/legal data | scoped V | scoped V | X | own V | scoped V | X | audited/purpose-scoped |
| Draft creative/version facts | D | D | D | own D | D | X | X |
| Confirm own identity/contribution | C | C | C | C | C | X | X |
| Approve composition snapshot | authority-based A | delegated A | X | X | X | X | X |
| Approve release/master snapshot | delegated A | delegated A | X | X | A | X | X |
| Edit splits/contracts | existing explicit workflow | delegated only | party workflow | party workflow | X | X | X |
| Generate preview-safe export | authority-based | delegated | X | X | A | X | operational only |
| Deliver clean master | explicit authority | delegated | X | X | explicit authority | receive only | controlled operation |
| Transfer custody/delete | verified controller | delegated explicit | X | X | scoped only | X | execute approved request |

Every sensitive API route must prove authority for the exact Passport, target, action and
snapshot server-side. RLS protects direct reads/writes; service-role routes must not become
an authorization bypass.

## Migration and backfill strategy

1. **Additive foundation:** create new tables, constraints, indexes, helper functions and RLS
   with no runtime reader and no mutation of migrations 001–149.
2. **Feature flag:** hide all Passport writes/UI until schema and production migration are
   confirmed. Existing Writer's Room and Release Report remain canonical during this step.
3. **Discovery report:** classify existing works, collaborators, split links, work versions,
   graduated projects and track metadata; report duplicates and conflicts without writing.
4. **Idempotent Passport creation:** create exactly one Passport per work using deterministic
   conflict handling and `ON CONFLICT` safeguards.
5. **Provenance backfill:** insert inherited/draft revisions from existing sources. Never mark
   legacy facts confirmed/locked unless existing evidence proves that state.
6. **Shadow read:** build the current Passport projection and compare it with legacy screens
   while the old paths remain authoritative.
7. **Human reconciliation:** surface conflicts, ambiguous duplicates and missing links to the
   owner; do not guess.
8. **Scoped cutover:** turn on Passport reads per account/work cohort, then writes, then
   graduation. Preserve compatibility projections until acceptance gates pass.
9. **Post-cutover audit:** compare counts, source links, snapshots and authorization denials;
   retain evidence before removing any compatibility path in a later phase.

## Red-test plan

Tests must fail before each implementation slice and prove:

- a collaborator cannot confirm another person's identity, alter splits, approve a release
  or download a clean master merely through membership;
- service-role routes reject cross-work and forged-target IDs;
- inherited facts refresh while confirmed/locked/delivered facts become outdated instead of
  changing silently;
- two concurrent confirmations create one valid head and preserve both attempted revisions;
- disputes block only the affected approval/use and preserve all claims;
- snapshot payload/hash never changes after approval/export;
- private fields never appear in ID3, public sidecars or recipient-scoped exports;
- source audio bytes and SHA-256 remain unchanged after every metadata/export operation;
- task completion alone never changes readiness;
- master replacement creates a successor selection and reopens required checks;
- backfill is idempotent, conservative and reports ambiguity instead of merging silently;
- custody transfer changes prospective authority without erasing historical controllers;
- deletion respects holds/retention and leaves only the approved minimal tombstone;
- DDEX/partner acceptance states cannot be set without real validation/acknowledgment evidence.

## Rollback strategy

- Roll back application behavior through feature flags and route/UI reversion, not destructive
  database rollback.
- New ledger and snapshot rows remain intact for diagnosis; never delete evidence to return to
  the old UI.
- Existing Writer's Room, Split Sheets, Contract Locker, Metadata Studio and Release Report
  paths remain operational until their Passport replacements pass cohort acceptance.
- Stop a cohort rollout on authorization leakage, snapshot drift, unexpected overwrite,
  source-hash mismatch or readiness regression.
- Correct data through successor revisions and reconciliation jobs, not in-place history edits.
- A later cleanup migration may remove compatibility reads only after a separate owner-approved
  audit and backup/restore rehearsal.

## Boundary with later phases

Phase 37.3 may create provider-neutral snapshot/export seams. Phase 37.4 owns standard-
specific CWR/RIN/ERN generation and validation. Phase 37.5 owns partner adapters, transport,
acknowledgments, retry choreography and accepted direct-delivery claims.
