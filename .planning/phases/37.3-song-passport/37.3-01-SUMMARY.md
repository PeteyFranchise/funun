# 37.3-01 — Song Passport Foundation Summary

## Outcome

Phase 37.3 Slice 1 is code-complete behind a server-only feature boundary that defaults
off. No artist-facing route, page or component imports the new foundation. Migration 151
is authored and human-gated; the new schema is not live until the owner applies it.

## What changed

### Additive database foundation

- One `song_passports` row per underlying `works` row, enforced by a unique foreign key.
- Append-only `song_passport_values` revisions for contributor, composition,
  recording-version and release fields.
- Typed targets and stable target keys, including database checks that a recording version
  belongs to the Passport's work and a release track belongs to its release project.
- `song_passport_field_heads` with a composite foreign key guaranteeing the current value
  belongs to the same Passport, layer, field and target.
- Immutable snapshots and authority actions guarded against update/delete at the database layer.
- Operational tasks with an explicit database comment that task state never drives readiness.
- Scoped authority grants for private identity, legal, composition approval, release
  approval, master selection, export, clean delivery, custody transfer and deletion.
- Composite foreign keys preventing cross-Passport supersession, actions and task links.

### Least-authority access

- RLS is enabled on every new table.
- Browser roles cannot write any Passport capability or evidence table.
- Work owner/member reads are separated from private identity and legal access.
- Identity subjects may see their own private identity values without receiving general
  access to the song's Passport.
- Private/legal access otherwise requires an active, unexpired, unrevoked scoped grant.
- Snapshots, actions and tasks are server-read only until later purpose-scoped APIs exist.
- SECURITY DEFINER helpers use an empty search path, validate the authenticated subject and
  expose only the three narrow read predicates required by RLS.

### Typed application foundation

- Added the canonical layers, trust states, privacy classes, source kinds, snapshot
  purposes and ledger actions.
- Added 47 stable field definitions across identity, composition, recording and release.
- Delivery-safe embedding is explicit; private identity and legal fields can never embed.
- Added typed target-key construction that rejects ambiguous contributor, version and
  release targets before they reach the database.
- Added pure action-level authorization proving that ownership/membership is not legal,
  release, delivery or custody authority.
- Added `SONG_PASSPORT_ENABLED`, server-only and false unless its exact value is `true`.
