<objective>
Re-theme the remaining buyer surfaces — the org shortlist, the org request dashboard +
requests list + request detail, and the guided request composer + new-request page — from the
old dark `bg-ink` / `text-white` styling to the light `.fnbl` token system established in
22-03. These pages already render inside the layout's light `.fnbl[data-theme]` wrapper; this
plan swaps their dark utility classes for token-driven light classes so they read correctly on
white and re-theme automatically when a buyer toggles to dark.

Purpose: Finish the light-theme platform convention. After 22-03 the shell is light but these
inner surfaces still carry dark Tailwind classes that look wrong on white. This is a
presentation-only pass — no server logic, no data, no auth changes.

Output: Seven re-themed files, all token-driven so both light and dark themes render correctly.

Theme-delivery decision (Claude's discretion, CONTEXT line 71): use Tailwind arbitrary values
that reference the FNBL custom properties (e.g. `text-[color:var(--ink)]`, `bg-[var(--wash)]`,
`border-[color:var(--line)]`, and the `--ok-*/--part-*/--req-*` families for status badges)
rather than hardcoded light hexes. This keeps each file Tailwind-first (matching its existing
idiom) AND single-sources the palette in fnbl-theme.ts, so the 22-03 dark toggle re-themes
these surfaces automatically. (Hardcoded light hexes would break in dark mode — do not use
them.)
</objective>
