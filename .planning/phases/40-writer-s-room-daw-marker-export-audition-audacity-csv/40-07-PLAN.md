<objective>
Put the feature in front of the writer: two controls on the take, each offering the DAW formats that
have been verified, each capable of showing the server's refusal in place rather than handing over a
file nobody wanted.

Purpose: E-11 exists because a take can display three comments in the room and still export empty —
all resolved, or all flagged for repositioning. Without the message that reads as a bug. The
controls are where that message lands.

Output: a small focused client component and a one-line mount, so a 1,266-line player does not grow
a fetch-and-blob state machine.
</objective>

  <action>
Create `components/catalogue/TakeMarkerExport.tsx`, a `'use client'` component taking `workId`,
`versionId` and an optional `className`. It takes nothing else — in particular it does NOT take the
comment list. The component has no business predicting whether an export will refuse; the server
computed that, and a client-side prediction is a second implementation of E-01, E-09 and E-11 that
will eventually disagree with the first.

Define the format options as a module-level constant array of objects with an `id` and a `label`.
Exactly two entries for now, in this order: the Audacity label track, then the spreadsheet CSV.
Label them by what the writer is choosing, not by what the file is — per E-13 a user picks their
DAW, not a serialization format. Write a comment directly above the array recording that the
Audition option is deliberately absent, that its serializer is written and tested, and that adding
a third entry here is the entire UI change once plan 40-08's verification passes.

Render two controls in the action row's visual vocabulary:

- *Export comments* — a quiet button that reveals the format choices. Keep the disclosure cheap: a
  small inline row of format buttons, or a native select plus a confirm, whichever reads quieter in
  the action row. Do not build a modal.
- *Export my pins* — a second, separate control with its own format choices, rendered as a distinct
  element with its own handler. Not a toggle on the first control, not a third option inside its
  format list. E-03 makes this separation the containment for E-02, and the interface is where a
  writer either sees two things or is misled into thinking one file might contain both.

Write two handlers, not one parameterised handler. Each builds its own URL as a template literal
containing its own literal path segment. A shared `runExport(kind)` helper would be exactly the
merge E-03 forbids, expressed in TypeScript instead of in a route.

Each handler does the same five things, duplicated deliberately:

1. Clear any message from a previous attempt, and set a pending flag that disables its own control.
   Two independent pending flags — exporting pins must not grey out the comments control.
2. `fetch` the route with `cache: 'no-store'`.
3. If the status is 409, parse the JSON, read the server's message, render it in place next to the
   control that produced it, and stop. No file is created. If the body has no message, fall back to
   a plain sentence rather than rendering an empty pill.
4. If the response is not ok for any other reason, render a short generic failure sentence. Do not
   surface a status code or a server string to the writer.
5. On success, read the response as a blob, read the filename out of the `Content-Disposition`
   header rather than rebuilding it client-side — the server already sanitised it and rebuilding it
   would be a second implementation of E-06's rule — then create an object URL, click a synthetic
   anchor, and revoke the URL. Fall back to a simple default name only if the header is absent.

For the comments handler only, after a successful download, read the skipped-count header, parse it
as an integer, pass it to `skippedRepositionNote`, and render the returned sentence if it is not
null. E-09 requires the writer to be told what was left out even when the export worked. Import
that function rather than writing the sentence here — one wording, one home.

Wrap the fetch in try/catch so a network failure renders the generic sentence rather than an unhandled
rejection, and clear the pending flag in a finally block so a failed attempt never leaves a
permanently disabled control.

Give the message element `role="status"` for the success note and `role="alert"` for a refusal or a
failure, and give each control an `aria-label` naming what it exports, since the visible labels are
short. Match the existing alert paragraph styling in the player — `text-[10px]` with a red tone for
errors and the lavender-dim tone for the informational skipped-count note.

Keep the whole component under roughly 160 lines. If it is growing past that, the disclosure
pattern is too elaborate; simplify the format choice rather than adding structure.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| export response → the writer's disk | A 409 JSON body and a 200 file body arrive on the same request and must never be confused |
| server-computed refusal → client-rendered sentence | The message crosses a boundary and must not be re-derived on the far side |
| two controls → one component | A single component renders both actions and must not let them converge on one code path |
