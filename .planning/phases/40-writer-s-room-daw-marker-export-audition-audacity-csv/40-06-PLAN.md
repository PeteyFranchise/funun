  <action>
Create `__tests__/writer-room-daw-export-separation.test.ts`.

Open with a header comment in the established doctrine-gate voice, explaining the specific thing a
human reviewer cannot catch. Say it concretely: a single export route with a type parameter, or a
shared row-fetching helper the two routes both call, would look like good DRY engineering in a
diff. It would also be the change that lets a private pin land in a shareable file, and nothing in
the running application would look different until someone forwarded the wrong file. Name E-02 as
the decision that created the exposure and E-03 as the containment, so anyone who trips this gate
reads the reasoning before deciding what to do about it.

Load both route sources with `readFileSync` and `path.join(process.cwd(), ...)` at module scope, so
a wrong path throws at load time rather than yielding an empty string that every assertion passes
against. Build a two-entry table of named sources for the groups that apply to both.

Group zero — the gate is real. One `it` asserting each loaded source is non-empty and contains the
literal `export async function`. This is the anti-vacuity check: a renamed or moved route file must
fail loudly here rather than silently satisfying every negative assertion below.

Group one — no crossover. Assert the comments export source contains neither the pins table name
nor the pin view type name, and assert the pins export source contains neither the comments table
name nor the comment view type name. Four assertions, stated in both directions on purpose — a
one-directional check would let the pins route grow a comments query.

Group two — no shared data path. Assert that neither route imports the other, and that neither
imports any module under the API route tree at all. The two routes may share the pure renderer
modules and the pure classifier module — E-13 requires the same three formats on both controls, and
the research is explicit that sharing the FORMAT RENDERERS is fine and intended while sharing the
DATA-FETCHING path is what E-03 forbids. Encode exactly that distinction: assert both sources
import from the pure export modules, and assert neither source contains a relative import that
climbs out of its own directory.

Group three — no mode parameter. Assert neither source contains a query parameter read for anything
other than `format`, by asserting that `searchParams.get(` appears exactly once per file and that
the character sequence immediately following it is the format key. A second query param on an
export route is the shape a merge would take, and catching it at one is cheaper than enumerating
every name it might have.

Group four — the pure read, per E-10. Over the table of both sources, assert none contains a row
creation call, a row modification call, an upsert call, a delete call, a stored-procedure call, a
notification-creating call, a realtime broadcast call, or a channel send call. Assert each source
matches `export async function` exactly once — a POST or DELETE added to an export route is a write
by definition. Reuse the notification and broadcast constant names from the private-pins doctrine
test so all three files agree on what silence means.

Group five — no service-role escalation. Over both sources, assert neither creates a service-role
client and neither calls an owner-check or membership-tier database helper.

Group six — the access gate is present in both. Assert each source contains `resolveWorkAccess` and
the `'contribute'` tier literal exactly once. This is a positive assertion among negatives on
purpose: the gate should fail if the check is removed, not only if something forbidden is added.

Give every describe block a name that states the decision it protects, including the decision id.
