  <action>
Create `docs/catalogue/AUDITION-MARKER-FORMAT.md`. Write it for a reader who has Audition open and
has never seen this phase — a producer, a future maintainer, or Pete six months from now.

Section one — what Funūn writes. State the whole format plainly: the `.csv` extension with a TAB
delimiter, the six columns in order, the `M:SS.mmm` time shape, the `decimal` literal in the Time
Format column, the `Cue` literal in the Type column, the empty trailing Description, and — in its
own short paragraph, because it is the one that bites — that the third column is a LENGTH and not
an end time.

Section two — how we know. Name the three corroborating sources and what each one independently
establishes: a community forum thread quoting a literal exported header row and two example rows;
an open-source CUE-sheet converter that tab-splits real Audition exports and discards row zero as a
header; and an open-source chapter-markdown generator that does the same and indexes Description at
column five, which only holds if there are exactly six columns in that order. Say plainly that
these agree with each other and that none of them is Adobe.

Section three — what is inferred, not observed. Three items, each with the consequence if it is
wrong:
  - **Encoding.** Assumed UTF-8. Adobe applications on Windows sometimes default to UTF-16 for
    exports. If wrong, accented and non-Latin display names mis-render or the import fails.
  - **Line endings.** Assumed CRLF, with the file ending in one. If wrong, the import may see a
    trailing blank row or refuse the file.
  - **The Type literal for a RANGE marker.** Assumed `Cue`, the same as every observed point
    marker, on the strength of Adobe's own statement that the only difference between point and
    range markers is that range markers have a duration. No corroborating source shows a range
    marker's row. If wrong, range markers may import as points or fail.
Also record the smaller open question: whether Audition's own export writes a trailing tab for an
empty Description or ends the line after Type. Funūn always writes six fields, because both
real-world parsers index positionally and an extra empty field is far less likely to break parsing
than a missing one.

Section four — the procedure that settles it. Write it as numbered steps, each with exactly one
command or one action, and say at the top that whoever runs it should do one step at a time and
record the output of each before moving on. The steps:
  1. In Audition, create three markers on any audio file: a point at 0:09.000, a point at 1:30.000,
     and a range from 1:12.000 running for six seconds. Name them anything.
  2. Export the marker list to CSV. Save it somewhere findable.
  3. Run `npm run export:audition-sample 2>/dev/null > /tmp/funun-audition.csv` to produce Funūn's
     bytes for the same three markers.
  4. Run `file /tmp/funun-audition.csv` and `file <the Audition export>`, and compare what each
     reports about encoding. Note any mention of UTF-16 or a byte-order mark.
  5. Run `od -c <the Audition export> | head -5` and read the line terminators — `\r \n` or `\n`
     alone — and whether a tab precedes each terminator.
  6. Run `awk -F'\t' '{print NR": "NF}' <the Audition export>` and confirm every line reports six
     fields.
  7. Run `cmp /tmp/funun-audition.csv <the Audition export>` and record the first differing byte,
     or that the files are identical. Marker NAMES will differ unless they were typed to match, so
     compare structure rather than expecting a clean match on the first attempt — the columns after
     the name are what matter.
  8. Import `/tmp/funun-audition.csv` into a FRESH Audition session and confirm three markers
     appear, that the two points sit at 9 seconds and 1:30, and that the range marker is six
     seconds long and not sixty-six.
State what each possible outcome means: identical structure means ship as is; a difference in
encoding or line endings is a small, localised change to the renderer; a range marker importing as
a point means the Type literal needs the real value; anything else means removing the option and
letting Audition follow separately, which E-12 explicitly allows.

Section five — if it fails. Name the two remediations in order of preference: correct
`renderAuditionMarkers` or `auditionTime` in `lib/catalogue/take-export-audition.ts` against the
real bytes, or remove the single Audition entry from the export control's format array and revert
the test's expected entry count. Say that the second option costs one line plus one number, and
that the serializer and its tests can stay in the tree either way.
