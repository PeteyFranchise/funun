<objective>
Stand up the private half of the feature: a separate route, at a separate path, reading a separate
table, returning only the caller's own pins for one take.

Purpose: E-02 lets an author export their own pins, and E-03 is the entire containment for that
decision. The containment is not a flag and not a test — it is that the shareable file and the
private file are produced by two files with no shared query, so there is nothing for a future change
to accidentally merge. This plan is the second of those two files.

Output: a route that mirrors the comments export's shape and shares its renderers, and shares
nothing else.
</objective>

  <action>
Create `app/api/works/[workId]/versions/[versionId]/pins/export/route.ts` exporting a single `GET`
handler and nothing else.

Open with a section-header comment recording why this file exists as a separate file rather than as
a mode of the comments export. State it plainly: an author may export their own pins, and the only
thing keeping a private mark out of a shareable file is that the two files are produced by two
routes with no shared query. A flag would be the change that breaks pin privacy, so there is no
flag to add. Also record that this path emits nothing at all, because a trace on a pin export would
tell the room that someone has pins — the exact disclosure D-11 exists to prevent.

Sequence the handler the same way the comments export does, so the two are recognisably siblings
even though they share no data path:

1. Await the work id and version id params.
2. Read and validate `format` against the same three-id allowlist. E-13 keeps the format list
   identical across both controls — a user picks their DAW, and which of their two things they are
   exporting does not change which DAW they use.
3. Create the API client and get the user. No user is a 401.
4. Rate-limit on a per-user key namespaced to THIS route, prefixed `work-version-pins-export:`,
   with the same generous allowance and fifteen-minute window as the comments export, fail-open.
   A separate key, not a shared one: sharing a bucket would let the rate of one export reveal
   activity on the other.
5. Call `resolveWorkAccess` with the `'contribute'` tier, exactly as the pins collection route
   already does. Room membership decides whether you may be here at all; authorship decides what
   you see.
6. Load the work's versions, confirm the requested version belongs to this work, and build the
   version display map for the filename. Return 404 if it does not — this is what stops a version
   id from another work being paired with a work the caller can reach.
7. Load the work's title with the caller's own client. Missing row is a 404.
8. Query the pins table selecting only the id, the timestamp and the creation time — the same
   narrow column list the collection route uses. Filter on the work id, the version id, AND an
   equality on the author column against the caller's own user id. Write a comment directly above
   the author filter recording that it is one of two independent gates: the table's author-only row
   policy is the other, and the phase constraint requires the API to filter explicitly rather than
   leaning on the policy alone. Never widen this to all pins on the take. Order by timestamp and
   bound the row count.
9. Map the rows into the pin view shape and call `classifyPinExport`.
10. If the reason is not `none`, return 409 with the reason and the message, matching the comments
    export's refusal posture so the two controls behave identically when there is nothing to hand
    over. There is one refusal case here — a pin has no resolution state and no repositioning flag
    to be excluded by. E-11 enumerates the comment cases; refusing an empty pin export rather than
    handing over an empty file is the same principle applied to the one case that exists.
11. Otherwise dispatch on the format to the same three renderers, build the filename with
    `exportFilename` passing the `my-pins` kind so the name reads as E-06's second example, and
    return the body with a charset-qualified content type, an attachment disposition, and
    `Cache-Control` set to no-store.

Do not set the skipped-count header on this route. A pin cannot be flagged for repositioning, and a
header that is always zero is a header someone will later wire to something that is not zero.

Do not create a service-role client and do not call any owner or membership-tier database helper.
Both widen a read, and this is the one route in the phase where a widened read is a privacy breach
rather than an inconvenience.

Wrap the data access in a try/catch returning a generic 500 with no raw database text.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → pin export route | A room member asks for pins on a take; only their own may come back |
| route → pins table | The author scope must be asserted by the query and by the row policy independently |
| exported pin file → anywhere | A private mark becomes a forwardable artifact, which the in-app pin never was |
| pin activity → the room | Any signal at all would reveal that someone has pins |
